# 발견·검증·비교 프로토콜

상태: **조사 작업 규칙**, 실제 서비스 수집기가 구현된 것은 아님. 2026-11-19.

## 1. 단순 링크 저장과의 차이

사용자 질문의 **왜 수요가 생겼는가 / 이 문제를 기존 도구로 해결할 수 있는가**에서 검색을 시작한다. 검색식은 대상 이름뿐 아니라 문제, 실패 형태, 사용 환경, 제약, 대체재를 포함한다.

예: '기록 저장소' → 'MCP tool session transcript', 'continuation after context compaction', 'evidence linked project memory', 'self-hosted alternative', 'read-only vs write access' 등의 서로 다른 검색 방향. 예시는 검색 방향일 뿐 실제 후보 채택 증거가 아니다.

## 2. 발견 채널 — 출처는 구체적으로 저장

| 채널 | 발견할 것 | 주의 |
| --- | --- | --- |
| GitHub 저장소·topics·awesome lists | 유지보수 중인 코드, 라이브러리, MCP, 예제 | Star/포크를 신뢰도 또는 적합성의 대리 지표로 확정하지 않는다 |
| GitHub Discussions·Issues·PR | 실제 제약, 실패 보고, 통합 사례 | 한 사람의 이슈를 제품 전체의 결함으로 일반화하지 않는다 |
| Reddit·국내외 개발 커뮤니티·Hacker News·GeekNews 등 | 사용자 고충, 비교 사례, 대체재 | 댓글·개인 주장과 재현 가능한 사실을 구분한다 |
| 제품 공식 사이트·가격표·변경 기록 | 무료 범위, 서비스 상태, API/지원 플랫폼 | 구독·가격/제한은 시점에 따라 바뀌므로 확인일 필수 |
| 패키지 등록소·라이선스 파일·소스 코드 | 설치·배포·의존성과 사용 조건 | 오픈소스/무료/공개 저장소는 별개의 속성 |

해외 자료도 대상으로 하며 필요하면 번역해 기록한다. 출처의 원문 URL·날짜·원문 의미를 보존한다.

## 3. 후보 하나당 최소 조사 항목

- 식별: `resource_id`(임시 가능), 표시 이름, 원본 URL, canonical URL, 자원 유형.
- 기능: 해결하는 문제, 주장하는 기능, 관련 capability, 사용 대상/조건.
- 조건: 라이선스(`unknown` 허용), 무료/유료/체험, 계정·호스팅·배포 제약, OS·언어·API·MCP 호환성.
- 건강도 스냅샷: 마지막 활동/릴리스 확인일(아는 경우), 이슈·유지보수 리스크, 저장소 중단·아카이브 여부.
- 근거: 링크마다 확인 시각(UTC), 해당 페이지/커밋/버전, 확인 가능한 문장·행동, 증거 단계, **확인하지 못한 항목**.
- 적용: 어떤 프로젝트/문제에서 `alternative` / `component` / `reference` 인가, 대안과 비교, 채택/평가/제외 이유.
- 상태: 발견 → 확인 대기 → 근거 검토 → 실험 → 의사결정 → 재검토 필요.

초기에는 자료를 `docs/workstreams/discovery/` 안에 Markdown/JSONL로 남기고 제품 DB에는 검증된 항목만 옮길 수 있다. 저장소의 현재 `lab/repo-intake`는 GitHub 주소 중복 정리 실험이고 웹·GitHub API를 자동 수집하지 않는다.

## 4. 증거 수준 (반드시 구분)

| 수준 | 의미 | 허용하는 표현 |
| --- | --- | --- |
| D0 발견 | 검색 결과/추천에 이름과 주소가 나타남 | '후보 발견, 내용 미검증' |
| D1 문서 확인 | README·가격표·공식 문서 또는 커뮤니티 글 내용 확인 | '작성자가 이렇게 설명함' |
| D2 구현 관찰 | 소스·설정·실제 API 자료를 확인함 | '코드에서 해당 경로/행동을 관찰함' |
| D3 독립 실행 | 재현 가능한 자체 테스트/명령을 실행함 | '환경·입력·커밋 범위에서 통과함' |
| D4 프로젝트 적용 | 우리 요구사항으로 통합하여 해당 테스트를 통과함 | '프로젝트 조건의 이 부분에 적합함' |

D1→D4는 자동 승격되지 않는다. **미확인 사항은 빈 값 또는 unknown**으로 남긴다. D4도 전반적인 품질/보안 인증은 아니다.

## 5. 재현 가능한 조사 순서

1. 검색 질의와 왜 찾는지를 기록한다.
2. 중복과 자원 종류를 구분한다. GitHub 소스, docs 하위 페이지와 별도 서비스는 무조건 하나로 합치지 않는다.
3. 적어도 두 가지 대안을 비교하고 장단점·불확실성을 적는다.
4. 라이선스·상업 이용/재배포/서비스 조건은 원본으로 확인하고 모르면 미확인으로 남긴다. 법적 판단을 대신하지 않는다.
5. 검증 가능한 작은 실험이 있으면 안전한 독립 환경에서 실행하고 명령·커밋·출력 요약을 남긴다.
6. 적용/보류/제외를 사유와 함께 기록한다. 의심스러운 README 명령은 그대로 실행하지 않는다.
7. 새 정보와 오래된 정보가 충돌하면 현재 선택과 과거 선택을 분리해 기록한다.

## 6. 품질 검사

- 최소 출처 URL, 검증 시점, 자원 유형, 상태, 미확인 표시가 없는 기록은 '추천 근거'가 될 수 없다.
- 이슈 페이지/README 링크가 있다는 사실을 라이선스 또는 동작 검증으로 취급하지 않는다.
- 가격·지원 기능·버전이 오래되면 `needs_recheck`.
- 추천 이유는 반드시 프로젝트의 요구/제약과 연결하고, 반례·제외 사유도 기록한다.
- 로봇 차단·약관·API 제한을 우회하지 않는다. 개인정보·비공개 코드·토큰은 수집하지 않는다.
- 원문을 통째로 복제하지 않고 링크와 자체 요약을 보관한다.

## 7. 초기 수집 실험의 종료 조건 (제안)

10–20개 서로 다른 유형의 실제 후보를 수동으로 조사해, 중복·근거 누락·불확실성 표시·비교 판단을 먼저 검증한다. 그 결과에 따라 50–100개 규모 확장과 자동화 대상을 결정한다. 숫자는 **제안된 실험 규모**이지 사용자가 확정한 목표나 현재 보유 자료 수가 아니다.
