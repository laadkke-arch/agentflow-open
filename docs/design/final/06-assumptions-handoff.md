# 06. 새 가정과 인계

## 1. 이 설계가 새로 세운 가정

근거와 섞이지 않게 따로 모았다. 연구 원장이나 실행 예제로 확인한 것은 여기 없다. 부문 문서의 가정 목록([request_utility 8절](sections/request_utility.md), [retrieval_judgment 9절](sections/retrieval_judgment.md), [discovery_ops 11절](sections/discovery_ops.md))을 합치고, 총괄 판정에서 새로 생긴 것을 더했다. 운영 시뮬레이션 재검토([07-review.md](07-review.md))에서 깨지거나 새로 생긴 가정은 C4·C11~C13에 반영했고, 그 가정을 확인할 조사는 07 7절에 우선순위와 함께 있다.

## 2. 실행 예제가 보증하는 것과 하지 않는 것

**보증한다(b).**
- 판독 결과가 주어졌을 때 기록, 재사용, 전파, 재생이 규칙대로 일어난다. 시험 40개가 통과한다(재검토에서 운영 고침 시험 14개를 더했다).
- 시계·작업자·예산·여러 프로젝트를 붙인 13장면에서 어디가 버티고 어디가 깨지는지([07-review.md](07-review.md) 3절, (s)).
- 세 사례의 문장과 수치가 [db/out/cases.json](db/out/cases.json)과 바이트까지 같다.
- R1 실행 영수증은 CPython 3.13.18과 3.12.3에서 실제로 돌린 출력이다.

**보증하지 않는다.**
- 새 검색 갈래별 결과가 실제 검색 엔진에서 그렇게 나오는지.
- 접수가 쓴 칸별 필요 문장과 꼬리표 문장의 품질. 판독 모델이 원문 줄을 정확히 찾는지.
- 공급자 소식 채널 주소.
- ii-svn-log 제작자 글의 일본어 원문. 저장소에 없고, 149 원장의 판독만 있다.
- 사람이 답을 읽고 무엇을 하는지. 249는 참가자 0명이고 267은 채점기 재현이다.
- 운영 시뮬레이션의 세계 모형(개정 게시 시각, 잡음 어휘, 예산 단위, 판독기 오류율)이 실제와 같은지.

### 3.2 완료 기준

1. [db/test_ledger.py](db/test_ledger.py)의 저장 계약·규칙·운영 고침·결정 시험 33개(`StorageContract` 13, `Rules` 2, `OperationalFixes` 14, `Decisions` 중 D1·D6·D7·D9 4)가 제품 코드에서 그대로 통과한다. 단위 2의 범위(채널·임차·대체·알림)를 시험하는 것은 단위 2에서 통과시킨다. D6c(요청 수치를 프로젝트 장부로)는 새 시험을 함께 쓴다.
2. R1을 실제 검색과 실제 원문으로 돌리면 다음이 모두 성립한다.
   - 1번 자리가 CPython 3.13 `asyncio.Queue`이고 근거 수준이 L4다(영수증 포함).
   - "[필수] 일꾼 작업을 정확히 4개"가 함께 필요한 것에 있다.
   - 접힌 목록에 세마포어 선획득(H1 U)과 전부 미리 생성(H2 위반)이 갈린 조건과 함께 있다.
   - 탐색 기록에 서랍 / 새 검색 경로와 맞은 토큰, 우연 적중 표시가 있다.
3. 같은 요청을 런타임 3.12로 다시 보내면 3.12.3 판의 같은 위치만 새로 열고, 지난 답은 문장 그대로에 알림 1건이 붙는다.
4. 다른 프로젝트가 같은 판·위치를 물으면 새 판독이 0건이고 파일 전체를 다시 읽지 않는다. 재사용 관문이 reopen이면 뒤집을 위치만 대조하고 가져오기 1회로 센다. 앞 프로젝트의 쪽지는 0건 보인다.
5. 공개 꼬리표에 요청 문장을 쓰려 하면 거절된다.

## 4. 첫 실제 사용 시험

[sections/request_utility.md 6절](sections/request_utility.md)의 최소 시험을 그대로 채택한다.

1. Studio 실제 요청 8건을 4명 이상에게서 받는다. Studio는 허락받은 선택 부분만 넘긴다.
2. 접수 때 자유 회상(이미 고려한 대안)과 대상 파일 지문을 봉인한다.
3. G·S·P 세 팔을 같은 원문 열람 예산으로 돌린다. 사용자에게는 무작위로 P와 S 중 하나만 보인다(4건씩). G는 발견·적용 분모에만 쓴다.
4. 7일 동안 Studio가 지문 변화와 작성자를 넘긴다. 작성자가 아닌 1명이 변경 지문에 검수·인수를 남긴다.
5. 사후 설명은 창이 닫힌 뒤 받는다.

보고는 8행 사례표와 기록 사슬 완결 여부뿐이다. 노출이 봉인보다 앞서거나, 기록이 끊기거나, 범위 밖 자료가 넘어가면 멈춘다. 이 시험은 사람이 참여하고 실제 프로젝트 자료를 다루므로 시작 전에 별도 승인이 필요하다.
