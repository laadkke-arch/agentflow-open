> **총괄 판정(2026-11-26).** 감시 키의 두 층과 공지 기한, 기한 작업과 채널 항목의 합치기, 요청 시계 재사용 게이트의 다섯 조건을 모두 채택해 [`Ledger.watch`, `Ledger.due`, `Ledger._enqueue`, `Ledger.reuse_gate`](../db/ledger.py)로 넣었다. 9절의 이견(골격은 재사용 관측마다 뒤집을 위치를 다시 연다)은 이 부문 쪽으로 판정했다. 152 재생에서 늘 요청 때 읽는 정책이 같은 예산에서 보류 때문에 더 많이 틀렸기 때문이다. 공통 사례에서 두 규칙은 이렇게 갈린다. 사례 A의 프로젝트 C는 채널 커서가 늙었고 마지막 직접 확인이 168시간을 넘어 게이트가 다시 열기를 요구한다(골격과 같은 동작). EVAL-X1에서는 공지 기한과 미처리 항목이 다시 읽기를 강제하고, E2·E3·E5에서 기한 작업이 채널 작업에 합쳐져 작업이 하나씩만 생긴다([../db/out/cases.json](../db/out/cases.json)의 `events[].merged`). 청구 없는 수집 관측을 지우지 않는 규칙, 사건별 처리표, 운영 지표 임계는 그대로 채택했고 임계값은 모두 가정이다([../06-assumptions-handoff.md](../06-assumptions-handoff.md)).

근거 표시: (a) 문서 판독, (b) 고정 입력 실행, (c) 사용자 미확인. (b)는 AF-RES-152 `replay.py`를 다시 돌려(base·archive-catalog·big-catalog) 원장 CSV와 바이트까지 같음을 확인한 출력의 값이다. 다른 연구의 실행 결과는 영수증만 읽어 (a)다. [가정]은 11절에 모았다.

요약하면, 채널 주소·커서와 이미 읽은 관측만 미리 보유하고, 뒤집을 위치에 두 층 **감시 키**와 기한을 달며(8절), 감시가 건전하면 재사용 관측을 다시 열지 않는다(9절).

## 1. 발견

**넘는 방법.** 출처를 언어가 아니라 항목이 들어오는 입구로 고른다. 149는 제작자 발표, 편집 제보(窓の杜), 배포 편입(F-Droid), 커뮤니티 제보를 입구로 나눴다 [149s] (a). 149는 BLOCKED라 입구마다 편향이 다르다는 설계 이유로만 쓴다. 언어와 지역은 입구를 따라온다. 호스팅은 합치지 않고 위치마다 남긴다. 형식은 항목 ID를 뽑을 수 있는지로 가르고, ID가 없으면 (가져온 시각, 내용 지문)을 판으로 쓴다.

**미리 모을 것과 요청 때 넓힐 것.** 배경 시계는 채널 주소·ID 규칙·커서만 유지하고, 요청 때 연 원문은 답에 쓰지 않은 것까지 관측으로 남긴다. 설명 카드는 같은 자료집에 요청이 반복될 때만 만든다. 072에서 카드 20편 구축은 HTTP 20회·2,087,664 B, 요청 때 여는 L은 요청당 4회·28,260 B였고, 둘은 HTTP로 5회째, 바이트로 약 74회째에 같아진다 [072r] (a). 요청 때는 묻는 언어와 영어로 찾고, 서랍에 다른 언어 관측이 걸리면 그 언어로도 찾는다. 한국어 질의를 영어 설명에 넣으면 recall@10이 .234에서 .124로 떨어졌다 [012] (a). 공급자 목록은 최근 창이 아니라 보관 목록 전체를 연다. 152에서 그렇게 하자 O의 높은 예산·희소 정답이 309에서 350/364로 올랐다(b).

**새 출처 하나의 비용.** 처음에 채널 주소·ID 규칙·층을 적고 겹침 차분을 시험한다. 그 뒤는 152 설정값(통지 1회 12,288 B·6초)으로 72시간 주기면 주 2.33회·28,672 B·14초다 [152c] (a). 이는 152 HIGH 예산(168시간당 24회)의 약 10%라서 바이트보다 횟수가 먼저 묶인다.

**유일한 작은 출처와 중복·열등 출처.** 양으로 가르지 않는다. 152 주류 수요에서 요청 때만 읽는 O는 curl 신규 3건을 0/3, 통지 차분 S는 3/3 찾았다(b). 분기마다 채널별 단독 기여(이 채널로만 들어와 적중을 얻은 관측 수), 선행 시간, 구체성을 센다. curl 8.14.1은 메일이, 8.15.0은 릴리스가 몇 분 빨랐으니 두 채널은 서로의 중복이다 [152r] (a). 窓の杜 월간 보관함은 다이제스트로 가는 색인일 뿐이었다 [149i] (a). 단독 기여가 1 이상이면 양이 적어도 남기고 주기만 늘린다. 152의 희소 전용 슬롯 F는 S보다 이득이 없었다(b). 단독 기여가 0이고 늘 함께 나오면 예비로 내려 주 채널이 끊겼을 때만 읽는다.

**탈락 후보.** 열어 본 후보는 공개 관측을 남기고 탈락 사유(무매치·근거 부족·조건 반증·충돌·우연 적중)는 비공개 탐색 기록에 둔다. 못 연 후보는 공개 쪽에 위치·발견 경로·"미판독"만 둔다. 다음 검색이 같은 위치를 돌려주면 기존 관측이 붙고 미판독이면 열 후보가 된다. 몇 달 뒤 재발견이 실제로 일어나는지는 관측된 적이 없다(c).

**R2(2027-03)에서 왜 걸리는가.** R2를 한 단계 위로 쓰면 "도구가 만든 기록을, 그 도구도 연결도 없는 PC에서 열람할 독립 파일로 넘기고 넘긴 뒤 불변을 보인다"다. 저장한 꼬리표와 "도구가 만든 기록", "도구가 없는 PC", "독립 파일", "열람"이 겹치고 이름·분야·언어는 겹치지 않으며, 겹친 말이 내용어라 우연 적중도 아니다. 걸리게 하는 것은 한 단계 위 꼬리표와 대상 사용자 문장이고, 넉 달 무적중에도 행을 지우지 않는 규칙이 그 조건을 지킨다. 걸리면 요청 시계가 제작자 글을 한 번 연다. 입력이 SVN에 묶이고 불변 근거가 없어 참고로 접힐 가능성이 높다(c).

## 3. 사건별 처리와 과거·현재의 읽기

과거 인용은 당시 관측 ID와 그때 유효한 관계로 다시 열고, 현재 추천은 지금 유효한 관계와 사용자 판의 최신 관측으로 다시 계산한다. 그래서 관계 행마다 주장·효력 시각과 취소 연결을 둔다.

| 사건 | 남기는 것 | 현재 추천의 처리 |
| --- | --- | --- |
| 이름 | 범위 붙은 별칭 | 값은 판 범위 같음이 있을 때만 잇는다. axe 4.8.0은 같은 `duplicate-id`를 기본 모드에서 보고하지 않았다 [253] (a) |
| 주소 | 주소 별칭, 실패 종류 | 별칭 대상의 정체를 다시 본다. 옛 `tree-sitter` 주소는 200인데 분리 뒤 library를 가리켰다 [023] (a) |
| 판 | 새 판은 새 관측 | 사용자 판에서 연다. 이월은 같은 층 지문이 같을 때만 한다. 266의 한 파일은 발표 14,234초 뒤 올라왔다 [266] (a) |
| 내용 | 개정마다 새 관측 | 최신 개정을 쓰고 HTTP 200은 근거로 쓰지 않는다 [152r] (a) |
| 가용성 | 실패 종류와 시각 | 상태로 두지 않고 요청 때 재시도한다. 152 모든 정책의 복구 직접 포착은 0/2였다(b). TTL 음성 캐시는 회복을 한 틱 늦췄다 [147] (a) |

**병합**은 범위·주장자·근거가 붙은 관계 행이고 과거 답에 끼우지 않는다. **분리**는 병합에 취소 행을 달고 그 병합에 기댄 자리만 표시한다. **우리 판독의 철회**는 인용한 자리만 "근거 철회"로 표시하고 문장은 둔다. **공급자 철회**는 새 관측으로 남기고 과거 인용은 당시 유효로 읽으며 현재 추천은 핀 형태로 갈린다. `==8.1.0`은 철회 파일을 경고와 함께, `<8.1.1`은 8.0.2를 골랐다 [229] (a). **복원**은 취소의 취소이고 의존 관계는 자동으로 되살리지 않는다. 161에서 병합 되돌리기만으로 다른 항목의 인용이 돌아오지 않았다 [161] (a).

## 5. 세 시계의 예산

**잰 배분(b).** 152 S 높은 예산·주류 유보 26주에서 배경 통지 181회, 후속 원문 8회, 요청 원문 86회였고, 364 질의 중 278건을 이미 읽은 근거(목록 72시간, 대상 168시간)로 답했다. 요청 횟수로 배경 66%·후속 3%·요청 31%, 바이트로 42%·5%·53%, 판독초로 28%·6%·66%다.

**목표와 시계.** 희귀 발견은 배경 ID 차분이 사고 표시일 창은 쓰지 않는다. P가 놓친 CF-2026-01은 표시 1월 1일·편입 1월 30일이라 30일 창에서 빠졌고, 보관 목록을 열자 P도 14/15였다(b). 신선도는 후속 시계가 채널 항목과 공지 기한으로, 요청 지연은 재사용 게이트가 산다.

**ID 차분.** 커서는 본 ID 집합과 마지막 성공 시각이다. 마지막 성공에서 48시간 겹쳐 읽고, 새 ID는 지금 집합에서 본 집합을 뺀 것이다. 표시일로 거르지 않는다. 빠진 ID는 삭제가 아니라 "목록 누락"이다. 해결된 상태 사건은 미해결 목록에서 빠져도 ID로 열렸다 [152r] (a).

**연결 규칙.** (1) 항목의 대상 키가 감시 키와 같을 때만 재확인 작업을 만든다. (2) 감시 키는 주장과 같은 층이어야 한다. 설치 주장은 파일 색인, 문서 주장은 문서 이력을 본다. 261도 영향받은 층만 다시 열라고 정리했다 [261] (a). (3) 확인 단계는 관측마다 감시 키를 하나 이상 쓰거나 "감시 없음"을 적는다. (4) 공지 기한이 있으면 기한 24시간 전과 기한 시각에(재검토: 24시간 뒤에도, 07 D4) 직접 읽고, 기한 경과만으로 무효로 하지 않는다. 기한이 지나면 캐시에서 빼는 152 규칙에서는 Pocket 내보내기 기한 연장 때 잘못된 제외가 S 27시간, P 279시간이었고 요청 때 읽는 O는 0시간이었다(b). (5) 개정이 둘 이상 쌓이면 각각 읽는다. 152 낮은 예산·주류 S는 첫 연장 판을 직접 확인하지 못했다 [152r] (a).

**EVAL-X1 E1~E5.** T0(2025-05-15) 답이 Pocket을 "확인할 후보"로 냈다고 둔다 [seal]. 확인 단계는 내보내기 도움말 관측 O0에 같은 주소 키와 (mozilla, pocket) 공지 키를, 원리 후보 관측(OAI-PMH §2.5.1·§3.5.1, RFC 8493 [263])에 절 번호 키를 달았다.

1. **E1(05-22).** 공지 채널의 새 ID 두 개(블로그 공지, 새 도움말 `future-of-pocket` rev 297191)가 공지 키에 닿아 후속 시계가 rev 297191을 열고 O1을 쓴다. O1의 기한 값은 "7월 8일 이후 내보내기 전용"과 "내보내기 10월 8일까지"이고, 감시 키는 `kb:future-of-pocket`이다. 프로젝트 쪽지에 R1 반증(기한 있음)과 R3 기한부가 붙고 T0 답은 그대로 재생된다.
2. **E2(07-08).** 저장 기한 작업과 채널의 rev 300072가 같은 관측을 가리켜 작업 하나로 합친다. O2는 "저장 종료, 내보내기 계속"이고 200은 쓰지 않는다. R3의 Pocket 자리가 현재 추천에서 철회된다. 152 높은 예산·주류 S는 이 변화를 51시간 뒤 직접 확인했다(b). 기한 작업이 이 지연을 없앨지는 재생하지 않았다(c).
3. **E3(10-08)·E4(10-09).** 기한 24시간 전 읽기가 먼저 돈다. rev 308355와 308427을 각각 열어 O3(11월 6일)과 O4(11월 12일)를 쓴다. 기한만 바꾼 관측이라 새 후보로 세지 않고, "10월 9일에 알던 기한"은 관측 시각으로 되묻는다.
4. **E5(11-12).** rev 313551로 O5 "내보내기·API 비활성, 삭제 대기"를 쓰고 R1의 Pocket 자리도 철회한다. 원리 자리의 사용 쪽지는 OAI-PMH·RFC 8493 관측을 가리키므로 건드리지 않는다(T2-b). 직접 도구 후보가 다 사라지면 "재탐색 제안" 작업을 만들고 "검증된 대체 없음" 문장은 조합 부문이 쓴다.
5. **비용.** 여섯 달 원문 열람 6회, 152 모형으로 196,608 B다.

## 7. 낯선 분야: 항공 감항성 개선 지시의 적용 대상 관리

**원리 [일반 지식].** 감항성 개선 지시(AD)는 형식·일련번호 범위·부품번호·장착 상태로 적용 대상을 정하고 이행 방법과 기한을 정한다. 운영자는 기체마다 모든 AD의 상태(이행, 반복 점검 중, 해당 없음과 이유, 종결)를 표로 유지하며, 대체 AD는 옛 이행의 인정 여부를 적는다. 대응시키면 AD는 채널 항목, 적용 대상은 감시 키, 기체별 상태표는 쪽지 영향 표시, 이행 기한은 공지 기한, 대체 AD는 개정 D1에서 D2로의 교체, 반복 점검은 감사 표본이다.

**사라지는 것.** 새 판마다 모든 활성 주장을 재검토하는 일(기존 고정판 [st])과 "이 변경이 우리와 관계있나"를 매번 따지는 일이 사라진다.

**새 실패.** 공급자 항목에 적용 대상이 구조화되어 있지 않아 추론해야 하고, 잘못된 "해당 없음"은 조용한 실패가 된다. 그래서 감사에서 "해당 없음"을 두 배로 뽑는다. 상태 행이 항목 수와 프로젝트 수의 곱으로 불어나므로 감시 키가 맞을 때만 만든다. "재확인 완료"가 "판정이 옳음"으로 읽히는 착시가 생기고, 프로젝트의 판·환경 기록이 틀리면 적용 판정이 전부 틀리므로 요청 부문의 출처 도장에 기댄다.

## 8. 다른 부문에서 달라지는 동작: DB와 확인 단계의 감시 키

DB의 뒤집을 위치 행에 `watch_key` 목록(층: 같은 주소 / 공급자·제품)과 `deadline`이 생기고, 확인 단계는 관측을 쓸 때 감시 키나 "감시 없음"을 반드시 쓴다.

**전(EVAL-X1 E1).** 골격대로면 뒤집을 위치는 O0의 문장이고 감시는 항목이 그 위치에 닿을 때만 움직인다. 5월 22일 공지는 블로그와 새 도움말 `future-of-pocket`(이력이 5월 22일에 시작 [152src] (a))에 나왔으므로 O0의 주소에 닿지 않아 재확인이 생기지 않는다. O0의 페이지가 기한을 반영했는지는 저장소에 없고(c), 반영하지 않았다면 R1은 7월 8일 이후까지 "확인할 후보"로 남는다.

**후.** O0의 공지 키에 두 ID가 닿아 6절 1단계가 돌고, 현재 추천은 후속 시계 지연만큼만 늦게 바뀐다. 7월 8일에는 채널이 없어도 기한 작업이 돈다. 비용은 공지 채널 배경 읽기(주 2.33회)와 원문 1회다. 무관한 공지가 제품 이름만 언급해 생기는 헛된 재확인 비율은 모른다(c).

## 9. 골격과 다른 판단: 요청 시계의 조건부 재열람

골격은 재사용 관측마다 뒤집을 위치를 다시 열지만, 이 부문은 다섯 조건이 모두 참이면 열지 않고 "채널 확인 시각"을 근거로 붙인다. (1) 감시 채널 커서가 주기의 2배 안에서 성공했다. (2) 감시 키에 미처리 항목이 없다. (3) 공지 기한이 지나지 않았다 **[재검토, 07 D4: 기한 창 T-24h~T+24h 밖이고, 기한이 지났으면 기한 뒤 직접 확인이 있다]**. (4) 감시 채널과 주장의 층이 같다. (5) 마지막 직접 확인이 168시간 안이다(152 S 설정) **[재검토, 07 D8: release·commit·tag·doi 판은 면제]**. 하나라도 거짓이거나 감시 없음이면 연다.

**판정.** 같은 예산에서는 이 판단이 맞다. 152에서 늘 요청 때 읽는 O는 보류 때문에 높은 예산 336·309/364, 낮은 예산 227·209/364를, 캐시와 채널을 쓴 S는 340·343·341·345/364를 맞혔다(b). 골격은 배경 채널 비용에 요청 때 읽기를 더하므로 O보다 보류가 많을 것으로 추론한다(재생 안 함). EVAL-X1에서는 조건 (3)이 7월 8일과 10월 8일에, 조건 (2)가 D1·D2 대기 중에 다시 읽기를 강제한다. 다섯 사건 모두 개정 ID가 있어 "항목도 기한도 없는 변경"이라는 남은 위험 밖이다. R2의 개인 글은 감시 없음이라 두 규칙이 같다. 골격이 맞는 경우는 값싼 조건부 요청(304)이 공유 예산 밖에 있을 때인데, 304 비율은 152에서도 열린 문제다(c). 재확인 범위(규칙 5)와 수집은 골격을 유지하고 층 조건과 버리지 않는 규칙만 더했다.
