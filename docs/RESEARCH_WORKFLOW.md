# 다음 작업자를 위한 연구·정리 운영 규칙

2026-11-19. **작업환경 설정 문서다. 제품 조사·설계의 실행 지시가 아니다.** 실제 과제는 별도 작업 지시로 배정한다. 앞으로 연구할 목적과 미결정 질문은 [제품 연구 브리프](product/RESEARCH_BRIEF.md)에 있다.

## 1. 만들어야 할 결과

사용자가 나중에 최상위 모델에 설계를 맡길 수 있도록, 근거·대안·제약·반례를 갖춘 적당한 크기의 연구 묶음을 만든다. 조사 단계에서 최종 설계 하나를 고르는 것을 기본 완료 조건으로 삼지 않는다. 명백히 부적합한 선택은 이유와 함께 제외하고, 서로 다른 좋은 선택은 조건을 붙여 보존한다.

**연구자료 저장 방식과 미래 제품의 DB는 별개다.** 여기의 Markdown·색인·인계 규칙이 제품의 테이블, 검색 엔진, 수집기 구조를 결정하지 않는다.

## 2. 질문 한 번에 완료할 작업 단위

한 요청은 독립적으로 답할 수 있는 연구 질문 하나 또는 함께 판단해야 하는 밀접한 질문 묶음이다. 기본 수행 범위는 기존 자료 확인 → 필요한 추가 조사 → 대안·반례 비교 → 가능한 검증 → 정리·저장 → 인계다. 이미 허용된 범위에서는 단계마다 '계속할까요'를 묻지 않는다.

완료 조건은 다음과 같다.

- 질문의 각 항목에 답하거나, 미해결 이유와 답을 바꿀 최소 추가 확인을 기록했다.
- 주요 사실에 실제 읽은 근거와 확인 범위가 있고, 제안·추정·사용자 요구를 구별했다.
- 서로 다른 대안의 작동 원리·장점·대가·실패 조건과 함께 쓸 수 있는 부분을 비교했다. 의미 없는 후보 수 채우기는 하지 않는다.
- 확정 결함·반례를 확인해 고쳤거나 논쟁점으로 남겼다. 자기 검토를 독립 검토로 부르지 않는다.
- 결과와 필요한 근거가 GitHub에서 다시 읽히며, 색인 갱신 제안·짧은 인계·다음 행동이 있다.

작업시간이나 보고서 길이보다 이 완료 조건을 기준으로 삼는다. 범위가 너무 넓으면 시작 시 독립된 질문으로 나눠 각 산출물을 정하고, 허용된 묶음은 같은 요청에서 끝낸다. 도구 제한이나 실질적 판단 대기로 멈추면 진행한 내용과 재개 지점을 저장한다.

### 요청문에 넣을 항목

```text
작업 ID: 소문자-고유-id
이번에 답할 질문 / 이 답을 어디에 쓸지:
확정 요구 / 예시·가설 / 아직 정하지 말아야 할 것:
읽을 색인·기존 자료·정확한 의존 커밋:
허용 작업·편집 경로 / 필요한 실행환경:
완료 조건 / 필요한 독립 검토:
산출물 위치 / 기록할 다음 행동:

위 범위의 조사·비교·검증·정리·저장·인계까지 수행해.
기존 근거를 재사용하고, 부족하거나 오래되었거나 충돌하는 부분만 추가 확인해.
최종 설계 하나를 억지로 고르지 말고, 조합 가능한 대안과 적용 조건을 남겨.
```

## 3. 세 세션을 쓰는 방법

세 역할을 항상 동시에 켜는 규칙은 없다. 과제 성격에 따라 아래 방식을 선택해 작업 지시에 기록한다. 기존 조사·DB·UX 역할은 과거 예시이며 필수 부서가 아니다.

| 방식 | 세션 1 | 세션 2 | 세션 3 | 적합한 때 |
| --- | --- | --- | --- | --- |
| 근거 → 대안 → 검토 | 실제 사례·구현·근거 확인 | 근거를 받아 여러 구성안과 조합 조건 정리 | 반례·누락·전제·검증 범위 독립 검토 | 질문이 연결되고 조기 설계 고정이 우려될 때 |
| 독립 탐색 두 갈래 + 대조 | 같은 문제의 한 탐색 축 | 겹치지 않는 분야·다른 원리 탐색 | 공통점·차이·상충·빠진 경로 대조 | 새로운 아이디어와 분야 간 참고를 넓힐 때 |
| 작성 + 독립 검토 | 조사부터 대안 정리까지 한 묶음 | 결과와 원문을 독립 검토 | 필요할 때만 사용 | 작은 과제나 입력 의존성이 큰 때 |

세션 2·3이 앞 결과에 의존하면 파일과 커밋을 받은 뒤 시작한다. 세 세션이 같은 검색·요약·전체 검사를 반복하지 않는다. 각 작성자는 자기 경로에서 작업하고, 한 명의 편집 담당이 검토된 결과의 현재 색인을 갱신한다. 편집은 최종 제품 설계 선택과 구별한다.

Dot은 작업 배정·상태 조회·인계와 색인 변경 전달을 맡는다. 근거의 해석이나 설계의 우열 판단은 담당 작업자·검토자가 맡는다. Dot의 컴퓨터에는 Git·짧은 로그 처리·기존 검사처럼 가벼운 실행을 맡긴다.

## 4. 자료가 늘어도 읽을 수 있게 저장

진입점은 [현재 자료 색인](research/INDEX.md)이다. 최신 상태·배정 과제 → 색인에서 필요한 항목 → 해당 연구 묶음 → 필요한 원문·실행 증거 순서로 읽는다. 전체 과거 보고서를 새 세션마다 넣지 않는다.

연구 묶음 하나는 나중에 독립적으로 채택·보류·교체할 수 있는 판단 단위다. 링크 하나마다 파일을 만들거나 여러 결정을 한 장문에 몰아넣는 것을 기본값으로 삼지 않는다. 분리할 때는 기존 ID와 대체 관계를 남기고, 합칠 때는 각 근거·제약·반례를 유지한다.

### 연구 묶음의 내용

| 항목 | 기록할 내용 |
| --- | --- |
| 식별·질문 | 고유 ID, 답하는 질문, 읽은 입력 버전, 현재 상태 |
| 짧은 핵심 | 발견한 것과 아직 결정하지 않은 것을 한눈에 읽을 요약 |
| 근거 | 원본 URL, 확인일, 고정 버전·코드 위치 또는 관측 범위 |
| 대안·기발한 조합 | 원리, 필요한 전제, 얻는 것과 감수할 것. 새 아이디어는 가설로 표시 |
| 반례·한계 | 적용하면 안 되는 경우, 미확인, 확인된 실패 |
| 관계 | 함께 쓸 수 있는 묶음, 충돌하는 묶음, 필요한 선행 자료 |
| 검토 | 누가 무엇을 검토했는지, 이견과 수정 여부 |
| 다음 확인 | 답을 바꿀 최소 실험·질문, 후속 담당자가 할 첫 행동 |

작은 묶음은 한 파일 안에 담는다. 코드·긴 로그·실험 입력처럼 따로 있어야 재현되는 자료만 별도 파일로 연결한다. 같은 설명을 상태·인계·색인에 반복 복사하지 않는다. 색인에는 질문·상태·경로·핵심 의존성만, 인계에는 이번 변경과 다음 행동만 둔다.

새 자료를 저장하기 전에 색인에서 기존 질문·동일 출처를 찾는다. 현재 문서를 갱신하고 의미 있는 변경은 Git 이력에 보존한다. 오래된 상세 기록은 현재 읽기 경로에서 내려 이력으로 연결한다. `검토됨`은 선택 완료나 사실 전체의 보증이 아니며, 이견은 삭제하지 않는다.

## 5. 최상위 모델에 넘길 설계 입력

편집 담당은 현재 목표·제약, 관련 연구 묶음의 짧은 안내, 대안 간 비교, 조합·충돌 관계, 미해결 질문과 검토 이견을 모아 전달한다. 원본은 파일·커밋으로 다시 찾아갈 수 있게 한다. 전체 아카이브를 복제한 장문은 기본 입력으로 삼지 않는다.

설계 담당은 묶음을 버리거나 다시 나누고 조립할 수 있다. 버린 이유와 채택 판단을 기록하며, 조사 단계의 유망 후보를 이미 확정된 설계로 취급하지 않는다. 나중에 환경이나 요구가 달라지면 관련 묶음과 결정만 다시 검토할 수 있어야 한다.

## 6. 요청 한도와 진행 관리

한 번의 Pro 요청으로 완결된 유용한 결과를 만드는 것을 목표로 한다. 작업자 호출·후속 메시지를 줄이기 위해 입력과 완료 조건을 먼저 묶고, 단순 진행 확인과 로그 정리는 Dot/실행 도구로 처리한다. 정상 작업에 반복해서 '계속해'를 보내지 않는다.

사용자가 언급한 '100회 정도'는 계정에서 확인한 고정 수치로 저장하지 않는다. 2026-11-19 확인한 [현재 모델 안내](https://help.openai.com/en/articles/20001354-gpt-6-and-other-models-in-chatgpt)는 Chat Pro 모델의 한도가 요금제에 따라 다르며 Work/Codex와 별도라고 설명한다. 실제 모델·남은 양·초기화 시각은 계정 표시를 따른다. 작업시간·세션 길이·추가 작업자 호출량을 이 문서가 보장하지 않는다.

## 현재 적용 범위

이 규칙과 연구 브리프를 준비했다고 제품 연구가 실행 중인 것은 아니다. [Dot 진행표](automation/dot-control.json)의 기존 두 작업은 연결 검증용이며 새 제품 연구 묶음을 자동 배정하지 않는다. 현재 허용된 환경 준비를 마친 뒤, 향후 작업 지시에서 연구 질문·범위·담당을 지정해 시작한다.
