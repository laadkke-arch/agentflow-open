# 참고 방법을 조합하는 공통 작업환경

기준일: 2026-11-15
상태: 설계와 문서 비교. 아래 후보를 설치하거나 비교 실행한 결과는 아니다.

## 목적과 원문 범위

목표는 특정 커뮤니티 세팅의 복제가 아니라, 조사·판단·구현·검증에서 얻은 경험을 다음 프로젝트에 재사용하는 작업환경이다. 일시적인 서비스 사용량 혜택을 필수 조건으로 삼지 않는다.

참고 글은 디시 AI 활용 갤러리의 게시물 177968이다.
https://gall.dcinside.com/mgallery/board/view/?id=ai_utilize&no=177968

앞선 직접 접속에서는 본문 확보에 실패했으나, 이후 사용자가 이 대화에 본문을 붙여 주어 제공된 텍스트를 읽었다. 이는 현재 사이트 본문과 최신 댓글을 다시 열람했다는 뜻이 아니다. 공개 저장소에는 원문이나 사용자 대화를 통째로 복제하지 않고, 필요한 방법의 요약과 적용 판단만 남긴다.

원문은 1~5단계에서 대화 요약과 프로젝트를 GitHub에 축적하고, 6~15단계에서 별도 SKILL 저장소·사전조사·기획·실행·피드백·다음 프로젝트 재사용으로 확장한다. 본 문서는 이 흐름을 참고하며, 원문의 사용량·용량·성능·안전성 주장을 검증된 사실로 채택하지 않는다.

## 그대로 가져갈 원칙과 바꿀 방법

| 원문에서 가져갈 원칙 | 우리에게 제안하는 적용 |
| --- | --- |
| 대화 밖에 기록을 남긴다 | 현재 상태, 결정 이유, 출처, 재현 가능한 검증 결과를 구분한다. 모든 대화를 같은 수준의 영구 지침으로 만들지 않는다. |
| 개발 전에 기존 자료를 조사한다 | 후보마다 해결 문제, 채택하거나 제외한 이유, 근거와 미확인 사항을 남긴다. 검색 결과와 직접 실행 검증을 구분한다. |
| 실패를 경험으로 남긴다 | 재현 조건과 원인을 기록하고, 필요한 경우 회귀 테스트를 추가한다. 다른 상황에서도 유효함을 확인한 절차만 공통 지침으로 승격한다. |
| GitHub를 기록의 중심으로 쓴다 | 코드와 작은 텍스트 기록은 Git, 서비스 운영 데이터는 DB, 큰 실행 산출물은 적절한 별도 저장소로 나눈다. |
| 빌드와 테스트 결과를 회수한다 | 빠른 편집·검사와 독립된 CI 검사를 분리할 수 있게 한다. 모든 작은 수정이 원격 실행을 기다리도록 고정하지 않는다. |
| 다른 AI로 옮겨도 기록을 활용한다 | 일반 Markdown과 표준 형식을 우선하고, 도구별 설치·호출·권한 연결은 별도로 확인한다. 파일 형식의 호환성과 자동 실행 호환성을 혼동하지 않는다. |

## 문서에서 확인한 참고 후보

### Agent Skills 형식

공식 형식은 SKILL.md와 선택적인 scripts, references, assets를 정의한다. 이름·설명, 필요 시 전체 지침, 필요 시 추가 자료를 읽는 단계적 로딩을 설명한다.

채택 후보: 짧은 시작 안내와 주제별 자료를 분리하고, 작업과 관련된 절차만 읽는 구성. 스킬 파일을 GitHub에 두는 것만으로 현재 채팅에 자동 설치되는 것은 아니다. 실제 사용할 도구의 발견·호출 방식을 확인한다.

출처: https://agentskills.io/specification
검증 수준: 공식 문서 확인. 이 저장소에는 아직 실행 가능한 스킬 패키지를 추가하지 않았다.

### GitHub Spec Kit

공식 quickstart는 요구사항, 설계, 작업 목록, 구현과 완성도 검토를 구분하며 작은 기능용 짧은 경로도 제공한다.

채택 후보: 무엇을 왜 만드는지, 구현 방식, 완료 조건을 구분하는 원칙. 첫 작업에는 짧은 기획과 작업 목록만 적용하고 전체 도구 설치나 모든 단계를 강제하지 않는다.

출처: https://github.com/github/spec-kit/blob/main/docs/quickstart.md
검증 수준: 공식 파일 내용 확인. 설치·실행 미실시.

### Superpowers

공식 README는 설계, 작은 작업 계획, 테스트, 체계적인 디버깅, 검토, 완료 전 검증을 묶은 개발 절차를 설명한다.

채택 후보: 증거를 확인한 뒤 완료를 보고하는 절차와 원인 중심 디버깅. 다른 프레임워크와 전체 규칙을 중복 설치하지 않고 필요한 절차를 비교한다.

출처: https://github.com/obra/superpowers
검증 수준: 개발자 README 확인. 성능·비용 우위의 독립 검증은 하지 않았다.

### DevSpace

공식 README는 연결된 개발 환경의 파일 편집, 명령 실행, 결과 검토, Git worktree 기반 병렬 작업을 제공한다고 설명한다. 로컬 사용자 권한과 인증정보를 사용하는 강력한 연결이라는 설명도 포함한다.

검토 후보: GitHub를 매번 중간 실행 통로로 사용하는 것보다 빠른 반복 작업이 필요해질 때 직접 작업환경 연결을 비교한다. 현재 연결돼 있거나 설치된 것으로 취급하지 않는다. 작업 폴더 분리와 보안 격리를 같은 것으로 보지 않는다.

출처: https://github.com/Waishnav/devspace/blob/main/README.md
검증 수준: 개발자 문서 확인. 사용자 PC 연결, 설치, 동일 작업 비교 실행 미실시.

### GitHub Actions와 Git worktree

GitHub 제공 러너는 별도의 실행 환경에서 검사를 수행할 수 있다. 빌드 결과·검사 보고·실패 화면은 workflow artifact로 저장할 수 있고, 의존성 캐시는 다른 목적의 기능이다. Git worktree는 한 저장소의 서로 다른 브랜치를 별도 작업 디렉터리에서 다루게 한다.

제안: Actions는 재현 가능한 검사 경로로 유지하고, 실제 병렬 편집이 생기면 브랜치뿐 아니라 작업 디렉터리도 분리한다. 큰 빌드 파일을 매번 소스 이력에 넣지 않는다. artifact 보존기간과 별도 백업 필요성은 배포 단계에서 정한다.

출처:
- https://docs.github.com/en/actions/concepts/runners/github-hosted-runners
- https://docs.github.com/en/actions/concepts/workflows-and-actions/workflow-artifacts
- https://git-scm.com/docs/git-worktree

검증 수준: 공식 문서 확인. 기존 최소 Actions 시험 외의 새 실행 환경은 만들지 않았다.

## 저장과 검색의 제안 구조

프로젝트별 현재 상태에는 목표, 작업 브랜치, 검증한 코드 버전, 남은 일, 다음 행동을 짧게 둔다. 세부 설계와 과거 결정은 연결된 문서로 보관한다. 초기에는 주제별 색인과 텍스트 검색을 사용하고, 실제 검색 실패가 누적될 때 더 복잡한 검색 방식을 검토한다.

조사 기록의 최소 항목은 대상, 해결하려는 문제, 공식 출처, 확인일, 지원 근거, 미확인 사항, 사용 조건, 채택·보류·제외 이유다. 커뮤니티 평판은 발견 근거로 쓰되 직접 확인한 기능과 구분한다.

재사용 지침에는 적용 조건, 필요한 입력, 수행 절차, 성공 확인, 적용하면 안 되는 조건, 사례·검증 기록, 버전을 남긴다. 단발성 오류의 우연한 해결법을 모든 프로젝트의 규칙으로 만들지 않는다. 폐기된 판단은 이력으로 보관하되 현재 선택에서 제외한다.

## 저장소 구분 제안

장기적으로는 공통 작업환경과 제품 저장소를 구분한다.

- 비공개 공통 작업환경 저장소: 공개하지 않을 조사·실험 기록, 검증된 재사용 절차, 템플릿, 프로젝트 색인. 비밀키는 비공개 Git에도 저장하지 않는다.
- 프로젝트 저장소: 해당 제품의 코드, 설계, 테스트, 상태와 결정. 공개 범위는 프로젝트별로 정한다.

공통 환경을 공개 제품 저장소의 영구 브랜치에 숨겨 두지 않는다. 브랜치는 변경을 검토하는 단위로 사용한다. 현재 chore/workspace-foundation은 초안 비교와 최소 실행 시험용으로 유지하며, 새 저장소 생성·권한 변경·main 병합은 이번 문서 변경에 포함하지 않는다.

Render는 최종 서비스 실행 대상으로 유지한다. 공통 지식 보관이나 로컬 개발 연결을 대신하는 만능 도구로 취급하지 않는다. 수업 자료의 Flask·TiDB·Render 도서관리 구현은 배포 참고 예시이지 공통 작업환경 전체에 대한 필수 구조가 아니다.

## 다음에 검증할 실제 작업

기존 6개 단위 검사와 입력 실패·복구는 실행 경로의 최소 시험이다. 이것만으로 조사 품질, 기억 검색, 일반적인 개발 오류 해결, 다중 프로젝트 재사용을 검증했다고 하지 않는다.

다음 시험은 하나의 실제 문제를 고르고 후보 도구 3개를 조사하여 비교 기록을 남기는 작업으로 한다. 예를 들어 저장소 주소의 중복 정리 방법을 검토하고, 재사용 여부를 판단한 뒤 작은 검증 사례를 남길 수 있다. 이는 예정된 시험이며 아직 수행하지 않았다.

판정 기준:
1. 어떤 출처 때문에 후보를 선택·제외했는지 추적할 수 있다.
2. 파일 형식이 맞다는 것과 내용이 검증됐다는 것을 구분한다.
3. 새 세션이 종료된 결정을 다시 묻지 않고 필요한 기록을 찾을 수 있다.
4. 다른 작은 작업에도 같은 절차를 적용할 수 있고 프로젝트 정보가 섞이지 않는다.
5. 수동 전달 횟수, 도구 왕복 횟수, 재작업과 실패 원인을 기록해 실제 개선을 판단한다.

직접 연결 도구와 기존 GitHub 경로의 속도·비용 비교는 같은 작업으로 측정한 뒤 결정한다. 도구 설치 개수나 문서 개수를 작업환경 완성의 지표로 삼지 않는다.
