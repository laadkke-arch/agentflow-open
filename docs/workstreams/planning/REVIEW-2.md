## 2. 얕거나 근거 없이 단정된 것

### 공통 (여섯 작업 모두)
1. **모든 문제는 연구자가 만든 합성 문제다.** K01–K06, P1/P2, P01–P04 어느 것도 실제 사용자의 설계·질문이 아니다. "실제로 도움이 되는가"라는 제품의 핵심 가치는 한 번도 실제 요청으로 시험되지 않았다.
2. **"독립 검토"는 모두 같은 세션 안의 내부 하위 에이전트다.** 각 작업이 이 한계를 적어 두기는 했다. 그래도 AF-RES-004의 18/18 라벨 일치는 작성자가 경계가 분명하도록 설계한 사례에서 나온 것이다. 이 판정 틀이 애매한 실제 후보를 구별하는지(변별력)는 보여 주지 않는다.
3. **검증 의식(SHA 고정, blob 대조, receipt, "미실시" 문구)에 비해 실질 조사량이 작다.** AF-RES-002의 HANDOFF·VERIFICATION.json·REVIEW·evidence/review.json을 합치면 약 63KB로, 종합 본문 RESEARCH.md(약 21KB)의 3배다. 다음 brief는 한계·미실시 문구를 파일 끝 한 절에 모으게 하고, 실질 내용의 최소량을 숫자로 정했다.
4. **실행 근거(D3)는 내부 출처 ID 검사기 한 번뿐이다.** 검색 방식(BM25·의미 검색·RRF)은 문헌으로만 비교됐고, 저장 표현이 검색에 미치는 영향은 전혀 실행되지 않았다.

### AF-RES-001
- 결론의 근거인 사례 6개가 모두 "정돈된 6문장"이다. 정보 후보표(§5)는 작성자가 만든 사례에서 각 필드가 필요한 이유를 끌어낸 것이라, 사례와 결론이 같은 손에서 나왔다(순환 위험).
- C안("AI 분해 제안")은 실제 모델 출력이 아니라 작성자가 손으로 쓴 것이다. 그래서 AI 분해의 실제 오류 양상·빈도는 알 수 없다.
- 추가 질문의 효과 근거(Qulac, GOV.UK, mixed-initiative HCI)는 다른 맥락에서 빌려 왔다. 실제 사람에게는 한 번도 묻지 않았다(`asked_to_user=false`).
- 사람이 사람에게 추천을 구하는 실제 기록(Software Recommendations Stack Exchange, Ask HN 등)이나, 구조화 질문을 실제로 운영하는 분야(도서관 참고 면담, 임상 PICO)는 보지 않았다.
