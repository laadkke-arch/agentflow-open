# 봉인 평가 사례 EVAL-X1 · 저장 목록을 외부 서비스에 맡기되 서비스가 사라져도 남게 하기

이 파일은 최종 설계서의 끝에서 끝까지 추적할 **기존 설계 예제 밖의 요청**을 새 구상을 읽기 전에 고정한 것이다. 정답을 적지 않았다. 대신 각 시점에 좋은 답이 반드시 포함하거나 피해야 할 것, 사실이 바뀌는 순서, 그 사실의 원자료 위치를 고정했다. 기계 판독용 사본은 [sealed-case.json](sealed-case.json)이다.

## 왜 이 사례인가

- 기존 설계 예제(K02 스캔 수집, pdfTeX 줄바꿈, 베이루트 시간대, roundtrip 고정 자료)와 겹치지 않는다. `work/design-gallim` 고정판 `fc68f0d1`의 `docs/workstreams/design/`에서 `pocket`, `bagit`, `oai-pmh`, `나중에 읽기`, `read-later`를 검색한 결과는 0건이다.
- 두 장면을 모두 시험한다. 장면 1은 이미 있는 서비스로 기능 하나를 생략할 수 있는가이고, 장면 2는 다른 분야(학술 기록 수확, 디지털 보존 포장)의 실패 복구 방식이 지금 설계를 바꾸는가이다.
- 사실이 실제로 여러 번 바뀐다. 같은 도움말 URL이 계속 200을 돌려주는 동안 저장 종료, 내보내기 기한 두 번 연장, 내보내기·API 중단이 차례로 일어났다. 이 순서는 저장소의 AF-RES-152 원장에 있다.
- **자료집에 검증된 정답이 없다.** 저장소에는 2025-05-22 이전 Pocket의 내보내기·API 동작을 직접 판독한 원자료가 없고, 대체 서비스를 판독한 연구도 없다. 제품이 정답 없음을 어떻게 처리하고 다음 행동을 무엇으로 제시하는지 볼 수 있다.

## 사용자가 건네는 요청 (T0 = 2025-05-15 00:00 UTC)

> **프로젝트 전체(짧게).** 개인 지식관리 웹앱. 구성은 웹 클리퍼(브라우저 확장) → 저장 목록(링크·제목·태그·저장일) → 전문 검색 → 공유 페이지다.
>
> **선택한 부분.** 저장 목록 계층. 클리퍼가 보낸 링크를 받아 보관하고, 변경분을 검색 계층에 넘긴다.
>
> **목적.** 저장 목록을 우리가 직접 만들고 운영하지 않고 이미 있는 서비스나 부품으로 대신하고 싶다.
>
> **지켜야 할 것.**
> - R1. 사용자가 저장한 링크·태그·저장일을 언제든 공개 형식으로 내보낼 수 있어야 한다.
> - R2. 외부 서비스가 종료를 발표해도 사용자 목록 전체의 사본이 우리 쪽에 남아, 종료 후 30일 동안 사용자가 조회할 수 있어야 한다.
> - R3. 클리퍼 → 저장 → 검색 순서는 유지한다. 검색 계층은 저장 계층의 추가·삭제를 받아야 한다.
>
> **선호.** 무료 또는 소규모 비용, 읽기 API 제공.
>
> **범위 밖.** 클리퍼 화면, 전문 검색 엔진 선택, 읽기 화면.
>
> **모르는 것.** 사용자 수, 기존 데이터 양.

## 각 시점에 좋은 답이 지켜야 할 것

정답 후보가 아니라 **판정 기준**이다. 어긴 경우의 이름을 함께 고정한다.

### T0 · 요청 직후 (2025-05-15)

- **T0-a 오승인 금지.** Pocket이든 다른 서비스든 R1·R2를 `지지`나 `검증됨`으로 돌려주려면 고정판 원문 위치가 있어야 한다. 저장소에는 그 위치가 없다. 따라서 직접 쓸 도구 후보는 `확인할 후보`여야 하고, 먼저 열 원문(해당 서비스의 내보내기 도움말·API 문서)과 확인할 한 가지를 함께 내야 한다. 이름의 인지도만으로 순위를 매기면 실패다.
- **T0-b R2의 소유자 판별.** R2는 외부 서비스 하나의 기능으로 충족되기 어렵고 우리 쪽 구조(지속 사본)의 성질이다. 좋은 답은 이 점을 짚고, 기존 서비스 후보와 별도로 `시험해 볼 원리`를 낸다. 예를 들어 증분 수확과 삭제 추적, 또는 고정성 검사가 붙은 포장이다. 이때 빌려오는 것과 대상에서 다시 확인할 것(호출 한도, 삭제 신호 유무, 이어읽기 토큰 만료)을 나눠야 한다. "종료 공지가 나오면 그때 일괄 내보내기"만 권하면 E3–E5의 기한 변경에서 R2가 깨지는 설계를 권한 것이다.
- **T0-c 해석의 갈림.** R1의 "언제든 내보낼 수 있다"는 (가) 사용자가 서비스 화면에서 직접 내보내기, (나) 우리 앱이 읽기 API로 가져오기의 두 뜻이 된다. (가)면 서비스의 내보내기 기능이 근거이고, (나)면 API 읽기 권한·호출 한도·증분 조회가 근거다. 답이 어느 해석을 골랐는지 밝히거나 한 번만 되물어야 한다.

### T1 · 저장 종료 직후 (2025-07-09)

- **T1-a 이유의 유효성.** URL이 200이어도 R3(저장 계층이 클리퍼 입력을 받음)를 충족하던 이유가 사라졌다. T0에 Pocket을 후보로 냈다면 지금은 그 이유가 무효라고 표시해야 한다. 200을 유효로 읽으면 낡은 추천이다.
- **T1-b 과거 답 재생.** T0 답은 당시 입력·근거·판정 그대로 다시 열려야 하고, 지금의 판정이 그 기록을 덮어쓰면 안 된다.

### E3·E4 · 기한 변경 (2025-10-08, 10-09)

- **E-a 같은 대상의 판 변경.** 같은 URL의 기한 변경을 새 항목으로 세지 않고 해당 이유의 기한만 갱신한다. 각 판의 기한을 따로 보존해 "10월 9일에 우리가 알던 기한"을 되물을 수 있어야 한다.

### T2 · 내보내기·API 중단 뒤 (2025-11-13)

- **T2-a 정답 없음 처리.** Pocket은 R1·R2 모두 반증이다. 자료집에 검증된 대체 서비스가 없으므로 지어낸 대안 대신 "검증된 대체 서비스 없음"과 다음 행동(내보내기 보증과 읽기 API를 기준으로 후보 탐색, 첫 확인 항목)을 내야 한다.
- **T2-b 원리의 생존.** T0에 낸 원리 후보(지속 사본, 증분 수확, 고정성 포장)는 Pocket이 사라져도 판정이 바뀌지 않아야 한다. 도구 하나의 철회가 그 도구와 무관한 원리까지 철회하면 실패다.

### T3 · 몇 달 뒤 다른 질문 (2026-03-01)

다른 사용자가 이름도 분야도 다른 요청을 한다.

> 연구실 위키의 "참고문헌 북마크" 부분을 외부 서비스에 맡기고 싶다. 서비스가 문을 닫아도 북마크가 우리 서버에 남아야 한다. 화면은 범위 밖.

- **T3-a 재발견.** EVAL-X1에서 찾은 원리 후보가 "Pocket"이라는 이름이 아니라 요청의 관계("외부가 사라져도 우리 쪽 사본이 남는다")로 다시 후보에 올라야 한다.
- **T3-b 판단 불승계.** EVAL-X1의 Pocket 판정과 사용자 맥락은 새 프로젝트로 넘어가지 않는다. 공개 원자료의 관측(어느 날 무엇이 닫혔나)만 재사용할 수 있다.

## 기록할 관측

- 오승인 수: 고정판 원문 위치 없이 R1·R2를 지지로 낸 횟수.
- 낡은 추천 시간: E2·E5 이후 해당 이유를 무효로 표시하기까지의 시간.
- 과거 답 재생 성공: T0 답을 T2에 당시 근거와 함께 연 횟수와 실패.
- 정답 없음의 처리: T2에서 지어낸 대안 수와 제시한 다음 행동.
- 원리 생존·재발견: T2에서 원리 후보 판정 유지 여부, T3에서 관계로 다시 오른 순위와 경로.
- 비용: 열람한 원문 수, 외부 요청 수, 바이트, 판독 시간.

## 봉인 당시 평가자의 노출

- 이 스레드는 봉인 전에 `work/design-gallim` 고정판 문서·코드와 AF-RES-012·147·150·152·257·258의 결과·인계, AF-RES-152 원장의 Pocket 행, AF-RES-263 원장의 BagIt 행을 읽었다.
- 다른 스레드의 새 설계 구상은 읽지 않았다.
- Pocket 이전 시점의 실제 내보내기·API 동작과 대체 서비스는 조사하지 않았다. 봉인 뒤에도 이 정보를 기준에 소급해 넣지 않는다.
