# 안 A · 수장고형: 처음 본 날 작동을 적어 두는 제품

상태: 구상안(2026-11-26 KST). 코드와 실행은 없다. 수치는 모두 아래 고정 커밋의 연구 결과에서 읽었고, 이 문서에서 새로 세운 가정은 **[가정]**으로 표시했다. 전체 비교와 공통 사례는 [README](README.md)에 있다.

## 0. 한 문장과 출발 전제

**언어·호스팅·분야가 제각각인 작은 자료를 처음 본 날, 원어 원문을 읽을 수 있을 때 "무엇을 받아 무엇을 내며, 무엇이 없는 누구에게 쓰이고, 무엇을 지키고, 어디서 깨지는가"를 언어 중립 칸으로 적어 두고, 몇 달 뒤 이름도 분야도 다른 요청이 오면 그 칸끼리 맞춰 다시 찾는 제품이다.**

이 안은 장기 운영에서 출발한다. 출발 전제는 세 가지다.

1. **요청 순간의 어휘로는 작은 외국어 자료에 닿지 않는다.** 한국어 질의는 주소에 목적·작동 설명을 한 줄씩 붙여도 Toyota·Bazel·TreeDB 세 원리 사례를 끝내 0점으로 남겼다. 영어 주소만으로 Toyota가 4위에 든 것은 공통어 `and` 하나 때문이었다. [링크 실험][link] 한국어 별칭을 붙인 검색도 공개 질문에서 별칭 적중 0이었고([126][r32]), 유일하게 적중한 별칭 ‘가중치를’은 질문과 다른 대상을 가리켰다([138][r35]). 이름을 번역하거나 별칭을 늘리는 일로는 부족하다.
2. **쓸모는 원문 속 한 줄에 있고, 그 한 줄은 처음 읽을 때 가장 싸다.** ii-svn-log의 제작자 글에서 쓸모 있는 문장은 "SVN이 없는 PC에서도 열람·공유"라는 한 줄이다. [149 원장 S-A-W1-1][s149] 주소와 제목(“ii-svn-log v1.00”)만 남기면 그 한 줄은 사라진다.
3. **같은 대상이라는 판단은 질문마다 다르다.** 주소 단위로 나누면 실제 같은 대상 6쌍을 갈랐고, 공통 작품으로 묶으면 다른 판 6/16쌍을 합쳤다. 방향과 범위를 함께 쓴 방식만 15/16쌍을 맞혔다. [150 인계][h150] URL의 마지막 값을 다른 요청에 재사용하자 밀집 현재 답 96건 중 40건을 잘못 승인했다. [147 인계][h147] 그래서 이 안은 같음을 하나의 병합으로 확정하지 않는다.

이 안이 가장 잘 맞는 세계는 "작고 드문 자료가 나중에 다른 이름으로 필요해지는 세계"다. 그런 일이 실제로 얼마나 자주 일어나는지는 아직 측정되지 않았다. **[가정]** AF-RES-149는 중앙 BLOCKED이므로 입구별 발견 효과의 근거로 쓰지 않고, ii-svn-log가 어디서 왔는지의 원장으로만 쓴다.

**가장 큰 약점.** 한 번도 요청되지 않을 자료에 입수·판독 노동을 미리 쓴다. 카드를 쓰는 사람이 칸을 잘못 채우면(예: "SVN 로그를 Excel로"처럼 이름 수준으로만 적으면) 나중에 아무도 다시 찾지 못하는데, 이 실패는 몇 달 뒤에야 드러난다.

## 3. 입수

### 3.1 입구

입구는 "누가 무엇을 언제 목록에 올렸는가"를 공급하는 곳이다. 종류별로 걸러지는 자료가 다르다는 것은 이 안의 설계 가정이다. **[가정]**

| 입구 종류 | 예시 | 걸러지는 자료 |
| --- | --- | --- |
| 지역 언어 다이제스트 | 일본어 소프트웨어 소식 사이트의 주간 다이제스트 | 편집자가 고르지 않은 자료, 시험 가능한 공개판이 없는 자료 |
| 배포 저장소의 신규 목록 | 자유 소프트웨어 앱 배포처의 새 앱 목록 | 빌드 검증·라이선스 관문을 넘지 못한 자료 |
| 전문 분야 주간지 | 특정 언어 생태계의 도구 소식 | 다른 분야의 자료 |
| 저자 자천 게시판 | 직접 만든 작품을 올리는 게시판 | 점수 관문을 넘지 못한 자료 |
| 소비자 쪽 호환성 이슈 | 플러그인·통합 측의 실패 보고에서 거꾸로 원작자 원문으로 | 소비자가 없는 자료 |
| 원리 입구 | 운영·제어·보존 분야의 공개 편람, 표준 목록 | 소프트웨어 이름을 쓰지 않는 원리 |
| 요청의 부산물 | 요청 때 실시간 탐색이 새로 읽은 원문 | 아무도 묻지 않은 자료 |

입구마다 언어, 지역, 신호 방식(목록·피드·메일), 겹쳐 읽기 폭, 마지막 성공 시각을 기록한다. 같은 자료가 여러 입구로 들어오면 각각을 입구 수확으로 남긴다. 어느 입구가 먼저 찾았는지는 나중에 몫을 나눌 때 쓴다.

### 3.2 입수 심사: 받을지, 무엇과 다른지

받는 조건은 세 가지다. ① 공개 원문이 있다. ② 원문에 작동 문장이 있다(무엇을 받아 무엇을 내는지 한 문장 이상). ③ 판을 가리킬 표지가 있다(버전, 커밋, 게시 리비전, 게시 시각 중 하나). 받지 않은 후보도 "입수 판정"으로 남긴다. 입구 수율을 셀 때 분모가 되기 때문이다.

작은 자료가 유일한 기능을 갖는 경우와 실제로 중복·열세인 경우는 **칸 단위로** 가른다.

- 기존 카드와 일곱 칸 중 하나라도 다르면 새 카드다. ii-svn-log는 "이력을 표 파일로 내보낸다"는 점에서 흔한 내보내기 도구와 같지만, "쓰는 쪽과 그쪽에 없는 것" 칸이 "원래 도구가 설치되지 않은 PC의 사람"이라는 점에서 다르다. 이 한 칸이 작은 자료의 유일한 기능이다.
- 일곱 칸이 모두 같고 조건만 좁으면 열세로 본다. 수장은 하되 "대표" 쪽지를 받지 못해 현재 추천에서 뒤로 간다. 열세라는 판단도 쪽지이므로 나중에 뒤집을 수 있다.
- 같은 원문이 다른 입구로 다시 들어오면 새 수장 기록을 만들지 않고 입구 수확만 더한다(키는 6절).

### 3.3 수장 기록: 표본처럼 다루는 관측

수장 기록은 "이 시각에 이 위치에서 이 판의 이 절을 이렇게 보았다"는 관측이다. 한 번 쓰면 고치지 않는다. 필드는 원문 위치(발견한 그대로와 정규형), 발견 입구, 발견 시각, 원문 언어, 호스팅 종류(개인 블로그·코드 호스팅·배포 사이트·기관), 판 표지, 절 위치, 절 지문, 짧은 발췌다. 발췌는 인용 허용 범위 안에서만 남긴다. 원문 전체 사본은 감사 요구가 있을 때만 별도로 둔다. 표시 문장과 주체·기준일은 짧은 발췌로도 4/4 복원됐지만, 원바이트를 입증하려면 사본이 필요했다. [196][r45]

### 3.4 작동 카드: 일곱 칸과 증거 층

카드는 수장 기록 하나를 근거로 쓴다. 칸은 요청을 나눌 때도 똑같이 쓴다. 칸이 같아야 몇 달 뒤 이름 없이 맞출 수 있다.

| 칸 | 뜻 | ii-svn-log 카드의 값 |
| --- | --- | --- |
| 받는 것 | 무엇을 입력으로 받나 | 버전관리 저장소의 커밋 이력 |
| 내는 것 | 무엇을 산출하나 | 표 계산 파일 하나 |
| 쓰는 쪽과 그쪽에 없는 것 | 누가 쓰며 그쪽에 무엇이 없나 | 원래 버전관리 도구가 설치되지 않은 PC에서 보는 사람 |
| 다시 움직이는 근거 | 무엇이 다음 동작을 일으키나(완료, 시간, 외부 신호, 사람 조작, 이전 상태) | 사람이 화면에서 한 번 실행하거나 명령 한 번 |
| 지키는 것 | 무엇이 보존되거나 넘지 않아야 하나 | 이력을 받은 사람이 볼 수 있음 |
| 막는 실패 | 무엇이 일어나지 않게 하나 | 도구가 없는 사람이 이력을 못 봄 |
| 깨지는 조건 | 어떤 전제에서 성립하지 않나 | 표 파일은 받은 사람이 고칠 수 있어 넘긴 뒤 불변을 보장하지 않는다. 실행은 확인하지 않았다 |

카드에는 이 밖에 증거 층, 원리일 때의 공여 분야, 원어 별칭(이 예에서는 「SVNがないPCでも閲覧・共有」 같은 원문 표현)을 둔다. 카드 문장은 원어 원문을 읽고 쓰되, 칸 값은 작은 고정 어휘(대상 유형과 관계 동사)와 한국어·영어 표현을 함께 적는다. 이 어휘가 소프트웨어와 다른 분야 자료를 모두 서술할 수 있는지는 검증되지 않았다. **[가정]**

증거 층은 네 가지이고, 답에서 쓰는 동사를 정한다. 이 구분은 257의 판독에서 직접 나왔다. 공식 갤러리의 아홉 번째 예제는 소스에서 개별 예측값을 계산했지만 공개된 결과는 집계 정확도와 시간이었다. [257][r257]

| 증거 층 | 답의 동사 | 요구되는 근거 |
| --- | --- | --- |
| 제작자 진술 | "…한다고 소개한다" | 제작자 원문의 절 |
| 코드에서 확인 | "…하는 코드가 있어 방법을 배울 수 있다" | 해당 판의 소스 줄 |
| 공개 출력에서 확인 | "이 링크에서 …결과를 바로 볼 수 있다" | 게시된 출력(그림·표·문자열) |
| 실행해 확인 | "…판에서 실행하면 …한다" | 정확한 판·입력의 실행 영수증 |

역할(직접 쓸 도구·이식할 부품·시험해 볼 원리)은 카드에 저장하지 않는다. 같은 대상도 프로젝트에 따라 관계가 달라지기 때문이다. [제품 브리프][brief] 역할은 답을 쓸 때 요청과 카드의 관계에서 정한다(5.6절).

카드는 수장 기록마다 1~3장으로 제한한다. 원문이 여러 작동을 말하면 칸 값이 다른 작동만 따로 쓴다. 카드를 고칠 때는 새 판을 덧붙이고 이전 판을 지우지 않는다. 답은 카드의 특정 판을 가리킨다.

## 4. 같음 판단: 표본관의 동정 쪽지

### 4.1 빌려온 원리

식물표본관에서 표본은 채집자·날짜·장소 라벨과 함께 영구 번호를 갖는다. 분류학자가 표본을 다시 동정하면 이전 이름표를 지우지 않고, 새 이름·동정자·날짜를 적은 쪽지를 덧붙인다. 논문은 이름이 아니라 표본 번호를 인용한다. 그래서 나중에 이름이 바뀌거나 종이 나뉘어도 옛 논문이 실제로 무엇을 보았는지 다시 확인할 수 있다. **[가정: 이 운영 관행은 일반적인 표본관 실무에 대한 설계자의 이해이며, 저장소 연구가 직접 판독한 원문은 아니다.]**

이 안에서 수장 기록은 표본, 작동 카드는 표본의 기재문, 같음 판단은 동정 쪽지다. 쪽지는 "무엇과 무엇이, 어떤 목적에서, 어떤 결로 같거나 다르다"를 적는다.

| 쪽지 필드 | 값 |
| --- | --- |
| 대상 | 수장 기록 둘, 또는 수장 기록과 묶음(작품·기능) |
| 관계 | 같은 판, 같은 작품, 같은 기능, 후계, 분할, 거울, 다른 대상, 철회 |
| 목적 | 인용·감사, 방법 학습, 설치·내려받기, 현재 추천 |
| 결 | 작품, 판, 파일, 절 |
| 근거 | 수장 기록 id와 그 절 |
| 서명 | 작성 주체(사람·판독기), 시각, 대체하는 이전 쪽지 |

### 4.2 어느 질문에 "같다"를 재사용하나

| 질문의 목적 | 재사용할 수 있는 쪽지 | 이유와 근거 |
| --- | --- | --- |
| 그때 무엇을 근거로 말했나(인용·감사) | 쓰지 않는다. 답이 가리킨 수장 기록만 읽는다 | 과거 답 112/112는 당시 전달값과 근거판을 함께 남긴 방식에서만 재생됐다. [147][r147] |
| 이 방법을 배울 수 있나 | "같은 작품" 쪽지. 단 카드의 깨지는 조건에 판 민감 표시가 없을 때 | 작동이 판에 묶이지 않으면 거울·이동 주소를 묶어도 답이 같다 |
| 이 파일을 설치·내려받나 | "같은 판" 쪽지만 | 같은 계열이라도 판·인터프리터·플랫폼마다 실제 파일이 다르고 공석이 정상이다. [248·266][r266] |
| 지금 무엇을 권하나 | 목적이 "현재 추천"인 최신 쪽지. 후계·철회를 반영 | 기관 통합에서 후계 관계는 양방향 기재가 필수가 아니었고, 기본 검색은 활성 레코드만 돌려줬다. [259][r259] |

같은 목적·결에서 서로 다른 쪽지가 있으면 현재 추천은 두 쪽지를 함께 보여 주고 보류한다. 한쪽을 고르는 규칙은 근거 층이 높은 쪽, 그다음 최근 쪽이다.

### 4.3 도입하면 사라지는 일

- **전역 병합·분리와 그 되돌림.** 병합 취소 뒤 하류에 따로 복구가 필요했던 사례([161][r44])처럼, 행을 합치고 되돌리는 연산 자체가 없다. 잘못된 같음은 "다른 대상" 쪽지를 더해 고친다.
- **옛 인용 고치기.** 답은 수장 기록을 가리키므로, 이름이 바뀌어도 옛 답은 그대로 읽힌다.
- **"주소의 마지막 값" 재사용.** 수장 기록은 주소가 아니라 관측이므로, 같은 주소의 다른 절·다른 판 값을 끌어 쓰는 경로가 처음부터 없다. 147에서 오승인 40/96을 낸 경로다.

### 4.4 새로 생기는 실패

- **쪽지 증식.** 같은 대상에 상충하는 쪽지가 쌓이면 현재 추천이 자주 보류된다. 보류 비율을 분기 지표로 본다.
- **표본 부패.** 온라인 원문은 표본처럼 보관되지 않는다. 지문과 발췌가 없으면 과거 근거를 다시 확인할 수 없고, 발췌는 인용 허용 범위라 원바이트 입증까지는 못 한다.
- **동정자 신뢰도 차이.** 판독기 쪽지와 사람 쪽지가 섞인다. 서명에 주체 종류를 남기고, 현재 추천에서 근거 층이 같으면 사람 쪽지를 앞에 둔다. **[가정]**
- **조회 비용.** 답마다 목적을 해석해 쪽지를 골라야 한다.

**더 단순한 방식이 이기는 조건.** 대상 대부분이 안정된 고정판 절이고 같음 판단이 드물면 쪽지 없이 "원문 위치 + 판 표지 + 절" 키로 충분하다. 고정 절 네 개의 두 시점·네 조회 32/32가 주소 하나로 보존된 대조가 그 예다. [150][h150]

## 5. 요청 처리

### 5.1 받는 것

요청 창구는 목적 원문, 선택 부분(전체 또는 일부), 선택 부분의 이웃(누가 무엇을 주고 누가 소비하나), 사용 중인 판, 이미 쓰고 있거나 시도한 도구를 받는다. Studio에서 무엇을 자동으로 가져오고 무엇을 한 번 묻는지는 안 B와 같은 계약을 쓴다([안 B 3절](B-REQUEST.md#3-요청-순간-studio에서-가져올-것-한-번-물을-것-그대로-둘-것)). 이 안의 차이는 받은 정보를 탐색이 아니라 카드 대조에 먼저 쓴다는 점이다.

### 5.2 칸으로 나누고 해석이 둘일 때

요청 원문을 카드와 같은 일곱 칸으로 나눈다. 원문 표현은 그대로 보존하고, 칸 값은 원문의 어느 구간에서 왔는지 가리킨다. 해석이 둘로 갈려 서로 다른 카드를 고르면, 두 카드를 조건부로 함께 보여 준다. 값을 하나씩 정한 대조에서 조건부 답은 무응답을 가정한 네 경우 모두 다음 행동을 냈고, 질문 방식은 한 건을 보류했다. [074][r19]

### 5.3 카드와 맞추는 규칙

- 표시 조건: 요청 칸과 카드 칸이 **두 칸 이상** 맞고, 그중 하나는 관계 칸(다시 움직이는 근거, 지키는 것, 쓰는 쪽과 그쪽에 없는 것, 막는 실패)이어야 한다. 받는 것·내는 것만 맞는 카드는 "이름이 비슷함"으로만 다룬다.
- 반대 칸이 필수 조건과 정면으로 부딪히면 "함정"으로 표시한다. 함정은 검색 상위에 오기 쉬운 이름 유사 후보를 막는 데 쓴다.
- 답에는 맞은 칸의 짝(요청 칸 ↔ 카드 칸)을 그대로 적는다. 사용자가 분야 이름을 몰라도 이 짝을 읽고 원문으로 들어갈 수 있다.
- 우연 적중 점검: 평가 때 카드 칸을 가리고 주소·제목만으로 다시 순위를 매긴다. 가린 뒤에도 같은 순위로 남는 후보는 어휘 우연으로 표시하고 원리 성적에서 뺀다. Toyota가 `and` 하나로 4위에 든 사례가 이 점검의 기준이다. [링크 실험][link]

### 5.4 제한된 실시간 탐색과 부산물 수장

카드만으로는 주류 자료의 최신 상태를 놓칠 수 있다. 요청마다 질의 6개, 원문 열람 6개 안에서 요청 어휘와 칸 표현으로 실시간 탐색을 한다. **[가정: 예산 수치]** 실시간 탐색이 새로 읽은 공개 원문은 수장 기록과 카드로 수장고에 들어간다. 이때 실시간 탐색이 찾은 항목 중 "그 전에 이미 공개돼 있었는데 수장되지 않았던 것"은 수장 누락으로 센다(8절).

### 5.5 근거 재확인

답에 쓸 카드마다 근거 수장 기록의 현재 상태를 본다. 사용자의 판과 수장 판이 같고 현재 절 지문이 같으면 다시 읽지 않는다. 판이 다르면 사용자 판의 해당 절을 읽어 새 수장 기록을 만든다. 공개 문서에 보이는 기능도 문서 빌드가 모든 선택 기능을 켜고 만든 것이면 기본 설치 사용자에게는 없을 수 있다. 이 경우 카드의 깨지는 조건에 "문서 빌드 조건"을 적고 답에 드러낸다. [261][r261]

### 5.6 답의 형식

답의 첫 줄은 해석이다. 그 아래 항목마다 다음을 쓴다.

| 필드 | 내용 |
| --- | --- |
| 종류 | 직접 쓸 도구(사용자의 실행 환경에서 그대로 쓸 수 있고 필수 칸을 충족), 이식할 부품(다른 환경의 구현·형식을 옮겨야 함), 시험해 볼 원리(다른 분야의 관계만 옮김), 함정(이름은 비슷하나 필수 칸을 어김) |

### 6.1 대표 조회와 쓰기: R2

2027-03 요청 "AI 작업 기록을 도구를 설치하지 않은 외부 감리자에게, 인터넷이 막힌 PC에서, 넘긴 뒤 바뀌지 않게"가 들어오면 다음 순서로 읽고 쓴다.

1. 요청과 해석을 쓴다. 칸 값: 받는 것 "작업 기록", 내는 것 "홀로 열리는 파일", 쓰는 쪽 "원래 도구가 없고 인터넷이 막힌 PC의 사람", 지키는 것 "넘긴 뒤 내용 불변", 막는 실패 "감리자가 못 열거나 넘긴 기록이 나중에 달라짐".
2. 색인에서 칸별 후보 카드를 읽는다. ii-svn-log 카드는 "쓰는 쪽"과 "내는 것"이 맞고 "지키는 것"에서 카드의 깨지는 조건과 부딪힌다. 결과는 부분 대응이다.
3. 카드의 근거 수장 기록과 그 사건을 읽는다. 원문 접근 상태가 정상이고 판이 v1.00 그대로면 지문만 대조한다.
4. "지키는 것" 칸을 맡을 카드가 없으면 그 칸으로 실시간 탐색을 한다. 새로 읽은 원문은 수장 기록·카드로 쓴다.
5. 답과 답 항목을 쓴다. 답 항목은 ii-svn-log 카드의 판, 수장 id, 맞은 칸 두 짝, 전달 문장을 가진다.
6. 수요 합계에 카드별로 1을 더한다(프로젝트 연결 없음).

### 6.2 동시 입수·재시도·오병합을 같은 사례에서 복구하기

- **동시 입수.** 같은 날 일본어 다이제스트 입구와 내려받기 사이트의 신규 목록 입구가 ii-svn-log를 동시에 가져왔다고 하자. 두 입수대가 같은 유일 키(원문 위치 정규형, 판 표지, 절 위치, 절 지문)로 수장 기록을 쓰려 하면 하나만 생기고, 다른 하나는 입수 판정에 같은 수장 id를 기록한다. 제작자 글과 내려받기 페이지는 원문 위치가 다르므로 수장 기록이 둘 생기고, 둘을 잇는 것은 "같은 판, 목적=설치" 쪽지 하나다.
- **재시도.** 카드 작성 중 판독기가 중단되면 카드 판이 생기지 않았거나 완성된 판이 하나 있다. 같은 수장 id에 같은 칸 값의 카드 판을 다시 쓰려 하면 같은 판으로 인정한다.
- **오병합.** 나중에 내려받기 페이지가 v1.01로 바뀌었는데 판독기가 "같은 판, 목적=설치" 쪽지를 그대로 이어 붙였다고 하자. 설치 목적의 답이 v1.00 파일을 가리키게 된다. 복구는 "다른 판, 목적=설치" 쪽지를 근거 수장 기록과 함께 더하는 것이다. 잘못된 쪽지를 쓴 답 항목은 "사용 쪽지"로 찾아 목적이 설치인 것만 재검토에 올린다. 방법 학습 목적의 답은 영향이 없다. 지우는 기록은 없다.

## 7. 이름·주소·판·내용·가용성이 따로 변할 때

| 사건 | 기록 | 과거 인용은 이렇게 읽는다 | 현재 추천은 이렇게 읽는다 |
| --- | --- | --- | --- |
| 이름 변경 | 카드에 원어 별칭 추가. 수장 기록은 그대로 | 당시 이름 그대로 | 새 이름과 옛 이름을 함께 표시 |
| 주소 이동 | 새 위치를 관측한 새 수장 기록, 지문이 같으면 "같은 판" 쪽지 | 옛 주소와 발췌 | 새 주소 |
| 새 판 | 새 수장 기록, 작동이 달라지면 새 카드, "후계 판" 쪽지 | 옛 판의 카드 | 사용자 판에 맞는 카드 |
| 같은 판 표지에서 내용 변경 | 사건과 재판독 작업. 카드의 깨지는 조건 재확인 | 옛 지문과 발췌 | 재판독 전까지 "확인 중"으로 표시 |
| 일시 실패 | 사건. 24시간 뒤 재확인 대기 | 영향 없음 | 마지막 확인 근거로 답하되 실패를 표시 |
| 영구 부재 | 사건. 후계 탐색 작업 | 발췌로 읽힘 | "원문 없음, 마지막 확인일" 표시. 후계 쪽지가 생기면 그쪽 |
| 철회(제작자·배포처) | 사건과 "철회, 목적=현재 추천" 쪽지 | 영향 없음 | 추천에서 제외 |
| 병합·분리·복구 | 모두 쪽지로 | 영향 없음 | 목적별 최신 쪽지 |

일시 실패와 영구 부재, 레코드 철회는 다른 상태다. 기본 검색에 안 보이는 것을 곧 종료나 철회로 판정하지 않는다. [259][r259] 공급자가 같은 문서의 기한을 두 번 바꾼 사례에서는 이전 판과 이유를 보관해야 당시 판단을 복원할 수 있었다. [152][r152]

## 8. 예산과 손실 감지

새 자료 발견, 기존 근거의 신선도, 요청 대기시간이 같은 예산을 두고 경쟁한다. 152의 재생은 정책마다 이기는 조건이 달랐다. 신호 수확과 후속 확인(S)·희소 공급원 보장(F)은 유보 기간 신규 15건 중 14건, 정기 확인(P)은 13건, 요청 때만 확인(O)은 10~14건을 찾았다. 높은 예산의 주류 수요에서는 P의 발견 지연 중앙값이 27시간, S가 57시간이었고, 낮은 예산의 희소 수요에서는 같은 13건이 P 92.1시간, S 27시간이었다. F의 고정 슬롯이 S보다 낫다는 관측은 없었고, 높은 예산의 안정 질의 159건은 모두 일치해 인기 안정 자료를 미리 다시 읽을 근거도 없었다. [152 결과][r152] · [정책 정의][p152]

이 안의 배분은 다음과 같다.

- **요청 몫**은 다른 몫에 밀리지 않는다. 대기시간은 제품의 약속이다.
- **입수 몫**은 입구마다 신호 수확과 겹쳐 읽기를 기본으로 한다(152의 S). 희소 입구에 고정 슬롯을 주지 않고, 분기마다 "나중에 답에 쓰인 카드 수 / 읽은 항목 수"로 몫을 다시 나눈다. 새 입구 탐색 몫은 고정한다. **[가정]**
- **신선도 몫**은 변경 신호, 활성 답(최근 90일 열람)이 인용한 수장 기록, 무작위 표본 순으로 쓴다. **[가정: 90일]** 수요만으로 우선하지 않는다.

자료가 커지거나 열람 예산이 줄면 늦추는 순서는 ① 수요 없는 카드의 재확인, ② 수율 낮은 입구의 수확 주기, ③ 카드의 둘째·셋째 장 작성이다. 요청 응답과 활성 답의 철회 신호 처리는 늦추지 않는다.

손실은 다음 관측으로 알아챈다.

| 손실 | 관측 |
| --- | --- |
| 발견이 늦어짐 | 입구별 "제작자 게시 시각 → 수장 시각" 분포 |
| 수장 누락 | 실시간 탐색이 찾은 항목 중 이미 공개돼 있었으나 수장되지 않은 수(입구 종류별) |
| 낡은 추천 | 무작위 재확인에서 카드의 칸이 더는 성립하지 않는 비율 |
| 쓸모없는 수장 | 수장 뒤 12개월 동안 한 번도 일치하지 않은 카드 비율 |
| 미룬 일 | 몫 부족으로 대기 중인 재확인·카드 작성 수와 가장 오래된 대기 시각 |

## 10. 이 안이 틀렸다고 판정할 관측

다음이 함께 관측되면 이 안은 안 B나 기준선에 진다.

1. 6개월 동안 수장한 카드 중 답에 쓰인 비율이 아주 낮다(기준은 평가 스레드가 정한다).
2. 답에 쓰인 카드 대부분을 같은 예산의 실시간 탐색도 찾았다.
3. 사람이 카드의 칸 대응을 판독했을 때 "대응 없음"이 많다(카드 품질 실패).
4. 수장 판독 노동이 요청 처리 노동보다 크고, 그만큼 사용자의 결정이 달라지지 않았다.

249의 사람 대상 평가안은 24분 안의 노출과 코드 변화를 본다. [249 프로토콜][p249] 몇 달 뒤 재발견은 그 창에 들어오지 않으므로, 이 안은 "그림자 수장 + 나중 요청 재생"으로 따로 평가해야 한다. 267의 합성 채점기 실행은 채점기가 설계한 차이를 잡는지까지만 확인했다. [267][r267]

## 11. 첫 구현 단위

1. 입구 세 개로 시작한다: 지역 언어 다이제스트 하나, 배포 저장소 신규 목록 하나, 영어 전문 분야 주간지 하나.
2. 입수 심사·수장 기록·작동 카드(일곱 칸, 증거 층)·동정 쪽지를 구현한다. 수요 합계는 만들지 않는다.
3. 8주 동안 그림자로 운영한다. 같은 기간의 요청은 안 B 방식(또는 기준선)으로 답하고, 이 안의 카드 대조 결과를 따로 기록한다.
4. 공통 요청 R1·R2를 재생하고, "수장고에서만 나온 후보"를 사람이 판독한다.
5. 8절의 손실 지표 다섯 개를 첫 분기부터 계산한다.
