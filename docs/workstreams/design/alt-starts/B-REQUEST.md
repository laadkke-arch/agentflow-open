# 안 B · 현장형: 가리킨 순간의 맥락으로 그 자리에서 찾고, 사례를 기억하는 제품

상태: 구상안(2026-11-26 KST). 코드와 실행은 없다. 수치는 모두 아래 고정 커밋의 연구 결과에서 읽었고, 이 문서에서 새로 세운 가정은 **[가정]**으로 표시했다. 전체 비교와 공통 사례는 [README](README.md)에 있다.

## 0. 한 문장과 출발 전제

**설계자가 Studio에서 한 부분을 가리킨 순간, Studio가 이미 아는 주변 맥락을 함께 받아 가장 그럴듯한 해석으로 바로 찾고 읽고 답하되, 답 첫 줄에 해석을 복창하고, 읽은 원문과 판정을 "사례"로 남겨 같은 칸의 다음 요청에서 다시 쓰는 제품이다.**

이 안은 설계자의 실제 요청에서 출발한다. 출발 전제는 세 가지다.

1. **첫 원문을 가르는 정보는 요청 순간에 가장 많다.** 공유 정의가 만든 그림 하나를 고치는 편집은 발생 위치를 알 때 6/6, 공유 정의만 알 때 0/6이었다. 같은 UI 문구에서 소비자 역할을 알면 48/48 자리를 갈랐다. [누적 판단][r44] 파일 되돌리기 요청에서는 같은 명령 이름 아래에서 무엇을 보존할지(마지막 커밋·스테이징·작업 트리)가 첫 절을 바꿨다. [256][r256] 이 값들 상당수는 Studio가 이미 알고 있다.
2. **미리 모은 자료 대부분은 다시 쓰이지 않는다.** **[가정]** 주류 질문은 일반 검색으로도 원문에 닿는다. 다만 일반 검색은 요청자 자신의 원이슈를 1위로 돌려주는 일이 8요청 중 5회였고, 자기 이슈를 뺀 외부 첫 해법은 개선 0·동률 4쌍이었다. [220][r48] 이 안의 가치는 일반 검색이 하지 않는 일, 즉 해석·분야 추정·판정·사례 재사용에 있다.
3. **원문을 한 번 읽는 비용은 크고 같은 칸의 문제는 반복된다.** 고정판 절과 셀을 한 번 읽어 두면 같은 판의 다음 요청에서 원문을 다시 열지 않고 답했다(147의 B·C안, 최초 취득 96 대 32). [147][r147] 그래서 영구 기억의 단위는 자료가 아니라 "요청의 칸 패턴과 그때 읽은 절, 판정, 뒤집힐 조건"이다.

**가장 큰 약점.** 아무도 요청하지 않은 작은 외국어 자료는 기억에 없고, 요청 순간의 어휘와 이름이 겹치지 않으면 실시간 탐색도 닿지 않는다. 공통 요청 R2에서 이 안은 ii-svn-log를 다시 찾지 못할 가능성이 높다([README 2절](README.md#2-같은-요청에서-세-질문의-답)).

## 3. 요청 순간: Studio에서 가져올 것, 한 번 물을 것, 그대로 둘 것

### 3.1 Studio에서 자동으로 받는 것

| 받을 정보 | 왜 필요한가 | 근거 |
| --- | --- | --- |
| 선택한 객체의 종류·ID, 공유 정의인지 한 번의 발생인지 | 편집 대상이 하나인지 전부인지가 첫 원문을 가른다 | 107의 6/6 대 0/6 [r44] |
| 이웃의 입출력: 누가 무엇을 주고 누가 소비하나 | 소비자 역할이 기능을 가른다 | 159의 48/48 [r44] |
| 사용 중인 판(잠금 파일, 실행 환경) | 판에 따라 기능의 유무·이름·파일이 다르다 | 256(Git 2.23 이전에는 restore 없음), 266(판·환경별 파일) [r256] · [r266] |
| 선택 기능을 켰는지(빌드 설정) | 공개 문서에는 모든 선택 기능을 켠 빌드가 보인다 | 261 [r261] |
| 이미 쓰거나 시도한 도구 | 이미 아는 대안을 새 발견으로 세지 않기 위해 | 141에서 작성자는 링크 전에 이미 외부 스텁을 알았다 [r38] |
| 목적 원문(한 문장 이상) | 해석의 근거. 칸 값은 원문 구간을 가리킨다 | 원뜻 보존 |

전체 프로젝트를 받지 않는다. 선택 부분과 이웃 한 겹이 기본이다. 이웃을 더 넓힐지는 판독 중에 "뒤집힐 조건"이 이웃 밖을 가리킬 때만 정한다.

### 3.2 한 번 묻는 조건

아래 세 조건을 **모두** 만족할 때만 질문하고, 질문은 요청당 한 번이다.

1. 해석이 둘 이상이고 해석마다 첫 원문이 다르다. 두 해석의 첫 절이 같으면 묻지 않는다. 옵션을 바꿔도 같은 결과가 나온 대조가 있었다. [074][r19]
2. 그 값을 Studio가 줄 수 없다.
3. 복창으로 감당할 수 없다. 해석이 셋 이상이거나, 잘못 읽은 해석을 따르면 되돌리기 어려운 손실이 생기는 경우다. 예를 들어 작업 트리만 되돌리려는 사람에게 스테이징까지 덮어쓰는 명령을 주면 원래 내용을 잃는다. [256][r256]

나머지 경우는 묻지 않고 복창한다(4절). 실제 되묻기에 대한 응답을 관측한 분모가 0/4(243), 0/4(230)라서 질문의 편익은 수치로 말할 수 없다. [누적 판단][r49]

| 요청 | Studio에서 더 받아올 정보 | 한 번 물을 정보 | 그대로 진행해도 되는 누락 |
| --- | --- | --- | --- |
| R1 작업 투입 제어(대기 8, 처리 중 4) | 실행 환경 판(3.13), 작업자를 고정 개수로 만드는지 항목마다 만드는지(코드), 변환→저장 이웃 | 없음. 원문이 세 조건을 명시했다 | 처리량 목표, 전체 메모리 상한(원문이 범위 밖으로 둠) |
| R2 외부 감리자에게 작업 기록 넘기기 | 현재 내보내기 산출 형식, 기록 구조, 이미 쓰는 도구 | 감리자가 사람 눈으로 보는가, 감리 프로그램이 기계로 읽는가. Studio가 알 수 없고 첫 원문이 갈리지만 복창으로 감당되므로 묻지 않고 복창한다 | 파일 형식 선호(첫 원문을 바꾸지 않음) |
| 파일 변경을 되돌리기 | 해당 경로가 추적 중인지, 스테이징 상태, Git 판 | 무엇을 보존할지(스테이징을 남길지). 잘못 읽으면 내용 손실이라 **묻는다** | 명령 이름 선호 |
| 공유 정의에서 그린 그림 하나만 고치기 | 선택한 것이 정의인지 발생인지 | 없음(Studio가 안다) | 색 이름 |
| 여러 오디오 파일로 내보내기 | 라벨 트랙 위치, 음소거 상태, 프로그램 판 | 파일 경계를 무엇으로 정할지가 Studio 밖이면 복창 | 파일 이름 규칙 |

## 4. 낯선 분야 운영 원리: 관제의 복창

### 4.1 빌려온 원리

항공 관제에서는 관제사가 지시하면 조종사가 핵심 값을 복창하고, 관제사는 복창을 듣고 틀린 곳을 바로 고친다. 확인을 위해 비행을 멈추지 않으며, 오해를 그것이 행동으로 바뀌기 전에 싸게 잡는다. **[가정: 이 운영 관행은 설계자의 일반 지식이며, 저장소 연구가 직접 판독한 원문은 아니다.]**

### 4.2 이 안에 들인 방식

해석이 둘이면 이 안은 질문으로 멈추지 않는다. 가장 그럴듯한 해석으로 끝까지 답하되, 답 첫 줄에 해석을 복창하고, 다른 해석에서 열어야 할 첫 원문 하나를 함께 둔다.

> 해석: "넘긴 뒤 바뀌면 안 된다"를 감리자가 받은 뒤 변경 여부를 확인할 수 있으면 된다는 뜻으로 읽었습니다. 변경 자체를 막아야 한다면 3번 대신 [그 해석의 첫 원문]부터 보세요.

사용자가 복창을 고치면 정정 사건을 남기고 그 해석으로 다시 답한다. 사례에는 정정 전후가 모두 남는다.

### 4.3 사라지는 일

- 막히는 되묻기 왕복과 그동안의 대기. 사람은 몇 시간씩 자리를 비우므로 질문 하나가 답 전체를 몇 시간 늦춘다.
- 질문을 할지 말지 정하는 판단 대부분. 3.2절의 세 조건을 모두 만족하는 경우만 남는다.
- 무응답을 처리하는 별도 경로. 조건부 답은 무응답 네 경우 모두 다음 행동을 냈다. [074][r19]

### 4.4 새로 생기는 실패

- **복창을 읽지 않음.** 사용자가 첫 줄을 건너뛰고 잘못된 해석의 답을 채택할 수 있다. 정정이 없다고 해석이 확인된 것은 아니므로, 사례에는 "정정 없음"과 "사용자가 해석을 확인함"을 다른 값으로 남긴다.
- **답이 길어진다.** 복창과 대안 첫 원문이 늘 한두 줄을 더한다.
- **복창이 맥락을 드러낸다.** 답을 다른 사람에게 공유하면 해석 문장에 프로젝트의 조건이 드러난다. 복창은 비공개 기록에만 둔다.
- **세 해석 이상에서는 무너진다.** 이때는 질문 한 번으로 돌아간다.

**더 단순한 방식이 이기는 조건.** 해석이 하나뿐이거나 두 해석의 첫 원문이 같으면 복창을 생략한다.

## 5. 탐색: 네 갈래와 멈춤 규칙

| 갈래 | 만드는 질의 | 무엇을 찾나 | 근거와 위험 |
| --- | --- | --- | --- |
| 직접 | 실행 환경·라이브러리 이름 + 요청 동사 | 직접 쓸 도구, 공식 API 절 | 주류 원문에 강하다. 이름이 비슷한 함정도 같이 온다 |
| 관계 중립 | 칸 값을 이은 문장(분야·제품 이름 없음) | 다른 이름으로 같은 작동을 하는 자료 | 분야 단서 없이 찾은 원리는 당시판 지지 0/144쌍이었다 [033][r38] |
| 분야 추정 | 판독기가 "이 관계를 오래 다뤄 온 분야" 2~3개를 추정하고 그 분야 말로 질의 | 시험해 볼 원리, 다른 분야의 실패 복구 방식 | 분야 단서를 준 검색은 원리 7군을 찾았다 [010][r38]. 추정이 틀릴 수 있어 추정과 적중을 기록한다 |
| 언어 | 요청 언어 + 영어 + 칸에 따라 하나 더 | 다른 언어권 자료 | 이름 번역으로는 대상이 어긋났다 [138][r35]. 번역은 칸 문장 단위로 한다 |

멈춤 규칙은 동사에 따라 다르다. 257에서 공식 갤러리를 끝까지 읽어도 "결과를 바로 준다"는 0건이 늘었고 "방법을 보여 준다"는 9위에서 처음 1건이 나왔다. API 페이지 안의 예제는 문서 내 이동 한 번으로 직접 답했다. [257][r257]

- 먼저 공식 API 절과 그 안의 예제를 연다.
- 사용자가 "방법"을 원하면 예제 목록을 원순서로 읽되, 해당 값을 실제로 소비하는 코드 줄을 처음 만나는 곳에서 멈춘다.
- 사용자가 "결과"를 원하면 공개 출력에 그 값이 있는 원문만 센다. 예제 목록 깊이를 늘리지 않는다.
- 목록이 정상 종료해 자리가 비면 그것은 실패가 아니라 정상 공석이다.

## 6. 판독과 판정

### 6.1 항목의 종류와 동사

판독기는 열람한 절마다 칸별로 충족·반증·미확인을 적고, 증거 층(제작자 진술·코드·공개 출력·실행)을 붙인다. 답의 동사는 증거 층을 넘지 않는다. 답 항목의 형식은 안 A의 5.6절과 같다: 종류(직접 쓸 도구·이식할 부품·시험해 볼 원리·함정), 맞은 칸, 한 줄 이유, 첫 원문(현재 주소와 확인한 판·절), 함께 있어야 작동하는 조건, 원리일 때 빌려올 것과 대상에서 다시 확인할 것, 뒤집힐 조건.

"함께 있어야 작동하는 조건"은 판독에서 직접 확인한 것만 적는다. 같은 기하 바이트를 쓰는 3D 모델이라도 필요한 재질 이미지와 디코더가 달랐고([247][r49]), 같은 아이콘도 문서 안에 넣는지, 묶음 파일의 한 기호를 부르는지, 개별 파일을 이미지로 부르는지에 따라 함께 줘야 할 파일이 달랐다([260][r260]).

### 6.2 일부만 맞는 비유를 전달하는 방법

다른 분야 원리는 "빌려올 것"과 "대상에서 다시 확인할 것"을 나눠 쓴다. 258의 온도 조절기 사례가 기준이다. 3D 모델의 세부 단계를 거리로 바꾸는 코드를 손으로 추적한 결과, 냉방 대역을 참고한 예측은 문서만 본 예측보다 4경로 중 3곳에서 더 맞혔지만, 아래 경계값과 정확히 같은 거리에서 먼 단계를 유지하는 한 경로는 틀렸다. 이력 폭을 0으로 두면 모든 예측이 같아졌다. [258][r258]

| 답에 쓰는 칸 | 이 사례의 값 |
| --- | --- |
| 빌려올 것 | 이전 단계를 기억해, 두 경계 사이에서는 현재 단계를 유지한다 |
| 대상에서 다시 확인할 것 | 경계값에서 어느 쪽 등호가 적용되는지, 거리 단위(화면 비율을 쓰는 엔진은 다르다), 처음 상태 |
| 다시 확인할 첫 원문 | 사용자가 쓰는 엔진 판의 단계 선택 코드 |
| 뒤집힐 조건 | 이력 폭이 0이거나 공간 혼합을 쓰면 이력 자체가 필요 없다 |

온도 조절기 쪽 원문끼리도 경계 등호가 서로 달랐다. 이 사실이 "등호는 대상에서 확인"을 원리 카드에 미리 적어 둘 이유다.

### 6.3 우연한 적중을 거르는 방법

이 안은 표시 전에 읽는다. 원리 후보는 판독기가 원문 문장에서 "공여 역할 → 대상 역할" 대응과 깨지는 조건을 쓸 수 있을 때만 "시험해 볼 원리"로 표시한다. 대응을 쓰지 못하면 "확인할 만한 링크"로만 준다. 이 비용 때문에 열람 예산의 일부(6개 중 2개)를 분야 추정 갈래 몫으로 고정한다. **[가정]**

### 7.2 요건 사실과 구별

요건 사실은 판정이 성립하려면 같아야 하는 칸 값이다. R1의 사례에서 "크기 제한 대기열 + 고정 작업자 4"라는 판정은 "투입원이 멈출 수 있다", "작업자 수가 고정이다", "실행 흐름이 하나다"에 의존한다. 제조 현장의 끌어당김 원리와 시간 기반 처리율 제한의 함정 표시는 앞의 두 사실에 의존하지 않는다.

재사용 규칙은 다음과 같다.

1. 새 요청의 칸 패턴과 같은 사례를 자기 프로젝트의 사례와 공개 사례에서 찾는다.
2. 요건 사실이 모두 같으면 판정을 재사용한다. 단 열람 관측의 판이 사용자 판과 다르거나 현재 절 지문이 다르면 그 절을 다시 읽는다.
3. 요건 사실 일부가 다르면 "구별"한다. 다른 사실에 의존하는 판정은 버리고, 의존하지 않는 판정만 재사용 후보로 꺼낸다. 버린 판정 자리는 이번 요청에서 새로 탐색한다.
4. URL이나 제목만 같은 열람을 다른 요청에 재사용하지 않는다. 같은 주소의 다른 지역·다른 판 값을 재사용한 경로가 147에서 오승인 40/96을 냈다. [147][r147]

예를 들어 몇 달 뒤 "외부 서비스가 일방적으로 밀어 넣는 알림을 처리보다 빨리 받는다"는 요청이 오면, 칸 패턴은 R1과 같지만 요건 사실 "투입원이 멈출 수 있다"가 다르다. 대기열 판정은 재사용하지 않는다(멈출 수 없는 투입원 앞에서는 넣는 쪽을 기다리게 해도 원천은 멈추지 않는다). 끌어당김 원리와 함정 표시는 재사용 후보로 나온다.

### 7.3 공개와 사적, 승격

- 열람 관측은 공개 원문에 대한 사실이라 처음부터 공개다. 누가 왜 읽었는지는 남기지 않는다.
- 사례는 프로젝트 비공개다. 요청 문구, 조건 수치(8과 4), 선택과 기각 이유가 들어 있다.
- 공개 사례로의 승격은 ① 서로 다른 두 프로젝트에서 같은 칸 패턴·같은 판정이 독립적으로 나왔거나 ② 사용자가 허락했을 때만 한다. 승격본에는 프로젝트 명사·수치·문구를 넣지 않는다. 주소만으로 마지막 값을 이어 쓴 구성에서는 다른 키·절의 근거를 쓴 72건 중 24건이 다른 프로젝트가 취득한 것이었다. [147][r147] **[가정: 두 프로젝트 기준이 의도 노출을 충분히 막는다]**

### 7.4 대표 조회와 쓰기: R1과 그 뒤

1. R1이 들어오면 요청·해석을 쓰고, 칸 패턴이 같은 사례를 찾는다(처음이면 없음).
2. 네 갈래 탐색 결과를 탐색 실행에 쓰고, 상위 절 여섯 개를 읽어 열람 관측으로 쓴다. 이미 같은 키의 열람 관측이 있으면 새로 쓰지 않고 그 id를 쓴다.
3. 사례 하나를 쓴다. 판정 항목 네 개와 각자의 의존 요건 사실을 함께 쓴다.
4. 답·답 항목을 쓴다.
5. 나중에 같은 프로젝트에서 작업자를 항목마다 만드는 구조로 바뀌어 다시 요청이 오면, 요건 사실 "작업자 수 고정"이 달라져 대기열 판정을 버린다. 그 자리를 허가 계수기의 절로 다시 읽는다. 허가를 작업을 만들기 전에 얻지 않으면 이미 만든 작업이 무제한 대기 집단이 될 수 있다는 것이 이 절의 깨지는 조건이다. [012 자료집][c012]

### 7.5 동시 요청·재시도·잘못된 재사용

- **동시 요청.** 두 프로젝트가 같은 공식 절을 동시에 읽으면 열람 관측의 유일 키 때문에 하나만 생기고, 두 사례가 같은 열람 id를 가리킨다.
- **재시도.** Studio가 같은 요청 판을 다시 보내면 요청 id와 판이 같으므로 새 답을 만들지 않고 기존 답을 돌려준다.
- **잘못된 재사용.** 칸 분해가 요건 사실 하나를 빠뜨려 R1 사례를 알림 수신 요청에 그대로 재사용했다고 하자. 사용자의 정정이나 나중 실패 보고로 드러나면 정정 사건을 남기고 다시 답한다. 원 사례는 고치지 않는다. 원 사례의 판정은 원래 요건 사실에서는 옳았기 때문이다. 대신 그 판정 항목의 "의존 요건 사실"에 빠졌던 사실을 덧붙인 새 판을 만들고, 같은 판정을 재사용한 다른 답을 찾아 재검토에 올린다.

## 8. 이름·주소·판·내용·가용성이 따로 변할 때

이 안은 상시 수집이 없으므로 변화를 세 경로로만 알아챈다. 사례를 재사용할 때의 지문 대조, 자주 쓰이는 사례의 배경 재확인, 사용자의 보고다.

| 사건 | 과거 답은 이렇게 읽는다 | 현재 재사용은 이렇게 한다 |
| --- | --- | --- |
| 이름 변경 | 열람 관측의 당시 제목 | 재사용 때 새 이름을 함께 표시 |
| 주소 이동 | 옛 주소와 발췌 | 새 위치를 읽어 새 열람 관측. 지문이 같으면 판정 유지 |
| 새 판 | 당시 판의 관측 | 사용자 판의 절을 다시 읽음 |
| 같은 판 표지에서 내용 변경 | 옛 지문과 발췌 | 판정을 재사용하지 않고 다시 읽음 |
| 일시 실패 | 영향 없음 | 마지막 관측으로 답하되 실패를 표시. 같은 요청 안에서 다른 후보 우선 |
| 영구 부재·철회 | 발췌로 읽힘 | 그 판정을 버리고 같은 칸을 다시 탐색 |

같음 판단은 사례 안에서만 한다. 두 열람 관측이 같은 대상이라는 판단은 그 사례의 목적에만 유효하고, 다른 사례로 옮기지 않는다. 병합·분리라는 연산이 따로 없다. 그 대가로 같은 대상을 여러 사례가 각자 다시 판단하는 중복 노동이 생긴다.

## 9. 예산과 손실 감지

이 안은 152의 "요청 때만 확인(O)"에 가장 가깝다. O는 유보 기간 신규 15건 중 10~14건을 찾았고, 같은 요청이 겹치면 반복 비용을 내며, 원격 조회가 막히면 바로 답하지 못한다. [정책 정의][p152] 인기 안정 자료는 요청 때만 114번 다시 확인했지만 결과는 모두 일치했다. [152][r152] 사례 재사용은 이 반복 비용을 줄이는 장치다.

예산이 줄면 줄이는 순서는 ① 열람 수(6→4), ② 언어 갈래의 셋째 언어, ③ 관계 중립 갈래다. 분야 추정 갈래는 마지막까지 남긴다. 이 갈래를 지우면 원리 후보가 사라지기 때문이다(10절). 대기시간이 늘면 답을 둘로 나눠 직접 쓸 도구를 먼저 보내고 원리를 뒤에 보낸다. **[가정]**

손실은 다음 관측으로 알아챈다.

| 손실 | 관측 |
| --- | --- |
| 놓친 후보 | 예산 안에서 열지 못한 상위 후보 수, 사용자가 나중에 다른 경로로 찾았다고 알린 원문 |
| 분야 추정 실패 | 추정한 분야에서 대응 문장을 쓴 후보 비율 |
| 반복 비용 | 사례 재사용률, 같은 열람 관측을 다시 읽은 횟수 |
| 복창 무시 | 정정률과, 정정 없이 나중에 오해로 드러난 답 수 |
| 낡은 재사용 | 재사용 때 지문 불일치 비율 |

| 분야 추정 갈래 | 원리 후보가 사라진다. 무단서 원리 검색은 지지 0이었다 [033][r38]. R1의 제조 원리와 함정 표시를 잃는다 | 남긴다 |
| 스쳐 본 목록 | 제목만 남는 기록이라 R2에서도 다시 찾지 못한다. 쓰이는 곳이 평가뿐이다 | **첫 버전에서 지운다.** 답·발견 가능성·복구 가능한 기록이 같다 |
| 공개 사례 승격 | 사례가 프로젝트 안에서만 재사용된다. 첫 사용자에게는 답이 같다 | 첫 버전에서 미룬다. 프로젝트가 여럿 쌓인 뒤 도입 |

## 11. 이 안이 틀렸다고 판정할 관측

1. 분야 추정 갈래에서만 나온 후보가 사용자의 이해나 결정에 기여하지 않는다.
2. 사례 재사용률이 낮아 읽기 비용이 기준선과 같다.
3. 복창 정정률이 0인데 정정 없이 오해로 드러난 답이 많다(복창이 읽히지 않는다).
4. 안 A의 그림자 수장고가 이 안이 못 찾은 채택 후보를 의미 있는 비율로 낸다.

이 안은 249의 사람 대상 평가안과 잘 맞는다. 같은 개발자의 사전 코드와 즉시·지연 노출 뒤 코드를 비교하는 설계이며, 한 요청 안의 효과를 본다. 다만 249의 실제 참가자는 아직 0명이고 예시 4건은 합성이다. [249 프로토콜][p249] 267은 그 합성 기록의 채점기가 설계한 차이를 잡는다는 것까지만 확인했다(한 회차 A 42/42, B 44/48 통과, 실패 4건은 모두 의도된 한 스냅샷). [267][r267]

## 12. 첫 구현 단위

1. Studio에서 3.1절의 맥락을 받는 계약(선택 객체, 이웃 한 겹, 판, 빌드 설정, 이미 쓰는 도구, 목적 원문).
2. 일곱 칸 해석과 복창, 3.2절의 질문 조건.
3. 네 갈래 탐색과 5절의 멈춤 규칙, 열람 6개.
4. 열람 관측·사례·답의 기록(7.1절). 공개 사례 승격과 스쳐 본 목록은 만들지 않는다.
5. 공통 요청 R1·R2와 고정 요청 12개로 기준선(일반 검색 + 그 자리 읽기)과 같은 예산에서 비교한다.
