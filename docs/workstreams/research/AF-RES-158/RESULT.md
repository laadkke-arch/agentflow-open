## Q5. 실패 인지·복구·반례
- 표2의 수신 증거는 UI를 직접 보았다는 당사자 보고, API 응답, 스스로 읽은 log를 구별. 기능 지원→발송→수신→읽음→복구는 별개. 실제 push/e-mail 수신까지 증거가 없어 승인 0. #5215 로그의 명시성은 운영자 권한에 따라 제출자에게 닿지 않을 수 있음.

## Q6. 조건부 추천
- 단일 링크 직접: “입고가 성공하여 문서 ID가 있고 원본 회수 API를 찾는다면 Paperless 해당판 original=true 절” 또는 “ingested tabular 파일의 저장 원본을 원하면 Dataverse 해당판 format=original 절.” 이것은 방법 계약이지 파일 존재 확인이 아니다.
- 근거 추가: 최초 접수와 영구 보관이 같냐는 질문, 오류 후 복구 가능 여부처럼 계약과 관측이 갈리는 경우 A+B를 함께 주고 누락을 표시. 실제 사용자에게 해당 객체의 성공/실패 확인이 목적이면 task/file ID, 동일 원본 hash, 권한·표시·최종 저장 기록이 있어야 직접 승인. 다른 판의 개선을 붙여 과거 판 문제 해결이라고 답하지 않는다. 
- 보류 문장: “이 사례에서 제출자가 작업 시작/오류를 보았다는 보고는 있으나 최종 레코드 및 원본 바이트의 동일성은 미확인. 접수 ID와 종단 상태, 해당 파일의 원본 회수 증빙을 먼저 확인해야 한다.” 실제 이해시간·선호 실측 없음.
