# AF-RES-017 — SCOPE v1 (수집 전 동결)

## 질문과 기준

소프트웨어에서 뒤늦게 발견한 외부 해결책의 종류, 당시 존재·발견 가능성, 실제 변경 비용, 발견 경로를 공개 1차 기록으로 조사한다. 제품 구현·유료 호출·로그인·권한 변경·상시 수집은 하지 않는다. 쓰기는 `docs/workstreams/research/AF-RES-017/`에 한정한다. source_commit은 `0209117d8ec00af39bd25844d52a18edc7323207`이다.

## 포함·제외와 관측 단위

한 사례는 한 조직/저장소의 한 선택 범위에서 자체 구현 또는 기존 선택을 외부 실체와 비교하고 교체·수정·유지·되돌림한 공개 결정 사건이다. 최소 공개 1차 본문, 결정/발견 날짜(월 이상), 변경/유지의 공개 증거를 요구한다. 같은 사건의 여러 글·PR은 한 사례로 묶는다. 조직/저장소별 최대3개, 계열4개 이상, 계열당 최대40%, 사례40개 이상을 목표로 한다. 정당한 자체 구현>=5, 늦은 채택의 되돌림>=3을 별도로 찾는다.

**인과 판정은 별도다.** `late_discovery_status`는 `explicit_unaware`(당사자가 몰랐다고 명시), `late_recognition`(알던 해결책의 적합성을 늦게 이해했다고 명시), `known_rejected`(알고 거절), `later_available`(당시 부재), `unknown`이다. 교체/성능 개선/새 팀 합류만으로 무지를 추정하지 않는다. strict late-discovery 분모는 앞의 두 값 중 날짜·외부 실체·변경 근거를 갖춘 사례다. 반례는 별도 층으로 명시하며 부족하면 전체 완료를 주장하지 않는다. 마이그레이션 사건 수와 늦은 발견 원인 확인 수를 합치지 않는다.

의도적으로 정당한 거절·되돌림·당시 부재·현재 흔한 검색어 적중·장식적 유추를 찾는다. 추천 질문 사이트, 합성 문제, Rust/PEP/Swift/KEP 재표집, 이름만 언급하는 2차 글은 주 사례에서 제외한다. 013의 엄격 채택 후 대체6개(C07/C12/C14/C21/C29/C31)는 출처 후보로만 보되 새로운 외부 실체 발견 근거가 없으면 제외한다.

## 분류와 코드북의 명칭 차이

사용자 표의 `형태(S1)`에는 016 CODEBOOK §4 S3.form의 app/service/library/framework/standard/document/pattern/research 및 data/mixed/unknown 정의를 그대로 쓴다. 고정 016의 실제 S1은 product/component/principle이므로 `legacy_S1`에 병기한다. 요청의 명칭과 원 파일의 명칭을 혼동하지 않는다. `기여(S2)`는 016 §3 whole/part/reference/comparison/none/mixed/unknown 그대로다. whole은 프로젝트 전체가 아니라 사례의 명시된 선택 범위 전체다. `관계(013 분류)`는 같은 목적 완성품/재사용 부품/같은 분야의 다른 설계/다른 언어·생태계/다른 분야 원리/표준·논문 중 하나, 복합이면 primary와 보조 관계를 구분한다. 타 분야는 이름의 유래가 아니라 원 분야 관계와 대상 설계의 명시적 연결을 요구한다.

## 시점·존재·검색

결정일은 최초 자체 구현 선택일, 발견일은 외부 실체를 새로 알거나 재평가했다고 문서에서 확인되는 날이다. 단지 출판일만 알면 `date_basis=publication_proxy`로 두고 월을 발명하지 않는다. 근거는 첫/선행 릴리스·고정 커밋·표준/논문 발행일이다. 최초라는 증거가 없으면 '늦어도 이날 존재'로 쓴다. `existed_at_decision`은 yes/no/unknown과 원 URL을 항상 보존한다. 유명함은 당시 스타/다운로드/사용처/인용 등 날짜 있는 관측이 있을 때만 known/well_known으로 코딩한다. 현행 숫자를 과거로 옮기지 않는다.

필요 문장<=25단어의 영문 요약 또는 원문 짧은 인용을 고정한다. 대상 이름·후속 결과·해결책 고유어를 의도적으로 추가하지 않는다. 원문 링크와 요약자(작업자)를 남긴다. 어휘 겹침은 영어 소문자, 영숫자 token, 지정 stopwords 제거, 단복수 단순 정규화만으로 need와 공식 설명의 고유 공유 token 수를 계산한다. 임베딩·번역·사후 동의어 확장은 쓰지 않는다. 공식 설명의 현행/역사 여부를 분리한다.

'흔한 검색으로 충분'은 사전 need에서 1~2개 보통 명사를 골라 이름 없이 한 질의, 상위5개 결과에 목표 실체가 있고 본문 적합성 확인 시 `current_easy_hit`다. 이 관측은 현재 검색의 과제이며 과거에도 같은 결과였음/제품의 추가 가치 0을 증명하지 않는다. 회고적 글/목표 사건 유출은 기록하고 검색 성공에서 제외한다. 모든 사례의 입력은 나중 별도 기준선에 쓸 수 있도록 정답 필드와 분리한다.

## 비용 지표

1. 코드: PR의 additions/deletions 및 관측 범위. 삭제 줄 수는 쓸모없는 노력의 시간 추정이 아니다. generated/vendor 파일 포함 여부 표시.
2. 이행: 저자가 밝힌 기간 또는 명확한 start/end 달력 차이. 사람 투입 시간과 달력 기간을 합치지 않는다.
3. 사고: 문서가 연결한 사고 횟수·영향 시간. 해당 기법을 알았으면 회피됐다는 인과는 별도다.
4. 번복: 같은 선택 범위의 명시적 되돌림 횟수.
5. 직접 진술 시간/금액: 단위·범위·저자 진술 위치. 통화 환산·인건비 추정 금지.

지표별 n/전체, median/min/max를 제시한다. 없는 값을0으로 넣지 않고 비용 미확인 사례를 센다. 서로 다른 단위를 합산하지 않는다. `attribution=reported_transition_cost|reported_ignorance_cost|inferred_calendar_interval`을 구분한다.

## 검토·동결·근거

A 코딩을 커밋/push한 뒤 새 문맥 B에게 코드북과 라벨 없는 관측 패킷만 준다. B는 A·RESULT·사례 라벨·Git 이력을 읽지 않는다. 형태/기여/관계 및 늦은 발견 증거 상태를 독립 코딩하고 raw를 그대로 보존한다. 일치율·Cohen kappa·불일치 목록을 산술 계산한다. 80% 이상 한 값이면 알려진 나쁜 후보/날짜 오류를 별도 진단으로 넣는다. B는 내부 별도 검토이며 사람 검토가 아니다. 모델 선택이 가능하므로 B에 다른 표시 모델을 사용하고 정확한 도구 model label을 기록한다. 파일 읽기 제한은 지시 수준이며 OS 격리는 아니다.

D0 검색 snippet 제외; D1 본문; D2 고정 코드; D3-search/fetch/run 관측; D4 실제 제품 적용(이번에는 하지 않음); H 가설. sources는 실제 URL·UTC·제목·판·읽은 절·짧은 확인·한계·used_in을 기록한다. 사용자 이름·프로필·본문 전문을 보존하지 않는다. 방법 문헌>=25개는 사례와 별도, 같은 site 최대3개 산입한다. 제외/실패를 별도 목록으로 남긴다.

## 전달과 한계

열람·분석·원응답·집계·자기 점검을 묶음별 즉시 커밋/push하고 HANDOFF를 마지막 단독 커밋한다. 필수 조건이 자료 부재나 차단으로 남으면 최소 재개 입력과 `REVIEW_READY_WITH_GAPS`/`BLOCKED`로 전달한다. 사건 중심 목적표본의 비율을 전체 소프트웨어 팀의 빈도로 일반화하지 않는다. 최소 수를 채우려고 이주 사례를 늦은 발견으로 바꾸지 않는다.
