## Q1. 발행판 귀속과 시각

**실측 2/4쌍, 8/16판독.** IANA 날짜층은 2024-02-01의 2024a와 2024-09-05의 2024b, 공지층은 2023-03-22의 2023a와 2023-03-24의 2023b다. 데이터 tar 바이트 수는 각각 451,270 / 459,393 B와 442,875 / 443,019 B다. 네 판의 SHA-512는 공지와 일치한다. 목록의 Last modified, NEWS 작성 시각, 게시일, Rule의 민간시 효력일을 분리했다. 셸에서 원 URL의 본문을 받는 데는 실패했다. 2024a는 Ubuntu 배포의 동일 바이트를 받고, 2024b와 2023a/b는 공식 공지에 명시된 Git 태그로 동일 바이트를 재구성했다. ## Q2. 같은 질문의 고정

교통은 서비스일과 노선·방향 키를 잡고 요일 활성 서비스에 해당 날짜의 추가·제거를 적용한다. 예정 수의 단위는 고유 `trip_id` 하나다. 기여 집합은 각 trip의 `stop_sequence` 순서로 `stop_id`와 시각을 대응한다. `direction_id`가 비어 있으면 결측 상태를 유지한다. MBTA는 현재 표에서 `trip_id`를 persistent로 부르지만 Glides와 정적 GTFS 사이의 서로 다른 스케줄·미매칭도 문서화한다. 식별자의 분야 일반 규칙과 기관별 지속성은 별도다. `frequencies.txt`의 출발 횟수, 24시 이후 운행, 예외가 있는 날의 승객 질문은 정해진 서비스일과 단위를 따라서 다룬다. [GTFS 필드 정의](https://gtfs.org/documentation/schedule/reference/) · [발행 권고](https://gtfs.org/documentation/schedule/schedule-best-practices/) · [MBTA 구현](https://raw.githubusercontent.com/mbta/gtfs-documentation/02da961b963ba3d3a66042ca4d5bd19e21ce5c0a/reference/gtfs.md) · [Glides TripKey](https://mbta.github.io/schemas/events/glides/com.mbta.ctd.glides.trips_updated.v1/)

유효한 동일 키·서비스일에 조건이 빈 경우에만 예정 0이다. 새 판에서 Route/방향 키가 없어지면 발행자의 대응표나 고유 패턴 대응을 확인한 뒤 판단한다. 동일 정류순서·시각의 양쪽 유일 지문을 찾아야 trip 재발급으로 표시한다. 모순 예외 또는 다대다 지문이면 보류한다. 이 규칙과 8개 요구는 값 계산 전 커밋됐다. [봉인 규칙](SCOPE.md) · [기대 원장](expectations.csv)

시간대 키는 IANA Zone과 UTC 순간이다. `zic`에서 별도 suffix가 없는 AT는 그 시점의 벽시각이므로 베이루트 공지의 04-21 00:00은 전환 직전 +02를 빼서 04-20 22:00Z로 고정했다. 21:00과 23:00Z를 같은 순서로 비교한다. `2023a`에는 3월 마지막 일요일 Rule, `2023b`에는 2023년에 한해 4월 21일 Rule이 들어 있다. 별칭이 필요하면 `backward`와 목표 Zone을 같이 고정한다. UTC→현지와 모호할 수 있는 현지→UTC는 각각 정의가 다른 요청이다. ## Q3. 판독 일치와 재실행

시간대는 판마다 배포 tar와 멤버 해시를 검증해 별도 폴더에서 `zic -b slim`을 실행했다. `zdump -i -t`의 부호 있는 오프셋·약칭에 UTC 오프셋 덧셈을 적용한 경로와, `ZoneInfo.from_file`의 명시 TZif 및 `astimezone`을 적용한 경로가 일치했다. 각 순간의 `zdump` 열린 TZif가 해당 절대 파일 하나인지 strace로 확인했고, Python TZPATH는 비웠다. Python은 지정 파일 객체를 열었고 두 판독은 같은 TZif·glibc zic 2.41을 공유한다. v2 계열 TZif의 구성과 약칭 규칙을 문서로 대조했다. 숫자 약칭 생략으로 처음 실패한 Choibalsan 대조는 매뉴얼에 따라 파서를 고치고 새 폴더에서 양쪽을 다시 실행했다. [실행·복구 영수증](evidence/receipts.json) · [TZif 형식](https://datatracker.ietf.org/doc/html/rfc9636#section-3) · [zdump 간격 형식](https://data.iana.org/time-zones/tzdb/zdump.8.txt) · [Python 명시 파일 생성자](https://docs.python.org/3.12/library/zoneinfo.html#zoneinfo.ZoneInfo.from_file)

실행된 시간대 8/8판독에서 두 판독기가 일치했고, 다른 입력 복사본·빈 build 폴더·역순 컴파일의 재실행에서도 8/8이 일치했다. 날짜 두 개는 한 요구 행의 두 순간이다. 같은 변환에서 나온 오프셋과 현지 표기에 별개의 독립 표본이라는 가중치를 주지 않는다. 교통 0/8 본판독은 미실시다. 교통 통제에서 공통 CSV를 Python 조인과 SQLite CTE·집계로 따로 계산해 양쪽 3개·집합 일치를 얻었고, 그 사실은 운영판 결손을 해소하지 않는다. ## Q4. 값의 유지와 근거의 유지

뉴욕은 2024a→2024b의 2025-01-15와 07-15 두 순간에 오프셋과 현지 표기가 각각 같았다. 배포 바이트와 `northamerica` 멤버 SHA-256은 다르고 이 환경에서 생성한 `America/New_York` TZif SHA-256은 같았다. 베이루트는 2023a→2023b의 04-20 21:00Z에서 +10,800초/04-21 00:00 EEST가 +7,200초/04-20 23:00 EET로 바뀌었다. 23:00Z는 두 판 모두 +10,800초와 04-21 02:00 EEST다. 두 순간을 요구하므로 뉴욕 유지 2/2, 베이루트 변경 2/2이며 교통은 비교 가능 0/4 요구다. [판독 원장](runs.jsonl#L9)

대조에서 다음 세 가지가 성립했다. `CET`는 두 고정 UTC에서 현지 표기까지 유지되지만 2024a `europe` 737행의 독립 Zone이 2024b `backward` 48행에서 `Europe/Brussels` Link가 된다. 같은 판 쌍이라도 `Asia/Choibalsan`의 2005-01-15 12:00Z는 +32,400초/21:00 +09에서 +28,800초/20:00 +08로 바뀐다. 이어진 2023c는 베이루트 21:00Z를 다시 2023a의 값으로 돌린다. 이는 발행판을 잘못 건너뛰면 과거 근거의 유지가 보일 수 있음을 보여 준다. 2023c와 역사·별칭 대조는 본판의 8판독에 산입하지 않았다. [CET 이전 선언](https://github.com/eggert/tz/blob/380c07cef01c71c1f93e9709d9f8c79b91cff063/europe#L737) · [CET 새 링크](https://github.com/eggert/tz/blob/6903dde39ed637adaafc352c4b6993739253f058/backward#L48) · [2023c 되돌림 공지](https://lists.iana.org/hyperkitty/list/tz-announce@iana.org/thread/NPQOFZRXK5QKUW7F4CC24W52OTZ7YOOT/) · [대조 실측](evidence/contrasts.json)
