## 판정과 범위

**PARTIAL.** 대상 두 사건의 공식 release-level 표시/사유, 파일명 목록(88개 현재 파일, 별도 삭제 그룹 1행), 공개 결정·영향, 인접 네 판, 명세와 24.0 코드 및 테스트, 6개 목적별 조건은 연결했다. 하지만 Simple raw file attributes와 version JSON 6/6 조회 실패, 삭제 파일의 과거 목록/실제 flag 변경 UTC 미확인. 따라서 Q2 핵심의 file-level yanked 값은 미충족이다. raw yanked=false를 배너 없음으로 추정해 채우지 않았다. 이는 새 설치 실행이 아니라 공개 문헌/관측 분석이다. 28개 고유 직접 자료, 44행 sources ledger(16 제외/실패/중복 포함), 두 software incident, 두 실제 학술 출판 계보; 자세한 모집은 frame.csv.

### Q1 누가 왜 철회했나?
M: [D01 banner](https://pypi.org/project/matplotlib/3.9.1/)는 관리자 사유이며, 일부 official Windows wheels 조건부 crash → 삭제 → sdist build fallback 실패 증가 → 전체 release yank라는 인과를 설명한다. [M01 issue](https://github.com/matplotlib/matplotlib/issues/28551) 07-12 ianthomas23 최초 issue, 07-15/17/24 환경 비교와 local Windows build 관측, 08-01 tacaswell 삭제 검토. [M02 initial announcement](https://discourse.matplotlib.org/t/matplotlib-announce-ann-matplotlib-3-9-1/24539) 07-06 최초 권고. 08-05 PyPI yank date, 08-06 D03 post1 wheel 재등장, 08-13 issue closed. root cause가 pybind11/delvewheel/compiler 중 무엇인지 확정하지 않음. 삭제/철회를 실제 클릭한 사람과 시각 미확인. post1은 후보이며 실제 수정 발표 F11 접근 실패, closure는 모든 환경 재검증 아님.

P: [M03 #12069](https://github.com/pytest-dev/pytest/issues/12069) 03-04 mr-c 보고(기존 signature 지원 plugin이 깨짐), Ronny 경고 누락/철회 제안, bluetech revert 제안, nicoddemus 철회 선언·제목 수정·pin; [M05 #12068](https://github.com/pytest-dev/pytest/issues/12068) 초기 경고 문제. 날짜/결정 합치 [D04](https://pypi.org/project/pytest/8.1.0/). [M04](https://docs.pytest.org/en/8.1.x/changelog.html#pytest-8-1-1-2024-03-08) Node fspath 및 py.path.local hook args 제거를 9.0.0까지 유예. changelog 03-08, PyPI 업로드 03-09. M03 03-10 private API 제거는 유지, deprecation warnings 문제 추가 수정 필요. "모든 plugin 정상" 아님.

### Q2 어느 파일인가?
releases.csv의 현재 보이는 파일별 filename/type/python/ABI/platform/display upload date를 기록했다. M 3.9.0→3.9.1→post1은 29→24→29 파일. 전후 Windows wheel 5개씩 관측, 중간은 0개. **삭제된 정확 과거 파일 이름/개수는 추론하지 않음**(인접판이 5개였다는 사실과 구별). sdist 1개는 계속 존재. CPython 3.9–3.12의 musllinux tag 1_1→1_2, pp39 macOS x86 tag 10_12→10_15도 관측; tag 동일성까지 가정하지 않는다. 3.9.1의 pp39 wheels 3개(Windows 제외), 각 CPython 5개. 3.9.0/post1은 pp39 4개, 각 CPython 6개. P 세 판 모두 py3-none-any wheel 1 + sdist 1, filename은 각 release 버전으로 다름. [D01–06 PyPI files](https://pypi.org/project/matplotlib/3.9.1/) 및 표1 각 URL. 
[R03 Simple API](https://docs.pypi.org/api/index-api/)는 file object의 yanked, upload-time, requires-python, filename 등과 HTML data-yanked를 규정. [R05 release UI](https://docs.pypi.org/project-management/yanking/)는 release 단위 yank/un-yank. [R01/R02](https://packaging.python.org/en/latest/specifications/file-yanking/)는 파일 링크 단위 표시와 변경 가능성을 설명. 현재 release banner는 raw file boolean/string을 직접 읽은 것이 아니다. F01–F06 version JSON 모두 DisabledError; F07 M Simple failed; F08 P Simple names 읽었으나 raw attr 빠짐; F15 local curl DNS 실패. 88/88 원시 file yanked 값/이유 미확인; 대상 현재 파일 26/26도 동일. D01/D04 release 이유와 raw file reason은 별도. 사용자 요구 "Simple/버전별 JSON에서 직접" 충족 못함. 현재 metadata를 당시 저장소 스냅샷으로 대체하지 않는다.

### Q3 설치 제약
[R01 PEP 592](https://peps.python.org/pep-0592/) Installer section과 [R02 current specification](https://packaging.python.org/en/latest/specifications/file-yanking/) 동일 normative lineage, 중복 집계 제외. 비철회로 충족 가능하면 철회 파일 무시 의무, 모두 철회라면 installer 거부 가능. exact (== no wildcard / ===)와 기존 lock exact artifact 예외는 허용되는 정책, 선택하면 경고 권장. 새 lock은 피해야 함. Mirror의 누락/flag 전달 정책 차이.
[R06 pip 24.0 factory](https://github.com/pypa/pip/blob/24.0/src/pip/_internal/resolution/resolvelib/factory.py#L304-L325) 코드: candidate set all_yanked와 is_pinned 결합; wildcard를 pin으로 취급하지 않음. 24.0은 해당 연도 구현이지만 실제 사용자 pip 버전 불명. [R07 functional tests](https://github.com/pypa/pip/blob/24.0/tests/functional/test_install.py#L2176-L2288) 정적 검사: unpinned simple은 non-yanked 2.0, exact 3.0 warning reason 및 성공, unavailable version diagnostic, all-yanked no pin error returncode1. 읽은 것은 assertion이며 test run 아님. [M03 03-09](https://github.com/pytest-dev/pytest/issues/12069) 실제 exact install transcript 및 Poetry lock 경고 진술(캐시 이용, 실제 lock 내용 미확인). [R04](https://packaging.python.org/en/latest/specifications/version-specifiers/) post-release 및 prefix 규칙: exact 3.9.1과 3.9.1.post1 다름. narrow wildcard도 exact 예외가 아님. pip가 어떤 다른 판을 고를지는 index/candidate/constraint/Requires-Python/tag/hash 등의 함수. 새로 생성한 lock을 과거 고정 lock과 혼동하지 않음.

## 경쟁 설명, 조합과 비용
A. 배포판 수준 badge만 유지: HTML로 저비용. 신규 범위의 선택 제외에는 효과적일 수 있으나 D01의 정상 주장과 실제 Windows 삭제 범위 분리가 안 되고 원래 판 기록이 덮어써질 수 있다.
B. 파일/환경별 유효성 모델: release-level yank 상태, per-file flag/available/deleted, filename/tag/hash, compatibility, issue affected runtime conditions를 별 필드. 사용자 OS/ABI 및 exact/wildcard/range/lock 구분으로 더 정확; 데이터 획득·저장·재검증 비용 증가. raw metadata 결손으로 완결 평가 못함. 파일 삭제와 yank flag 두 이벤트 필요.
C. 목적 기반 routing: 최소 release URL + notice link + observed date + scope, 목적/constraint 입력으로 first/companion 분기. A와 결합하여 먼저 표시, B는 필요시 추가. 기존 환경 기록과 future installation recommendation의 역할 분리. 미확인 판은 보류. 사용자의 환경을 모르는데 모든 관련 링크를 늘어놓는 비용(선택 burden)도 고려. 
D. event history: uploaded_at, issue_observed_at, maintainer_decision_at, displayed_yank_date, metadata_checked_at, corrected_release_at를 각각 보관; 날짜 precision/unknown과 출처 표지. 후판이 구판을 대체하는 relation은 "같은 이름"이 아니라 해당 issue의 수정범위 증거. 상태 변화와 UI 접근 가능성을 분리하는 X01–X07의 원리는 재사용하되 설치 의미는 R01/R06에서 가져옴. 비용은 6판/88 current files의 검사 및 이력 수집량, 실제 운영비/latency 실측 없음. 어느 구성을 최종 채택할지는 후속 설계자에게 열어 둔다.
