# AF-RES-003 — 같은 사실을 세 저장 원리로 표현하기

이 파일은 **수작업 연구 사례**다. 최종 데이터 계약·API·평가팩·정답 벤치마크가 아니다. A/B/C의 표현은 연구자가 작성한 예시이며, 외부 제품이 실제로 이런 형식으로 저장한다는 주장이 아니다. 괄호의 I/M/R ID는 세 `SOURCES-*.md` 원장에 연결된다. 링크는 각 원장에 정확한 주소·버전·확인 시점과 함께 있다.

## 비교의 공통 조건

- **A: 링크 + 짧은 설명.** 설명에 제약·시점·근거를 쓸 수 있다. 글이라는 이유로 정보 표현이 불가능하다고 가정하지 않는다.
- **B: 설명할 대상과 출처 링크의 역할을 분리.** 제품군 아래 기능·배포·모드에 관한 작은 주석을 둘 수 있다. 모든 하위 범위를 별도 객체로 만들지는 않는다.
- **C: 대상에 관한 주장과 그것을 뒷받침하거나 제한하는 근거를 구별.** 한 문단 안에서도 가능하다. 별도 ID·구조는 반복 참조·정정이 필요할 때만 붙인다.

세 안에 **동일한 근거와 동일한 미확인**을 준다. C에만 더 많은 원문을 주어 유리하게 만들지 않는다. 아래 비용은 문서 대조로 도출한 가설이며 저장 용량·작성 시간·검색 정확도를 실측한 수치가 아니다.

## C01 — ngx의 저장소와 문서는 몇 개의 제품인가

**고정 사실/미확인:** ngx README는 자기 문서 URL을 제공한다. 문서 사이트 본문 자체는 해당 하위 조사에서 403이었다. 문서 링크의 귀속은 확인했지만 모든 문서 내용은 미확인이다(I03).

| 안 | 같은 사실을 남긴 실제 표현 예 |
| --- | --- |
| A | `ngx README(I03) — Paperless-ngx 소개. 공식 문서 링크도 여기에서 찾을 수 있음. 문서 본문은 이번에 미열람.` |
| B | `대상: Paperless-ngx / 출처: README=소개, docs URL=공식 문서로 연결됨 / docs 본문 확인=없음.` |
| C | `주장: README가 이 docs 주소를 공식 문서로 연결함 / 주어: ngx와 docs 주소의 관계 / 근거: I03 Documentation / D1. docs 내용 주장 없음.` |

**답/실패/비용:** 세 안 모두 사람이 읽을 때 한 제품의 두 접근 경로임을 설명할 수 있다. A를 URL별 제품 목록으로 기계 해석하면 중복이 생기고, B는 대표 대상에 모으기 쉽다. 이 관계 하나만 다시 찾는 목적에는 C의 별도 주장 ID가 불필요하다. 어떤 안도 미열람 docs의 기능 내용을 입증하지 않는다.

## C02 — Supabase를 self-host하면 관리형 기능이 따라오는가

**고정 사실/미확인:** 공식 자료는 managed/self-hosted/local을 구별하고 self-hosted에 managed backups/PITR 등 일부 기능이 없다고 설명한다. 같은 문서는 자체 호스팅 사용자가 backups/disaster recovery를 책임진다고도 설명한다. 실제 배포 검증은 없다(I04–I06).

| 안 | 같은 사실을 남긴 실제 표현 예 |
| --- | --- |
| A | `self-hosting 문서(I05) — managed backups/PITR 미포함, 백업·재해복구는 사용자 책임이라는 설명. 2026-11-19 UTC 확인. 설치 시험 없음.` |
| B | `대상: Supabase / 범위 주석: self-hosted / 문서: I05 “How ... differs”, 운영 책임 설명 / managed 기능 제외와 사용자 백업 책임을 함께 보존.` |
| C | `주장: self-hosted의 managed backups/PITR 제외; 사용자에게 백업·재해복구 책임 / 각 문장의 주어·수식어·범위와 I05 해당 절 연결 / D1 / 실제 환경 미확인.` |

**답/실패/비용:** A도 이 한 질문에 답한다. B는 제품군을 유지한 채 배포 범위를 주석으로 둘 수 있다. 반복적인 배포별 비교·정정이 필요하면 C가 해당 문장을 따로 고치기 쉽다. “제품과 링크를 나눴다”는 이유만으로 조건을 빼면 B도 실패한다. self-hosted와 hosted를 반드시 완전히 다른 제품 객체로 나누는 것이 유일한 해법은 아니다.

**C 자체의 반례:** 원문을 원자 주장으로 바꾸다가 `managed backups 미제공`을 `backups 없음`으로 축약하면 근거 링크가 있어도 의미가 틀어진다. 주장 분해는 부정의 범위·수식어·운영 주체를 보존해야 한다. 독립 주장 수가 많다는 사실은 정확성의 증거가 아니다.

## C03 — 이름 변경, 포크, 후계는 같은 병합인가

**고정 사실/미확인:** Supabase는 Netlify GoTrue를 포크했고, Supabase 내부 gotrue→auth 이름 변경을 발표했다. JS 패키지 호환 발표는 당시 v2 지원 기간 범위다(I07–I08). Paperless-ng는 원 Paperless의 fork이며 GnuPG 지원 제거를 설명하고 ngx를 직접 계승으로 안내한다(I01–I03). 실제 이전은 없다.

| 안 | 같은 사실을 남긴 실제 표현 예 |
| --- | --- |
| A | `I08 — Supabase 내부 이름 변경; Netlify와는 fork. 호환 발표는 당시 v2에 한정. I02 — Paperless fork·기능 차이·ngx 후계 안내.` |
| B | `Supabase Auth ← 옛 Supabase GoTrue 이름; Netlify GoTrue와 fork 연결. Paperless / ng / ngx는 계보로 묶되 각 프로젝트 참조 유지.` |
| C | `이름 변경 판단의 근거=I08; 포크 판단=I07/I08; v2 호환 문장=별도 범위; Paperless 기능 제거=I02. 후계라는 이유로 이 주장들을 다른 대상에 복사하지 않음.` |

**답/실패/비용:** A도 구별 가능하지만 정리자가 이름만 비교하면 포크까지 합칠 위험이 있다. B는 별칭과 계보를 표현하기 좋고, C는 예외적 호환 약속·기능 변경만 독립 정정할 수 있다. 세 안 모두 “후계”를 버전 전부의 대체 가능성으로 해석하면 실패한다. 기록을 하나로 병합하는 작업과 실제 외부 프로젝트의 계승 사건은 구별해야 한다.

## C04 — 같은 OpenAlternative URL이 계속 같은 재사용 대상을 뜻하는가

**고정 사실/미확인:** I09 고정 README는 현재 저장소를 목록으로 설명하고 옛 앱 boilerplate를 Dirstarter에서 제공한다고 말한다. 두 코드의 동일성·현재 상품 조건은 미확인이다.

| 안 | 같은 사실을 남긴 실제 표현 예 |
| --- | --- |
| A | `고정 README I09 — 현재 curated list. 옛 앱은 Dirstarter로 이동했다는 작성자 안내. 코드 동일성·현재 제공 조건 미확인.` |
| B | `OpenAlternative repo / 관측 역할: 이 SHA에서는 목록 / 옛 앱 자료와 Dirstarter는 관련 후보 / 완전 동일성=보류.` |
| C | `현재 역할 설명과 이동 보고를 두 문장으로 보존. 같은 주소의 예전 설명을 지우지 않고 범위·근거 SHA를 유지. 코드 same 판단은 별도 미해결.` |

**답/실패/비용:** URL을 고정 키로 쓰는 것 자체는 문제가 아니다. 같은 키의 최신 설명으로 과거 의미를 덮어쓰고 옛 판단까지 바꾸는 것이 문제다. A도 고정 SHA 메모를 남기면 보존할 수 있다. C는 서로 다른 시점의 주장을 추적하기 편하지만, 코드 이동 보고만으로 완전한 동일성을 만들어낼 수 없다.

## C05 — SQLite에 검색과 changeset이 있으면 검색 데이터의 변경을 그대로 전송할 수 있는가

**고정 사실/미확인:** FTS5는 virtual table 모듈이고 session은 virtual table 변경을 직접 포착하지 않는다. FTS5 문서는 일반 content table의 trigger 유지와 rebuild를 설명한다. 두 기능의 구체 조합 구현은 시험하지 않았다(M01/M02/M04).

| 안 | 같은 사실을 남긴 실제 표현 예 |
| --- | --- |
| A | `FTS5(M01) + session(M02): session의 직접 virtual-table 캡처는 지원 안 됨. 일반 원본표+색인 유지/재구축 조합은 추가 검증 필요.` |
| B | `SQLite / 기능 참조 FTS5, session / 각각의 문서·제약 주석 / 사용자 빌드 포함 여부 unknown.` |
| C | `FTS5의 대상 종류=M01; session의 제외 조건=M02; 직접 캡처 경로의 부적합=연구자 결합 판단; 일반표 경로=조건부 가설, 실행근거 없음.` |

**답/실패/비용:** “SQLite는 검색과 동기화를 지원한다”까지만 저장하면 모든 안에서 잘못된 합성이 가능하다. B에 좁은 제약 주석이 있으면 충분할 수 있다. C의 이득은 서로 다른 근거에서 나온 결합 판단과 개별 사실을 분리해 반박 가능하게 하는 것이다. **FTS를 쓰는 DB는 동기화 불가능**이라는 일반화도 실패다. 함수·tokenizer·컴파일 옵션마다 새 제품을 등록할 필요는 없다.

## C06 — 로그를 재생한다는 공통점이 같은 메커니즘인가

**고정 사실/미확인:** Redis AOF는 상태 복원용이며 rewrite로 명령 목록이 줄어든다. SQLite changeset도 중간 변경을 합칠 수 있다. Event Sourcing 문서는 업무 사건 보존을 설명한다. SQLite/PostgreSQL WAL과 PostgreSQL logical decoding은 서로 다른 층·조건을 가진다(M02/M03/M05–M08). 상호 이식은 시험하지 않았다.

| 안 | 같은 사실을 남긴 실제 표현 예 |
| --- | --- |
| A | `AOF(M07) — 상태 복원·rewrite. Event Sourcing(M08) — 업무 사건 보존 패턴. replay 유사성만으로 감사 이력 대체 가능 판단 금지.` |
| B | `Redis AOF 기능, Event Sourcing 패턴 문서를 따로 참조 / 관계 메모: 기록으로 상태를 재구성한다는 비교 관점 / 기능 동일성 없음.` |
| C | `공통점=연구자 유사성 주장; 한계=중간 사건 보존 여부. 각 구현의 사실은 각 원문에 연결. 다른 제품으로 적용 성공=미확인.` |

**답/실패/비용:** A는 아이디어를 다시 찾기에 충분하다. B는 구현과 패턴 문서를 혼동하지 않게 한다. C는 여러 구현에 반복 적용할 유사성·제약 판단을 추적하기 좋다. 그러나 메커니즘의 이름을 새로 붙이는 순간 정답이 생기는 것은 아니다. 두 대상 사이의 비교 문장으로 시작해도 되며, 전 세계 메커니즘 분류체계를 먼저 만들 이유는 없다.

## C07 — 소개·상태 안내·코드가 다르면 무엇을 고치는가

**고정 사실/미확인:** OSSInsight 소개는 Explorer를 설명한다(R09). 열람한 Explorer 페이지는 maintenance 안내다(R11). 고정 ask 코드에는 503 분기가 있다(R10). 실제 API 응답과 배포 SHA 일치는 미확인이다.

| 안 | 같은 사실을 남긴 실제 표현 예 |
| --- | --- |
| A | `Explorer: 소개 R09; 2026-11-19 안내 R11=maintenance; 고정 코드 R10=503 분기. 실제 POST·배포 일치 미확인.` |
| B | `OSSInsight 안의 Explorer에 세 출처 역할을 연결. 다른 분석 기능의 상태는 별개.` |
| C | `문서상 기능 / 페이지의 상태 안내 / 특정 코드 경로를 별도 관측 문장으로 저장. 어느 것이 어느 시점·범위를 말하는지 유지.` |

**답/실패/비용:** A도 정확히 쓸 수 있다. B가 출처를 단순 목록으로만 가지면 “이 코드가 현재 서비스인가?”에 답할 수 없다. C도 배포 연결 근거가 없으면 보류해야 한다. 어느 안에서도 이 세 자료를 합쳐 “실제 API 테스트 통과/실패” 또는 “제품 전체 종료”로 만들 수 없다. 근거가 세 개여도 동일 작성원·배포 관계가 밝혀지지 않았으므로 독립 검증 횟수로 세지 않는다.

## C08 — 다른 분야의 반례: 여러 식별자와 여러 실체를 혼동하지 않기

**고정 사실/미확인:** DataCite는 동일 연구 결과의 복수 DOI 연결 예를 제공한다(R12). BIBFRAME는 작품·출판 형태·사본을 구별한다(R04). 예시 DOI의 실제 파일 동일성과 특정 도서 소장품은 자체 검사하지 않았다.

| 안 | 같은 사실을 남긴 실제 표현 예 |
| --- | --- |
| A | `R12 — 같은 결과에 DOI 둘이 있을 수 있음. R04 — 작품과 판본·사본의 속성 범위는 다름. 소프트웨어에 기계 대응하지 않음.` |
| B | `무엇의 식별자인지 대상 범위를 먼저 적고 복수 접근 경로를 연결. 다른 판본/사본을 단순 별칭으로 합치지 않음.` |
| C | `동일 판단을 주장으로 보존하고 발행자의 예시와 자체 확인을 구별. 판본/사본 차이 주장은 각 층에만 적용.` |

**답/실패/비용:** 이 사례는 “주소가 다르면 다름”과 “제목이 같으면 같음”을 동시에 반박한다. 제품군과 설치본을 모두 표현할 수 있다는 이유로 둘 다 먼저 만드는 것도 비용이다. 실제 설치본을 찾는 질문이 없다면 사본 수준은 저장하지 않는 안을 유지한다.

## C09 — 같은 SQLite 문서가 다르게 설명하면 언제 더 나누지 않는가

**고정 사실/미확인:** atomic commit 문서는 rollback mode 범위를 밝히며 WAL에서는 다르게 수행된다고 말한다(M10/M03). 실제 모드·파일시스템은 미확인이다.

| 안 | 같은 사실을 남긴 실제 표현 예 |
| --- | --- |
| A | `SQLite atomic commit: rollback 설명 M10; WAL 설명 M03. 적용 모드를 확인해야 비교 가능.` |
| B | `SQLite 하나 / rollback·WAL 범위별 문서 메모. 새 완성품 ID 생성 없음.` |
| C | `모드별 동작 문장을 따로 연결 가능. 다만 한 번의 모드 선택 설명이라면 별도 주장 ID까지 필요 없음.` |

**답/실패/비용:** 이 예에서는 B의 모드 메모만으로 가짜 모순과 제품 과분할을 막을 수 있다. C를 모든 문장에 강제하는 초기 결론에 대한 반례다. 더 복잡한 구조가 필요하다는 판단은 실제 반복 정정·공동 사용·자동 질의 요구가 생긴 뒤에 한다.
