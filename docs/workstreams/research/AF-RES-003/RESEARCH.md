## 1. 설계자가 먼저 읽을 판단

**주소·대상·주장을 구별하는 것이 필요하지만, 셋을 언제나 독립 객체로 저장할 필요는 없다.** 같은 제품의 문서 두 개는 하나의 제품에 연결할 수 있고, 같은 이름의 포크 둘은 구별해야 한다. 같은 제품의 기능도 배포·모드·버전에 따라 적용 범위가 다르다. 추상적인 원리가 닮았다는 비교는 실제 구현이 동일하다는 판단과 분리한다. 이 구분은 짧은 메모 안에서도 보존할 수 있다.

이번 표본에서는 다음 세 안을 조건부로 유지한다.

| 보존 원리 | 적합한 질문 | 필요한 대가 | 이 안만으로 해결되지 않는 것 |
| --- | --- | --- | --- |
| A. 링크와 짧은 문맥 있는 설명 | 나중에 원문을 다시 읽을 수 있는가 | 사람이 설명을 읽고 동일성·범위를 복원 | 다수 기록의 정정·반례 전파·자동 집계 |
| B. 대상과 출처의 역할 분리 + 필요한 범위 주석 | repo/docs가 중복 제품인가, 제품 안의 어느 부분인가 | 대상 귀속·별칭·계보 관리 | 링크별로 어느 문장을 지지하는지 불명확하면 상충 이유를 못 찾음 |
| C. 주장과 근거·범위의 연결 | 어느 조건에서 무슨 말을 믿고 비교했으며 무엇이 반박됐나 | 주장 분해·주어/범위 판정·정정 연결의 작성 비용 | 원문 자체의 정확성, 현재 실행, 전이 성공의 자동 보증 |

**초기 비교 제안:** A를 원문 재방문용으로 허용하고, 중복 귀속이 실제 문제가 된 대상에 B를, 독립 정정·상충·재사용이 필요한 문장에만 C를 적용하는 조합을 검토한다. A→B→C를 모든 자료가 거쳐야 하는 성숙 단계로 규정하지 않는다. 단순한 범위 주석으로 해결되는 C02/C09와 별도 판단 추적이 유용한 C05/C07을 함께 보라([사례](CASES.md)).

## 3. 같은 대상이라는 말의 범위를 먼저 고정한다

### 3.1 네 가지 질문을 한 판정으로 합치지 않는다

| 질문 | 관측할 것 | 허용되는 좁은 판단 | 잘못 확장한 판단 |
| --- | --- | --- | --- |
| 같은 접근 경로인가 | 원래 주소, 도착 주소, 주소 문법·관측 시점 | 링크 중복 후보 | 주소가 같으므로 모든 시점·기능이 같음 |
| 같은 것을 설명하는가 | 공식 귀속·프로젝트 이름 이력·대상 범위 | 여러 출처가 동일 제품/기능을 설명함 | 문서 자체와 제품이 같은 객체임 |
| 같은 구체 산출물인가 | 고정 버전·파일/패키지 좌표·필요한 경우 내용 식별 | 그 산출물 범위의 동일성 | 코드가 같으므로 운영 주체·서비스 조건까지 같음 |
| 목적상 서로 대체/참고 가능한가 | 요구조건과 구현·배포·보존 의미 | 특정 질문에 한정한 관련성/전이 가설 | 유사함을 전역 동일성·호환성으로 사용 |

URI의 문법적 비교와 제품 동일성은 질문이 다르다(R01). 패키지 좌표(R07), 내용과 문맥을 구별하는 SWHID(R08), 서지의 추상 작품/사본(R04)은 각각 다른 층의 식별 문제를 다룬다. 이 차이를 한 전역 canonical URL로 해결하려 하지 않는다.

### 3.2 최소 판정은 같음·관련됨·보류

- **같음:** “이 두 기록이 가리키는 것은 무엇이며 어느 범위에서 같은가”와 귀속 근거를 적는다. 예: Supabase 내부 옛 이름과 새 이름의 프로젝트 계보(I08). 그 판단을 모든 패키지 버전 호환성에 적용하지 않는다.
- **관련됨:** 부분, 포크, 후계, 설명, 구현, 유사 원리처럼 관계를 좁게 밝힌다. 같은 제품군으로 모아 보여도 구성원의 속성을 자동 복사하지 않는다.
- **보류:** 동일성·다름을 가를 근거가 부족하다. 보류 이유와 다음 확인을 남긴다. OpenAlternative의 이전 앱과 Dirstarter의 코드 동일성이 이 경우다(I09).

이 세 상태는 외부 세계의 완전한 온톨로지가 아니라 연구 판정의 최소 표현이다. 관계가 확인되지 않은 두 항목을 억지로 `related`에 넣지 않는다. 같은 이름만 있고 귀속 근거가 없으면 연결 가설조차 미확인이다.

`similar-to`, `fork-of`, `successor-of`, `part-of`를 통과하며 동일성 병합을 전파하지 않는다. 진짜 동등성 판단도 비교한 대상 범위가 일치해야 연쇄 추론을 검토할 수 있다. SKOS의 `exactMatch`와 `closeMatch`는 추론 성질이 다르고, `owl:sameAs`와도 같지 않다(R02). 따라서 “모든 관계는 비추이적”이라는 반대 방향의 단순 규칙도 부적절하다.

## 4. 실제 사례가 요구한 경계와 반대 사례

### 4.1 제품군을 묶어도 배포 범위는 남긴다

Supabase의 repo·문서·hosted 경로는 같은 제품군에 관한 여러 자료다. 그러나 self-hosted의 managed 기능 제외는 명시되어 있다(I04–I06, C02). 한 제품 항목 아래 배포 주석을 두는 안과 별도 선택 대상을 두는 안을 모두 유지한다. 배포를 독립 비교·선택하는 사용자 질문이 없으면 별도 제품 객체가 늘어날 필요는 없다.

### 4.2 포크·이름 변경·후계는 다른 연결이다

Netlify GoTrue→Supabase는 fork이고, Supabase 내부 gotrue→auth는 이름 변경이다(I07–I08). Paperless 계보에서는 후계 안내와 함께 실제 기능 차이가 문서화되어 있다(I01–I03). “함께 찾아야 한다”와 “같은 주장을 공유한다”를 분리한다. 원저장소가 archived라고 모든 구형 설치가 중지됐다고 판단하지 않는다. 후계라는 작성자 설명도 실제 이전 성공 근거와는 다르다.

### 4.3 기능은 독립 제품이나 저장소가 없어도 참조할 수 있다

FTS5와 session은 SQLite 안의 기능이지만 각각의 제약이 조합 판단에 영향을 준다(M01/M02, C05). 별도 기능 참조는 유용하다. 그러나 모드·빌드 옵션 차이는 범위 메모로 충분한 경우가 있고(M03/M04/M10, C09), 모든 함수·옵션·문서 절에 영구 대상 ID를 부여하면 질문보다 구조가 커진다.

**분리 조건 제안:** 해당 부분에 대해 독립적으로 고르기, 교체하기, 호환성을 묻기, 반례로 정정하기 중 실제 질문이 있고 상위 항목 설명만으로 그 범위를 유지하기 어렵다면 별도 참조를 만든다. 단지 명사·제목·URL이 있다는 이유는 분리 근거로 부족하다. 처음에는 “SQLite 안의 FTS5”라는 경로가 안정적으로 다시 가리켜지면 충분하며, 반복 연결이 생기기 전에는 전역 ID를 강제하지 않는다.

### 4.4 유사 메커니즘은 비교자가 만든 주장일 수 있다

SQLite/PostgreSQL WAL, PostgreSQL logical decoding, Redis AOF, Event Sourcing에는 기록과 재구성이라는 비교 지점이 있다. 그러나 보존 단위와 조건이 다르다(M02/M03/M05–M08). 특히 순효과 changeset과 rewrite되는 AOF에서 모든 중간 업무 사건의 보존을 추론할 수 없다(C06).

최소 형태는 `대상 A의 구체 동작 ↔ 대상 B의 구체 동작 / 닮은 점 / 깨지는 조건 / 각 근거 / 연구자 해석`이다. 반복 비교가 누적되어 정의·반례를 따로 관리할 필요가 생기면 공통 원리에 별도 참조를 부여한다. 보편적인 메커니즘 이름표를 먼저 만들지 않는다. 명명 자체가 적용 성공의 증거가 되지 않는다.

### 4.5 대상은 유지하면서 설명의 시점·근거를 정정할 수 있다

OpenAlternative의 주소는 유지되면서 README가 설명하는 현재 역할이 달라졌다(I09, C04). OSSInsight는 제품 소개, Explorer 상태 안내, 특정 코드 경로를 서로 다른 범위로 읽어야 한다(R09–R11, C07). 이는 URL마다 새 제품을 만드는 안과 최신 설명으로 과거 판단을 덮는 안 둘 다의 반례다.

## 5. 무엇을 더 저장할지: 필드보다 막아야 할 실패

아래는 **보존해야 할 의미**다. 컬럼·테이블·타입·필수 API 키 목록이 아니다. A에서는 문장으로, B에서는 대상 주석으로, C에서는 참조 가능한 판단 단위로 남길 수 있다.

| 추가할 의미 | 없을 때 생기는 구체 실패 | 최소 표현 | 언제 더 구조화할까 |
| --- | --- | --- | --- |
| 원래 주소와 원문 위치 | 주소 정규화 중 근거 절을 잃음 | URL + 절/파일·symbol | 동일 자료의 부분을 반복 인용할 때 |
| 설명의 주어·수식어·부정 범위 | self-hosted에 managed 기능을 옮기거나 “managed backup 미제공”을 “backup 없음”으로 축약 | “Supabase self-hosted에서 managed …; 사용자 책임은 …” | 배포/기능별 정정·비교가 반복될 때 |
| 확인 시점과 원문 버전 | 현재 안내와 과거 약속을 한 시점으로 읽음 | 확인일 + SHA/문서판; 없으면 live | 같은 주장이 시간에 따라 달라질 때 |
| 원문이 말한 시점·버전 | 2023 v2 약속을 모든 미래 버전에 확대 | “발표 당시 v2 지원 기간” | 한 대상의 여러 시점 주장을 함께 쓸 때 |
| 확인한 내용과 미확인 | 소스 분기를 실제 운영응답으로 승격 | D1/D2 + 확인 내용 + 미실시 | 문서/코드/실행 근거가 함께 들어올 때 |
| 관계 판단과 이유 | rename/fork/후계를 한 병합으로 처리 | 관계 한 구절 + 출처 + 판단자 | 병합/분리의 되돌리기·이견 관리 필요 시 |
| 해석·가설의 주체 | 유사 원리 설명을 제공자의 구현 사실로 전파 | “연구자 비교; 적용 미검증” | 여러 비교자가 재사용·반박할 때 |
| 이전 참조와 정정 연결 | 분리 뒤 과거 근거가 고아가 되거나 엉뚱한 대상에 붙음 | 옛 참조→새 판단, 이유·미귀속 목록 | 실제 병합/분리/대체가 발생할 때 |

짧은 최소 예:

> 대상은 OSSInsight의 Explorer. About은 기능을 설명한다(R09, D1). 2026-11-19 UTC에 읽은 공개 페이지는 maintenance를 안내한다(R11, D1). 고정 SHA의 ask 함수에 조기 503 경로가 있다(R10, D2). 배포 SHA와 실제 POST 결과는 미확인. 원문 위치는 각 원장 참조.

이 한 문단에는 이미 대상·범위·근거·미확인이 있다. 저장 객체가 세 개인지 한 개인지는 아직 정하지 않아도 된다. 중요한 문장을 독립 정정할 수 있어야 하는 시점에만 쪼갠다.

최신 확인으로 과거 버전에서 유효했던 설명까지 지우지 않는다. **관측 시점**과 **주장의 적용 시점**이 다를 수 있다는 점을 보존하면 되며, 이 구분만으로 모든 문장에 별도 영구 ID를 요구하지는 않는다.

### 원문을 보존하지 않는 최소안의 정확한 한계

고정 코드에는 commit/path/symbol을, 문서에는 원문 URL·절·문서 버전 또는 확인일을 남긴다. 정규화된 URL을 만들더라도 original URL과 fragment를 보존한다. 텍스트 위치만으로는 수정에 취약하다(R06).

**확인일은 당시 문서를 복원하는 수단이 아니다.** live 원문이 바뀌면 짧은 자체 요약과 확인 위치만 남고 전체 내용은 복원되지 않을 수 있다. 정밀한 재현이 필수인 주장은 불변 출처·허용된 snapshot 등 추가 보존 여부를 그때 결정한다. 이번에는 원문을 통째로 복제하지 않았고, 크롤러·갱신주기·스냅샷 저장 정책은 결정하지 않았다.

## 6. 저장 대안의 공정한 비교와 조합

### A를 유지할 이유

소수 자료를 사람이 다시 읽고 한 번 비교한다면, 충분히 구체적인 짧은 메모가 목적을 달성한다(C01/C02/C09). A가 조건을 표현할 수 없다고 정의한 뒤 C가 승리한다고 결론내리는 비교는 무효다. A의 위험은 반복된 설명이 서로 달라지거나 정정이 누락되는 관리 비용이다. 이 비용을 실제로 측정하지 않았으므로 대규모 운용의 성능 주장으로 바꾸지 않는다.

### B가 막는 오류와 남기는 선택

“같은 제품을 설명하는 여러 링크”와 “별개의 포크”를 구별하는 데 직접 도움이 된다(C01/C03). 서비스·기능·모드는 일단 범위 주석으로 둘 수 있다. 항상 제품·기능·메커니즘을 별도 종류의 객체로 만들 필요는 없다. 이 안의 경계는 주석이 길어지고 여러 사람이 같은 문장을 독립적으로 고쳐야 할 때다.

### C를 필요한 곳에만 적용할 이유

한 대상의 상반된 자료, 다른 대상에 대한 원리 전이, 병합 판정 자체를 반박할 필요가 생기면 유용하다(C05/C06/C07). 근거를 “주장에 연결”해야지 문서 링크가 있다는 이유만으로 그 문서의 모든 기능을 가져오면 안 된다. 주장 분해도 오판할 수 있다. 제약을 별도 조각으로 떼어 원래 문장과의 연결을 잃으면 오히려 위험하다.

C02는 그 직접적인 반례다. self-hosted에서 **managed backups**를 제공하지 않는다는 설명을 분해하며 `backups 없음`으로 만들면, 같은 원문의 사용자 백업·재해복구 책임 설명을 잃는다(I05). 근거를 연결한 짧은 주장도 부정 범위·수식어·운영 주체를 보존하지 않으면 거짓이 될 수 있다. C의 이득은 올바른 의미 보존을 전제로 한 추적 가능성이지 자동 정확성 향상이 아니다.

문서 한 개의 복사·재인용을 여러 링크로 저장해도 독립 근거가 늘어난 것은 아니다. 원래 출처·파생 경로가 불명확하면 독립성은 unknown으로 남긴다(R05). D1/D2/D3는 여기서 증거의 **관측 방식**을 뜻하며 사실의 전역 신뢰 점수나 추천 점수가 아니다.

### 확장할 조건과 멈출 조건

| 관측되는 관리 문제 | 확장 후보 | 멈춰도 되는 조건 |
| --- | --- | --- |
| repo/docs를 두 제품으로 반복 등록 | B의 대상 귀속·링크 역할 | 한 메모에서 안정적으로 관리됨 |
| 여러 배포의 기능 설명이 섞임 | 먼저 B의 범위 주석; 반복 정정 때 해당 문장만 C | 배포별 한 문장으로 질문 해결 |
| 반례가 생겼는데 어느 요약을 고칠지 모름 | 주장-근거 연결과 정정 이력 | 모든 독자가 동일 소수 원문을 직접 대조함 |
| 비슷한 원리가 여러 제품에서 반복 인용 | 공통 정의·범위·반례를 가진 메커니즘 참조 | 한두 대상의 비교 문장이 충분함 |
| 합치기/나누기로 과거 링크가 엉킴 | 유지되는 기록 참조와 변경 연결 | 아직 공유·역참조·변경이 없음 |
| 원문 변경 때문에 핵심 판단을 재현 못함 | 해당 근거의 불변 위치·허용된 추가 보존 검토 | 정확한 과거 재현을 요구하지 않는 재방문 메모 |

특정 후보 수·링크 수를 임계값으로 정하지 않는다. 데이터의 크기보다 실제로 실패한 질문이 확장 이유가 되어야 한다. 판단자 간 일치도·작성 시간·잘못된 병합률을 측정해야 이 조건의 실효성을 평가할 수 있으며, 이번 표본은 그 성능을 입증하지 않는다.

## 7. 병합·분리·대체에서 보존할 연결

여기서 **기록 병합**은 카탈로그 중복을 정리하는 편집 행위이고, **포크·후계·이름 변경**은 외부 프로젝트에 관한 주장이다. 두 층을 섞지 않는다. 아래 규칙은 이 사례들을 보존하기 위한 제안이다.

| 작업 | 보존할 것 | 자동으로 하면 안 되는 것 | 사례 |
| --- | --- | --- | --- |
| 중복 기록 병합 | 옛 참조·원래 URL·각 근거·동일 판단 이유·시점·범위·반대 의견 | 모든 속성의 무조건 합집합; 과거 주어를 새 대상으로 일괄 치환 | C01/C03 |
| 넓은 기록 분리 | 이전 기록 참조, 나뉜 대상들의 관계, 주장별 귀속, 아직 배분 못한 근거 | 주장을 양쪽에 복제해 모두 확인된 것으로 만듦 | C02/C04/C05 |
| 이름 변경 | 옛 이름·사용 맥락·이름 변경 근거·현재 표시명 | 이름이 같은 다른 조직/포크까지 병합 | C03 |
| 후계·대체 추가 | 방향, 대체 범위·조건, 이전 대상과 과거 판단·원문 | 옛 대상 삭제; 모든 버전·기능·설치의 종료/호환 추론 | C03, I11 |
| 출처 주소 변경 | 발견 URL·새 도착 URL·확인 시점·당시 내용의 위치 | 모든 인용을 최신 URL로 덮어쓰기 | I10, R01 |
| 잘못된 판단 정정 | 기존 판단과 새 판단, 정정 이유·근거·시점 | 역사를 지우거나 출처가 말하지 않은 결론으로 근거 자체 수정 | C07 |

예를 들어 넓은 `GoTrue` 기록에 출처가 섞였다면 Supabase와 Netlify로 나누고, 각 근거를 확실히 귀속할 수 있는 것만 옮긴다. 어느 쪽인지 모르는 예전 메모는 **미귀속**으로 남긴다. 옛 ID는 분리 이력과 두 후보로 찾아갈 수 있어야 하며 한쪽으로 조용히 redirect하지 않는다. 반대로 문서 위치만 두 개인 ngx는 출처 둘을 유지한 채 대상 하나에 연결해 과분할을 피할 수 있다.

불확실한 동일성 판단은 원본 항목을 지우지 않는 검토 상태로 남기는 안이 안전하다. 확정 병합 뒤 오판이 발견돼도 이전 근거와 연결을 복원할 수 있어야 한다. 이 원칙은 구현 방식이나 사건 저장소를 채택했다는 뜻이 아니다.

잔여 이견은 기능을 별도 대상으로 승격하는 시점과 C의 작성 비용이 얼마나 빨리 정당화되는가다. “독립적으로 고르거나 정정할 질문”이라는 기준은 유망하지만, 실제 여러 작성자의 일치도와 비용은 측정하지 않았다. 조기 분해에 신중한 안과 처음부터 재사용할 핵심 주장만 분리하는 안을 모두 설계자에게 남긴다.

## 9. 답을 바꿀 최소 추가 확인과 후속 첫 행동

1. **B의 범위 주석이면 충분한가:** C02와 C09의 메모를 다른 설계자가 읽고 정확한 주어·조건을 복원하는지 확인한다. 반복 정정이 없다면 C 확대의 필요성은 약해진다.
2. **C의 이력이 실제로 필요한가:** C07에 새 상태 안내 한 개가 추가되었다고 가정하고 기존 판단 중 무엇만 바뀌는지 수작업으로 표시한다. 이때 A/B도 같은 정보를 보존하게 해 공정하게 비교한다. 이는 제안된 후속 관찰이지 이번에 수행한 사용자 시험이 아니다.
3. **오병합을 되돌릴 수 있는가:** C03의 넓은 GoTrue 기록을 분리하면서 미귀속 메모가 남는지 확인한다. 자동 병합의 정확률을 이 사례로 일반화하지 않는다.
4. **전이 판단이 바뀌는가:** C05의 실제 조합 또는 C06의 감사 이력 대체를 채택하려면 대상 버전·입력·보존 요구를 고정한 별도 실행 증거가 필요하다. 이번 저장 연구의 완료를 그 실행에 의존시키지 않는다.

실행 검사를 요청받지 않은 제품을 설치·호출하지 않았다. 이번 결과의 문서·계약·경로 검사는 `HANDOFF.md`와 검사 증거에 기록한다. 통합 담당은 **먼저 이 문서 §1, CASES의 C02/C05/C07/C09, REVIEW의 잔여 이견을 읽고, 다음 설계 과제에서 어떤 관리 문제를 우선 해결할지 정한다.** 그 선택 전에는 테이블 수·DB 스택·최종 API·검색순위·URL 갱신주기·수집기를 확정하지 않는다.
