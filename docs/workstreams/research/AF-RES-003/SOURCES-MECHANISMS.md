## 1. 직접 읽은 자료

### M01 · SQLite FTS5

- 주소: <https://www.sqlite.org/fts5.html>
- 위치·버전: 동적 공식 문서. `1. Overview of FTS5`, `2.1–2.2 Compiling and Using FTS5`, `4.4.3–4.4.4 External Content Tables / Pitfalls`, `Appendix A: Comparison with FTS3/4 / Application Porting Guide`. 고정 커밋 미확보. 관측 위치: 열람본 186–252, 579–677, 1916–1968행. 외부 콘텐츠 절은 독립 검토 지적 후 **2026-11-19T15:43:01Z**에 추가 확인했다.
- 확인: FTS5는 SQLite virtual table 모듈이다. SQLite 소스 트리 안에 있으며 정적 포함과 loadable extension 구성이 가능하다. FTS3/4에서 이동할 때 CREATE 문·쿼리·보조 함수 변경이 필요하다고 설명한다. 외부 콘텐츠 구성은 원본 표와 검색 색인의 일관성을 사용자가 유지해야 하며, trigger 예제와 기존 행의 색인 rebuild를 설명한다.
- 한계: 사용자의 SQLite 빌드에 FTS5가 포함되었는지, 확장 로딩이 허용되는지, 기존 쿼리가 호환되는지는 확인하지 않았다. 이식 안내를 모든 입력의 자동 호환성으로 읽지 않는다.
- 식별에 주는 근거: 저장소가 따로 있어야만 독립 기능으로 다룰 수 있는 것은 아니다. `FTS5 설명 문서`와 `FTS5 기능`도 같은 종류의 대상이 아니다.

### M02 · SQLite session extension

- 주소: <https://www.sqlite.org/sessionintro.html>
- 위치·버전: `1. Introduction`, `1.2 Obtaining`, `1.3 Limitations`, `2.3 Changeset Construction`. 페이지 표시 갱신일 2025-05-31 13:08:22Z; 고정 커밋 미확보. 열람본 49–124행.
- 확인: 호환되는 스키마·시작 데이터에 changeset을 적용하는 기능이다. 활성화 빌드 옵션이 있고, virtual table 변경을 수집하지 않는다. 같은 행의 반복 수정을 합치며 한 세션 안의 INSERT 뒤 DELETE는 변화로 남기지 않는다.
- 한계: 실제 빌드·동기화·충돌 처리·데이터 이식을 시험하지 않았다. changeset을 모든 중간 사건을 보존하는 감사 기록으로 해석할 수 없다.
- 식별에 주는 근거: SQLite라는 상위 이름에 기능을 모두 합치면 적용 제외 조건이 사라진다. 기능 이름과 별개로 포착 대상과 보존 의미를 남길 필요가 있다.

### M03 · SQLite WAL

- 주소: <https://www.sqlite.org/wal.html>
- 위치·버전: `1. Overview`, `2. How WAL Works`, `2.1 Checkpointing`. 동적 공식 문서, 고정 커밋 미확보. 열람본 61–92행.
- 확인: WAL은 rollback journal과 다른 모드이며 변경을 별도 WAL에 추가하고 나중에 checkpoint한다. 일반 WAL 사용에서 모든 프로세스가 같은 호스트에 있어야 하고 네트워크 파일시스템을 지원하지 않는다고 설명한다.
- 한계: 문서상 모드의 성질이다. 특정 플랫폼·빌드·파일시스템에서 동시성·복구를 실행하지 않았다. 성능 수치는 이 조사에서 재인용하지 않는다.
- 식별에 주는 근거: `WAL`이라는 이름만으로 다른 DB의 WAL과 하나의 재사용 부품으로 합칠 수 없다. 구현 대상과 운용 조건이 필요하다.

### M04 · SQLite compile-time options

- 주소: <https://www.sqlite.org/compile.html>
- 위치·버전: `1. Overview`, `SQLITE_ENABLE_FTS4`, `SQLITE_ENABLE_FTS5`, `SQLITE_ENABLE_JSON1`. 동적 문서; 고정 커밋 미확보. 열람본 47–52, 444–467행.
- 확인: 컴파일 옵션으로 기능을 포함하거나 제외할 수 있다. FTS4/FTS5 활성화 옵션이 별개다. JSON1 활성화 옵션은 3.38.0 이후에는 no-op이며 JSON 기능을 빼는 다른 옵션을 안내한다.
- 한계: 소스에 옵션이 있다는 사실은 배포된 바이너리의 기능 목록을 증명하지 않는다. 현재 환경의 `compile_options`도 실행하지 않았다.
- 식별에 주는 근거: 제품 이름이 같아도 버전·빌드 범위가 다르면 기능 주장의 진릿값이 달라질 수 있다. 옵션마다 새 제품 ID를 만드는 방식도 과분할이다.

### M05 · PostgreSQL 18 WAL

- 주소: <https://www.postgresql.org/docs/18/wal-intro.html>
- 위치·버전: PostgreSQL **18**, `28.3 Write-Ahead Logging (WAL)`, 열람본 18–27행. 메이저 버전 경로를 고정했지만 문서 패치 개정의 불변 스냅샷은 아니다.
- 확인: 데이터 파일 변경보다 먼저 WAL 레코드를 영구 저장하며, crash 후 REDO와 WAL 아카이브를 이용한 시점 복구를 설명한다.
- 한계: 해당 기능의 설정·보관 범위·백업을 시험하지 않았다. SQLite WAL 파일과 형식·이식·운영 계약이 같다는 근거는 제공하지 않는다.
- 식별에 주는 근거: 동일한 원리 이름을 가진 구현들의 공통점은 관련성 주장이다. 그 이름이 파일 호환성이나 대체 가능성을 보증하지 않는다.

### M06 · PostgreSQL 18 logical decoding

- 주소: <https://www.postgresql.org/docs/18/logicaldecoding-explanation.html>
- 위치·버전: PostgreSQL **18**, `47.2.1 Logical Decoding`, `47.2.2 Replication Slots`, 열람본 26–49행.
- 확인: 저장 수준 WAL을 응용에서 이해할 형태로 디코딩한다. 논리 슬롯은 정상 운영과 crash 복구에서 전달 성질이 다르며, 재시작 뒤 일부 변경이 다시 전달될 수 있어 소비자가 중복 처리를 고려해야 한다.
- 한계: 특정 output plugin·소비자·장애 복구는 실행하지 않았다. 문서의 정상 동작 조건을 모든 상황의 exactly-once 보장으로 승격하지 않는다.
- 식별에 주는 근거: WAL과 logical decoding은 같은 제품 안에서 연결된 다른 역할이다. 기능·하위 원리·소비 계약을 한 줄 요약으로 합치면 조건을 놓친다.

### M07 · Redis persistence / AOF

- 주소: <https://redis.io/docs/latest/operate/oss_and_stack/management/persistence/>
- 위치·버전: Redis Open Source의 동적 `latest` 문서. `Persistence`, `Append-only file`, `Log rewriting`, `How durable is the append only file?`, 열람본 95–99, 156–181행. 고정 커밋 미확보.
- 확인: AOF는 쓰기 명령을 기록해 상태를 복원한다. rewrite는 현재 상태를 재구성하는 데 필요한 명령으로 줄인다. Redis 7.0 이후 multipart AOF와 설정별 fsync 차이를 설명한다.
- 한계: 특정 버전·설정·디스크에서 내구성을 측정하지 않았다. 오래된 문서의 단일 파일 설명을 모든 버전에 적용하지 않는다.
- 식별에 주는 근거: append-only라는 이름만으로 전체 업무 사건의 영구 보존을 결론내릴 수 없다. 현재 상태 복구와 사건 이력 보존을 구별해야 한다.

### M08 · Azure Architecture Center Event Sourcing

- 주소: <https://learn.microsoft.com/en-us/azure/architecture/patterns/event-sourcing>
- 위치·버전: 동적 공식 패턴 문서. `Context and problem`, `Solution`, `When to use this pattern`; 열람본 31–49, 130–155행. 고정 커밋 미확보. 페이지 앞에 인증 안내 문구가 있었으나 이 절들의 본문은 읽혔다.
- 확인: 업무 사건을 권위 있는 기록으로 보존하고 상태를 재구성하는 패턴이다. 일반 CRUD·수명이 짧은 시제품·주로 정적인 참조 데이터에는 복잡성이 정당화되지 않을 수 있다고 설명한다. 시스템 전체에 일괄 적용할 필요도 없다고 한다.
- 한계: 설계 패턴 설명이며 어떤 제품이 이를 완전히 구현했다는 증거가 아니다. 개별 주문·결제 시스템의 성공 사례를 실행하거나 조사하지 않았다.
- 식별에 주는 근거: 원리 문서는 참고 대상이고 DB의 실제 로그 구현은 별도 대상이다. 유사성을 도출한 문장을 그 구현의 속성으로 자동 전파하지 않는다.

### M09 · SQLite FTS3 and FTS4

- 주소: <https://www.sqlite.org/fts3.html>
- 위치·버전: `1.1 Differences between FTS3 and FTS4`, `1.2 Creating and Destroying FTS Tables`. 동적 문서; 고정 커밋 미확보. 열람본 124–157행.
- 확인: FTS3와 FTS4는 대부분의 코드를 공유하며 인터페이스가 같고, FTS4에는 추가 최적화·옵션이 있다고 설명한다. CREATE VIRTUAL TABLE에서 서로 다른 모듈 이름을 사용한다.
- 한계: 이 문서의 오래된 추천 문구를 현재 모든 신규 프로젝트의 권고로 쓰지 않는다. FTS5까지 동일한 인터페이스라고 확장하지 않는다.
- 식별에 주는 근거: 같은 페이지가 여러 모듈을 설명할 수 있다. 반대로 모듈 이름이 다르다고 완전히 별개의 제품인 것은 아니다.

### M10 · SQLite atomic commit

- 주소: <https://www.sqlite.org/atomiccommit.html>
- 위치·버전: `1. Introduction`, `7.6 Persistent Rollback Journals`; 동적 설명 문서, 고정 커밋 미확보. 열람본 116–122, 382–403행.
- 확인: 본문의 기법은 rollback 모드에만 해당하며 WAL의 atomic commit은 다른 메커니즘이라고 명시한다. rollback journal의 DELETE·PERSIST·TRUNCATE 구성은 커밋 표시 방법이 다르다.
- 한계: 실제 파일시스템에서 atomic commit이나 고장 주입을 시험하지 않았다. 문서의 하드웨어 가정이 사용자의 환경에서 성립하는지도 미확인이다.
- 식별에 주는 근거: 한 제품의 서로 다른 모드 설명을 모으면 모순처럼 보일 수 있다. 모드 범위를 보존하면 제품 ID를 불필요하게 늘리지 않고 구별할 수 있다.

핵심은 모든 기능에 독립 제품 레코드를 만드는 것이 아니다. **별도로 찾거나 비교하는 질문이 있고, 그 기능만의 제약·출처·대체 판단을 붙여야 할 때** 별도 기능 참조가 유용해진다. 이 기준은 연구자의 제안이다. 단일 사용 메모는 `SQLite의 FTS5, 해당 절 링크`로 시작해도 된다.

## 3. 동일 사례에 세 저장 원리를 적용한 대조

세 안은 테이블 수가 아니라 보존하는 의미의 차이다. C도 짧은 한 문단 안에 표현할 수 있다.

- **A · 링크 + 짧은 설명**: 자료로 다시 돌아가는 북마크. 원문 위치·확인일·미확인을 한 줄에 붙일 수 있다.
- **B · 대상과 링크 분리**: 무엇을 가리키는지와 그것을 설명하는 여러 자료를 구별한다. 작은 기능·버전·모드 메모를 대상 아래 둘 수 있다.
- **C · 주장과 근거 분리**: 특정 대상·범위에 관한 문장을 직접 근거에 묶고 연구자의 비교·전이 판단도 별개 문장으로 남긴다.

| 같은 사례/질문 | A로 답하는 것 / 실패 | B로 답하는 것 / 실패 | C로 보존하는 것 / 비용 |
| --- | --- | --- | --- |
| **K-M1** SQLite 검색·변경 전송: “두 기능이 있다는 사실만으로 모든 변경을 전송할 수 있나?” | 두 기능의 읽을 곳은 찾음. 제품 한 줄로 압축하면 포착 제외 조건을 잃기 쉬움 | 기능별 자료를 모음. 같은 상위 제품 아래 있다는 사실만으로 호환을 증명하지는 못함 | 각 기능의 범위와 제외 조건을 특정 절에 연결. 결합 가능성은 별도 판단으로 둠. 메모·검토량 증가 |
| **K-M2** SQLite 원자적 커밋: “문서 두 개의 설명은 모순인가?” | 두 설명을 기억할 수 있으나 요약의 적용 모드를 빠뜨리면 충돌처럼 읽음 | 하나의 제품 아래 WAL/rollback 모드 구별. 충분히 잘 쓴 범위 메모라면 여기까지로 답할 수 있음 | 모드별 주장에 출처 연결. 많은 구현 설명을 상시 대조하지 않는다면 C 전체 분해는 불필요 |
| **K-M3** WAL 공통 원리: “SQLite의 기법을 PostgreSQL과 동일 부품으로 볼 수 있나?” | 공통 키워드와 읽을 곳을 찾음. 동일 파일·동일 적용 조건은 답하지 못함 | 제품별 구현 참조를 분리. 상위 공통 원리는 설명문으로 둬도 됨 | 원리의 공통점과 구현 차이를 주장 두 개로 보존. 실제 이식은 여전히 미검증 |
| **K-M4** AOF와 업무 사건: “재생 가능하니 모든 원인을 되짚을 수 있나?” | replay라는 말의 두 출처를 찾음. 보존 단위 차이를 짧은 문구에서 누락할 위험 | AOF 기능과 패턴 자료를 구분. 유사 관계만으로 감사 가능성을 답할 수 없음 | 현재 상태 복원과 업무 사건 보존을 따로 기록. 적용 가설을 원문 사실로 승격하지 않음 |
| **K-M5** FTS 계열: “문서 항목을 합쳐도 예전 옵션의 호환성을 알 수 있나?” | 모든 페이지를 별도 후보로 세면 중복·과분할. 하나로 압축하면 변형을 놓침 | 제품→기능 계열→모듈 범위를 메모로 유지. 호환성 질문이 없으면 이것으로 충분 | 변경된 계약만 별도 근거 문장으로 둠. 모든 보조 함수에 새 대상 ID를 붙일 필요 없음 |

**A를 실패하도록 일부러 정보 없이 정의하면 안 된다.** 목적이 “나중에 공식 설명을 다시 읽기”뿐이면 좋은 한 줄 북마크가 충분하다. 반대로 A의 설명문에 대상·범위·근거·판정까지 다 넣으면 파일 형식은 A여도 이미 B/C가 보존하려는 의미를 갖는다. 복잡한 저장 구조로의 확장은 형식 취향이 아니라 실제로 실패한 질문으로 정당화해야 한다.

K-M1은 두 기능의 모든 결합이 불가능하다는 주장이 아니다. M01의 4.4.3–4.4.4에는 원본 표의 변경을 trigger로 검색 색인에 반영하는 설명이 있고, trigger 설치만으로 기존 행이 색인되지 않아 rebuild가 필요할 수 있다고 명시한다. 일반 테이블을 동기화하고 색인을 유지·재구축하는 조합은 검토할 수 있지만, session 적용과 결합한 구현·실행은 미실시다. 확인한 것은 **virtual table의 변경을 session이 직접 포착한다고 간주할 수 없다는 경계**다.

## 4. 초기 생각을 깨는 반례

1. **초기 생각: 같은 제품 안의 기능은 하나의 설명으로 충분하다.** K-M1에서는 기능 존재를 합성해 잘못된 조합 결론에 이를 수 있다. 결론 변경: 제품은 묶되 제약의 주어는 해당 기능으로 유지한다. 상위 제품의 기능 집합과 임의 기능 조합의 유효성은 다르다.
2. **초기 생각: 변경 기록을 재생하면 모든 사건을 복원할 수 있다.** M02의 순효과 중심 changeset과 M07의 AOF rewrite가 반례다. 결론 변경: 무엇을 보존하고 무엇을 지우는지를 원리 비교의 필수 문장으로 남긴다. 용어 `log / change / replay`만으로 업무 이력을 뜻한다고 판단하지 않는다.
3. **초기 생각: 같은 원리를 쓰는 제품들은 그 부분이 같은 대상이다.** K-M3은 추상 원리가 닮아도 구현 환경이 다름을 보여준다. 결론 변경: 보편 원리 ID를 만들기 전에, 두 구체 대상을 비교하는 유사성 문장을 근거와 함께 보존할 수 있다. 공통 이름을 생성했다고 재사용 적합성이 검증되지 않는다.
4. **초기 생각: 같은 제품의 문서가 다르게 말하면 한쪽이 오래되었다.** K-M2처럼 모드가 다를 수 있다. 결론 변경: 버전뿐 아니라 설정·모드를 먼저 확인한다. 모든 차이를 새 제품이나 시간 순서의 대체로 바꾸지 않는다.
5. **초기 생각: 더 잘 나누면 항상 정확해진다.** FTS의 함수·토크나이저·모듈을 질문 없이 모두 독립 대상으로 등록하면 링크와 조작 대상만 늘어난다. 결론 변경: 목적에 필요한 경계만 별도 참조로 승격하고, 상세 구문은 원문 위치로 충분하면 남겨둔다.

## 5. 최소 추가 정보와 확장 조건

다음은 최종 필드·API 제안이 아니라, 정보 하나를 더 남길 때 방지하는 오류다.

| 남길 의미 | 막는 구체 실패 | 가벼운 표현으로 충분한 경우 |
| --- | --- | --- |
| 주어가 제품/기능/구체 구현/원리 자료 중 무엇인가 | M07의 실제 기능을 M08의 일반 패턴과 같은 구현으로 병합 | 문장 첫머리에 `Redis의 AOF`라고 쓴다 |
| 적용 버전·모드·빌드 범위 | K-M2의 가짜 모순, M04의 기능 보유 오판 | 조건 한 구절과 unknown 표시 |
| 직접 원문 위치와 확인 시점 | 긴 제품 문서가 모든 주장 전체를 뒷받침한다고 오해 | 절 이름 + URL + 확인일 |
| 관찰 사실과 비교자의 전이 해석 구분 | “원리가 유사함”을 “도입하면 동작함”으로 승격 | `문서 설명` / `연구자 해석` 두 문장 |
| 병합 전 이름·출처·조건 | 모듈 계열을 합치면서 호환성 경계 소실 | 기존 이름을 별칭 이력으로만 남기지 말고 모듈별 조건 유지 |
| 분리 전 공동 부모와 범위 | 한 제품의 여러 기능을 여러 완성품으로 부풀림 | `SQLite 안의 기능`이라는 연결 |
| 대체 범위와 제외 항목 | 새 모듈 등장만으로 옛 모듈의 모든 사용이 교체됐다고 주장 | `이식 안내 존재; 적용 여부 미확인` |

**확장 신호:** 같은 대상을 설명하는 자료가 여러 개여서 수정·반례를 한꺼번에 추적해야 하면 B가 유리하다. 한 제품 안에서도 상반된 주장을 범위별로 구별해야 하거나 다른 제품으로 전이하는 근거가 반복 사용되면 해당 주장에만 C를 적용할 이유가 있다. 소수 북마크·한 번의 수동 읽기에는 별도 주장 ID, 보편 메커니즘 분류표, 사건 이력 저장소가 필요하다는 증거가 없다. M08의 복잡성 경고는 참고 반례이며, 이 연구 저장소에 Event Sourcing을 채택하자는 뜻이 아니다.

## 6. 남은 확인과 다음 행동

- 실제 바이너리의 기능·모드·동작을 확인해야 한다면 별도 실행 과제에서 대상 버전과 입력을 먼저 고정해야 한다. 이번 문서의 D1 판단을 D3로 표시하지 않는다.
- 다음 설계자가 할 최소 행동: K-M1과 K-M4를 먼저 읽고 “대상만 구분한 안으로 충분한가, 범위를 가진 주장까지 따로 있어야 하는가”를 판정한다. 그 뒤 호환성 질문이 없는 K-M5에서 과분할 비용을 반대 방향으로 확인한다.
- 본 파일 작성자는 자기 검토를 했다. 부모가 전달한 독립 검토 지적(FTS 동기화 전체 불가로 확대하지 말 것)에 따라 M01 외부 콘텐츠 절을 추가로 읽고 K-M1의 범위를 제한했다. 전체 묶음의 독립 검토·판정은 부모의 별도 기록을 따른다.
- 조회한 10개 자료 외 검색 결과만을 근거로 추가한 자료는 없다. 정적 문서 열람으로 확인할 수 없는 배포·동작·도입 효용은 전부 미실시다.
