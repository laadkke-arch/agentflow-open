# Q1–Q7 답·근거 및 반증

## Q1. 날짜판 규범 본문 및 fragment (P1/P3)
최초 REC 3판 모두 본문 열람 성공. 2008-12-11 [W01](https://www.w3.org/TR/2008/REC-WCAG20-20081211/) L2–19, L463–467, L138–146; 2018-06-05 [W02](https://www.w3.org/TR/2018/REC-WCAG21-20180605/) L0–26, L1204–1213, L272–301; 2023-10-05 [W03](https://www.w3.org/TR/2023/REC-WCAG22-20231005/) L0–27, L1429–1436, L274–303. 원문 의미(표1)는 날짜판에서 읽었으며 가변 Understanding의 현재 배너를 원문에 덧붙이지 않았다. 2.0/2.1에는 4.1.1 레벨 A의 4개 조건과 규격상 예외, 불완전 태그 설명 노트가 있고, 2.2에는 제거 표시·설명만 있다. 1.1.1은 3판 모두 A로 동등 목적의 대체 텍스트와 Controls/Input, time-based media, test, sensory, CAPTCHA, decoration/formatting/invisible의 여섯 예외 범주. 2.0 Controls 참조는 Guideline 4.1, 2.1/2.2는 SC4.1.2; 동일 요구 핵심이지 모든 문자가 같지는 않다(W04 #2).
2.0 header는 errata 및 latest 참조, 2.1/2.2 header는 발행 당시 Status와 별도 latest를 표시한다. [W10](https://www.w3.org/TR/WCAG20/) 현행 2008-12-11; [W11](https://www.w3.org/TR/WCAG21/) 현행 2025-05-06; [W12](https://www.w3.org/TR/WCAG22/) 현행 2024-12-12. 2.2가 2.0/2.1 자체를 폐지한다는 해석은 W12 L38–39에 반한다. 별칭과 날짜판을 동일 저작으로 중복 산입하지 않았다.
fragment 후보: 2.0 #ensure-compat-parses, #text-equiv-all; 2.1/2.2 #parsing, #non-text-content. 6개 요청으로 문서 본문/절은 확인했으나 웹 텍스트 추출에서 실제 target id/name 또는 scroll target을 반환하지 않아 0/6 DOM 확인. F07 raw 요청 DNS 실패. 2.2 tombstone heading은 관측, target id의 유지 여부는 미확인. 이 차이를 HTTP 성공→anchor 성공으로 바꾸지 않는다. 옛 원문의 후대 편집 경고 배너 여부도 DOM 수준 미확인; 본문 상태와 header errata 링크만 판정했다.

## Q3. 규범력 구별
W01/02/03의 SC가 normative 요구 원문. W01 Status L39–40은 Understanding/Techniques의 비규범적 지위 및 원 REC 변경 불가/errata 또는 후속판 처리 구분. [G07](https://www.w3.org/WAI/standards-guidelines/wcag/faq/) L105–117은 현행 안내. G01/G09/G12는 결정 과정의 1차 기록, 그 자체가 REC는 아니다. F77 절 후단 테스트 기대가 여전히 원래 4.1.1 failure를 가리키므로 현재 적용 실패로 읽지 않는다. 2.0/2.1에서 모든 기술을 동일하게 충족 간주하는 것은 과잉 일반화(HTML/XML 한정). 옛 Understanding 배너와 날짜판 동일성은 별도 실측하지 않았다.

예제는 실제 특정 감사 보고서를 제공받지 않았으므로 합성. 옛 감사: 2018-06-05 W02 #parsing과 v4.7.2 A03을 같이 남기고 당시 duplicate ID 조건 및 해당 검사기의 wcag411/violation 기대를 인용한다. 덧붙이는 현재 설명은 W05 → W09 #parsing (HTML/XML 충족 간주) 또는 W08 #parsing (제거). 날짜판 원 요구 문장(고유 ID 및 완결 태그), 당시 rule tag, 당시 결과 종류를 덮으면 복원할 수 없다. 당시 검사 결과를 소급 거짓/참으로 단정하지 않는다.
새 HTML 수정: 4.1.1 자체의 fail은 현행 HTML/XML에 적용하지 않되 2.2 [4.1.2](https://www.w3.org/TR/2024/REC-WCAG22-20241212/#name-role-value) (W08 L1441ff)와 [1.3.1](https://www.w3.org/TR/2024/REC-WCAG22-20241212/#info-and-relationships), [G08](https://www.w3.org/WAI/WCAG22/Understanding/name-role-value.html) L22–31, G06 L27–29 및 A06/A23을 먼저 확인. 중복 ID 자체와 잘못된 접근성 이름/역할 또는 프로그램적 관계는 구별. 실제 accessible name, 관계 대상, 역할 확인 후 별도 SC로 보고. 단순 중복 p 두 개와 aria-labelledby가 모호한 버튼의 차이는 COUNTEREXAMPLES.md C1/C2 참조. HTML 규격의 author 적합성 문제는 남을 수 있으나 WCAG 4.1.1과 같지 않다. 1.1.1 image-alt는 핵심 계속 유효(C3). 사용자 요구가 역사 인용인지 현재 수정인지 모르면 양쪽을 명시적으로 병기한다.

## Q6. 다른 분야: RFC update/obsoletion/errata (P5)
[rfc-controls.md](rfc-controls.md) 참조. [R01 RFC2119](https://www.rfc-editor.org/info/rfc2119/) 1997-03 status L224–238와 [R02 RFC8174](https://www.rfc-editor.org/info/rfc8174/) 2017-05 §2/status L160ff,258–269: 8174 Updates 2119, 대문자에 BCP14의 특별 의미 한정. 소문자로도 일반 요구 서술 가능. 업데이트는 2119의 정의를 폐기하지 않는다. [R03 RFC2616](https://www.rfc-editor.org/info/rfc2616/) L10123–10131은 7230–7235 6개로 대체; [R04 RFC7231](https://www.rfc-editor.org/info/rfc7231/) L5804–5813은 9110이 후계. [R06 RFC7230](https://www.rfc-editor.org/info/rfc7230/) L55–75은 9110/9112 두 후계. [R05 RFC9110](https://www.rfc-editor.org/info/rfc9110/) L75,126,7483–7486, [R07 RFC9112](https://www.rfc-editor.org/info/rfc9112/) L78–105, [R08 RFC9111](https://www.rfc-editor.org/info/rfc9111/) L72–100: HTTP 의미/HTTP1.1 메시지 구문/캐싱 분리. 따라서 옛 framing/캐시 인용에 단일 9110 자동 대입은 반례. 7232–7235 개별 당시판과 정확한 section별 후계 매핑 미완료; R07 상태의 9931 업데이트 상세 미확인.
[R09 공식 errata 정책](https://www.rfc-editor.org/series/rfc-errata/) L69–80은 reported/verified/held/rejected 구분 및 원 RFC 문서를 수정하지 않는 방식. [R10 EID499](https://www.rfc-editor.org/rfc/inline-errata/rfc2119.html) L0–1,33–51은 Verified 및 Abstract에 NOT RECOMMENDED 누락 정정. inline 렌더는 informative이고 인용 대용 아님. 해당 EID 직접 기록 서버 F05 실패로 보고/검증 날짜 미확인. 단순 관련링크는 update/obsoletes/verified를 뜻하지 않는다. 레코드의 현재 상태와 원 RFC 발행 당시 텍스트는 별도 인용.

## Q7. 자동 교체의 실패 조건과 갱신 정책
(1) 문장 그대로+노트 변경: W02→W09는 본문만 비교하면 정정 놓침. (2) tombstone: W03/W08 번호 생존은 norm 생존 아님. (3) audit history: A03→A06 rule ID 그대로이나 결과 의미 변경. (4) 대조 1.1.1: 핵심 유지, cross-ref만 정정(W04 #2), 모두 obsolete 표시하면 경고 남발. (5) G06 및 A18의 옛 기법 링크 살아 있음; 관련 결함 실제 영향은 검토해야 하며 링크 자체가 새로운 4.1.1 규범으로 되살리지는 않음. (6) R03/R06 분기: 현행 단일 대체 링크 거짓.
업데이트 trigger는 단순 HTTP status가 아니라 (a) edition, (b) SC body fingerprint와 note/status fingerprint, (c) correction/decision relation type 및 scope, (d) 소비자 rule id + tags + enabled + result taxonomy, (e) 사용자 목적. 새로운 판/정오표/판정 변경을 발견하면 기존 ClaimRevision은 immutable, current guidance 새 revision; 사소한 cross-reference는 warning 또는 주석. 실제 raw fragment와 내용을 확인한 경우에만 verified target. 미확인 상태에서는 candidate link + 절명 표시하고 기존 링크 제거 금지.

# 비용·조합 대안
- 경고만: 기존 링크 1 + 상태/시점 메타데이터, 판단 1건. 기존 본문이 핵심 동일하거나 목적이 역사적이면 합리적. 단 새 HTML 수정에는 정확한 다른 SC가 필요.
- 두 링크 병기: old citation 1 + correction/edition 1–2 + applicable SC/rule 1–2; 관계마다 수동 검토 1+. audit/education에 유용, 가장 가역적. 원문 및 새 근거가 상충하면 서로 다른 판의 주장으로 분리.
- 완전 교체: 화면 현행 전용 안내에서만 선택 가능. 실제 저장 시 old provenance를 삭제하지 않음. 목적·버전·scope 확정, 대체 절 검증, 관계 적용 검토가 전제. 분기 후계/법정판 불명/기존 감사 인용/정정 범위 모호 시 금지. 시간·바이트 비용 실측 없음. 경고를 무조건 붙이는 전략과 모든 링크 스냅샷 저장의 운영 비용도 미측정.

데이터 설계 대안: Citation(original_url, intended_version, fragment_candidate, target_observed, captured_at, user_purpose, exact_claim_ref) / Edition(published_at, status, immutable_version_url, alias_url) / ClaimRevision(body, normative_status, scope, note, evidence_source) / ChangeEvent(proposed_at, adopted_at, merged_at, published_at, evidence, relation, applies_to) / ConsumerRule(version, tag, rule_id, enabled, reviewOnFail, expected_result, observed_result, input_ref) 를 분리하거나 단순 원장에 같은 필드만 보관. 222의 identity/alias와 연결할 때 code·Name 불변 사례에서 요구 상태 변화 사례로 확장; 두 경우를 같은 alias merge로 처리하지 않는다. 최종 제품 설계 결정 아님.
