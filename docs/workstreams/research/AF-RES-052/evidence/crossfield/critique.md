# 목적지 관측 전 방법론 검토

검토자: crossfield 보조 판독자. 같은 모델 계열의 별도 문맥 검토이며 사람의 독립 검증은 아니다. 루트가 요청한 SCOPE와 단계① 기록 및 이미 작성된 목록 메타데이터만 읽었다. Python/Markdown 공급자 목적지는 추가 열지 않았다. 선택 요구 4건의 GitHub issue API 본문은 독립적으로 재열람했다. 외부 원문을 새로 열어 후보 기능을 확인하지 않았으며, 아래는 정답 관측 전의 방법론 지적이다.

검토 기준 커밋: 최초 규칙 `842b7099bba6869000abad23f0316d34556bd080`, 요구 동결 `817ebda103ee5926c308ad563a5879c2cf66fc32`. 미커밋 메타데이터 파일을 읽은 내용은 관측 결과가 아닌 초안 검토로 취급한다.

## 1. 가장 큰 위협: 조직·편집 구분을 기능 절로 부르는 것

SCOPE의 기능 절 정의는 실질적으로 모든 본문 제목을 포함한다. 그러나 사용자 지시는 **첫20 기능 절**이다. 현재 Markdown `section-scan.csv`의 첫 절 Official과 루트가 전달한 Python PyPA Projects는 소유/편집 범주다. Official은 parser/generator/CLI/specification을 한데 담고 있어, 하나의 사용자 기능에 해당하는 절로 읽기 어렵다. Plugins도 포괄적인 객체 종류이고 Built on / Built with는 생태계 관계이며 Related lists는 목록 라우팅이다.

이는 결과를 본 뒤 양성을 채우기 위한 변경이라는 증거는 아니다. 규칙이 먼저 커밋됐다는 점은 보호 장치다. 다만 사용자 조건에 대한 **사전 조작적 정의의 범위 차이**이므로 결과에서 숨길 수 없다.

권고하는 보수적 처리:

1. 목적지 열람 전에 각 절을 `functional`, `project-specific`, `ownership/editorial`, `routing`으로 분류한다. 분류 근거는 제목·목록 설명뿐으로 한정한다.
2. 사용자 지시를 엄격하게 읽은 본 분석에서는 ownership/editorial/routing을 기능 절로 간주하지 않는다. 적격 절이 없으면 해당 보강 자리를 **미충원/미확인**으로 유지한다.
3. 현재 봉인한 Official/PyPA Projects 풀은 삭제하지 말고, **모든 편집 절을 허용한 감도·확장 표본**으로 제시한다. 자연층 4자리를 대체하지 않는다.
4. 두 해석에서 보강 모집의 분모와 결과가 어떻게 달라지는지 표시한다. 먼저 고른 풀을 유지하려고 뒤의 기능명·요구를 새로 보태면 안 된다.

판정이 바뀌는 최소 조건은 발행자가 해당 범주를 특정 기능의 선택 목록으로 명시한 원문, 또는 사전에 고정된 기능 절에서 동일 메타데이터 조건을 만족하는 풀이다. 단지 URL이 많다는 사실은 기능 범주임을 입증하지 않는다.

## 2. 실제로 목적지가 선노출된 중복 라우팅 원문

`evidence/markdown/catalog-receipts.json`은 remark 라우팅 README 전문과 예제가 열렸다고 명시한다. 동시에 `pools.csv`의 M-S1-R1 목적지는 `https://github.com/remarkjs/remark`다. 저장소 첫 화면의 README는 위 라우팅 원문과 같은 저작이다. 따라서 R1의 `destination_opened=False`만으로 완전한 목적지 비노출을 표현하면 부정확하다.

권고:

- R1 및 이를 대표로 쓰는 A/B/C에 `prior_exposure=true`, `exposure_reason=routing-source-overlap`, 라우팅 SHA와 읽은 구간을 기록한다.
- 외부 목적지로 이동한 횟수와 내용이 이미 노출되었는지는 별도 필드다. 경로 예산은 사용자의 화면에서 출발해 다시 산정하되, 판독자의 맹검성은 주장하지 않는다.
- 그룹 키는 끝까지 발행 목록의 사전 메타데이터만 사용한다. README의 기능 설명으로 C의 빈 용도·판·역할을 채우지 않는다.
- 미노출 부분집합에 대한 해석과 전체 풀 해석을 구별한다. 이 중복 때문에 전체 연구를 폐기할 필요는 없지만, '모든 목적지를 열기 전에 봉인'이 완전히 성립했다는 완료 주장은 유보한다.

Python의 `objects.inv` 요청은 현재 기록상 모두403이다. 내용 선노출로 세지 않되 `request_attempted`와 `content_exposed`를 분리하면 기록이 명확해진다. 이 현재 stable/latest inventory 요청을 역사적 목적지의 고정 href 복원 성공으로 쓰면 안 된다.

## 3. 표시 필드와 승격 단위

M-S1의 B 배열 1;6은 목록 라벨에 의하면 remark 상류의 반복 링크가 mdast 링크를 앞으로 올리는 **URL 가시성 기회**다. 그러나 rank6은 Abstract syntax tree specification이라고 표기되어 있다. 별개 상류/URL과 독립 실행 구현은 다른 단위이므로, 이것만으로 네 번째 이후 독립 구현이 승격했다고 말하면 안 된다. 보강 양성은 실제 요구·도착 절·같은 판의 조건이 모두 확인된 이후에만 센다.

C의 `overview` 역할은 'Repository.'나 'Website.'라는 표면 종류만으로는 명시적 문서 역할이라 보기 어렵다. strict C에서는 별도 역할 표시가 없다면 unknown이 더 보수적이다. 지금은 제품판과 일부 용도도 미상이므로 이 정정이 주 C 배열을 바꾸지 않을 가능성이 높지만, 나중의 unknown-version 완화 감도에서는 영향을 줄 수 있다.

보수적 감도는 정확히 **제품판 결측 하나만** 같은 sentinel로 바꾼다. 용도·역할 등 다른 미상 필드를 동시에 동일 값으로 간주하지 않는다. 역할을 추론값으로 채우거나 `main`, `latest`, 목록 SHA를 제품판으로 쓰는 완화는 별도 조작이다. 이를 섞으면 C의 개선 원인을 알 수 없다.

기능명사 목록은 대체로 원문 코드·기대 출력·문장에서 고정되어 있다. 새로운 기능명을 후보 결과를 본 뒤 추가하는 증거는 발견하지 않았다. 자연 요구는 모두 기존 도구의 설정·진단 맥락이므로, '실제 설계자가 대체 공급자를 선택했다'는 사례로 확대하면 안 된다. 대체 조합 허용은 판독자의 사전 선택 규칙임을 유지해야 한다.

P-N1의 data files는 실제 L61의 필요 표현이 있어, 단순히 예시 설정에 있다는 이유만으로 도입한 인위적 조건이 아니다. 반대로 보강 목적 후보 PP-575의 PNG 보존처럼 문서 자체가 '예시 구성 보존이지 별도 필수 선언은 아니다'라고 인정한 경우에는 strict 자연 적격과 같은 강도로 취급하지 않는 것이 좋다.

## 5. 빈 풀의 해석과 결론 범위

정확 명사→목록 제목 매칭이 실패하면 자연 풀은 관측된 빈 배열이고 대표 차이는 관측0일 수 있다. 그러나 이는 **선택된 공개 목록의 제목 매칭 절차에서 후보를 얻지 못함**이다. 공급자 문서에 적합 구현이 없다는 뜻도, 부품 선택 요구 자체가 없다는 뜻도 아니다. 특히 기능 명사를 소유/편집 제목과 대조하는 목록 구조가 빈 풀의 원인일 수 있다.

필수 표에는 다음을 분리하면 된다.

- 후보 풀: 빈 배열이 직접 관측됨 → 관측0.
- 전체 생태계에 해당 기능이 있는가 → 이번 원풀 밖이므로 미확인.
- 조건부 기회가 없는데 승격 성공률을 계산하는가 → 해당 없음.
- 4번째 이후 URL이 올라왔는가 → metadata visibility.
- 올라온 것이 독립 구현이고 요구를 완결하는가 → 목적지 조사 후 별도 판정.

이 검토는 코드·시험의 기능 정답이나 두 번 열람 결과를 판정하지 않았다. 위 수정·감도는 정답을 본 뒤 채택하기보다 단계② 봉인 전에 옛 규칙·영향 행과 함께 기록하는 것이 적절하다.
