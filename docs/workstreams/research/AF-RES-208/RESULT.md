## Q2 — 정체성과 현재 표시
[K1 §3.8.4.4](https://www.rfc-editor.org/rfc/rfc5545#section-3.8.4.4) UID+RECURRENCE-ID(+해당 revision SEQUENCE)와 [K4 events](https://developers.google.com/workspace/calendar/api/v3/reference/events) recurringEventId+originalStartTime은 각각 규약/제공자 키. 원래 시작과 현재 start는 별개다. E1 공개 fixture는 Los Angeles 2012-10-02 10:00 RID, 실제 15:00 DTSTART; 2012-11-05 18:00Z RID가 11/6 20 local로도 이동됨. 전자는 +5h, 후자는 날짜 경계 횡단. E1은 사람이 보고한 사건이 아니라 fixture. K4의 event.id는 개별 instance를 API 요청 대상으로, iCalUID는 관련 반복 회차에 공통일 수 있다. 수신 측 iTIP UID+RID와 SEQUENCE/DTSTAMP 순서는 K2 §2.1.5. 변환 계약은 서로 같은 문자열이라는 뜻이 아니다.
C1 원래 3/16→3/27와 반대 원래3/30→3/20: Mar23 경계에서 display sort는 양쪽을 잘못 분류한다. 원래 경계가 정책이면 RID sort; 사용자가 표시일 이후만 원한다고 명시하면 display selection 후 ID로 수정. 다음은 old/new export로 실제 식별과 날짜를 비교.

## Q3 — RANGE와 패턴 분할
K1 §3.2.13 단건 default 및 THISANDFUTURE, §3.8.4.4 원래 순서로 후속, 별도 component 미영향, 일정 시간차/동일 새 duration. 예: 월요일 weekly를 모두 금요일로 옮기는 uniform shift와 월/수 중 월요일만 금요일로 옮기는 요구는 다르다. 후자는 note 그대로 기존 truncate + 미래 FR 및 WE 두 패턴이 후보. C3b에서 uniform shift면 수요일도 일요일로 이동하므로 탈락. F11 Sabre iterator 고정 소스는 RANGE 미지원 명시, E3 test는 생성 no throw만 보장. E2 ical.js test는 offset/cache assertion 포함하지만 실행하지 않았다. §3.8.5.3 mismatch undefined이므로 #8957 new DTSTART만 바뀐 상태를 정상 반복으로 보지 않는다. C0 무예외/고정 TZ/동일 shift는 분할과 RANGE가 표시상 같지만 UID, RSVP, notification 보장 다름. C4는 local 09 기준 DST 3/29 이후 UTC가 08→07로 변하는 대조. timezone engine에서 delta 계산 검증 필요.
보존할 moved exception은 E1 + K1, cancellation은 K1 §3.8.5.1와 [K2 §4.4.3](https://www.rfc-editor.org/rfc/rfc5546#section-4.4.3) (1997-08-01 21Z RID), K3. EXDATE는 생성 규칙보다 우선하며 DTSTART 자체 제외여도 원래 anchor는 유지. 규범 문구는 사용자 출력이 아니다.

## Q4 — Google식 분할의 경계와 실패 조건
[K3 guide](https://developers.google.com/workspace/calendar/api/guides/recurringevents) 2026-09-17판은 access/modify/delete instances까지, L219 “this and following”을 개별 수정하지 말라는 주의, L225 원시각, L228–354 PUT 취소 예를 확인했다. 현재 페이지 영문/한국어, split/reset 검색으로 두 요청 예·예외 reset 주의 원문은 찾지 못했다. 과거 개발자 [H1](https://stackoverflow.com/questions/65185532/google-calendar-api-edit-recurring-events-this-and-following-option-persis) 는 Dec11–20 시리즈 15일부터 title 변경 분할 후 18일 description 예외 손실을 보고하나 현재 공식 계약이 아님. 별도 [K2 §4.4.7](https://www.rfc-editor.org/rfc/rfc5546#section-4.4.7)은 전체 재스케줄 REQUEST에 예외정보 명시 포함 없으면 소실될 수 있다는 직접 규칙; Google 보장으로 일반화 금지.
설계 후보, **제작자 원예제의 재현이 아니라 두 API 계약을 조합한 추론**:
1. K5 instances with showDeleted=true, pagination, relevant bounds; K4 recurringEventId/originalStartTime·status·start/end, attendee status 및 reminders snapshots; 원래 key로 경계 산출하고 이동 전/후 양방향 경계 횡단 조사. 범위 없는 무한 계열은 finite window로만 검증; 삭제 목록에는 최소 필드만 보장.
2. K6 PUT 기존 master에 inclusive UNTIL을 target RID 이전으로 설정(예: C1 Berlin Mar23 09=08Z, UNTIL=20260323T075959Z) 또는 정확한 COUNT; 기존 DTSTART와 prior exclusions 유지. ETag condition; prior moved exception이 cutoff 넘어 표시돼도 old RID이면 prior. UNTIL 형식은 DTSTART DATE/UTC/TZID의 유형에 맞춤. 
3. K7 POST 새 master, start/end 및 TZID·BYDAY·COUNT/UNTIL 조정; 원래 occurrence mapping을 저장. 새 master의 id와 원래 id가 같다고 가정하지 않음. 요청 순서 실패 시 gap/duplicate를 예방할 사전 검증·복구/재시도 계획. 구/신 계열 두 요청 자체로 atomicity/rollback 보장 없음.
4. 각 future override를 재지정할 mapping의 존재성/충돌을 검증, 취소 tombstone을 재적용. 참가자 추가는 moved NR2의 override에도 적용해야 할 필드만 patch, DTSTART는 유지; 신규 초대/취소 통지와 reply status 검토. K4 reminders는 per-user이며 attendee 응답/알림 개인 상태의 복사가 보장되지 않는다. K6/K7 sendUpdates none 사용시 외부 동기화 문제 경고; 적절 옵션을 사용자 계약으로 결정. iTIP CANCEL은 affected attendee에게 별도 발송 요구(K2 §3.2.5); 실제 receiver 확인 없음.
5. GET/instances 양쪽 및 수신자 캘린더에 expected original key→display→status→attendee→alarm 목록을 대조. old/new mapping 없거나 취소 resurrection, double invitation, time gap 발생 시 실패. H1과 F7 순차 update/create는 이 검증을 필요로 하지만 원인을 확정하지 않는다.

## Q6 — 다른 분야: 운행일 예외
[T1 GTFS calendar_dates](https://gtfs.org/documentation/schedule/reference/#calendar_datestxt) key=(service_id,date), type1 추가/2 제거, 기본 calendar와 조합 혹은 날짜만 명시. [T2 공식 예](https://developers.google.com/transit/gtfs/examples/gtfs-feed#calendar_datestxt) 2006-07-03/04 WD 제거 WE 추가; 운영 실측 아님. [T3 SFMTA](https://www.sfmta.com/getting-around/muni/fares/muni-holiday-schedules) 2026-11-26 weekend/Sunday operators, 11/27 weekday non-school; [T4 TriMet](https://trimet.org/schedules/holidays) 11/26 buses/MAX Sunday WES 없음, 11/27 buses/MAX regular WES 없음. [T5 MBTA](https://github.com/mbta/gtfs-documentation/blob/master/reference/gtfs.md#calendar_datestxt) holiday_name 확장. 기관별 날짜 정책이 다르며 실제 GTFS feed·운행 실측 없음.
옮길 것은 기본 생성 규칙 + 명시 add/remove 날짜라는 구조와 복합키 범위. WD 제거+WE 추가가 이동한 회차의 같은 identity라는 뜻은 아니다. 참석자의 RSVP, iTIP ordering, moved RID와 originalStart, alarm 전달을 GTFS에 매핑할 계약은 없다. 운영자는 날짜별 trip service, 편집자는 내 일정 표시, API는 stable instance/series key, 초대 수신자는 자신의 변경/취소·응답을 보존한다. 서로 다른 관점의 join이 필요한 사례. 다음은 공식 기관 archive feed의 실제 service_id/date 행과 trips 연결을 read-only 확인.

## Q7 — 탐색기 first link와 질문 비용
단순 '반복 일정 이번부터'를 문자열로만 찾으면 사용자 버튼, data contract, mutation recipe가 섞인다. 검색 입구를 (1) original selection set: single/future/series 또는 display interval, (2) change field: start/pattern vs attendee/reminder, (3) preserve old/moved/cancelled/participants, (4) provider & TZ로 분해. 세 후보를 제거하지 말고 scope 조건 붙인 link+원문 절+반례를 반환.
- 단건: ID/override 문서가 먼저, 사용자가 해당 회차만 바꾼다면 저비용. 잘못 미래 전체를 수많은 단건 PUT하면 K3 비용.
- 연속: uniform recurrence semantics와 구현 지원 확인이 먼저; 기존 별도 예외가 원하는 필드에서 변화해야 하는 N2이면 RANGE 단독 불충분. C3b의 selective 변경도 불가능.
- 분할: 복잡 패턴과 provider 계약이 먼저; UID 매핑과 보존·복구 비용. prior occurrence/attendee 불변성이 중요한데 보존 계약 없으면 조건부로만 제공.
- 질문은 답변 후 방법이 달라지는 경우만. 실제 #8957 #8450 #6437은 scope 명시; 날짜/예외 조건 이미 있으면 추가 질문 생략. #4862는 원발화만으로 갈리지 않으므로 한 질문. 후속 다른 저자 F6의 답을 원작성자에게 귀속하지 않음. 사용자의 한 말이 실제로 모호해도 유용한 조건부 링크 제공 후 실행 전에 확인. 실제 질문·응답 실험/랭킹 테스트 0.
- 설계자가 사용할 최소 기록안: verbatim request span, intended field, scope and boundary basis, preserved occurrence IDs/date examples, exceptions and participant perspective, provider/version/TZ, evidence kind/specific section, unknown, flip condition. 링크 후보는 이 조건으로 정렬한다는 가설이지 최종 제품 DB schema 아님. 원문 주소보다 단일 방법을 먼저 정하는 것은 위험. 
- 경쟁 설명 A UI-only vs saved RRULE mismatch; N1 readback으로 UI-only 단독 약화. B attendee UI-only vs server payload loss; N2 raw evidence 없어 보류. C N4 stale BYMONTH vs correct RRULE expansion; 저장본 없으므로 먼저 rule consistency 절을 조건부 제공. counterexamples.md 및 methods.csv의 C0–C4/역방향 대조 참조.
