# Python·Swift 원문 조사 인계

## 범위와 현재 원장

GPT-6 Astra Pro, ChatGPT 공유 Linux Cloud workspace의 내부 하위 에이전트가 원문을 읽고 항목을 분절했다. 원문 저자와 독립된 설계 문서가 골드의 출처이고, 항목 단위·역할·stance는 작업자 코딩이다. 내부 별도 검토나 실제 사용자의 판단으로 포장하지 않는다.

- `draft-cases.json`: Python 9개, Swift 8개, primary 골드103개와 review-only2개.
- `sources.json`: 직접 읽은 문서·고정 판과 경로 이력85건. 같은 문서의 여러 판, Git 이력, 같은 사이트의 추가 페이지를 최소 자료수에 중복 산입하지 않는다.
- `selection.json`: 91개 스크리닝/사전 취득 기록. Swift28~65의38개는 비교절 길이 계산을 위한 자동 취득이며 **직접 읽은 D1 문서나 포함 판정으로 세지 않는다**.
- `SEARCH_LOG.json`: 실제 실행한 주소·질의 문자열186개. 개별 HTTP 요청의 최초 시각은 보존하지 않았고, 시각 필드는 원문 열람 묶음의 확인·기록 완료 UTC임을 명시했다. 정밀 요청 시각을 재구성하지 않았다.
- `history-metadata-complete.json`, `history-P386.json`: SHA·committer UTC·parent만 보존한 이력. 과거의 작은 이력 파일은 탐색 순서를 보여 주는 보조 메모이며 최종값은 complete/P386을 우선한다.
- 접두부의 최종 이름과 cutoff는 root의 `cases/PREFIX_MANIFEST.json`이 권위 원장이다. 이 폴더의 사례 ID는 P/S 번호를 유지한다.

비사례 최소수의 사이트 상한에 맞출 때 Python 템플릿은 실제로 연 [PEP1 공식 본문](https://peps.python.org/pep-0001/)을 사용할 수 있다. [PEP12 공식 본문](https://peps.python.org/pep-0012/)도 읽었지만 Python 리뷰2건을 함께 세면 같은 등록 도메인 상한 때문에 둘을 모두 최소수에 넣지 않는다. GitHub 템플릿 슬롯에는 Swift 초기 템플릿 한 건을 사용하고 나머지 역사 판은 보조 근거로 둔다.

## 2. 선정에서 발견한 오류와 보정

PEP386을 처음에는 Distutils와 Setuptools라는 패키지 단위 두 개로 묶어 제외할 뻔했다. 재검토에서 원문은 StrictVersion과 LooseVersion의 다른 문법·정렬 한계를 각각 비교하고 parse_version도 따로 비교함을 확인했다. SCOPE의 독립 설계 변형 분절 규칙에 맞추면 최소3개를 충족하며, RPM과 Debian/Ubuntu의 패키징 비교까지 primary5개다. 대체층 번호순에서354 다음에 들어가야 했으므로 제외를 유지하지 않았다.

root는 최초30개 접두부를 유지하면서 C31을 별도의 선행 커밋으로 추가했다. 이 보정은 결과가 좋은 사례를 고르는 변경이 아니라, 같은 작업 안에서 일관되지 않았던 분절 단위를 바로잡은 것이다. 원장 `sampling_correction`에 처음의 잘못된 판단과 이유를 남겼다. 다만 이미 다른 사례의 첫 기준선 실행이 시작된 뒤 발견한 보정이므로 최초30개와 추가1개를 구분해 보고해야 한다.

Swift0002·0004는 비교 항목이 있어도 최초로 확보된 공개 판이 이미 Accepted였다. 그 판의 Motivation을 결정 전 입력이라고 부를 수 없어서 제외했다. 다른 과거 문서가 세상에 없다고 주장하지 않으며, 연결된 초기 리뷰/PR의 고정 판을 찾으면 재검토할 수 있다. 많은 초기 Swift 문서는 비교절이 비어 있거나, 한 대안의 여러 단점을 나열한다. 단점 bullet 수를 대안 수로 바꾸지 않았다.

## 5. 다른 분야 인용과 골드의 성격

| 계열 | primary 항목 | 같은 분야 다른 설계 | 재사용 부품 | 다른 언어·생태계 | 다른 분야 원리 |
|---|---:|---:|---:|---:|---:|
| Python PEP9개 | 73 | 53 | 12 | 8 | 0/73 |
| Swift Evolution8개 | 30 | 25 | 2 | 3 | 0/30 |

이 표의 분모는 선정된 문서의 primary 항목이며 전체 언어 설계 문서나 설계자 수요의 분포가 아니다. 분절 단위와 역할은 작업자가 정했고 신뢰도를 측정하지 않았다. 다음 경계들을 명시적으로 검사했다.

- Haskell의 zip은 다른 언어의 기능·이름 선례다. PEP201에서 이름 선택의 근거가 되지만 먼 분야 원리는 아니다.
- PEP433의 Perl·Ruby·OCaml 및 C 런타임은 같은 디스크립터 상속 문제의 생태계 간 사례다.
- PEP509의 PySizer는 메모리 프로파일링에서 쓴 dict 변경 카운터를 최적화 가드가 참고한다. 목적 차이는 있으나 동일 실행기 자료구조의 가까운 영역이라 보수적으로 부품에 둔다.
- Swift0018의 Kotlin·Scala와 Swift0021의 lens도 같은 언어 설계 영역이다. lens라는 단어의 어원을 물리 광학의 원리 전이로 세지 않는다.
- PEP433의 이름 후보 sterile에는 생물학적 어원 설명이 있지만 파일 디스크립터 설계의 작동 원리를 생물학에서 가져온 것이 아니다. 순수 이름 후보는 기능 골드에서 제외하고 장식적 용어 차용의 관측으로만 남겼다.

primary의78/103개가 같은 분야의 다른 설계이며 상당수는 제안 안에서 만든 가상 구문·API 선택이다. 외부 프로젝트 URL을 검색해 얻는 성공과 구조가 같은 내부 대안을 제안하는 성공을 분리해야 한다. 이름만 바꾼 제품이나 언어 이름만으로 적중을 주면 이 코퍼스의 목적과 맞지 않는다.

## 6. 리뷰가 골드를 바꾸는 방식

Swift0021의 lens와 placeholder partial application은 각각2015-12-17/12-29 토론 원문을 읽었다. 고정 제안은 그 글을 직접 연결하므로 `added_in_review=true`를 근거와 함께 기록했다. 모든 글에서 최초로 제안한 사람을 추정하지 않는다.

Swift0022 수락 글에는 고정 제안 본문에 없는 implicit conversion과 magic `.selector` member가 있다. 이2개는 `review_gold_items`로 분리하여 primary3개 분모를 유지했다. 문서 본문만 읽으면 리뷰가 고려한 전체 대안 집합을 빠뜨릴 수 있다는 최소 관측은2개이며, 이를 골드 밖 유용 후보나 새 기준선의 발견으로 혼동하지 않는다.

Python의 두 리뷰는 [implicit lambda 반론](https://mail.python.org/pipermail/python-dev/2017-November/150109.html)과 [공식 수락](https://mail.python.org/pipermail/python-dev/2017-December/151042.html)이다. 제약에 대한 그때의 믿음과 수락의 사실은 보여 주지만, 이후 구현 방식까지 포함한 영구적 정답을 만들지는 않는다.

## 한계와 root가 이어서 할 일

기준선과 후보 채점은 이 하위 작업의 범위가 아니므로 실행 결과를 보거나 적중을 예측하지 않았다. root는 중립 ID 매핑 후 A/B의 원 응답과 대조하고, 실제로 열린 후보의 L/E/H/T를 판정해야 한다.

얇은 접두부(P0202/S0019), 처음 초안에서 최종 골드까지 긴 간격(P0554), Git 반영과 결정의 시차(P0563/S0025/S0022)가 회수율의 해석을 바꿀 수 있다. 이들은 문맥 부족·문서 진화·시각 증거의 한계로 보고해야 한다. 여러 오래된 골드 외부 링크는 대상 제안에서 인용된 주소를 보존했을 뿐 직접 유효성을 검사한 후보가 아니다. 깨진 후보 링크 지표에 이 미검증 골드 주소를 섞지 않는다.

최종 로그에 Python205~209의 부분 탐색5개와 추가 이력·실패 주소6개를 덧붙였다. complete_evidence.py를 다시 실행하면 이 최종 append를 재현해야 하므로, 재실행할 때는 현재 JSON을 보존하고 변경을 비교한다.
