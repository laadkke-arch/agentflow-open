# Design problem input — C05

Cutoff date: 2017-09-27

## Context and purpose

Kubernetes application events should help application developers understand what happened without making a cluster failure worse. Repeated scheduling failures can flood the API server. Existing event fields have ambiguous meanings, messages contain semantics that deduplication ignores, timestamps have one-second granularity, and grouped events are difficult to query. The goals are clearer event semantics and reduced performance impact on the cluster.

## Required boundaries

- Event reporting must not cause or worsen cluster performance failures.
- Preserve an application developer’s ability to understand events about their application.
- Moving persistence outside etcd or retaining events longer is outside this decision.

Find public existing approaches and references that can help this design. Explain the useful part and its conditions.
