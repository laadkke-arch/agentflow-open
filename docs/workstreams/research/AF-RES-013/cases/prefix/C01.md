# Design problem input — C01

Cutoff date: 2020-10-02

## Context and purpose

A Kubernetes controller creates batch jobs on recurring cron schedules. Its API has been stable for several releases and should become supportable for the long term. The controller needs an implementation that uses shared change notifications instead of repeatedly polling the API, addresses current controller problems, and exposes throughput and latency metrics. The status should also make the most recent successful job completion available.

## Required boundaries

- Preserve recurring cron schedule execution within the Kubernetes controller model.
- Replace repeated API polling with informer-based observation.
- Support measurement of controller throughput and latency.

Find public existing approaches and references that can help this design. Explain the useful part and its conditions.
