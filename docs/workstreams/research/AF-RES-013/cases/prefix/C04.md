# Design problem input — C04

Cutoff date: 2018-11-12

## Context and purpose

In a Kubernetes cluster, node agents register their own labels, including labels supplied on their command lines. This helps automatic registration but spreads management across many node configurations. More seriously, a compromised node can advertise labels reserved for sensitive workloads, attract those workloads, and obtain their secrets. The design needs to bound that authority while supporting the node-registration workflow.

## Required boundaries

- A compromised node must not gain trusted placement identity merely by asserting its own labels.
- Consider sensitive-workload and secret exposure through scheduler placement.
- Address node-label authorization rather than replace the entire workload scheduler.

Find public existing approaches and references that can help this design. Explain the useful part and its conditions.
