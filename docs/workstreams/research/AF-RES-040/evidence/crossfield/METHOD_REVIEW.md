## 2. 후보 → 묶음 → 첫 세 대표

현재 28–53행은 A에서 원 URL 완전 일치, B에서 확인된 상류, C에서 검증된 의미 signature를 사용한다. 45행의 입력 순회와 51행의 최초 대표 선택, 85–96행의 첫 세 그룹 선택은 사전 규칙과 맞는다. 최종 진입점은 213–214행에서 요구별 rank를 정렬하고 1–6을 확인한다. 빈 URL은 그룹에서 제외하고 빈 카드로 남긴다. 후보의 적격도에 따른 사후 재순위화는 이 코드에 없다.

단, 문자열 키는 **수동 판단의 운반 형식**이다. 같은 문자열이 같은 계약이라는 증명은 아니다. `identity_verified`, `upstream_verified`, `document_group`, component/purpose/판/역할의 근거가 원문과 연결되어야 C의 의미가 성립한다. 특히 scope_key가 없을 때 빈 문자열로 통합되는 것은 같은 의미 범위를 별도로 확인했다는 뜻이 아니다. 현재 코드의 목적은 라벨을 재현 가능하게 계산하는 것이며 라벨의 타당성을 자동 검증하는 것이 아니다(`recount.py` 1–5행).

분리해 보존해야 하는 세 종류는 다음과 같다.

| 층위 | 현재 필드·계산 | 말할 수 있는 것 | 이 지표만으로 말할 수 없는 것 |
| --- | --- | --- | --- |
| 링크 또는 카드 | representative_ids, hidden_members, cutoff_groups | 어떤 원 주소가 첫 화면에 직접 나타나는가 | 실제 소비자가 무엇을 인지했는가 |
| 접근 가능한 원문 근거 | closure, preserved_atoms, hidden_required_atoms | 첫 대표 원문들을 열고 끝까지 읽을 수 있다는 가정에서 입증 가능한 조건 | 읽기 시간, 탐색 성공률, 실제 클릭·채택 |
| 완전한 요청 대안 | eligible_paths, preserved_path_ids | 원 요청의 필수 조건을 모두 입증한 경로가 접근 가능한가 | 실제 프로그램 성공·사용자 만족, 풀 밖 대안의 부재 |

## 3. 원문 전체 closure의 정당한 범위와 한계

75–78행은 대표 후보의 document_group과 같은 모든 후보 절을 접근 가능으로 만든다. 이는 같은 고정 문서의 fragment가 읽기 권한 경계가 아니라는 해석에 맞는다. `method-clarifications.md` 5–13행도 이를 명시했다. 같은 파일의 다른 절은 스크롤하여 읽을 수 있으므로 해당 절의 카드가 사라졌다는 이유만으로 근거 손실로 세면 과장이다.

반대로 다음 조건은 필요하다.

1. document_group은 **같은 고정 원문 전체**만 가리켜야 한다. 같은 프로젝트·같은 사이트·다른 판 문서를 하나로 묶으면 숨은 근거를 읽었다고 잘못 계산한다.
2. 원문 안의 다른 URL에 링크되어 있다는 이유로 그 다른 문서의 내용까지 closure에 넣으면 안 된다. 현재 함수는 document_group만 사용하므로 입력이 정확하면 이 경계를 지킨다.
3. closure는 주 풀에 라벨링된 절들의 접근 범위다. 고정 문서 전체의 가능한 모든 기능을 전수 탐색·추출했다는 주장은 아니다.
4. 같은 문서의 먼 절까지 읽을 수 있다는 것은 접근 상한이다. 실제 사용자가 그 절을 찾아냈다는 관측이 아니다. 따라서 ‘추가 클릭 0에서 도달 가능’과 ‘첫 화면에서 해당 기능을 인지’는 구분한다.

`hidden_card_components`(142행)는 비대표 후보의 component 목록이다. 동일 component가 대표에도 있을 수 있고, closure를 통해 이미 접근 가능할 수도 있다. 그러므로 그 필드를 그대로 ‘완전히 가려진 기능 수’라고 쓰면 안 된다. 기능이 카드에서 전혀 보이지 않는 수가 필요하면 전체 component에서 대표 component를 빼야 하고, 근거 손실은 `hidden_required_atoms`로 별도 판단해야 한다.

## 4. same_document 반복과 기능 중복은 다른 지표

129–130, 150행의 `functional_duplicate_slots`는 대표 signature 반복이다. 151행의 `same_document_repeat_slots`는 대표가 가리키는 원문 ID 반복이다. 두 값은 더해서 총 낭비 슬롯으로 만들 수 없다. 같은 슬롯에 두 성질이 함께 있을 수 있기 때문이다.

- 같은 원문에 PNG 읽기와 PNG 쓰기처럼 다른 부품이 있으면 문서 반복은 있어도 기능 중복은 없다.
- 같은 부품·판·역할의 독립된 설명 두 개는 기능 중복으로 라벨링될 수 있어도 원문은 서로 다를 수 있다.
- 같은 문서의 같은 기능 앵커가 반복되면 두 지표에 모두 잡힐 수 있다.

합성 예제에서 세 대표는 기능 중복 1슬롯과 문서 반복 1슬롯을 동시에 만들었다. 이것은 둘이 같은 수치라는 증명이 아니라, **서로 다른 속성의 비가산 지표**임을 보이는 검사다.

잔여 한계: 기능 중복 계산은 identity_verified를 따로 보지 않는다. 미확인 후보의 signature가 우연히 같아도 반복으로 셀 수 있다. 현재 읽은 비어 있지 않은 후보 39개는 모두 identity_verified=true여서 그 문제는 현 입력에서 노출되지 않았다. 향후 미확인 후보를 포함하면 ‘확인된 중복’과 ‘기록 키의 반복’을 나누어야 한다.

## 5. atom·path 분모와 오병합 지표

### 5.1 분모의 올바른 분리

120–125, 156–160행은 요구의 필수 atom, 풀에서 입증된 atom, 완전 적격 path를 구분한다. 0인 path 분모를 `해당 없음`으로 두는 것은 SCOPE 64행에 맞다. 전체 8건에서 documented/partial/unknown을 세는 234–239행도 조건부 회수의 분모와 분리되어 있다.

검토 시점 원 코딩 파일에서는 다음을 확인했다.

| 파일 | 직접 확인한 범위 | 현재 입력의 결론 | 해석 한계 |
| --- | --- | --- | --- |
| `evidence/gdal/coding-G.json` | eligible_paths/eligible_paths_relaxed: 39–40, 92–93, 149–150, 201–202행 | G1–G4의 완전 적격 경로 모두 0 | 부분 기능 설명이 실제 오류 해결이나 배포 포함을 입증하지 않는다는 엄격 라벨이다. 소프트웨어로 해결 불가능하다는 뜻은 아니다. |
| `evidence/sphinx/coding-S.json` | 31–32, 78–79, 114–115, 149–150행 | S1–S4의 완전 적격 경로 모두 0 | 요구한 판·행동의 해결 근거 부족이다. 현재 기능·대안 자체가 없다는 전수 조사 결과가 아니다. |

따라서 원 코딩 그대로라면 **완전 적격 요구는 0/8, 조건부 경로 회수는 해당 없음**이다. ‘모든 팔의 회수율이 0%’나 ‘C가 적격 대안을 되살리지 못하므로 효과가 없다’라고 바꾸면 안 된다. 살아난 링크·기능 이름과 살아난 완전 적격 대안도 다른 값이다. 이 표본은 부분 근거 보존을 비교할 수 있지만 완전 적격 대안 회수의 우열에는 노출이 없다.

### 5.2 path 라벨의 자동 검증은 남아 있다

`available_paths()`(71–72행)는 수동으로 적힌 required_candidate_sets의 가시성만 확인한다. 그 조합이 실제로 모든 필수 atom을 충족하는지는 검사하지 않는다. 합성 입력에서 atom을 하나도 제공하지 않는 잘못된 path를 주면 `documented`를 반환했다. 이는 실제 입력의 오류를 발견했다는 뜻은 아니며 **잘못된 입력을 막는 일관성 검사가 없음**을 확인한 것이다.

현재 완전 path가 모두 빈 집합이어서 이 오류의 실제 노출은 없다. path가 생기는 다음 조사에서는 각 witness set의 지원 atom이 모든 필수 조건을 충족하는지, 부품·구현·판이 서로 호환되는 조합인지 확인해야 한다. 증명 문서 조합이 여러 개라는 이유만으로 동일 구현 대안을 여러 path ID로 세지 않도록 대안 단위도 고정해야 한다.

### 5.3 오병합 구조와 실제 손실을 분리

131–132행의 `heterogeneous_merged_pairs`는 **모든 그룹** 안에서 signature가 다른 쌍이다. 화면 밖 그룹도 포함하고, 같은 원문 closure로 근거가 그대로 남는 쌍도 포함한다. 따라서 이를 ‘첫 화면에서 실제로 피해를 낸 오병합 건수’라고 부를 수 없다.

147행의 `merge_hidden_required_atoms`는 표시 그룹의 숨은 회원을 추가로 열면 돌아오는 조건이다. 이것은 그룹 병합에 따른 접근 손실을 더 직접적으로 보여 준다. 단, atom 수가 같더라도 별개 완전 대안이 가려질 수 있으므로 path 손실과 분리해 보고해야 한다. 원 요청에서 필요하지 않은 이질적 쌍은 구조적 경고일 수 있지만 그 요청의 해로움으로 자동 세지 않는다.

### 5.4 보완 근거 지표의 측정 단위

현재 `complementary_sets_n`은 단일 required atom의 명시적 support_set에서 필요한 서로 다른 원문 집합 수다. G2처럼 MapInfo 기능 atom과 Java 호출 atom이 각각 다른 원문으로 입증되고 둘을 함께 읽어야 부분 경로가 성립하는 경우는 이 계산에 자동 포함되지 않는다. `coding-G.json`의 G2 `partial_paths`는 그 조합을 적지만, recount는 partial_paths를 읽지 않는다.

결과에서는 ‘단일 atom에 필요한 보완 원문 조합’이라고 명명하거나, 별도 표에서 G2의 다중 조건 부분 경로 보완쌍을 제시해야 한다. 두 종류를 합산하려면 atom/부분경로/완전경로 가운데 어느 단위를 세는지 먼저 선언해야 한다.

### 5.5 짝 집계에서 수의 동률과 동일 보존은 다르다

245–252행은 요구별 보존 atom **개수**만 비교해 tie를 준다. 한 팔이 a를, 다른 팔이 b를 보존해도 둘 다 1개라 tie다. 이 값은 `paired_atom_comparison_all_8`이라는 이름 아래 ‘개수의 짝 비교’로만 해석해야 한다. SCOPE 64행의 양쪽 보존/한쪽만/둘 다 없음에는 실제 atom·path 집합 또는 명시된 요구 답변 가능 상태의 교집합·차집합이 필요하다. 최종 표에서 행별 목록을 대조하고, 요구 수준의 답변 가능 짝 집계도 분리해야 한다.

## 6. 민감도와 실제 노출

U와 Vg/Vr를 하나씩 바꾸는 코드 분리는 확인되었다. 그러나 비어 있지 않은 후보 39개가 모두 identity_verified=true이고 각 요구 안에서 후보의 version 값이 하나뿐이었다. 그러므로 현재 입력에서 U/Vg의 무변화는 **바뀔 대상이 없어서 생긴 결과**다. 미확인 합침이나 판 무시가 안전하다는 증거로 쓸 수 없다. Vr에서도 빠진 오류 해결·배포 포함 근거가 새로 생기는 것이 아니므로 적격 경로는 여전히 0으로 코딩되어 있다.

K(114–116행)는 표시된 세 그룹의 모든 원문 회원을 한꺼번에 접근 가능으로 만든다. SCOPE 56행이 선언한 상한 분석에는 맞지만 ‘실제로 사용자가 총 한 번 더 클릭했다’는 관측은 아니다. 그룹별 펼치기와 각 원문 확인을 모두 무료 접근으로 만든 가정이다. 결과표에는 **표시 그룹의 회원 원문 접근을 허용한 상한**이라고 적고 실제 클릭 수·비용·채택은 미확인으로 둬야 한다.

따라서 `K_list`와 `K_source_upper_bound`를 구분해야 한다. K_list는 형제 링크 목록만 펼친 상태라 숨은 문서의 근거를 읽은 것으로 세지 않으며 proof 범위는 기본값을 유지한다. K_source_upper_bound는 그 목록에 속한 모든 원문까지 읽었다고 가정하는 계산이다. 후자는 추가 원문 열기 수를 측정하지 않았으므로 **실제 총 2클릭 회수**라고 부를 수 없다. 부모 조사자는 이 두 열을 결과표에 분리하겠다고 통지했다. 결과표가 아직 없으므로 그 반영 완료는 이 문서에서 인증하지 않는다.

`returned_eligible_paths_vs_A`의 A 비교선은 126–128행에서 기본 A 접근 범위다. A는 완전히 같은 URL만 묶으므로 정상적인 document_group 라벨 아래에서는 A의 K 확장이 새 문서를 열지 않아 A0와 AK가 같아야 한다. 최종 입력에서 같은 URL이 서로 다른 document_group을 갖지 않는지 확인하면 이 전제가 유지된다.

## 7. 복원 검사와 표시 통제의 한계

219–220행의 검사는 모든 그룹에서 원 회원 ID를 회수해 원 순서를 되찾는지 확인한다. 이는 **비어 있지 않은 후보의 ID·그룹 회원 복원** 검사다. 빈 슬롯은 별도 unfilled_pool_slots/input_order/input_urls로 남지만 이 assert는 빈 슬롯을 검사하지 않는다.

회원 목록만으로는 왜 합쳤는지, 당시의 용도·판·설정·근거 역할·출처 판단을 복원할 수 없다. 의미 판정까지 되돌리려면 `analysis-input.json`, pool, relations, source 원장, 변경 기록과 그 고정 해시를 함께 보관해야 한다. 현재 all_members_restorable=true를 ‘오병합의 모든 의미 정보를 자동 복원함’으로 설명하면 과장이다.

217–218행의 예산 검사는 카드 수 3, 카드당 직링크 최대 1, 설명 80자 이하를 확인한다. 서로 다른 대표 사이 실제 설명 길이가 같다는 검사는 아니다. SCOPE 54행과 `method-clarifications.md` 15–17행은 이 차이를 이미 밝힌다. 같은 후보의 텍스트와 동일 상한은 통제하지만, 사용자가 요구한 엄격한 동일 실제 길이를 만족한 실험이라고 주장하면 안 된다.

`same_pool_all_arms`/`budget_equal`의 true(228행)는 같은 함수 입력과 위 검사에서 파생된다. 독립 실행자가 원장을 다시 취득했거나 화면을 실제로 렌더링해 인지 난이도까지 확인했다는 뜻은 아니다.

## 8. 최종 집계 전 남은 최소 확인

1. 최종 analysis-input에서 8요구×6슬롯, 39개 비어 있지 않은 후보와 9개 빈 슬롯, 원 순서·원 URL의 봉인을 대조한다. 부모 조사자가 후속 수정하면 그 이유와 실제 최종 수를 다시 기록한다.
2. Sphinx 수동 60쌍과 GDAL 수동 10쌍이 동일 방향·판정·근거로 들어갔는지 확인한다. 미제공/빈 쌍은 unknown이어야 한다. 특히 Sphinx S4-1↔S4-2의 unknown(코딩 원장 1815–1833행 부근)을 no로 만들지 않는다.
3. atom 개수 짝 비교와 별개로 보존 집합, 완전 답변 가능 여부의 양쪽/한쪽/양쪽 없음 집계를 남긴다. 원 코딩대로라면 완전 적격 회수 분모는 0이며 이 값은 숨기지 않는다.
4. 보완 원문 지표의 단위를 명명하고 G2의 부분 경로 쌍을 별도로 설명한다. same_document 반복과 기능 중복, 구조적 이질 쌍과 필수 조건 손실도 서로 바꾸어 쓰지 않는다.
5. 최종 입력에서 같은 URL→같은 document_group의 일관성과 요구별 고정판을 확인한다. 그 뒤 부모 조사자가 `recount.py --check-only`와 세션 검사, 커밋된 RESULT/acceptance 재열람을 수행해야 한다. 이 내부 검토는 그 최종 검사를 대신하지 않는다.

후속 수정 통지: 부모 조사자는 집계 전에 G4-1 원문에 포함된 gdalinfo/Size 예제로 G4.A2 지원을 추가하고, 기존 풀 라벨을 보존한 정정 원장을 남기겠다고 알렸다. 이 문서의 원 코딩 hash와 해당 파일의 후속 hash는 달라질 수 있다. 검토자는 원문 해당 절을 새로 판독하거나 이 정정 후 수치를 재계산하지 않았다. 이 수정은 완전 적격 경로 분모 0이라는 주장과 구별하여 기록해야 한다.

## 판정

최초에 발견한 네 가지 방법 구현 문제는 부모 조사자의 수정 뒤 코드와 합성 확인에서 해결되었다. 남는 핵심 제한은 **주 표본의 완전 적격 대안 분모가 0이라는 점, U/V 변화 대상이 없다는 점, 원문 전체 접근 상한을 실제 사용자 발견·효용으로 바꿀 수 없다는 점**이다. 이는 부정적·비진단적 관측으로 명시해야 한다. 최종 원장과 비교표가 작성된 뒤의 수치 재검산은 아직 이 문서의 확인 범위에 포함되지 않는다.
