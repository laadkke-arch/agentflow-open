## 2. 자연 후보 취득 — Q2

요구 하나당 최대 6개, 부족하면 빈 슬롯이다. 아래 탐색 순서를 각 요구에 동일하게 적용한다. 후보 순서는 문서에서 발견한 순서이지 예상 적격도순이 아니다. 요청 본문에서 입력/출력 형식·API·builder·extension 명칭을 먼저 추출하고, 대소문자/공백/하이픈만 표준화한다. 형식 이름의 공인 확장자 대응(예: GeoTIFF/tif/tiff)은 발견 원문에 대응 근거가 있을 때만 추가하고 기록한다.

1. 요청에서 명시한 공급자의 공식 버전 매뉴얼 목차/드라이버·builder·extension 색인. 요청 명칭이 제목/링크 텍스트/항목 설명에 나오는 항목을 원 문서 순서대로 취한다. 동일 페이지의 개별 앵커는 원 URL로 보존한다. 같은 페이지의 여러 호출/형식은 별개 후보가 될 수 있지만 고유 원문 수는 한 개다.
2. 요청에서 명시한 다른 공급자가 있으면 그 공급자의 같은 종류 공식 목차를 원 요청의 언급순으로 읽는다.
3. 주 공급자의 공식 패키지 레지스트리 설명(PyPI의 GDAL/Sphinx 등). 명시된 기능/형식과 직접 연결된 프로젝트·문서·소스 링크를 표시순으로 취한다. 레지스트리 페이지 자체는 요청과 관련된 구현/배포/판 정보를 제공하는 경우만 후보로 쓴다. 무관한 라이선스/기부/계정 링크는 제외한다.
4. 공식 튜토리얼/통합 예제 목차에서 해당 형식/호출/출력과 직접 관련된 항목을 원 목차 순으로 읽고 취한다. 공급자의 공식 문서가 별도 구현을 지목하면 그 구현의 공식 문서를 원문 출현순으로 취한다.

현재 공식 웹 문서가 요청 판의 고정판을 제공하면 그 판을 쓴다. 없으면 발행자 Git 태그의 해당 문서 파일을 사용한다. 요청 판이 미지정이면 최초 열람 시각의 안정판·태그를 기록한다. 어느 것도 확인할 수 없으면 판 미확인으로 남기고 엄격 적격을 주지 않는다. 후보 발견용 색인과 실제 후보 원문을 구별한다. 확인할 수 없는 링크도 자연 순위에 남기고 counted=false로 기록한다. 6개를 채우기 위해 임의 검색어·다른 제품·별칭을 사후 삽입하지 않는다. 접근 실패 시 선언된 다음 단계로 이동하되 실패 주소와 원 순위는 남긴다.

`pool.csv`는 요구별 6행, candidate_id, rank, raw URL, discovery ledger/locator, discovery order, pinned version, frozen UTC, read status, evidence locator, source_id, eligibility atom IDs, upstream, component, purpose, version, evidence_role, unknown을 가진다. 추가 스트레스 사례는 별도 `evidence/stress.jsonl`이며 주 풀과 분모에 합치지 않는다.

## 3. 동일성·방향 판정 — Q3

주소, 상류 프로젝트, 구현/배포판, 부품/호출, 요청 목적, 설정/판, 근거 역할을 별개 필드로 둔다. 주소의 호스트 대소문자와 명시적 기본 포트만 비교용으로 정리하되 원 URL은 보존한다. fragment, query, path case, trailing slash, http/https, raw/blob 형식을 임의로 같게 만들지 않는다. A에서는 원 URL의 완전 일치만 제거한다.

같은 프로젝트 판정은 공식 repository metadata·프로젝트 링크·태그·발행자 문서의 명시적 귀속으로 확인한다. 공유 도메인/공급자/이름만으로 합치지 않는다. fork는 별도 상류로 둔다. 버전이 다른 배포를 한 B 그룹에 넣되 이로 인한 손실을 센다.

쌍 판정은 `same_implementation_use`, `substitutable_distinct_implementation`, `same_project_different_function`, `complementary_evidence`, `unknown`이다. 각 방향 A→B/B→A는 `yes/no/conditional/unknown`으로 별도 기록한다. 판단 범위는 문서가 입증하는 계약에 한정하며 실행 호환성을 주장하지 않는다. 근거 역할은 capability(기능), invocation(호출), constraint(제약), distribution(배포/판), example(소비 위치)로 나눈다. 같은 문서가 복수 역할을 가지면 집합으로 남긴다. 한 방향의 호환/변환을 대칭 동등성으로 쓰지 않는다.

## 4. 표시 처치 — Q4

- A: 정확히 동일한 원 URL만 같은 그룹. B: 확인된 상류 프로젝트/저장소 하나가 한 그룹. C: 같은 구현의 부품×목적×판×근거 역할 집합이 확인되고 요청에 대한 의미 범위가 같은 경우만 그룹. 별도 구현은 완전히 대체 가능해도 C에서는 분리한다.
- B/C에서 미확인 귀속·부품·판정은 후보별 singleton. 판 `미지정`은 판 증거가 같을 때만 같은 값으로 취급한다. 문서 판 미확인은 합치지 않는다.
- 그룹 대표는 원 풀에서 최초 출현. 그룹 순서도 최초 출현. 첫 3그룹만 보여 주고 부족한 자리는 빈 카드로 둔다. 후보 재순위화·적격 대표 선택은 하지 않는다.
- 각 화면은 정확히 3카드, 카드마다 원문 직링크 최대 1개, 설명 최대 80 유니코드 글자. 동일 후보의 제목·설명은 팔 사이에서 동일하다. 숨은 회원의 사실을 대표 카드에 추가하지 않는다. 링크/제목을 제외한 설명은 80자 상한에 맞추되 인위적 패딩하지 않는다. 설명 길이 차이가 생기면 실제 길이를 기록한다.
- 기본은 추가 클릭 0: 화면의 대표가 가리키는 원문만 판독한다. 숨은 형제와 잘린 그룹의 내용을 안다고 가정하지 않는다. `views.jsonl`에 24개의 실제 카드와 모든 그룹/원 멤버/대표/숨김 원인을 보존한다.
- 추가 클릭 1 민감도: 표시된 세 그룹 각각의 회원 목록을 펼쳐 그 그룹의 모든 원문을 확인할 수 있는 상한 분석이다. 표시되지 않은 네 번째 그룹은 여전히 숨김. 이는 클릭 비용 실측/실제 UI가 아니며 실제 채택·효용은 미확인이다.

## 5. 손실과 분모 — Q5

보기 생성 전에 전체 후보가 입증하는 원 요청의 조건·용도·판을 atom으로 라벨링한다. 적격 대안은 원 요청의 필수 atom을 충족하는 구현/부품 경로다. 단일 링크로 충분한 경우와 둘 이상 원문을 함께 읽어야 하는 경로를 구별한다. 버그 원문 자체는 공급자 능력 입증이 아니다. 문서가 현상을 설명해도 요청한 버그 해결을 실제 검증하지 않았으면 실행 성공은 미확인이다.

각 요구×팔에서 (1) 보존 atom/적격 전체 atom, (2) 완전한 적격 경로/풀에 있는 완전 적격 경로, (3) 숨긴 필수 용도/판과 URL, (4) 같은 기능·판·근거 역할의 반복 표시 슬롯, (5) B/C 병합 때문에 숨은 다른 기능·판·근거 역할, (6) A에는 없고 다른 팔에 나타난 별개 적격 대안, (7) 보완 근거쌍 보존, (8) 근거 미확인을 센다. 중복 슬롯은 표시 링크 수에서 입증한 동일 기능×용도×판×역할의 수를 뺀 값이다. 독립 구현은 같은 용도라도 중복 슬롯으로 세지 않는다.

풀에 적격 경로가 없는 요구의 조건부 경로 회수는 `해당 없음`; 0/0을 0%나 100%로 쓰지 않는다. 전체 답변 가능은 별도로 8건 분모를 유지하고 documented/partial/unknown을 나눈다. 집계는 8건 짝(양쪽 보존/한쪽만/둘 다 없음)을 먼저 보고 비율의 분모를 같이 적는다. 표본은 두 프로젝트의 목적 표집이며 일반 모집단 성능·인과 사용자 효과를 추정하지 않는다.

## 6. 반례·타 분야·민감도 — Q6/Q7

주 표본과 독립된 다음 보조 묶음을 찾는다: 같은 상류의 다른 행동, 별도 구현의 동일 용도 대체, 한 URL의 여러 부품, fork 전후 계약 차이, 같은 기능의 여러 주소, 상호 보완 근거, 한 방향 호환. 발견 못 한 종류를 억지 예로 채우지 않는다.

도서관: IFLA LRM 운영 모델/공식 가이드와 운영 기관(LoC/OCLC/국립 도서관)의 구체 레코드를 최소 2개 직접 읽는다. 음악: MusicBrainz의 work/recording/release 가이드와 구체 작품·녹음·발매 레코드를 최소 2개 직접 읽는다. 같은 연주의 다른 표기와 같은 작품의 다른 편곡/녹음을 구별하며 제공자·소비자·편집자의 목적을 비교한다. 운영 원칙과 소프트웨어 적용 가설을 분리한다. 실패 주소·대체·다음 확인을 남긴다.

민감도는 기본 C에 한 번에 한 요소만 바꾼다: U(미확인 키를 같은 확인 상류 안에서 합침), V(판만 제거), K(표시 그룹의 회원까지 한 번의 펼치기 허용). A/B도 K를 같은 방식으로 산출한다. 목적·근거 역할을 동시에 없애지 않는다. 바뀐 요구·대표·분모를 행별로 기록하고 변화가 없으면 0으로 남긴다.

## 7. 출처·검사·종료

외부 고유 원문 최소 24: 소비자 8, 독립 공식 공급자 문서 8, 동일성/관계/비호환 배포·규격·소스 4, 도서관 2+음악 2. 한 원문을 범주 둘에 중복 산입하지 않는다. 같은 문서의 URL/표현 형식은 duplicate_group 하나다. 모든 sources 행에 요청된 14키와 직접 읽은 범위·한계·UTC·위치·counted를 둔다. 검색/실패/미열람은 최소수 제외. 외부 본문 대량 복사는 하지 않고 검증 가능한 사실 요약·위치·필요한 최소 인용을 보존한다.

중간 커밋은 ① 이 계약·manifest → ② 60노출/8요구·48슬롯 → ③ 관계·24보기·손실·반례 → ④ 결과·재계산·자체 점검·수용 JSON → 최종 HANDOFF 단독 커밋 순이다. 각 원격 SHA는 다음 묶음의 commit ledger에 기록한다. 최종 검사 전 RESULT와 acceptance-evidence를 커밋하고 고정 SHA에서 다시 읽는다. 공통 start/check의 실패를 다른 검사 성공으로 덮지 않는다. 모든 변경이 owned_path 안인지, dot-control blob 불변인지, 원 순서/예산/원 멤버 복원이 맞는지 검산한다.

예상 반대 결과: B가 충분한 이름 수준 요청, C가 역할별로 지나치게 나누어 슬롯을 소모하는 요청, C도 최초 대표 선택 때문에 필수 호출을 숨기는 요청, 모든 팔이 같거나 후보 부족으로 차이를 판정 못 하는 요청. 이 결과도 발견 그대로 남긴다.
