## Q1. 최초 요청의 논리
원문을 atom의 집합이 아닌, 목표와 논리식과 적용 scope가 연결된 식으로 보존해야 한다. M1/M5에서 HTML은 산출물이고 offline은 이용 환경, HTML과 offline 두 플러그인을 요청한 것이 아니다. M3은 파일 직접 열기에서 root/deep + search 요구, B4/B5는 동일 빌드 안 chapter/index/print 경로에 이미지/링크 보존. B2는 OR(one-page without popup, search), 한 가지가 목표를 달성하면 된다. B3은 optional Mermaid와 PDF/EPUB renderer의 질문이지 AND 확정 아님. S3은 HTML 최신성 우선과 일요일 PDF 재생성, 평일 기존 PDF 링크 허용이라는 시간범위; S4는 PDF 접근이 목적과 반대(일부 조건에서 print 제거). 원문 quote와 current edit 한계는 requirements.csv R- 행에 기록.

## Q2. 후속을 소급하지 않는 방법
최초 기록은 고정하고 subsequent observation을 별도 event로 append. F-M1의 solved는 자기 보고, F-M2 upgrade 후 solved 뒤 search 질문은 새 이슈 가능성, F-M3 감사는 수용 아님. B1은 처음 전체 cache 제안 이후 일부 chapter 선택/가능한 만큼 cache/asset inventory를 검토: 각각 후속 명료화 후보 또는 변경이며 최초 정책에 덮어쓰지 않는다. B2 검색 안내 뒤에도 one-page 유용성 언급: 초기 OR을 AND로 소급 변경하지 않는다. B5의 normalization은 원작성자 진단이지 fix 검증은 아니다. S1 PDF 복사 확인과 접근 문제는 서로 다른 atom. 사용자 identity, 댓글 author, event timestamp, span, role(원작성자/유지자/제3자), change_kind(initial/clarifies/adds/diagnoses/accepts/acknowledges/unknown) 저장. 현재 API updated_at은 수정 이력 자체가 아님.

## Q3. 정확판·출력 차이
D1/D2는 URL 방식, D3는 search 설정, D4는 print와 HTML renderer, D5는 print 기반 자동 PDF와 후속 outline, D6는 집계 print page 및 브라우저 수동 저장, D7은 자동 PDF/env gate, D8은 HTML JavaScript. PDF와 인쇄용 HTML, browser에서 저장한 PDF, 미리 복사한 PDF는 서로 다른 artifact type. 파일 존재/렌더 품질/asset 독립성/최초 네트워크 필요 여부를 별도 predicate. 이후판의 문서가 초기 요청 시기에 존재했다는 증거 아님. D4/D5의 print disable과 자동 PDF 의존은 설정상 반대. J2/J3/J12는 파일 생성 또는 일반 HTML 성공이 PDF 접근/품질을 보장하지 않는 반례.

## Q4. 공동 양립
개별 지원 support(A,x), support(B,y)에서 compatible(A,B,version,config,order,build,output_scope)를 추론하지 않는다. J5 [print-site + privacy](https://github.com/timvink/mkdocs-print-site-plugin/issues/101)는 양 순서에서도 외부 자산 남음. J6 [PDF + outline](https://github.com/HollowMan6/mdbook-pdf/issues/15)은 PDF 성공 로그 뒤 outline KeyError. 반대 설명: J7 [조건부 성공](https://github.com/HollowMan6/mdbook-pdf/issues/18) 유지자가 동일 설정 생성 보고, 원작성자는 제공 PDF에 sidebar outline 확인(본문 목차 아님), J9 [fork 우회](https://github.com/orzih/mkdocs-with-pdf/issues/93) HTML JS, PDF PNG 대체 보고. 이 두 양성은 실제 쌍의 정확한 버전, 실행 로그 및 원격 산출물 직접 검증이 없어 일반 양립을 증명하지 않는다. J8 fork만 바꾸어도 환경 오류가 남고, J10 우선순위·상속 문제는 실제 산출물 없는 설정 이슈. 핵심 관측은 공동 존재와 속성 유지: 같은 build_id에서 HTML/print/PDF의 manifest/path/hash, link resolution, network trace, assets, feature assertions. 양립 미확인과 실제 충돌 보고를 구분.

## Q5. 비교 표현
표3은 검색 후보를 바꾸지 않은 비교이며 성능 실험이 아니다. 평면 목록이 모든 원자 필수라고 가정하면 B2의 허용 대안을 불필요 배제하고 S3에서 불필요한 동시 빌드 요구를 만들어낸다. 반대로 독립 support 합집합을 충족으로 가정하면 M3/B4/B5/J5에서 잘못 승인한다. 논리보존 답은 원문에서 확인된 범위만 승인, 우선순위 미정이면 보류한다. 확인 한 문장은 가장 판정을 뒤집을 scope/logic(동일 build? file://? preferred vs required?) 하나에 집중한다. 사용자의 답이 없을 때 조건부 두 분기로 제시. 동일 두 링크는 원문에 있지 않은 최신판 추천을 당시 가능성으로 오인하지 않도록 판 한계 포함.

## Q7. 판정을 뒤집는 최소 변화

M2의 같은 배포물 요구, B3의 PDF에서도 Mermaid 필수, B1의 cold offline 여부는 질문 하나로 분기. 엄밀한 자연 요청에서 두 별개 링크가 필수이고 공동 성공까지 확인된 사례는 확보 못 함; 별도 J7 조건부 양성으로만 대조. S2의 명시 대안 acceptance 미확인.

## 조건부 대안 — 탐색기 표현 제안
입력 이벤트 원문 span → goal → requirement expression tree: AND(children), OR(children,min=1), PREFER(soft,target,rank), IF(condition,then,else), NOT(atom), UNKNOWN(alternatives,missing_span). Atom(type=artifact|capability|quality|environment|process, predicate, scope={version,build_id,deploy_id,audience,network,output_path,time}, requiredness, polarity, source_span). scope의 unknown은 wildcard match가 아닌 미확인이다. 사용자가 말한 동시가 동일 빌드인지 동일 배포인지 시간창 내인지 따로 보존. 중첩식 예: S3 AND(fresh(HTML,each_merge), IF(Sunday,refresh(PDF), retain(previous_PDF)), accessible(pdf_link,each_publish)). B2 OR(no_popup(one_page), search) + prefer(one_page) ; S4 IF(restrict_easy_PDF, AND(NOT(print_button),NOT(print_html)), ordinary_HTML). 후보 atom별 evidence에는 source_id/판/행/valid_time/claim_type를 저장, 공동 판정에는 composition_evidence를 요구. 결과 verdict: supported_single, supported_combination(scope), alternative_sufficient, reported_conflict(scope), unknown, inapplicable. AND가 필요할 때 proof edge가 없으면 hold; OR는 하나만 충족해도 다른 branch 미지원 때문에 배제하지 않음. 사용자가 부정한 출력은 검색 조건에서 positive keyword로 바꾸지 말 것.

## 추가 분석 — 반대 설명, 재현 입력
문서 작성자의 효율(S3) vs 독자의 현재 문서/오프라인 접근(M3,S2), 플러그인 유지자의 설정 범위/호환 순서(J5,J10)와 렌더러 제한(J6,J12)을 분리. 반대 설명 A: 두 부분 증거면 충분하다(서로 대안이면 B2에 한해 성립). B: 두 출력 요청이면 무조건 두 플러그인 필요하다(M1은 환경 predicate, M5는 비교, D6는 단일 도구/수동 저장 가능). C: 충돌은 모든 판에서 불가능하다(J7/J9의 조건부 양성이 반례). D: 출력 파일만 존재하면 성공이다(B4/B5/J12 반례). 같은 문헌으로 구분할 때 author intent와 공동 관측이 별개라 어느 쪽도 추론으로 대체 못 한다.

Codex Cloud 후속 입력 게이트(실행하지 않음): J5의 재현 fork https://github.com/pycolas/mkdocs-print-site-plugin/blob/master/mkdocs.yml#L19 를 원저자 시점 SHA로 고정하고 MkDocs/Material/privacy/print-site 정확판과 lock 확보. 두 페이지+상대 이미지+외부 asset 최소 docs, 동일 mkdocs.yml 두 순서와 fresh site_dir. 준비된 환경에서 `mkdocs build --clean --strict -f mkdocs.yml`, site 파일 manifest와 HTML의 외부 asset 목록, 네트워크 차단 후 chapter/print_page 각 접근 기록 비교.
