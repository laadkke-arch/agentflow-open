## 표본 구성 계획

공개 1차 자료 최소 20개를 실제 열어 읽고 `sources.json`에 URL·확인 시각·고정 버전 또는 확인 범위·확인한 내용·한계를 남긴다. 검색 결과 발췌만 읽은 페이지, 실패한 열람, 동일 페이지의 fragment 차이는 이 수에 넣지 않는다. 저장소 운영 지침은 외부 연구자료 수에서 제외한다. 원문을 통째로 복제하지 않고 자체 요약과 좁은 위치를 남긴다.

목적·대상 부분·필수 제약을 짧은 자유문으로 고정한 3~4개 문제와 총 12~18개 후보를 만든다. 서로 다른 문제 영역을 포함하고 같은 후보에 제약 하나만 바꾼 대조도 둔다. 후보는 연구자가 의도적으로 선정한 판정 자극이며 검색기 출력·대표표본·완전 정답 목록이 아니다. 후보 이름·인기·공식 문구가 답을 대신하지 않도록, 필요한 조건과 적용 단위를 적는다. 가능하면 완성 대안, 재사용 부품, 참고 원리의 역할을 모두 포함하되 역할별 같은 개수를 강제하지 않는다.

## 판정 단위와 증거 경계

판정 단위는 **문제 × 후보 × 제안한 사용 방식 × 명시된 설정 × 제공 근거**다. 후보 제품 전체를 좋음/나쁨으로 평가하지 않는다. 역할(`alternative`, `component`, `reference`)과 판정은 별개다. 한 후보가 전체 대안으로 실패해도 좁은 참고 원리로 유용할 수 있으나, 그때는 사용 방식이 다른 별도 행으로 평가한다. 실패한 전체 대안의 점수를 참고 가치로 올리지 않는다.

문제는 합성 입력이다. 외부 자료의 사실과 합성 사용 조건을 구별한다. `DIRECT_DOCUMENTED`도 연구자의 문서 기반 기대 판단이며 설치·통합 성공을 의미하지 않는다. 저장소의 D1 문서 확인, D2 구현 관찰, D3 독립 실행, D4 프로젝트 적용을 자동 승격하지 않는다.

## 네 판단축 — 합산하지 않는다

| 축 | 기록값 | 질문 |
| --- | --- | --- |
| L 출처 연결 | `ok / broken / missing` | 이 후보와 주장에 연결한 원문·버전·위치를 실제 찾을 수 있는가? |
| E 원문 뒷받침 | `supported / contradicted / unknown` | 원문은 정확히 그 주장과 조건을 지지하는가? 다른 대상·다른 버전·홍보 표현만 인용한 것은 아닌가? |
| H 요구 충족 | 각 필수 조건마다 `pass / fail / unknown / not_in_scope` | 제시된 사용 방식이 조건을 만족하는가? `not_in_scope`는 처음부터 범위를 좁힌 참고 원리에만 쓰고 전체 대안에는 쓰지 않는다. |
| T 전이 논증 | `not_needed / mapped / analogy_only / unknown` | 출발 분야의 어떤 요소·관계·불변조건을 대상에 옮기는가? 필요한 연결 작업·실패 조건·반증 관측이 있는가? |

L이 통과해도 E/H/T가 통과하지 않는다. 문서가 주장을 지지한다고 해서 합성 문제의 필수 제약까지 만족하는 것은 아니다. 출처가 없으면 사실 자체를 거짓으로 판정하지 않는다. 알려진 위반과 자료 부족을 분리한다.

## 기대 판정 4종과 우선순위

1. `SURFACE_OR_CONSTRAINT_MISMATCH` — 제안한 사용 방식에 결정적인 알려진 제약 위반이 있거나, 이름만 같은데 핵심 작동 관계가 다르다. 어느 조건이 실패하는지 적는다. 자료가 없다는 이유만으로 이 판정을 주지 않는다.
2. `INSUFFICIENT` — 결정적인 사실·설정·주변 조건이 미확인이며 결과가 그 답에 따라 달라진다. 알려진 결정적 위반이 없다. 추가 확인 한 가지와 답별 판정 변화를 적는다.
3. `CONDITIONAL_TRANSFER` — 참고할 관계가 원문으로 뒷받침되고, 대상의 좁은 부분과 대응·연결 작업·비적용 영역·실패 조건을 구체적으로 적을 수 있다. 실제 전이 성공은 주장하지 않는다. 필수 전제가 미확인인데 단순히 ‘조건부’라는 말로 건너뛰지 않는다.
4. `DIRECT_DOCUMENTED` — 제안한 설정·적용 단위의 모든 필수 조건에 긍정 근거가 있고 결정적 모순·미확인이 없다. 통상적인 설정·연결은 구체적으로 밝혀야 하며, 문서에 없는 새 안전장치나 알고리즘을 몰래 추가해서는 안 된다.

혼합 근거에서는 결정적 `fail`을 우선하고 다른 `unknown`도 보존한다. `unknown`을 0점으로 바꾸거나 점수 평균으로 지우지 않는다. 근거가 바뀌면 같은 후보라도 판정이 바뀔 수 있다. 자료 부족의 경우 ‘이 자료 묶음만으로 부족’과 ‘제품 자체가 지원하지 않음’을 구별한다.

## 채점과 보류

각 응답은 후보별 `판정 / 역할·적용 단위 / E / 조건별 H / 근거 위치 / 조건·실패 / 최소 다음 확인`을 작성한다. 기준 답의 문구 일치보다 원문과 필수 제약의 추적 가능성을 본다.

안전한 판정의 필수 통과 항목:

- 결정적 위반을 직접 적합으로 승인한 경우가 0개여야 한다.
- 근거 부족을 검증된 효용·적용 성공으로 확정한 경우가 0개여야 한다.
- 참고 원리는 대응 관계·필요 연결·적용하면 안 되는 경우를 모두 적어야 한다.
- 문서 열람/코드 관찰/실행/통합의 증거 수준을 정확히 표시해야 한다.

보조 점수는 차원별 0~2로만 기록한다: 근거 정확성(없음/부분/결정 근거 정확), 제약 추적(없음/부분/전부), 설명 유용성(홍보/추상 조건/구체 다음 확인). 합계나 평균으로 필수 실패를 상쇄하지 않는다. 이 점수는 사람/모델 응답의 진단용이며 후보 제품 순위 점수가 아니다. 보류 자체는 실패가 아니고, 확인 가능한 근거가 있는데 전부 보류하는 것은 근거/제약 추적에서 감점한다.

## 독립 평가 절차

1. 작성자가 기준·문제·후보 입력을 고정하고 기대 판단을 별도 파일에 저장한다.
2. 새 문맥의 내부 검토자에게 `PROTOCOL.md`와 `CASES.json` 및 그 안의 원문 URL만 제공한다. `EXPECTED.json`, 해석이 포함된 `sources.json`, 연구 결론은 제공하지 않는다. 정답을 읽지 말라고 명시한다. 제공 문맥을 분리할 뿐 강제 파일 접근 격리라고 부르지 않는다.
3. 검토자는 후보 순서를 바꾸어 원문을 확인하고 독립 판단을 저장한다. 문제 작성에 참여한 연구자는 블라인드 검토자가 될 수 없다.
4. 기대 판단과 응답을 뒤에 대조해 제약 해석/사실 오류/자료 부족/진짜 가치 판단 이견을 구분한다. 작성자 혼자 고친 것을 합의라 부르지 않는다. 원래 응답·수정·채택하지 않은 이견을 남긴다.
5. 예산·도구 때문에 두 번째 독립 판정자가 없으면 한 명만 했다고 적는다. 내부 모델 검토는 사람 사용자 시험이나 독립적인 모델 계열 간 재현성 검증이 아니다.

## 누락·재현율의 해석

이 팩은 외부 세계의 적합 후보 전체를 알지 못한다. 따라서 검색 전체의 recall, precision, nDCG, 승률 또는 사용자 효용을 계산하지 않는다. 팩 안에서 의도한 위험 유형을 놓친 건수, 근거 없는 승인 건수, 보류/오답 혼동, 후보별 이견 수만 분모와 함께 보고한다. ‘다른 유용한 후보가 없었다’는 결론도 허용하지 않는다. 후속 검색 비교에는 독립적으로 수집한 후보 풀, 미판정 분리, 새 후보 추가 시 기준 동결/재판정 절차가 별도로 필요하다.

## v1.1 명확화 — 독립 v1 판정 이후

이 절은 R11/R12에서 드러난 H의 적용 층위 이견을 처리한다. 원본 기준은 `f4f08a0ef5f5354f814abb2d6fe98d0b2f53b114`에서 읽을 수 있다. 네 축·네 라벨·우선순위·합격 gate는 바꾸지 않았다.

- 각 행에 `H_assessment_scope`를 붙인다. `proposed_configuration`은 명시된 구성을 문서와 입력 조건으로 평가하며, `reference_design`은 제안된 좁은 설계 관계 및 필요한 연결의 논리적 충족만 평가한다.
- 문서 기반 설계 조건의 `pass`를 관측된 구현 성공으로 읽지 않는다. `runtime_observation: not_performed`를 별도로 남긴다. 조건부 참고의 미구현 상태는 `implementation_H: unknown`으로도 표시할 수 있다.
- R11/R12의 숫자 상한이 대상 요구에서 사라지는 것은 아니다. 참고 원문 자체가 그 상한을 입증했다는 뜻도 아니다. 설계 범위의 pass를 쓸 때에는 credit/permit·buffer·완료 사건의 연결과 실패 조건을 함께 기록해야 한다.
- 원래 v1 검토자가 실행 검증을 reference 범위 밖으로 읽어 일부 H를 `not_in_scope`로 표시한 것은 원응답에 그대로 보존한다. 이를 사후에 라벨 오답이나 합의된 수정으로 바꾸지 않는다.
- 원문으로 확인되지 않은 비결정적 조건도 `unknown`으로 남긴다. R03의 log 보존과 본문 재구성, R04의 local field 변경과 메모 편집 수명은 별도다. 이미 다른 조건이 fail이어도 빈칸을 pass로 채우지 않는다.
