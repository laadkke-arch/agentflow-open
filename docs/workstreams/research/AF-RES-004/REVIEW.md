# AF-RES-004 검토 기록

## 1. 무엇을 실제로 검토했는가

새 문맥의 내부 검토자 A와 B가 각각 **18개 행**을 기대 답 없이 판정했다. 입력은 `PROTOCOL.md` v1, `CASES.json` v1.0, 그 안의 원문 URL·고정 문서 위치였다. 원래 응답을 먼저 커밋한 후 작성자가 대조했다. 이후 B는 기대 답을 볼 수 있는 비블라인드 수정 검토를 수행했다. 이 단계들을 하나의 블라인드 시험으로 합치지 않는다.

| 단계 | 입력/저장 커밋 | 실제 시각(UTC) |
| --- | --- | --- |
| 기준 v1 동결 | `f4f08a0ef5f5354f814abb2d6fe98d0b2f53b114` | 2026-11-19 15:51:21 |
| 입력 v1.0 동결 | `b245a275b0e8d1a2552aa36b5900cd219ff73b73` | 16:08:57 |
| 작성자 답 v1.0 동결 | `13e7655212726ce1941c3aeb278c834611378887` | 16:11:54 |
| A 원판정 완료 / 보존 | `29baa1d14a5468fcfc10f1ff289013a0f93a4743` | 응답 내부 완료 시각 16:21:45 |
| B 원판정 완료 / 보존 | `d0a2f23bfa0f2dc32824ce507c56d83d3d7fd82e` | 응답 내부 완료 시각 16:22:03 |
| B의 v1.1 수정 검토 | `d6cfd4fbb2c32a5753db0b99a0af1d52d221aa5b` | 응답 내부 검토 시각 16:28:30 |
| B의 v1.2 R12 한 항목 확인 | 아래 §5에 응답을 보존 | 작성자 수신/확인: 16:32 UTC |

한국 날짜는 모두 **2026-11-20**이다. 커밋 시각과 검토자가 파일 안에 적은 검토 시각을 구별했다.

원자료는 [A](blind-review-a.json), [B](blind-review-b.json), [v1.1 수정 검토](revision-review.json)에 있다. 원판정 A/B는 수정하지 않았다. 최초 기대 답은 [동결 커밋의 EXPECTED](https://github.com/laadkke-arch/agentflow-open/blob/13e7655212726ce1941c3aeb278c834611378887/docs/workstreams/research/AF-RES-004/EXPECTED.json)에서 읽을 수 있다. 현재 CASES/EXPECTED는 v1.2이므로 원판정의 입력과 다르다.

## 2. 독립성 및 원문 확인 범위

A는 CASES의 A 순서, B는 B 순서를 사용했다. 두 검토자 모두 PROTOCOL/CASES 외의 프로젝트 근거 파일, EXPECTED, 작성자 결론, 다른 검토자의 답을 사전 열람하지 않았다고 기록했다. 작성에 참여했던 방법론 조사자는 블라인드 검토자로 사용하지 않았다.

| 검토자 | 실제 읽은 서로 다른 후보 자료 | 접근 보완 | 한계 |
| --- | --- | --- | --- |
| A | 26개. 어느 행에도 쓰이지 않는 S11은 미열람 | 웹으로 읽은 23개와 고정 Git 원본 S08/S09/S17 3개 | 모든 Git pin을 재대조하지는 않았음. 읽은 절만 주장 |
| B | 27개. 직접 행 근거 26개, S11은 Standard/FIFO 범위 확인 배경 | 고정 Git 원본 9개 추가 대조. S17 웹 실패는 지정 커밋 fetch로 보완 | 재열람을 별도 자료 수로 세지 않음 |
| B 수정 검토 | S12 1개 재확인 | v1.1 지정 세 파일의 원격 커밋과 로컬 사본 대조 | 전체 18행·27원문 재평가가 아님 |
| B v1.2 확인 | R12와 수정 이력만 | 지정 CASES/EXPECTED의 두 커밋 | 외부 자료 재열람·실행 없이 연결 명시 여부만 확인 |

B가 v1.0 로컬 PROTOCOL/CASES를 원격 동결 파일과 대조했을 때 끝 LF 한 개 차이만 있었다. 의미 변경은 없었고 검토자는 입력을 수정하지 않았다. 최종 저장 확인에서는 작성자가 원격 Git blob에 맞춰 로컬 끝 LF를 정리하고 byte 수준으로 대조한다. 이 정리는 연구 내용이나 원판정을 바꾸는 수정이 아니다.

**문맥 분리의 한계:** 동일 모델 계열 내부 검토이며 인간 평가나 독립 모델 계열 간 재현성 검증이 아니다. 파일시스템을 강제로 격리하지 않았고, 접근 범위는 지시와 각 검토자의 기록에 근거한다. 후보·역할·설정·제공 원문을 작성자가 고른 데서 오는 프레이밍도 남는다. 사전 학습 지식을 제거한 실험이나 현장 사용자 시험으로 설명하지 않는다.

## 3. v1.0 원판정의 결과

| 항목 | 작성자 최초 기대 | A 원판정 | B 원판정 |
| --- | ---: | ---: | ---: |
| DIRECT_DOCUMENTED | 7 | 7 | 7 |
| CONDITIONAL_TRANSFER | 3 | 3 | 3 |
| SURFACE_OR_CONSTRAINT_MISMATCH | 6 | 6 | 6 |
| INSUFFICIENT | 2 | 2 | 2 |
| 작성자와 최종 라벨 일치 | 해당 없음 | 18/18 | 18/18 |

A와 B의 최종 라벨도 18/18 같다. 그러나 **라벨 일치가 조건별 근거의 완전성을 뜻하지 않았다.** A는 H 값 1개, B는 H 값 5개에서 최초 기대 답과 달랐다. 중복을 합치면 4개 행의 5개 조건이다.

| 행·조건 | 최초 기대 | A | B | 이견의 성격 |
| --- | --- | --- | --- | --- |
| R03 / P01-H2 | pass | pass | unknown | patch log 보존과 초기 상태+log 재구성 경로의 구별 |
| R04 / P01-H1 | pass | unknown | unknown | local field setter와 기존 메모의 offline 편집 생애주기 구별 |
| R11 / P03-H1 | pass | pass, 구현 unknown 별도 | not_in_scope | reference 설계의 숫자 상한과 관측된 구현 상한을 어느 H 층위에 기록하는가 |
| R12 / P03-H1 | pass | pass, 구현 unknown 별도 | not_in_scope | 위와 같은 적용 층위 이견 |
| R12 / P03-H2 | pass | pass, 구현 unknown 별도 | not_in_scope | 적용 층위 이견. 이후 수정 검토에서 실제 연결 누락도 별도 발견 |

다음은 원응답을 읽어 확인한 **제한된 관문 관찰**이다. 검색 품질이나 실제 제품 효용의 지표가 아니다.

| 관찰 항목 | A | B |
| --- | ---: | ---: |
| 지정된 알려진 실패 6행을 직접 적합으로 승인 | 0/6 | 0/6 |
| 지정된 설정 미제공 2행을 직접 적합으로 승인 | 0/2 | 0/2 |
| 조건부 참고 3행의 대응·필요 연결·반례 기록 | 3/3 | 3/3 |
| 후보 설치/실행/통합 성공을 관측했다고 주장 | 0/18 | 0/18 |

이 표는 H 세부의 과잉 확정이 없다는 뜻이 아니다. R03-H2처럼 최종 라벨은 올바르지만 비결정적 조건을 과하게 승인하는 문제가 실제로 드러났다. 보조 0~2 점수는 전 행에 수치화하지 않았다. 규칙과 합격/실패 응답 예시는 PROTOCOL/RESEARCH에 남겼고, 이번 실제 대조는 라벨·조건별 이견·필수 관문·근거 위치에 집중했다. 합계·평균 점수나 검색 전체 recall/precision/nDCG를 계산하지 않았다.

## 4. 원문·입력으로 심사한 이견과 수정

### 4.1 R03: 보존된 log가 복구 경로를 대신하지 않는다 — B 지적 채택

v1.0은 IndexedDB에 patch log를 보존한다는 입력만으로 H2를 pass로 썼다. 초기 문서의 영속 보존과 재진입 시 replay 경로는 명시되지 않았다. 작성자는 B의 더 좁은 해석을 채택해 v1.1 이후 H2를 **unknown**으로 수정했다. R03의 결정적 H3 실패는 [RFC6902 §3/§4.3](https://www.rfc-editor.org/rfc/rfc6902.html)의 순차 replace 의미와 반대 도착 순서의 합성 trace로 유지된다. 최종 mismatch 라벨은 바뀌지 않는다.

A의 원래 H2 pass도 그대로 남긴다. A가 이후 unknown에 동의했다고 쓰지 않았다. 이 사례는 “라벨만 비교하면 근거의 작은 과장이 보이지 않는다”는 자체 반례가 되었다.

### 4.2 R04: setter 존재를 메모의 전체 생애주기로 확대하지 않는다 — A/B 지적 채택

[Yjs Awareness(S06)](https://docs.yjs.dev/getting-started/adding-awareness)는 local field 변경과 비영속 presence 상태를 설명한다. 이 정보만으로 기존 메모를 서버 단절 동안 어떤 수명으로 편집하는지까지 확정한 최초 H1 pass는 넓었다. v1.1 이후 H1을 **unknown**으로 좁혔다. 명시적인 persistence 부재의 H2 fail과 단일 본문 의미의 H3 unknown은 유지한다. Awareness가 CRDT라는 사실 자체를 부정하지 않는다.

### 4.3 R08/R18: 시간의 기준점과 visibility 한계 — 공통 지적 채택

두 검토자는 24시간 완료를 수락부터 대기·단절·재시도를 포함한 총 경과시간으로 해석했으며 순수 처리시간이면 다시 판정해야 한다고 적었다. v1.1은 총 경과시간 **24시간 미만**을 입력에 명시했다.

[SQS visibility timeout(S12), Best practices](https://docs.aws.amazon.com/AWSSimpleQueueService/latest/SQSDeveloperGuide/sqs-visibility-timeout.html)의 최초 수신부터 최대 12시간 및 연장해도 한계가 초기화되지 않는 설명을 작성자도 재확인했다. R08은 이 한계 안에서만 연장하고 timeout 후 중복 재전달은 주어진 멱등 handler로 다룬다고 명시한다. 이 변경은 실제 작업 완료시간이나 계정 설정의 관측이 아니다. R18의 외부 증가→delete 전 중단→재전달 반례는 그대로 남는다.

### 4.4 R11/R12: 설계와 구현의 같은 pass 기호 — 프로토콜 명확화

A는 설계 범위 H pass와 implementation_H unknown을 분리했다. B는 실제 숫자 상한의 구현 검증을 좁은 reference 범위 밖으로 읽어 일부 H를 not_in_scope로 썼다. 서로 다른 층위를 같은 칸에 넣을 여지가 있었으므로 원래 B 값을 억지로 오답으로 만들지 않았다.

PROTOCOL v1.1은 H_assessment_scope와 runtime_observation을 추가하고, 현재 EXPECTED의 참고 행에는 implementation_H unknown을 별도로 둔다. **대상 문제의 숫자 상한을 면제한 것이 아니다.** 설계상 pass를 쓰려면 원문의 관계와 대상의 permit/credit·buffer·완료 연결을 설명해야 한다. 원문이 제공하는 사실과 연구자가 더하는 연결 조건은 분리한다. 원래 라벨·우선순위·fail gate는 유지했다.

### 4.5 R09·S09: 확인된 원판정의 일치, 새 수정으로 포장하지 않음

작성자·A·B 모두 R09의 복제/보존 정책뿐 아니라 결과 영속화와 manual ack의 순서도 unknown으로 남겼다. manual ack라는 이름만으로 후처리 ack를 단정하지 않았다. 또한 고정된 RabbitMQ 4.1 문서에 4.3 설명이 섞이는 한계를 모두 구분했다. 원문이 명시한 queue argument와 실제 runtime 검증을 분리했다. 이는 원래 기록에 이미 있었던 일치점이며 “독립 검토 뒤 처음 고친 결함”으로 세지 않는다.

### 4.6 v1.1 수정 검토가 다시 찾은 R12 연결 누락 — 실질적인 v1.2 보완

B는 v1.1의 대부분 수정을 확인하면서, R12의 **4 permits와 queue 8만으로 producer가 실제 기다리게 되지는 않는다**는 이견을 새로 남겼다. lazy iterator를 끝까지 읽으며 permit을 기다리는 task를 먼저 만들면 처리 중 4·큐 8을 지켜도 대기 task가 누적될 수 있다. 실행한 결과가 아니라 주어진 설계에서 허용되는 논리 반례다.

이 지적은 단순 표기 문제보다 크다. 작성자는 v1.1 H2 pass의 연결 설명이 불충분했음을 인정하고, v1.2의 CASES R12에 다음을 새 조건으로 넣었다.

- producer가 실제 가용 permit과 유한 큐 용량을 기다린 뒤 다음 작업을 만든다.
- 입력별 permit 대기 task를 먼저 만들지 않는다.
- 다른 무제한 buffer로 작업을 옮기지 않는다.

EXPECTED의 H2 이유·transfer_conditions.bridge·minimum_next_check에도 같은 조건을 연결했다. 이 연결은 **대상 소프트웨어에 추가할 설계 조건**이다. [Toyota 원문(S18)](https://global.toyota/en/company/vision-and-philosophy/production-system/)이 제공한 실행 기능도 아니고 v1.0 블라인드에서 이미 확인된 구성도 아니다. 원래 v1.1의 잔여 이견 파일을 완료/동의로 덮어쓰지 않았다.

## 5. B의 v1.2 한 항목 확인 — 비블라인드 응답 보존

B는 다음 두 커밋의 R12 및 revision_history만 다시 읽었다.

- CASES `ba1b7737ed48793ed709c8c8c4a1e0d683f7e31e`
- EXPECTED `246401445671320e506916ca57fe28fc03680c76`

B의 후속 응답 첫 문단을 그대로 보존한다.

> v1.2 R12의 한 변경을 비블라인드로 확인했습니다. 앞서 남긴 R12-H2의 연결 조건 누락은 문서상의 설계 조건 수준에서 해소됐으며, 이번 확인 범위에서 남은 이견은 없습니다.

후속 응답은 CASES configuration과 EXPECTED H2/bridge에 producer의 실제 대기·선행 task 금지·우회 buffer 금지가 명시됐음을 확인했다. 이를 대상 측의 실질적인 새 연결로 기록한 수정 이력에도 동의했다. CONDITIONAL_TRANSFER, reference_design, runtime_observation=not_performed, implementation_H=unknown은 유지됐다고 확인했다.

**확인 한계도 함께 보존한다:** B는 전체 재평가·외부 원문 재열람·소프트웨어 실행을 하지 않았고 파일을 수정하지 않았다. 이는 새 블라인드 시험·독립 합의·제품 검증이 아니다. 기존 B가 수정 의도와 기대 답을 읽은 좁은 문서 확인이다.

그 뒤 EXPECTED의 notice에서 “현재 v1.1”을 “중간 v1.1 / 현재 v1.2”로 고친 커밋은 `16089f5ba43c34837840ead5435bc9a87251bd61`이다. 작성자가 위 B 확인 커밋의 JSON과 대조해 **변경된 최상위 필드는 notice뿐이고 R12와 revision_history는 동일함**을 확인했다. 이 메타데이터 수정까지 B가 다시 검토했다고 주장하지 않는다.

## 6. 현재 상태와 남은 한계

현재 입력/기대 답은 v1.2, 기준은 v1.1이다. 최초 최종 라벨 18개는 유지하지만 두 H 값은 미확인으로 좁혔고, 시간 조건·증거 층위·R12의 필요한 연결을 보강했다. v1.0의 라벨 일치를 현재 버전 전체의 새 블라인드 결과로 소급하지 않는다.

현재 문서 변경 범위에서 열려 있는 결정적 이견은 없다. 그러나 다음은 여전히 미검증이다.

- 후보의 실제 설치·작동·장애 복구 및 프로젝트 통합(D3/D4).
- 전이 원리를 구현했을 때의 비용·복잡도·성능 또는 사용자 이득.
- 작성자가 고르지 않은 새 문제와 후보에서도 같은 기준이 작동하는지.
- 인간 판정자·다른 모델 계열·실제 사용자 과제의 재현성.
- 전체 검색 공간의 유용 후보 누락/재현율.

후속 검증은 새 작성자의 holdout 문제나 실제 적용 시험을 별도 배정해 추가해야 한다. 이 묶음의 완료는 작동 가능한 평가 절차와 추적 가능한 문서 기반 기대 판단을 인계한 데 있으며, 검증된 제품 실효성을 선언하는 데 있지 않다.
