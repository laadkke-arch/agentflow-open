## 4. 포함·분석 원칙

1. 시스템 기능은 제작자 문서·공식 구현·제작자 논문으로 확인한다. 외부 평가 연구는 기능 약속을 실제 보증으로 바꾸지 않게 하는 반증 자료로 쓴다.
2. 운영 상태는 '접속됨'만으로 서비스 전체 가용성이라 하지 않는다. 운영은 공식 문서/제품 안내가 유지되는 상태라는 문서상 판정이며, 종료·부분 중단은 사건 범위를 명시한다. 쇠퇴는 사용량/갱신의 직접 근거가 없으면 쓰지 않는다.
3. 데이터 라이선스와 소프트웨어 라이선스, 무료 열람과 재사용 허가, API 존재와 실제 접근 성공을 구별한다. 법률 자문이 아니라 읽은 조건의 기록이다.
4. 시스템의 자료 규모는 원문 수치와 날짜가 있을 때만 적는다. 과거 수치를 현재 전수 색인 규모로 갱신하지 않는다.
5. 결과 설명에서 링크 존재·주장 뒷받침·부분 적합성·전이 가능성·최신 유효성을 따로 읽는다. 제품 소개 문구는 효과의 실험 증거가 아니다.
6. 실패는 전면 종료, 특정 제품 중단, API 중단, 데이터 갱신 중단, 운영 모델 전환을 구별한다. 공식 이유의 직접 인용은 자료 하나당 총 25단어 이하로 제한한다. 연구자 원인 해석에는 H를 붙인다.

### 다섯 요소의 사전 판정 기준

- 구조·부분 입력: 부분의 구성/관계와 목적을 동시에 받을 수 있는 문서화된 입력. 자유문을 받는 것만으로 구조 해석 정확성을 보증하지 않는다.
- 부품 단위 연결: 완성품 전체가 아닌 패키지·기능·패턴·코드 구간을 별도 결과로 연결.
- 타 분야 원리: 서로 다른 영역 사이에서 옮길 원리/관계의 대응을 설명. 여러 업종의 문서를 색인한다는 사실만으로 충족하지 않는다.
- 링크 중심 설명: 결과의 원문 위치와 도움의 이유를 검토할 수 있게 연결.
- 근거 유지: 출처/버전/갱신 또는 무효화 관계를 관리. URL 생존만으로 주장의 유효성 유지를 충족하지 않는다.

표의 '이미 충족'은 해당 요소의 문서상 기능 충족, '부분 충족'은 일부 경로/사람 판단 필요, '비어 있음'은 **이번에 읽은 공식 범위에서 확인하지 못함**이다. 시장 전체에 기능이 없다는 선언이 아니다. 목표 문제에서의 D4 유용성은 별도 검증이다.

## 5. 검색·반증 원칙

- 질의 원문, 실제 UTC 시각, 도구/엔진, 관측한 결과, 후속으로 연 source ID를 SEARCH_LOG.json에 남긴다. 순위를 도구가 제공하지 않으면 생성하지 않는다.
- 일반 발견에는 검색 도구를 쓰고, 최신 상태·공식 출처·모순 확인에는 강한 검색 엔진과 공식 도메인/작성자 원문을 사용한다.
- 반대 가설 A: '범용 LLM 검색이 이미 충분히 한다'. 부분 문제 입력·자료 파일·repository 문맥·인용·추천 설명을 공식 문서와 실제 평가 논문에서 찾는다.
- 반대 가설 B: '기존 디렉터리와 awesome 목록이 이미 충분하다'. 오래 유지된 목록의 선택 기준·기여·링크 관리와 구체 부품 목록을 찾는다.
- 필수 반례 탐색: 풍부한 구조이나 중단, 간단한 링크 목록이나 지속, 유료 노출/SEO 영향, 허위 링크/인용 실측, 예상 빈자리를 이미 제공한 기능.
- Q7 공개 실행은 선택 사항이다. 시행하면 로그인·계정·유료 API 없이 P1/P2/P03의 원문만, 시스템당 최대 3질의. 화면에서 본 순위·링크·설명만 D3로 기록한다. 본문 문서 열람을 실행 관측으로 올리지 않는다.

## 6. 분담·보존·커밋

내부 병렬 조사: (a)–(c), (d)–(e)/생성형 평가, 실패 자료를 독립 분담하고 주 작성자가 (f)–(g)와 종합·반증을 담당한다. 내부 검토는 '내부 별도 검토'라고 기록한다. 모든 파일은 owned_path 내부에만 쓴다. 주 작성자만 커밋·원격 ref를 갱신한다.

커밋 순서: (1) 이 SCOPE (2) a–c 행/원장/질의 (3) d–g 행/원장/질의 (4) 실패 (5) LANDSCAPE/GAP (6) SELF_CHECK 및 재현 가능한 무결성 검증 (7) HANDOFF 단독. 중간 보정 커밋은 해당 이유를 남긴다. 마지막에 원격 HANDOFF 본문을 다시 읽어 바이트 일치를 확인한다.

Q1–Q8 각각 서로 다른 출처 종류 2개 이상과 반증 질의/결과가 있어야 자기 점검을 통과한다. 기능 부재·인과·현 상태를 확인할 수 없으면 결론을 좁힌다. 필수 자료를 보강할 수 없을 때는 완료를 주장하지 않고 이유와 최소 다음 확인을 인계한다.
