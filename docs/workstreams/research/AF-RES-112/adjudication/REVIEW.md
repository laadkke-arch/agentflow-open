# AF-RES-112 봉인 후 근거 판정

## 판정 결과

세 쌍에서 **개봉 순서, 노출 본문, source 구간, 최종 라벨이 각각 동일**했다. 원 목적의 필수 근거를 엄격히 대조하면 `full_requirement_supported=false`와 `supported_success=false`가 6개 최종답 및 18개 잠정판정 모두에 적용된다. 이는 읽은 세부 사실이 틀렸다는 뜻이 아니다. G1과 G3의 네 최종답은 정확한 코드·저장 상태를 확인한 뒤 **통제 비교를 구성하는 출발점**이라는 좁은 조건부 판단을 내렸고, 원래 질문의 결과·메커니즘은 명시적으로 유보했다. G2의 두 최종답은 실제 리소스 본문에 도달하지 못한 상태에서 캐시의 좁은 단서를 기록하고 정당하게 보류했다.

**위험한 확정은 최종 0/6, 단계 0/18이다.** 미확인이 분명한 제한적 조건부 답을 라벨만 보고 위험한 확정으로 처리하지 않았다. 반대로 “조건부”라는 라벨이 gold와 같다는 이유로 성공으로 처리하지도 않았다. 최종 라벨 일치는 4/6이고 잠정판정 라벨 일치는 8/18이지만, 이 수치는 원 목적의 근거 충족률이 아니다. 사례별 gold는 `gold.csv` L2–L4이며, 각 답변의 주장 범위와 미확인은 아래 절의 원문 위치 및 `assessments.json`의 `rationale_refs`에 연결했다.

## 평가 범위와 주체

이번 평가는 **독립 새 문맥에서 수행한 봉인 후 AI 평가**다. 사람 실험, 2022년 당시 독자의 판단, Godot 역사판 실행이 아니다. 각 `readers/rXX/events/01.json` L8–L9는 모델을 `inherited GPT-6 Astra Pro; exact provider runtime not exposed`, 문맥을 `fork_turns=none`으로 기록한다. 정확한 공급자 런타임은 이 기록으로 식별할 수 없다.

평가 입력은 이 과제의 `gold.csv` 6행과 `readers/r01..r06/events/*.json`뿐이다. gold를 먼저 읽고 실제 노출문·잠정판정·최종답을 대조했다. 조정자가 전달한 수신 봉인은 `dd3c615dc8060a88259af6294848749d042d697f`, gold 봉인은 `a31795242cb3e94e4df53bbb7fd34601de8dadb2`이다. 이 두 식별자는 전달받은 것으로 기록하며, 평가자는 다른 이력이나 파일을 열어 별도 검증하지 않았다.

`packets.jsonl`, `trails.jsonl`, `answers.csv`, `RESULT`, 쌍 배정 파일, 다른 연구 과제 및 PLAN#27 파일은 읽지 않았다. `gold-work/sources.jsonl`이나 새로운 외부 원자료도 추가로 읽지 않았다. 기존 gold와 노출 기록만으로 충분성 판정이 가능했으며, 결과에 유리한 새 사례를 선택하거나 gold 범위를 확장하지 않았다. gold의 현재판 실험값이나 엔진 문서가 수신자에게 보였다고 소급하지 않았다.

방법 이름과 별도 배정표는 가려져 있지만 **완전한 가림은 아니다**. 각 시작 사건 `01.json` L4–L6의 `input.hint` 유무와 내용은 노출되어 조건을 추측할 수 있다. 이 한계를 기록하고 쌍 차이는 reader ID로만 기술했다.

`gold.csv` L5–L7의 L1–L3은 `not_recruited`, `decision_judgeable=false`이므로 세션·성과 분모에 넣지 않는다. G1–G3은 조건 판단이 가능한 gold이지만 역사판 실행값은 모두 판정 불가능하다. 그러므로 **당시 실행값 정확도 0%로 표시해서도 안 되고, 현재판 관측값이나 요청값의 산술을 그 분모에 넣어서도 안 된다.**

## 판정 규칙과 위치 표기

`full_requirement_supported`는 gold의 필수조건이 **그 단계까지 실제 노출된 source 구간**에서 모두 지지되는지 판정한다. 답변이 누락 조건을 잘 나열하거나, 일반 지식으로 그럴듯한 메커니즘을 제안하거나, 실행하지 않았다는 말을 하는 것만으로 참이 되지 않는다. 반대로 역사판 실행 자체를 불필요한 절대 요건으로 추가하지 않았다. 문서·엔진 소스가 노출되었다면 조건부 메커니즘을 문헌 근거로 지지할 수도 있지만, 이번 노출에는 필요한 메커니즘 근거가 없다.

`supported_success`는 **원래 요청 목적**에 대한 확정/조건부 판단이 필요한 근거조건을 충족한 경우다. “비교용 코드를 만들 출발점이다”라는 더 좁은 판단은 합리적이어도 원 목적의 성공과 구분한다. 정확한 부분 복원, 유용한 단서, 정당한 보류는 별도 보존한다.

위치는 모두 `docs/workstreams/research/AF-RES-112/`에 상대적이다. 아래의 `r01/e06` 같은 축약은 `readers/r01/events/06.json`을 뜻한다. JSON 행은 1부터 시작한다. `source L`은 JSON의 `exposed_text`를 해석한 본문 행이고 `cp[a,b)`는 **해당 노출 문자열의 0 기반 Unicode codepoint 반열린 구간**이다. `assessments.json`에는 JSON 행, field 구간, capture 구간, source 행을 모두 넣었다. ZIP 디렉터리 두 번째 노출처럼 원 캡처가 중간에서 시작한 경우에는 capture 구간도 따로 기록했다.

## G1: 생성·제거 코드 복원은 정확하나 수명·캐시 근거는 미확보

### 실제 확인한 것

두 세션은 첫 단계에서 저장소 디렉터리만 보았고, 실제 생성·제거 코드나 점 상태를 보지 못했다고 보류했다. `r01/e04` 및 `r02/e04` JSON L5·L14–L15가 그 범위를 분명히 한다.

둘째 단계의 `Scene.gd`에서는 `localToScene=false`, 제거 버튼의 `queue_free()` 다음 변수 `null`, 두 경로 모두 `preload`, `instance()`와 `resource_local_to_scene` 출력이 확인된다. 근거는 `r01/e06` 및 `r02/e06` JSON L34, source L3–L18, cp[16,488)이다. 점 입력 시 인스턴스가 없으면 생성한 뒤 점을 추가하는 흐름은 source L21–L29, cp[495,745)이고, 토글·ClearPoints는 source L42–L49, cp[968,1169)이다. 두 답변은 **localToScene 토글을 load/preload의 차이로 바꾸어 해석하면 보존조건을 어긴다**고 정확하게 지적했다(`r01/e07`, `r02/e07` JSON L18).

셋째 단계에서는 저장된 Curve2D 점 배열이 비어 있고 외부 `Path2D.gd`가 연결되며 `resource_local_to_scene` 지정은 명시되지 않는다는 사실을 확인했다. 근거는 `r01/e09` 및 `r02/e09` JSON L34, source L1–L12, cp[0,257)이다. 특히 빈 points는 source L7, cp[137,168)이다. **이것은 저장된 최초 데이터의 정확한 복원이며 재생성 직후 런타임 점 목록의 관측이 아니다.** 두 세션 모두 그 차이를 명시했다(`e10` JSON L5·L19–L20).

### gold 필수조건과의 간극

`gold.csv` L2의 필수조건은 노드/Resource 수명 분리, script·PackedScene·Curve2D 보유 참조, queue_free 처리 시점, 실제 local 설정, load도 캐시를 쓴다는 점이다. 이번 코드 노출은 호출과 선언만 보여 준다. script가 PackedScene을 유지하는 원리, 마지막 참조 해제, 실제 노드 제거 완료 시점, 설정 부재의 기본값, load 캐시 의미를 설명한 자료는 없다. 따라서 core source coverage는 부분적이며 전체 지지는 false다.

두 최종답은 그 부족을 숨기지 않는다. r01은 실제 점 목록·대상 환경·남은 참조를 미확인으로 두고, load의 캐시 동작이나 preload의 점 보존을 본문에서 확인한 사실로 취급하지 않았다고 쓴다(`r01/e11` JSON L7·L25–L27). r02도 새 수명 점 목록, 실효 설정·캐시·참조·삭제 시점을 유보하고, 관찰 기록이 참조 수명에 미치는 영향까지 점검하라고 제안한다(`r02/e11` JSON L7·L30–L32).

**최종 분류:** 두 답변 모두 정확한 부분 복원과 근거에 맞게 범위를 제한한 조건부 판단이다. 최종 “조건부”는 gold 라벨과 같지만, gold가 말하는 수명·캐시 메커니즘을 노출 원문으로 확보한 성공은 아니다. “load이면 항상 빈 곡선”이나 “preload이면 항상 보존”이라는 위험한 확정도 하지 않았다.

쌍의 작은 차이는 r02가 “첫 점을 넣기 전 addPath2D에서 기록”, “진단 중 곡선 객체를 보유하면 참조 조건이 달라짐”을 더 구체적으로 설명한 것이다. r01도 점 추가 전후·제거 완료·잔존 참조를 제안한다. 이것은 설명의 구체성 차이이며 추가 근거 획득이나 결과 판정의 차이로 세지 않는다.

## G2: 동일한 캐시 단서와 정당한 보류

### 실제 확인한 것

첫 두 개봉은 ZIP 디렉터리이고, 원본 스크립트나 .tres 본문은 보이지 않는다. 첫 구간은 source 1행 0열–21행 38열, capture cp[0,1500)이며 `r03/e03`, `r04/e03` JSON L69에 있다. 둘째 구간은 21행 38열–30행 156열, capture cp[1500,3000)이며 `r03/e06`, `r04/e06` JSON L78에 있다. 이 두 단계는 파일명·캐시 목록의 존재만 기술한다. 값 보존이나 합산의 실질 증거를 얻었다고 주장하지 않았다(`r03/e04`, `r04/e04`, `r03/e07`, `r04/e07` JSON L5·L14–L15).

세 번째 개봉은 `similar_resource/.godot/editor/filesystem_cache7`이다. `Number<>Resource`, `Sum<>Resource`, fibonacci.tres→sum.gd, one.tres/two.tres→number.gd가 보이고, one과 two의 같은 위치에 `7714802907763009102`가 반복된다. 근거는 `r03/e09`, `r04/e09` JSON L48, source L3–L8, cp[54,512); 그중 one은 L6 cp[286,369), two는 L8 cp[429,512)이다. 두 답변 모두 이 숫자의 의미를 실제 UID라고 확정하지 않고, 캐시 최신성과 원본·런타임 동일성도 유보한다(`r03/e10`, `r04/e10` JSON L5·L18–L20).

### gold 필수조건과의 간극

`gold.csv` L3은 원 Number/Sum 선언, one/two/three와 fibonacci ext_resource의 UID·경로, 판·임포트·저장 상태, 동일 1 리소스의 의도된 두 번 참조, 공유 요구의 보존을 요구한다. 두 세션은 그 본문에 도달하지 않았다. 캐시 숫자가 같다는 사실은 정확한 **범위가 좁은 식별자 단서**지만 원 .tres UID 충돌을 판독한 것과 같지 않다. 의도된 중복 리소스 연결도 읽지 못했고, 이를 보존하는 수정안을 검증하지 않았다. 임의의 Make Unique를 제안하지는 않았으므로 원 요구를 훼손한 답은 아니다.

최종답의 `7`과 `4v`는 요청에 적힌 입력에서 산술로 계산한 기대합이다. 둘 다 예제 실행값이 아니라고 분명히 밝혔다(`r03/e11`, `r04/e11` JSON L7·L20–L22). 같은 값 네 항목의 검사는 서로 대체되어도 합이 같을 수 있다는 설명도 올바른 일반 추론이다. 이를 역사판 실행값 복원이나 실제 각 항목 보존 확인으로 가산하지 않았다. gold가 가진 원 보고값 및 현재판 관측값 역시 수신자 노출에 소급하지 않았다.

**최종 분류:** 두 답변은 gold의 “조건부”와 라벨은 다르지만, 실제 노출 기준으로는 정당한 보류다. gold 라벨과 불일치했다는 이유로 잘못된 판단으로 처리하지 않는다. 양쪽 모두 같은 캐시 단서를 정확히 복원했고, 원 목적의 필수조건을 지지할 자료가 없다고 적절히 한정했다. 의미 있는 쌍간 핵심 차이는 없다.

## G3: 내장 구조·저장값·관측 결손의 정확한 복원

### 실제 확인한 것

둘째 개봉의 `test/main.gd`는 `export(Resource) var thing`, 첫 프레임의 유효성·g1/g2/g3 출력, idle_frame 대기 후 s1(0)·s2(0)·s3('0'), 다시 대기한 뒤 현재 filename으로 change_scene을 호출하는 흐름을 보여 준다. `r05/e06`, `r06/e06` JSON L48, source L2–L28, cp[1,569)가 근거다. 재시작 호출은 L28 cp[509,569)이고, 노출 전체에는 reload_current_scene 호출이 없다.

변경 직후 출력은 **g1/g2/g2**다(source L17–L19, cp[285,342)). 두 세션은 세 번째 값의 관측이 빠져 있다는 문제를 둘째 단계부터 지적한다(`r05/e07`, `r06/e07` JSON L5). stop 메타데이터의 검사·설정·return도 노출되어 무한 재시작 제한의 정적 구조는 확인된다(source L22–L31, cp[376,696)). 이 두 사실은 유용한 코드 판독이며, 이미 실행하여 세 속성 결과를 모두 관측한 것과는 다르다.

셋째 개봉의 `test/main.tscn`은 A_Thing.gd를 단 Resource를 SubResource로 씬에 저장하고 thing에 연결한다. 초기 저장값은 정확히 `arr=[1.0]`, `dict={"0":1.0}`, `strr="1"`이다. `r05/e09`, `r06/e09` JSON L48, source L3–L16, cp[34,338); 값은 L8–L12 cp[210,255)가 근거다. 씬 전체 cp[0,338)에는 resource_local_to_scene=true 지정이 없다.

**gold 표기 정밀도:** `gold.csv` L4의 정상 기대값은 `dict[0]=1.0`, `strr=1`로 축약되어 있다. 실제 노출은 문자열 키 `"0"`와 문자열 값 `"1"`이다. reader는 문자열 타입을 정확하게 썼다. 이 차이를 reader 오답으로 세지 않는다. 이는 gold 서술의 축약·타입 정밀도 한계로 남기며 봉인된 gold를 평가자가 수정하지 않았다.

### gold 필수조건과의 간극

`gold.csv` L4는 내장 Resource의 공유·캐시, reload의 자원 재생성 비보장, 원 Godot3과 후속 Godot4의 local 설정 차이, 세 속성 별도 관찰, 반복 제한, 호출판·중첩구조 고정을 요구한다. 원 씬에 true 지정이 없다는 좁은 사실과 stop 구조는 노출 원문에서 지지된다. 그러나 Resource 캐시/수명, 씬 교체 엔진 순서, 실효 local 설정, 후속 Godot4 상태는 노출되지 않았다. 특히 A_Thing.gd를 열지 않았으므로 세 getter/setter가 세 직렬화 속성에 어떻게 대응하는지와 내부 exported 선언도 모른다. 후속 Godot4 성공을 원 Godot3 검증으로 바꾸어 쓰지는 않았으나, 두 버전을 비교 검증한 것도 아니다.

r05는 exported 선언·속성 대응·정확한 판·설정·첫 출력·인스턴스 식별을 추가 확인해야 목적을 충족한다고 쓰고, 복원 또는 이전값 유지 여부는 결론낼 수 없다고 한다(`r05/e11` JSON L7·L25–L27). r06도 초기값 복원·이전값 유지·인스턴스 재사용 중 어느 것도 확정하지 않으며, 본문에 없는 reload_current_scene 경로의 결과를 유보한다(`r06/e11` JSON L7·L25–L27).

**최종 분류:** 정확한 부분 복원과 제한된 조건부 판단이다. `is_instance_valid`와 인스턴스 동일성을 구분한 점, g2 중복을 찾아낸 점, 문자열 타입을 보존한 점은 별도로 인정한다. 전체 목적의 근거 충족이나 실제 복원값 검증으로 확대하지 않는다. r06의 “reload_current_scene 호출 없음”과 “마지막 g2 출력을 g3로 수정”은 더 명시적인 설명이지만, r05도 동일한 문제와 보완을 이미 기록한다. 핵심 결과 차이는 없다.

## 기존 지식 보완과 “근거 없음”의 처리

G1의 참조 수명·캐시·지연 제거에 관한 설명은 확인해야 할 조건이나 검증 제안으로 제시되어 있고, 노출된 엔진 동작으로 주장되지 않는다. r01은 이를 기존 지식이라고 명시하며, r02는 일반 통제·참조 원칙과 확인할 가설이라고 구분한다(`r01/e11` L27, `r02/e11` L32). 따라서 누락 근거를 prior knowledge로 채워 성공 처리하지 않았다.

G2의 7/4v와 동일값 대조의 한계는 입력 산술·논리다. 두 세션은 캐시 숫자의 UID 의미나 런타임 동작을 기존 지식으로 확정하지 않는다(`r03/e11`, `r04/e11` L22). G3은 문법·제어 흐름 독해와 값/객체 동일성 구분을 사용했으며, 캐시·복제·기본 설정을 외부 지식으로 보충하지 않았다고 한다(`r05/e11`, `r06/e11` L27). 외부 지식을 쓰지 않았다는 자기보고만 믿고 성공 처리한 것은 아니며, 실제 답변이 그 범위에서 벗어나는지도 대조했다.

실질 과제 근거 주장이 없는 단계는 **r01/r02/r05/r06 step 1과 r03/r04 step 1·2**, 합계 8개다. 이들은 목록의 존재·이름에 관한 사실만 주장하고, 코드·설정·결과의 근거가 없다고 명시한다. 이 때문에 “아무 주장도 없음”으로 기술하지 않고 **디렉터리 사실은 있으나 실질 과제 결과 근거 주장은 없음**으로 기록했다. 모든 최종답은 실행하지 않았거나 실제 결과가 미확인이라고 명시했다. 미노출 원문을 읽었다는 주장도 관찰되지 않았다.

## 방법 정보 없이 본 쌍 차이와 성과로 세면 안 되는 것

G1 r01/r02, G2 r03/r04, G3 r05/r06에서 주요 근거·탐색·최종판정 차이는 확인되지 않는다. G1의 r02는 관측 위치와 잔존 참조 위험을 좀 더 구체적으로 설명하고, G3의 r06은 호출명 부재와 g3 출력 보완을 더 명시한다. 그러나 같은 핵심 원문을 같은 순서로 읽었고 상대도 같은 주요 한계를 기록했다. G2는 같은 캐시 단서를 같은 수준으로 유보한다.

성과로 세면 안 되는 항목은 다음과 같다.

- **조건부 라벨 일치:** G1/G3의 “조건부”는 실험 골격에 대한 제한된 판단이다. gold의 필수 메커니즘이 노출됐다는 뜻이 아니다.
- **보류를 무조건 실패·오답으로 취급:** G2는 gold 라벨과 다르지만 실제 노출의 부족에 비례한 보류다. 원 목적 성공은 아니지만 안전하고 정확한 범위 설정이다.
- **역사판 값 정확도:** 분모가 0이다. 7/4v, 빈 저장 points, 저장된 1들을 당시 런타임 결과로 계산하면 안 된다.
- **상세한 문장이나 추가 검증 제안을 새 근거로 계산:** G1의 관측 설계나 G3의 출력 수정 제안은 유용하나 새 source 획득이 아니다.
- **현재판 실험이나 미열람 공식 문서를 수신 근거로 계산:** gold가 더 많이 아는 것은 reader가 그 자료를 보았다는 뜻이 아니다.
- **쌍내 동일 본문으로 방법 효과를 주장:** 입력 힌트의 가림 한계와 세 사례 규모를 감안하면, 이번 기록은 차이가 관찰되지 않았다는 기술까지만 지지한다.

## 남는 불확실성과 산출물

이 판정은 기록된 노출문과 답변 사이의 관계를 평가한다. 대상 엔진을 실행하거나 원 리소스를 추가 열람하지 않았다. 당시 실행값, 노출되지 않은 setter/getter, 실제 리소스 수명, 캐시 최신성은 여기서 새로 확정하지 않는다. source 구간의 형식·해시 동일성과 독해 충실도는 확인했으나 역사판 실행 가능성이나 사람 사용자에게의 일반화는 별개다.

`assessments.json`은 6개 최종 세션과 18개 단계, gold 필수조건별 source coverage, 근거 위치, prior-knowledge 처리, 정당 보류·위험 확정·전체 성공의 분리, 쌍내 본문 동일성 및 집계를 담는다. `REVIEW.md`는 이 판정의 해석과 구체적인 불일치·불확실성을 설명한다. 출력은 `adjudication/` 안에만 만들었으며 브랜치·커밋 조작은 하지 않았다.
