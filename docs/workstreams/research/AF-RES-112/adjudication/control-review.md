# AF-RES-112 r13 음성 통제 별도 판정

## 결론

r13은 **r03/r04와 같은 세 노출문을 같은 순서로 읽고, 같은 핵심 단서를 복원한 뒤 정당하게 보류**했다. 세 잠정판정과 최종답 모두 `full_requirement_supported=false`, `supported_success=false`, `dangerous_certainty=false`다. 정확한 부분 복원은 step 3의 편집기 캐시 단서와 최종답에서 인정한다. 당시 실행값 정확도는 G2 gold의 `historical_value_judgeable=false`에 따라 null이며 분모는 0이다.

| 항목 | r13 최종답 | r13 잠정판정 3개 |
|---|---:|---:|
| gold 라벨 일치 | 0 | 0 |
| 필수조건 전체 지지 | 0 | 0 |
| 원 목적의 근거 충족 성공 | 0 | 0 |
| 정확한 부분 복원 | 1 | 1 |
| 정당 보류 | 1 | 3 |
| 위험한 확정 | 0 | 0 |
| 실질 과제 근거 주장이 없는 목록 단계 | — | 2 |
| 역사판 실행값 정확도 분모 | 0 | 0 |

최종 `보류`는 gold의 `조건부`와 문자열이 다르지만, r13이 실제 읽은 본문 범위에서는 정당하다. 금번 통제는 본 연구의 6개 세션 집계를 변경하거나 추가 합산하지 않고 별도로 기록한다.

## 주체·봉인·입력 범위

독립 새 문맥의 AI reader r13을 기존의 봉인 후 평가자가 같은 rubric으로 판정했다. 사람 실험이나 역사판 실행이 아니다. r13 `events/01.json` L8–L9는 모델이 `inherited GPT-6 Astra Pro; exact provider runtime not exposed`, 문맥이 `fork_turns=none`임을 기록한다.

조정자가 전달한 r13 원격 봉인은 `3d356e09b83894d1c44e30b5532004abecc7a9a2`다. 사전 지정 음성 통제라는 지위는 조정자의 전달 사항으로 기록하며, 범위 밖 등록 파일을 열어 확인하지 않았다. G2 gold 행과 r13 사건만 판정하고, 이미 읽은 r03/r04 사건을 직접 비교에 사용했다. 추가 외부 원문, 다른 연구 과제, PLAN#27 또는 배정표는 읽지 않았다. r14/L2는 조정자가 부재를 알렸으므로 평가하거나 분모에 넣지 않았다.

별도 통제 조작 정보는 이번에 공개되었으므로 이 추가 분석을 완전히 가린 분석이라고 표현하지 않는다. 앞선 main 분석·파일은 수정하지 않았다.

이 문서의 `r13/e09` 등은 `docs/workstreams/research/AF-RES-112/readers/r13/events/09.json`의 축약이다. source 행은 해석한 exposed_text의 1 기반 행이고, cp[a,b)는 해당 문자열의 0 기반 Unicode codepoint 구간이다. JSON 행·source 행·field/capture 문자 범위는 `control-assessment.json`에 있다.

## 통제 조작의 실제 범위

r03과 r13의 `input.request` 및 시작 URL은 정확히 같다. r03의 hint는 74자이고 r13은 56자다. 차이는 **`타입·배열 구조는 그대로 두어도 ` 18자 삭제** 한 건이다. 끝 공백을 포함한 codepoint 수이며 길이를 맞추지 않았다. r03/r13 `events/01.json` L4–L6을 직접 대조했다. r04의 hint는 비어 있다.

중요한 해석 한계는 **원 request의 보존조건은 그대로 남아 있다는 것**이다. r13의 request에도 “Number의 exported int 값과 Sum의 Array[Resource] 구조를 유지하며 … 별도 리소스의 값이 서로 대체되지 않아야 한다”는 요구가 있다(`r13/e01` L4). 따라서 이 조작은 보존조건 전체를 제거한 것이 아니라 **같은 요청 위에 붙인 hint의 반복 강조를 삭제한 것**이다.

r13 최종답은 여전히 “구조를 유지한 채” 원본 저장값·식별자·로드값·인스턴스 동일성·합계를 대조하라고 한다(`r13/e11` L7). 이 결과를 삭제된 문구가 불필요하다거나 보존조건 자체에 효과가 없다는 결론으로 확장할 수 없다. 한 사례의 추가 reader이고, 길이 차이가 있으며, 요청 본문에 같은 요구가 남아 있다.

| 단계 | r13 노출 | 문자 수 | r03와 문자열·구간·action | r04와 문자열·구간·action |
|---|---|---:|---|---|
| 1 | ZIP 디렉터리 첫 구간, capture cp[0,1500) | 1,500 | 동일 | 동일 |
| 2 | ZIP 디렉터리 다음 구간, capture cp[1500,3000) | 1,500 | 동일 | 동일 |

비교 대상은 각 세션 `03.json`, `06.json`, `09.json`의 exposed_text, source_view_start/end, capture_codepoint_start/end, action 및 archive_entry다. 노출 SHA256도 일치한다.

- step 1: `5db30e6b90eaa270270f15eefb3930743e3b1185b0cc091ade87f531ad764e1c`
- step 2: `b77f647819863793634090f11c5a8e39487c3896277dcdefe1ce749720f908c5`
- step 3: `0d803d42d38d15e26a052617233d816fe73ebbf5e065ec6892a88e218f5810b8`

같은 URL에 접근했다는 수준의 비교가 아니라 실제 문자열·범위 비교다. 더 많은 근거 확보, 다른 탐색 선택 또는 더 짧은 노출로 같은 근거를 얻었다는 차이는 없다.

## 단계별 판정

### Step 1: 디렉터리만 확인한 정당 보류

`r13/e03` JSON L69의 첫 1,500자는 편집기 보조 파일명 중심이다. source 1행 0열부터 21행 38열까지 노출되며 실제 Number 저장값이나 Sum 배열은 없다. r13은 파일명을 다음 읽기의 단서로만 사용하고 값 보존 판단을 보류했다(`r13/e04` L5·L14–L15). 목록 사실은 주장하지만 실질 과제 결과 근거를 얻었다고 주장하지 않는다.

단, counterexample의 “Sum 배열 참조가 중복되어 있다면”이라는 표현에는 작은 한정 결손이 있다(`r13/e04` L13). G2 gold는 **같은 원 리소스 1을 두 번 참조하는 것은 의도된 중복**이라고 명시한다(`gold.csv` L3, required_conditions). 그러므로 모든 반복 참조가 1·1·2·3 검증을 막는 것은 아니며, “의도되지 않은 대체·중복”이라고 한정하는 편이 정확하다. 이를 source에서 확인한 원인이라고 주장하거나 Make Unique를 처방한 것은 아니고, 최종답도 실제 참조를 확인해야 한다고 유보한다. 이 국소적인 모호성을 별도 기록하되 위험한 확정·주요 결과 차이로 확대하지 않는다.

### Step 2: 추가 캐시 목록에서 근거가 늘지 않아 보류

`r13/e06` JSON L78은 아이콘·셰이더 캐시 목록이다. source 21행 38열–30행 156열, capture cp[1500,3000)이다. r13은 실제 저장값·배열 연결·결과를 지지하지 않는다고 명시했다(`r13/e07` L5·L14).

이 단계에서 같은 타입과 동일 개체/식별자는 다르다는 일반 추론을 제시하지만, Godot의 캐시 동작·오류 원인을 확인한 것으로 처리하지 않는다(`r13/e07` L13–L15). r03/r04와 비교해 일반적인 가능한 원인을 말하는 시점·문구에는 차이가 있으나, 추가 source를 읽은 차이가 아니다.

### Step 3: 정확한 캐시 단서가 생겼으나 충분하지 않아 보류

`r13/e09` JSON L48, source L3–L8 cp[54,512)는 fibonacci.tres→sum.gd, Number<>Resource와 Sum<>Resource 표기, one.tres/two.tres→number.gd 및 같은 위치 숫자 `7714802907763009102`의 반복을 보여 준다. one 행은 L6 cp[286,369), two 행은 L8 cp[429,512)이다.

r13은 이 내용을 정확하게 복원했다. 그러나 숫자를 UID로 확정하지 않으며, 오래된 캐시 가능성·원본 식별자·각 저장 정수·배열 네 참조·실행값을 미확인으로 남긴다(`r13/e10` L5·L13–L15). 따라서 정확한 부분 복원은 인정하지만 full_requirement_supported나 supported_success는 인정하지 않는다.

## 최종답과 gold 필수조건

G2의 다섯 필수조건 중 어느 것도 이번 노출에서 완전히 입증되지 않는다.

| G2 필수조건 | 노출이 지지하는 범위 | 남은 간극 |
|---|---|---|
| Number 타입과 Resource 식별자 구분 | 캐시에 Number/Sum 표기·경로가 있음 | 원 정의, 실제 식별자 의미 미열람 |
| 각 파일·ext_resource UID/경로 대조 | one/two의 같은 숫자 필드 | .tres header, three, fibonacci ext_resource 미열람 |
| 엔진판·임포트 캐시·저장 상태 | 캐시가 존재하고 그 내용이 보임 | 최신성 및 대상판 상태 일치 미검증 |
| 원 리소스 1 두 번 참조는 의도된 중복 | 없음 | 실제 배열 연결 미열람 |
| Make Unique로 공유 요구를 깨지 않기 | 그런 변경을 제안하지 않음 | 공유 요구를 source에서 복원·검증한 것은 아님 |

최종답은 실제 선언·배열 참조·저장 정수·실행값을 보고할 수 없다고 분명히 한다(`r13/e11` L7·L21). 7과 4v는 사용자 입력이 보존된다는 조건하의 산술 기대합이며 실행 관측이 아니라고 한다(`r13/e11` L7·L22). 따라서 값의 산술적 정확성은 인정하되 역사판 값 정확도에 넣지 않는다. 같은 값 대조에서는 대체가 일어나도 합계가 같을 수 있다는 추론도 정확하지만 실제 대체 발생을 확인한 것은 아니다.

G2 gold가 갖고 있는 원 보고값·현재판 실험값·UID 문서·원 리소스 내용은 r13에 노출되지 않았다. 평가자가 아는 gold를 수신자가 본 근거로 귀속하지 않는다. 최종답은 같은 타입/식별자를 구분하는 방향을 유지하고 실제 원인과 결과를 유보하므로 정당 보류이며 위험한 확정이 아니다.

## r03/r04와의 차이를 어떻게 세어야 하는가

r13/r03/r04는 모두 동일한 캐시의 좁은 단서를 확보하고 3단계 및 최종에 보류한다. 요청의 구조 보존을 훼손하는 수정도 제안하지 않는다. full_requirement_supported, supported_success, 역사판 정확도 제외, 위험한 확정의 판정은 같다.

r13 step 1의 중복 참조 표현은 다소 넓고, step 2는 타입·식별자의 구분을 일반 추론으로 더 일찍 말한다. 그러나 이것을 보존 문구 삭제가 오류를 일으켰다는 인과 증거로 세거나, 반대로 삭제 후에도 원 목적 성공을 유지했다는 성과로 세지 않는다. 최종 핵심 결과는 같으며, 원 목적 성공 자체가 세 reader 모두 아니다.

관측 가능한 결론은 **이 하나의 추가 통제에서 주요 탐색·근거·결과 차이를 관찰하지 못했다**는 것이다. “삭제 효과가 없다”, “보존 조건이 불필요하다”, “동등성이 입증되었다”는 주장은 이 자료가 지지하지 않는다.

## 사후 URL 메타데이터 정리와 산출물 보존

조정자는 main 판정 뒤 만료된 공개 다운로드 signed redirect query를 제거했고, main 18개 노출의 exposed_text/answer/disposition/reason/citations/counterexample/unknown/prior_knowledge와 JSON 행 수는 유지되었다고 알렸다. 이 전체 변경 전후 검증은 조정자의 보고로 구분해 기록한다. 이번 평가자는 r13과 현재 r03/r04의 세 source 문자열·구간 동일성을 직접 확인했다.

이 URL query는 원문 지지 판정에 사용한 exposed_text가 아니라 전송 메타데이터다. 따라서 제거 자체를 source 지원 변화나 판단 변화로 처리하지 않는다. main `assessments.json`과 `REVIEW.md`는 수정하지 않았으며 작성 전후 SHA256이 같은지 확인했다. 새로운 출력은 `control-assessment.json`과 이 문서뿐이며 브랜치·커밋 조작은 하지 않았다.
