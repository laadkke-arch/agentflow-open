왕복 키는 `(case_id, question_comment_id, answer_comment_id)`이며 직접 정보답 왕복 3개다. 겹치는 대기 시간을 합산하지 않는다. 기다린 시간은 질문의 기회비용과 동일하지 않다. 읽기 시간, 클릭 수, 대체 노동, 답을 안 기다렸을 때의 결과는 미확인이다. D08의 첫 답부터 구체 성공 보고까지는 약 36분이지만 그 시간이 안내의 효과나 총 작업시간을 나타내지는 않는다.

선정 A8/B2의 현재 댓글 목록은 REST `per_page=100`의 next 없음과 HTML 앞/뒤 timeline의 pagination 종료를 대조했다. 삭제 placeholder는 관측하지 않았으나 탐지 흔적 없이 삭제된 기록이 없었다고 증명할 수는 없다. root body 원판은 모두 완전 복원하지 못했고, B2의 첫답 인용으로 일부 조각만 보강했다. `created_at`과 `updated_at`이 다른 답은 현 수정본이며, 생긴 시각만 보고 그때의 문구를 확정하지 않는다. 구체 URL·해시·수정시각은 chains에 남겼다.

## 사전 매칭과 실제 반례

`pairs-frozen.csv`의 두 짝은 후속 열람 전에 고정한 같은 저장소·분기·bug종류·정보 점수 차이≤1·가장 가까운 최초시각 규칙이다. D02–D01은 concurrency와 lambda 기능이라는 목적 차이, maintainer/requester 및 미래 노출 차이가 크다. D05–D07은 interval과 NumPy 변환이라는 다른 기술 경로를 비교한다. 둘 다 정확한 같은 조건의 대체 전략 실험은 아니다. 결과는 `contrasts.csv`에 양 방향·미성립 한계를 함께 둔다.

사전 예측이 맞아 보이는 순간에도 다음 구분이 필요했다.

- D02: 실제 경험이 있다는 답 뒤 설계 논의가 깊어졌지만, 명시적 연결은 동시에 제공한 다른 논거를 받는다. 사전 질문 하나의 효과는 미확인이다.
- DB04: 실제 데이터의 토큰과 단순화한 예제가 달랐다. 예제의 값만으로 중복 질문이라고 판정하면 잘못된다. 그러나 답을 받았다는 사실만으로 후속 권고나 사용 변화가 입증되지는 않는다.
- DB07: 목표 재질문에도 답은 왔으나 새 정보의 편익과 다르다. native 미지원도 수용 가능하다는 조건은 새로 공개됐지만 원래 선호였는지 대화 중 형성됐는지 미확인이다.
- D05: 답이 없는 질문에도 공급자가 수정했다. 그 수정은 사용자 환경의 직접 확인이나 사용 성공을 대신하지 않는다.
- D08: 질문 없는 실행 성공과 지원자 오류가 같은 사건에 공존한다. 성공 보고가 앞 안내 모든 문장을 승인하는 것은 아니다.

선정 외 B26 전체 및 root에서 제외한4건도 봉인 뒤 공개 댓글을 읽었다. `screening-followups.jsonl`은 30행이며 B8 분모에는 DB04/07만 들어간다. DB01의 극찬 뒤 행 누락, DB18의 읽기 성공과 행 펼침 목적 미달, DB24의 구체 수정판 실행은 추가 반례이며 선정 양성률을 바꾸지 않는다. DB17의 질문답/실행 사례는 전역 interleave 첫8 이후여서 포함하지 않았다. DB01/DB17의 HTML 중간 timeline은 pagination이 남지만 REST 전체 댓글은 각각45/21개로 next 없음이고 재요청 수와 일치했다. 모든 cross-reference를 읽었다고 하지 않으며 그 한계는 audit 행에 남긴다.

## 민감도·남은 검사

원판 전체 확인 하위집합은 0이므로 해당 없음이다. A 엄격 미노출 하위집합은6건(D01/D04 제외), B는 DB04 개명 정정 후1건이다. B 미노출에 남는 DB07의 직접 답은 기존 목표의 재진술이다. A에서 공급자 겸 요청자인 D01/D04/D06을 제외하면5건이다. 이 제외들은 엄격 권고 변경/완전 사슬의 관측 양성 0을 바꾸지 않지만, 작은 조건부 분모를 더 줄인다. 이 관측 0은 효과가 없다는 결론이 아니다. 미확인 실제 사용을 전부 실패/전부 성공으로 가정해도 공개된 구체 성공 1건과 추정 성공을 섞어서는 안 된다.

실제 DuckDB 바이너리·테스트는 실행하지 않았다. 읽은 회귀시험은 공급자 기대값과 구현의 근거이며 로컬 성공 영수증이 아니다. 추가 재현이 필요하면 다음 고정 입력을 사용해야 한다: D08은 `duckdb==1.0.0`에서 원 이슈의 입력과 두 frame을 실행; DB07은 `3dcba6d0b59d50a5cb23a9878ed2847f654712d4`에서 원 R 입력·window 전후 row-number 배치를 비교; D05는 `3098c5a5e1c810294bb5b1407420f08ca1a87a94`의 `test/sql/function/timestamp/test_icu_dateadd.test`를 같은 zone/ICU 설정에서 실행. 이 작업에서는 코드 원문 대조와 자료 집계 검사를 수행했다.
