# P2 — 오프라인 공동 기록: 완성품·부품·다른 분야 원리

상태: 연구 묶음 검토 가능. 확인일 **2026-11-20 KST / 2026-11-19 UTC**.
입력: [사전 고정 문제](PROTOCOL.md#3-문제-p2--오프라인-공동-기록).
질의·출처·관측·한계의 재현 기록: [evidence/p2.json](evidence/p2.json).

## 1. 판단

**검색 결과의 “오프라인·충돌 없음”을 곧바로 이 문제의 완료 조건으로 읽을 수 없다.** 기록이 장치에 남는 것, 다른 수정도 보존되는 것, 사용자가 상충을 알아보는 것은 따로 확인해야 한다. 완성품 경로는 사용 흐름을 묶어서 찾고, 부품 경로는 빠진 책임을 드러내며, 다른 분야 원리 경로는 무엇을 충돌로 볼지 다시 묻게 한다.

이번에 Joplin은 요구 동작을 여러 공식 페이지에 연결할 수 있는 완성품 후보로 남았다. Yjs와 Automerge는 앱을 만들 때 고려할 부품이다. Outpost는 검색어가 잘 맞는 결과였지만, 저자가 밝힌 단일 사용자 예제의 범위와 운영 한계를 함께 보면 전체 선택과 원리 참고를 분리해야 한다. Git과 TreeDB 논문은 이력 전달과 합의된 상태의 결정을 분리해 생각하게 한다. 이는 후보 분류·전이 판단이며 제품 채택이나 실행 성공 판정이 아니다. [P2-S01] [P2-S02] [P2-S03] [P2-S04] [P2-S05] [P2-S07] [P2-S09] [P2-S12] [P2-S13]

읽은 서로 다른 1차 자료는 **14개**다. 13개는 문서·코드의 관련 절, 1개는 논문 저자 초록·서지까지만 읽었다. 코드 관찰은 Outpost 한 파일뿐이다. 검색 snippet·중복 사본·내부 지침은 이 수에 넣지 않았다. 제품 실행, 계정 사용, 설치·배포, 현장 팀 적용은 하지 않았다.

## 2. 실제 탐색 경로와 비용

최초 문제는 “오프라인에서 공유 기록 수정 → 재접속 후 수정 보존 → 상충 확인·해결 → 파일로 내보내기”였다. 실시간 동시 타이핑, 특정 언어, 암호화, 중앙 서버 부재, 유료 서비스 배제는 필수 조건으로 추가하지 않았다. 자체 운영은 선호 조건 그대로 유지했다.

| 경로 | 실제 질의와 확인 | 얻은 것 | 추가 부담·관측 누락 |
| --- | --- | --- | --- |
| 완성품 | Q01 목적·제약 자유문 → Q04 공식 제공자 문서 → Q07 추가 확인 | Joplin의 동기화·충돌 복사본·공유·내보내기 근거. Outpost의 구체 예제와 한계 | 한 개 소개 페이지로 충분하지 않았다. 여러 언어/미러 목록이 반복됐으며 Anytype FAQ는 읽을 수 없었다. CryptPad의 오프라인 쓰기 조건은 이번 경로에서 확인되지 않았다. |
| 부품 | Q02 동작·충돌·영속화 → Q05 공식 문서/API 어휘 | Yjs provider의 역할 분리, Automerge의 기본 값과 충돌 값 구분 | 영속화·네트워크·화면·내보내기 책임을 앱 수준에서 다시 조합해야 한다. Q02 반환 묶음에 없던 CouchDB 모델은 Q05의 DB 관점 추가 후 확인했다. |
| 다른 분야 원리 | Q03 버전관리·분기·병합·불변식 → Q06 원 논문 → Git 공식 설명 | 소스 버전관리와 사진 관리에서 얻은 충돌 단위·분기 이력 원리 | 새로운 용어와 읽을 자료가 늘고 목표 문제와 대응을 연구자가 설명해야 한다. 논문에서 설명한 전이가 P2 성공 사례가 되지는 않는다. |

서로 다른 질의 문자열은 7개, 실제 제출 문자열은 반복을 포함해 10개다. 최초 세 문자열을 한 호출로 보냈더니 결과가 합쳐져 나왔으므로, 질의별 귀속을 기록하기 위해 각각 재실행했다. 이 추가 비용을 성공한 독립 검색 세 번으로 세지 않는다.

공식 도메인과 `getConflicts`는 연구자의 사전지식으로 넣은 보조 단서다. 특히 Q04는 Joplin·Anytype 등을 공식 근거에서 확인하려고 고른 도메인 제한이며, 초기 결과만에서 자동 생성한 확장 질의가 아니다. **이 자료는 검색엔진·검색 기법의 통제 실험이 아니다.** 반환 묶음의 순위를 측정하지 않았고, 선택 후보 수를 정확도나 재현율로 환산하지 않았다.

## 3. 요구 부분과 후보 근거

아래 “문서”는 D1이며 “코드”는 D2다. 통합 시험을 통과했다는 표시가 아니다.

| 필요한 부분 | 확인한 후보 원리 | 요구와 연결할 수 있는 범위 | 아직 앱/운영에서 확인할 부분 |
| --- | --- | --- | --- |
| 오프라인 읽기·쓰기 | Joplin 로컬 자료 + 동기화; Yjs의 y-indexeddb; Automerge의 로컬 storage adapter | 로컬에 있는 자료를 네트워크 없이 다루는 구성 | 처음 읽지 않은 공유 자료까지 있는지, 앱을 새로 열 수 있는지, 저장소가 지워졌을 때의 복구 [P2-S01] [P2-S08] [P2-S10] |
| 상충 수정 보존 | Joplin Conflict 복사본; Automerge 다중 값; CouchDB 서로 다른 revision | 기본 화면의 한 값과 별개로 다른 수정이 남을 수 있음 | 사용자가 발견하고 비교하는 화면, 해결 전후 변경의 보존 [P2-S02] [P2-S09] [P2-S11] |
| 공유 기록 편집 | Joplin Cloud의 초대 수락·공유 노트북; 부품은 별도 network/provider | 완성 앱의 공유 기능 또는 자료 동기화 부품 | 확인한 Cloud 기능을 임의 자체 운영 대상에 그대로 일반화하지 않음 [P2-S04] [P2-S07] |
| 파일 내보내기 | Joplin JEX/raw·HTML/PDF; Outpost JSON backup | 원문과 메타데이터를 가져갈 경로 | 모든 충돌본·과거 이력·첨부가 요구대로 복원되는지는 미실시 [P2-S03] [P2-S05] |
| 수정 충돌의 표시·해결 | Outpost의 revision 검사와 충돌 패널 설명 | stale baseRev를 구분하는 실제 서버 코드와 양쪽 비교의 설계 예 | 특정 클라이언트의 실제 재송신·해결 성공·팀 운영은 미확인 [P2-S05] [P2-S06] |

Outpost의 인증 없음 자체를 사용자가 말하지 않은 필수 조건으로 만들어 자동 탈락시키지는 않았다. 신뢰된 소수 장치의 예제로 사용할 가능성은 남긴다. 다만 “팀이 쓰는 완성 앱”으로 검증된 것처럼 반환하지 않고, 구체 동기화 경로의 참고 후보로 남긴다.

## 4. 첫 유망 결론을 깨는 반례

### 자동 병합이 상충을 보여 준다는 결론

Automerge의 같은 속성 동시 대입에는 기본으로 노출할 winner가 있다. 다른 값은 `getConflicts`로 가져올 수 있다. CouchDB도 기본 GET은 winner만 반환하며 명시적으로 다른 revision을 찾아야 한다. 따라서 엔진이 값을 보존하더라도 앱이 기본 값만 표시하면 사용자는 수정이 사라졌다고 느낄 수 있다. [P2-S09] [P2-S11]

합성 입력으로 “장치 A는 상태를 통과, B는 재검토로 수정”을 생각할 수 있다. 관측할 것은 최종 값의 일치뿐 아니라, 상대 수정이 남아 있고 사용자에게 드러나는지다. 이 입력을 실행한 것은 아니다.

### 값 충돌이 없으면 의미 충돌도 없다는 결론

서로 다른 속성에 “상태=승인”과 “결론=반려 사유”를 각각 쓰는 경우를 생각하자. 자료형 병합이 가능해도 기록의 의미가 맞는지는 별도 판단이다. 이것은 P2의 합성 반례 가설이다. 구체 업무 규칙을 이번에 확정하지 않았으므로 특정 CRDT의 구현 결함이라고 부르지 않는다.

### 로컬 저장 provider 하나로 오프라인 앱이 완성된다는 결론

Yjs 문서는 문서 데이터 보존과 별개로 네트워크 없이 HTML·JS·CSS를 열기 위한 service worker를 설명한다. “오프라인 저장 지원”을 발견한 뒤에는 이미 열린 페이지에서 타이핑하는 경우와 브라우저를 닫고 다시 여는 경우를 구분해 읽어야 한다. [P2-S08]

### “수정 손실 없음”이라는 소개 문구가 모든 기간을 보장한다는 결론

Outpost README는 삭제 표식 만료 뒤 오래 오프라인인 장치에서 노트가 되살아날 수 있다고 명시한다. 고정 코드에서는 오래된 삭제 행과 적용 ID 원장의 정리, 기존 행이 없을 때 비삭제 입력을 삽입하는 경로를 관찰했다. 실제 클라이언트 전송을 재현하지는 않았다. 따라서 소개 문구만으로 무제한 단절·재접속 보장을 붙이지 않는다. [P2-S05] [P2-S06]

### 명시적 이력이 항상 더 좋은 해결책이라는 결론

여러 상태를 이해하고 나중에 합치는 부담도 있다. 단순 메모에서 쉽게 되돌릴 수 있는 수정까지 매번 사람에게 물으면 기록 흐름을 방해한다. 반대로 즉시 하나의 승인 상태에 따라 행동해야 한다면 미합의 이력을 실행 상태로 다뤄서는 안 된다. 조정 필요성은 구체 불변식과 연산에 달려 있다는 저자 초록도 확인했지만 정리 증명은 읽지 못했으므로 포괄적 불가능·가능 정리를 P2에 적용하지 않았다. [P2-S14]

## 5. 다른 분야 전이: 확인된 서술과 우리 가설

| 출발 분야 | 요구 부분에 대응시키는 것 | 근거의 정확한 수준 | 적용하지 않을 경우 |
| --- | --- | --- | --- |
| 소스 버전관리 | 공통 기준, 양쪽 수정, 해결을 기다리는 상태 | Git 공식 병합 문서를 읽음. P2로의 전이는 연구자 가설 | 줄 병합 결과를 업무 의미·참조 제약의 검증으로 대체할 때 [P2-S12] |
| 사진 관리·구조화 자료 | 한 속성보다 큰 편집 의도와 묶음 단위 | TreeDB 논문이 사진 편집 반례와 DVCS→구조화 자료 대응을 명시함. 제안 수준 D1 | 최종 사용자에게 분기 이력을 이해시키는 비용이 목적을 넘어설 때 [P2-S13] |
| 복제 DB | 동일 기록의 여러 revision을 보존하고 읽을 때 선택·해결 | CouchDB 공식 replication 모델 D1 | revision tree를 무제한 사용자 변경 이력으로 취급할 때 [P2-S11] |

TreeDB 원문은 **변경을 전달받음**과 **공동 이력에 병합함**을 분리한다. 이 연결은 원문에 있는 전이 서술이지만, 현장 팀에서 유용하다는 것은 아직 우리 가설이다. 실제 운영 제품의 채택 성공이나 UI 실험으로 보고하지 않는다. [P2-S13]

서로 다른 검색 경로는 하나만 남길 경쟁안이 아니다. 완성품의 충돌 화면에서 필요한 작업을 찾고, 부품 문서에서 보존·표시 경계를 확인하고, 다른 분야 반례로 충돌 단위를 점검할 수 있다. 결합할 때 유지해야 할 것은 요구 문장과 후보가 책임지는 부분 사이의 연결이다.

## 6. 누락·오탐·중단 기준

- **키워드 오탐:** personal/single-user 예제, 협업 데모, 전체 앱이 모두 offline·conflict라는 단어를 쓴다. 검색에서 발견됐다고 같은 역할의 후보로 합치지 않았다.
- **문서 단위 누락:** 제품 이름을 찾았어도 현재 conflict·export·sharing 문서가 함께 반환되는 것은 아니었다. 추가 확인을 거쳐 요구별 근거를 붙였다.
- **관점에 따른 관측 누락:** Q02의 반환 묶음에는 CouchDB가 없었다. 후속 DB 관점을 넣어 찾았다는 관측까지만 남긴다. 그 검색엔진 전체가 CouchDB를 놓쳤다는 뜻이 아니다.
- **인기도:** 이번 결과로 인기도가 실제 순위를 왜곡했다고 입증하지 않았다. 별·유명세로 적합성을 판정하지 않았고, 주 작성자의 다른 발견 채널 조사와 합쳐서만 다룬다.
- **읽기 실패:** Anytype FAQ와 Automerge 소개 페이지는 readable lines 0, invariant-confluence 논문 PDF는 DisabledError였다. 각각 원문 부재·미지원·서비스 장애로 일반화하지 않았다. Automerge의 별도 참조 문서는 정상 열람했다.
- **종료:** 각 경로의 연결과 반례를 확보했으므로 새 제품 수를 늘리지 않았다. CryptPad/Anytype를 떨어뜨리거나 추천하기 위해 추측하지 않고 자료 부족으로 남긴다.

다음 확인은 두 가지 중 실제 선택을 바꾸는 하나부터 한다. 완성 앱 사용을 고려하면 후보의 두 장치 단절·동일 속성 수정·재연결에서 상충 인지가 가능한지 확인한다. 직접 개발을 고려하면 실제 기록 한 종류에서 “한 속성의 경쟁”과 “서로 다른 속성의 의미 모순”을 구별할 필요가 있는지 먼저 정한다. 이는 공통 판정팩·제품 DB 설계가 아니라, 현재 보류 이유를 줄이는 후속 확인이다.

## 7. 출처 연결
