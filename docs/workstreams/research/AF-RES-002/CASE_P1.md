# P1 — 문서 묶음 처리: 완성품·부품·다른 분야 원리 비교

작성일: 2026-11-20 KST / 2026-11-19 UTC. 고정 문제와 범위는 [PROTOCOL.md](PROTOCOL.md)의 P1이다.
실제 질의·관측 후보·원문별 확인 내용·한계는 [evidence/p1.json](evidence/p1.json)에 기록했다.
외부 원문은 **16개**를 직접 읽었다. 문서 D1 14개와 코드 D2 2개이며, 설치·제품 실행 D3 및 목표 통합 D4는 수행하지 않았다.

## 1. 결과와 판정 범위

**완성품 경로는 사용 경험을, 부품 경로는 실패와 재시도의 책임을, 다른 분야 경로는 계산 재사용과 공개 상태의 경계를 드러냈다.**
세 경로는 같은 후보의 순위를 만드는 데 쓰기보다 서로 다른 미확인 조건을 찾는 데 유용했다.
이 P1에서 완성품 후보를 바로 버릴 근거도, 특정 큐와 OCR 부품을 조립해야 한다는 근거도 확보하지 못했다.

검색 초반에 유망했던 가설은 “폴더 OCR와 중복 탐지가 있는 제품을 고르고 재시도를 지원하면 요구를 충족할 것이다”였다.
공식 문서와 고정 코드를 확인하자 수정이 필요했다. Paperless-ngx의 조사한 기본 브랜치 스냅샷은 중복을 기본 허용하며, Docspell의 업로드 중복 생략도 기본값이 false다.
이 사실은 **중복 탐지 기능의 존재와 기본 중복 공개 방지 정책이 다름**을 보여 준다.
다만 이것을 모든 Paperless 배포판의 현재 동작으로 일반화하지 않는다. 조사 SHA와 사용자가 실제 배포할 버전의 일치는 미확인이다. [P1-S01] [P1-S02] [P1-S06]

재시도에서도 같은 구별이 필요했다. Celery는 재시도와 ACK 시점을 다른 기능으로 설명하며, 같은 task ID를 다시 쓰는 것 역시 중복 부작용 방지 보장이 아니다.
BullMQ 문서도 멱등성을 작업 작성자가 설계해야 한다고 명시한다.
따라서 P1의 “같은 입력의 결과가 중복 공개되지 않음”은 큐 이름이나 retry 체크박스로 완료 판정할 수 없다. [P1-S09] [P1-S10]

## 2. 고정 요구를 검색할 때 바꾸지 않은 것

| 요구 | 조사에서 유지한 의미 | 잘못된 대체 지표 |
| --- | --- | --- |
| 파일별 실패 격리 | 손상 입력이 다른 파일의 영속 성공을 없애지 않음 | 예외를 한 번 잡음 |
| 중단 후 재시도 | 미완료 항목을 알아보고 다시 처리할 수 있음 | worker 재시작 가능 |
| 중복 공개 방지 | 재처리해도 같은 입력의 공개 결과가 중복 생성되지 않음 | task ID 또는 파일 이름이 같음 |
| 실패 확인 | 실패 입력과 원인·현재 상태를 연결할 수 있음 | 로그에 “완료”가 있음 |
| 자체 운영 | 직접 평가·운영 가능한 배포와 접근 조건 | 소개 페이지의 self-hosted 문구 |
| 재사용 선택 | 전체 사용 경험을 채택하거나 필요한 동작만 가져옴 | 같은 기능 단어가 있는 모든 후보를 같은 종류로 순위화 |

언어·큐·DB·처리량·OCR 정확도 목표는 사전에 정하지 않았다.
“정확히 한 번 실행”도 요구로 추가하지 않았다. 실행이 여러 번 일어나더라도 공개 결과가 조건을 만족할 가능성을 열어 두었다.
이는 제품 보장이 아니라 고정 요구를 해석하는 조사 기준이다.

## 3. 실제 검색 경로와 확인 부담

최초 세 질의에는 제품명을 넣지 않았다.

| 경로 | 실제 시작 질의 | 추적한 원문 | 얻은 판단과 남은 비용 |
| --- | --- | --- | --- |
| 완성품 | `self hosted document management watched folder PDF OCR failed documents duplicate detection` | Paperless 문서·고정 코드, Docspell 공식 문서, Jiandu 공식 페이지 | 입력→검색→실패 관찰을 한 제품에서 검토할 수 있다. 기본값·버전·배포 접근·중단 조건의 추가 확인이 필요했다. |
| 부품 | `job queue retry idempotent tasks batch independent failures persistent result` | OCRmyPDF, Celery, BullMQ, Spring Batch | 변환·전달·재시작·트랜잭션 단위를 분해할 수 있다. 각 부분 사이의 상태와 공개 책임은 앱 쪽에 남는다. |
| 다른 분야 원리 | `crash recovery atomic publish output file write ahead log content addressable build cache` | Bazel, SQLite, Build Systems à la Carte, Reflow | 계산 식별과 저장된 공개 결과를 구별할 근거를 얻었다. 원 분야 전제를 P1에 대응하고 깨지는 경우를 별도로 설명해야 했다. |

총 **10개 질의 문자열을 6회 검색 호출**로 실행했다.
Q01–Q03은 한 호출로 결과가 섞여 반환되었으므로 개별 후보가 어느 질의에서 나왔는지 배정하지 않았다.
Q04–Q06은 경로별 단독 질의다. Q07–Q09는 공식 원문 검증을 위한 한 묶음이며, Q10은 논문이 언급한 Reflow 후속 추적이다.
결과의 전체 순위·전체 개수·시간당 발견률은 계산하지 않았다.

Docspell 이름은 관측한 후보에서 이어 갔다.
Celery와 BullMQ는 연구자가 알고 있던 이름을 후속 공식 문서 질의에 넣었다.
SQLite는 검색 반환 후보였다고 꾸미지 않고, atomic commit 개념에 대한 기존 지식으로 공식 페이지를 직접 연 경로로 기록했다.
Bazel은 반환된 공식 과거 문서에서 현재 공식 설명으로 이동했다.
따라서 이 조사는 “제품을 모르는 사람도 같은 결과를 얻는다”는 검증이 아니다.

원문 접근에도 비용이 있었다. Paperless 공식 사이트의 configuration·usage 페이지는 403이 반환되어 읽은 자료 수에서 제외했다.
공식 GitHub에서 당시 기본 브랜치 SHA를 확인한 후 문서와 코드를 읽었다.
OCRmyPDF 검색 제목은 17.13.1이었지만 실제 열린 `latest` 문서 헤더는 17.14.2였다.
후보 이름만 기록하면 이런 시점·버전 차이를 놓친다. [P1-S01] [P1-S08]

## 4. 완성품 경로: 사용 경험은 가까우나 운영 조건은 별도다

| 후보와 역할 | 직접 확인한 적합 근거 | 요구 충족을 단정할 수 없는 조건 | 이 조사에서의 처리 |
| --- | --- | --- | --- |
| Paperless-ngx — 전체 사용 후보 | 소비 폴더, OCR·색인·검색, 실패 작업 확인 안내 | 조사 스냅샷의 중복 기본 허용. 중복 거부 설정과 배포 버전 확인 필요. 중단·동시 입력의 공개 유일성 미검증 | 조건부 후보 유지 |
| Docspell — 전체 사용 후보 | 파일별 item, 처리 단계, 작업 로그·재시도·실패 상태 | `skipDuplicates=false` 기본값. 오류에도 불완전 item이 생성될 수 있어 item 존재와 OCR 성공이 다름 | 조건부 후보 유지 |
| Jiandu — 기능은 근접 | PDF·사진·폴더 입력·검색 라이브러리 설명 | 원문이 패키지 없음·프로젝트 라이선스 미선택·저장소 접근 필요를 명시 | 현재 공개 소스 평가 경로에서 중단 |

Paperless의 중복 처리 주장은 문서만 확인하지 않았다.
고정 SHA `4973be8499bc61dc4f791a609d0d31e9ac9ccd41`의 `pre_check_duplicate`는 원본/보관 checksum을 조회한 뒤 경고하고,
`CONSUMER_DELETE_DUPLICATES`가 참인 분기에서 입력 삭제·실패 진행 상태·중복 예외를 만든다.
이 코드는 기본 정책에 대한 문서 해석을 지지한다.
그러나 체크와 저장 사이 전체 동시성 제약을 검토한 것은 아니므로, 이를 근거로 경쟁 버그가 존재하거나 불가능하다고 선언하지 않는다. [P1-S01] [P1-S02]

같은 저장소의 `consume_file`은 중복 예외를 별도 결과 객체로 바꾸고, 일반 예외는 실패 진행 상태를 보낸 뒤 다시 발생시킨다.
문서의 “중복 작업 실패”와 큐 backend 실패, 화면 진행 상태를 같은 상태라고 읽으면 안 된다.
실제 backend 상태는 실행하지 않았다.
관리자 화면에서 실패 작업의 오류 메시지를 보라는 안내까지 확인했지만, 모든 실패 입력의 보존·재처리가 자동 보장된다는 결론은 내리지 않았다. [P1-S03] [P1-S04]

Docspell은 재시도 후에도 실패한 작업을 표시하지만, 오류·취소 후 제안 정보가 없는 문서를 만들 수 있다.
또한 최근 작업 화면의 80개 제한은 그 화면이 전체 배치의 영구 감사 원장인지 별도 확인해야 함을 보여 준다.
업로드를 archive 항목별로 나누는 옵션은 작업 단위를 세분화하되 원래 archive를 남기지 않는다.
“더 잘게 나누면 항상 더 안전하다”는 주장도 입력 보존 요구와 함께 검토해야 한다. [P1-S05] [P1-S06] [P1-S07]

## 5. 부품 경로: 무엇을 다시 실행하고 무엇을 보존하는가

| 부품·모델 | 가져올 수 있는 동작 | 앱이 여전히 책임질 조건 |
| --- | --- | --- |
| OCRmyPDF | 파일 변환, 배치 예제, 폴더 watcher | 문서 검색 경험, 항목 상태, 공개 결과의 식별·내구성 |
| Celery 또는 BullMQ | 작업 실행·전달·재시도 모델 | 재실행해도 같은 최종 상태가 되게 만드는 사용자 작업 |
| Spring Batch | 저장 상태에 따른 restart, retry/skip, 청크 트랜잭션 | 올바른 실패 단위, 출력의 트랜잭션 또는 멱등성, 외부 파일 작업의 경계 |

이 표는 기술 조합을 확정한 것이 아니다.
특히 Celery와 BullMQ를 함께 채택하거나 Spring Batch를 P1의 기본 구현으로 채택하라는 뜻이 아니다. [P1-S08] [P1-S09] [P1-S10] [P1-S11]

### 반례 A — “완료” 로그가 성공 결과를 뜻하지 않는다

OCRmyPDF 공식 배치 문서의 `misc/batch.py` 예제는 파일별 예외를 기록한 뒤 공통 경로에서 완료 로그를 남긴다.
이 예제의 로그만 세면 건너뛴 입력과 오류를 성공으로 오독할 수 있다.
이는 예제의 정적 관측이며 OCRmyPDF 제품 전체의 상태 관리가 잘못되었다는 평가가 아니다.
현재 watcher는 입력 폴더 안에 출력·보관 폴더를 두는 반복 처리 구성을 거부한다.
폴더 경계는 개선되어 있어도 목적지 충돌 기본값 `SUFFIX`와 중복 공개 방지는 다른 정책이다. [P1-S08]

### 반례 B — 재전달·재시도·멱등성은 다른 보장이다

Celery의 `Task.retry`는 처리 가능한 오류를 다시 시도하는 기능이고 `acks_late`는 메시지 ACK 시점을 바꾼다.
문서가 제시한 파일 카운터 증가→메타데이터 저장→파일 복사 순서에서 중단되면 일부 상태만 바뀔 수 있다.
같은 task ID를 쓰는 서로 다른 두 작업의 동작도 정의되지 않는다고 명시한다. 이것은 `Task.retry` 자체가 잘못되었다는 뜻이 아니다.
BullMQ의 공식 멱등 작업 지침은 성공까지 여러 번 실행해도 최종 상태가 같아야 한다는 설계 책임을 작업 쪽에 둔다.
큐에 넣는 중복을 줄이는 것과 이미 일부 실행된 작업을 안전하게 다시 수행하는 것은 따로 검증해야 한다. [P1-S09] [P1-S10]

### 반례 C — 청크의 앞 항목을 처리했다고 이미 보존된 것은 아니다

Spring Batch 4.3.9 문서는 저장된 실행 문맥에 의한 재시작과 청크 내 반복·재시도를 설명한다.
청크 트랜잭션이 끝나기 전에 뒤 항목이 실패하면 앞의 미커밋 항목도 rollback될 수 있다.
문서는 입력의 트랜잭션성과 출력의 트랜잭션 또는 멱등성을 조건으로 둔다.
따라서 “부분 성공 보존”은 단순히 항목 예외를 잡았는지보다 **어떤 단위가 이미 영속 커밋되었는지**로 판정해야 한다.
버전 있는 원리 설명을 읽은 것이며 최신 Spring Batch의 채택 적합성을 검증한 것은 아니다. [P1-S11]

## 6. 다른 분야 원리: 실제 사용 사례와 P1 전이 가설을 분리한다

| 원 분야와 직접 확인한 사실 | P1에 대응할 수 있는 질문 | 그대로 옮기면 깨지는 경우 |
| --- | --- | --- |
| 빌드 시스템: Bazel은 action 결과 메타데이터와 CAS 출력 blob을 구분 | “이 입력을 이 변환 정의로 계산한 결과가 이미 있는가?” | OCR 설정·도구·모델이 바뀌었는데 입력 bytes만으로 재사용하면 낡은 결과를 고를 수 있음 |
| 생물정보학: Reflow 제작자는 NGS 처리, 증분 실행·memoization을 실제 용도로 설명 | 여러 문서 변환을 의존 작업으로 보고 변경 영향만 다시 계산할 수 있는가? | 계산 재사용이 동일 문서의 공개 row 유일성이나 외부 부작용을 보장하지 않음 |
| DB 복구: SQLite 설명은 journal과 commit 판별점으로 중단 복구를 다룸 | “이 항목은 공개 완료로 영속 기록되었는가, 복구가 필요한가?” | DB 밖 파일 이동·큐 ACK·API 호출까지 자동으로 원자화된다고 오해함 |

Bazel 문서의 알려진 한계에는 빌드 중 입력 변경과 추적되지 않는 외부 도구가 포함된다.
따라서 내용 해시만 붙이면 모든 재계산 판단이 안전해진다는 주장은 원 분야에서도 성립하지 않는다.
P1에서도 변환 정의와 환경을 식별에 포함할 필요가 있다는 것은 여기서 얻은 **전이 가설**이다. [P1-S12]

원논문 *Build Systems à la Carte*는 스케줄링과 재계산 판단을 분리하고 빌드 도구와 Excel을 비교한다.
논문이 언급한 Reflow를 별도로 추적하자 공식 고정 README에서 GRAIL의 NGS 워크로드, 모델 학습·분석 사용과
입력/코드 변경에 따른 증분 계산을 확인했다.
이것은 다른 분야 활용이 제작자에 의해 문서화된 사례다.
외부 독립 운영 평가나 P1에 적용한 성공 사례라고 부르지 않는다. [P1-S14] [P1-S15]

SQLite 원문은 rollback journal 방식의 원자적 commit을 설명하며 WAL 구현 설명이 아니다.
파일 잠금·동기화·삭제에 대한 가정도 제시한다.
이를 참고해 P1의 임시 변환 결과와 영속 공개 기록 사이 복구 규칙을 질문할 수 있지만,
DB 트랜잭션 하나가 파일·큐·외부 시스템 전체에 걸친 원자성을 준다는 결론은 범위를 넘는다. [P1-S13]

이 세 자료를 결합하면 다음 가설을 세울 수 있다.
**계산 재사용의 식별과 사용자에게 보이는 문서 공개의 식별을 구분하고, 중단 후에는 공개 기록과 산출물의 관계를 다시 확인한다.**
이는 최종 DB/API 스키마가 아니며 특정 제품의 부족함을 입증한 결과도 아니다.
전체 제품이 이 요구를 이미 충족한다면 새 실행 기반을 만들 필요는 없다.

## 7. 오탐·관측 누락·확증 편향 점검

**기능 유사성 오탐.** 완성품 질의 Q04에 OCRmyPDF 배치 문서가 나타났다.
OCR가 가능하다는 점은 맞지만 그것만으로 완성된 검색·실패 관리 경험이 있다고 분류하면 역할을 혼동한다.
Paperless의 “duplicate”도 탐지·경고·거부 기본값을 구별하지 않으면 조건을 잘못 읽는다. [P1-S01] [P1-S08]

**이름 오탐.** Q10은 GRAIL Reflow를 찾기 위한 질의였지만 도구 반환에 RectifiedFlow의
`run_lib_reflow.py`, GRPO-Flow 등 다른 저장소가 나타났다.
이 후보들은 D0로만 기록했고 GRAIL 데이터 처리의 근거에 쓰지 않았다.
이 관측으로 검색 엔진의 site 필터 전체 동작을 단정하지 않는다.

**접근 조건 오탐.** Jiandu는 목적 문구가 잘 맞아 직접 열었지만, 공개 소스 평가 경로가 현재 열려 있지 않다고 자체 설명한다.
검색 문구만으로 설치 가능한 공개 대안으로 승격하지 않았다.
접근 조건이 변하면 재평가할 수 있다. [P1-S16]

**관측 가능한 누락.** 단독 부품 질의 Q05의 반환 묶음에는 Celery·BullMQ 공식 결과가 없었고,
후속 이름·공식 도메인 질의 Q08–Q09에서 관련 원문을 얻었다.
Q04의 완성품 묶음에서는 Bazel·Reflow가 관측되지 않았으나 원리 질의와 논문 추적으로 확인했다.
이것은 이번 반환 결과의 차이이며 색인 누락·전체 재현율·경로 성능 우위의 측정이 아니다.
완성품 질의에 OCRmyPDF가 나타난 점은 경로들이 완전히 분리되어 있지 않다는 반례다.

**인기도에 의한 오판은 위험으로 남기되 관측 결과로 꾸미지 않는다.**
이 조사에서는 stars 변화나 인기 순위의 인과 효과를 시험하지 않았다.
익숙한 후보를 아는 상태에서 원문 검증을 확장했기 때문에 연구자 지식 편향은 남는다.
미열람 Nestbox·Lekto·작은 큐 저장소는 채택 순위의 패배자가 아니라 이 조사에서 검증하지 않은 후보다.

## 8. 수정한 결론과 다음 검증의 입력

P1에서 전체 사용 경험이 목적에 맞는다면 Paperless-ngx·Docspell 같은 완성품의 **정확한 배포 버전·설정과 실패 경계**를 먼저 확인하는 편이 합리적이다.
변환 부품만 필요한 제품 요구가 있다면 OCRmyPDF와 작업 실행 부품의 책임을 나누되,
재실행 안전성과 공개 결과 상태는 별도 검토 대상으로 남긴다.
원리 탐색은 새 기술을 늘리는 이유보다 “무엇이 이미 성공했고 무엇을 다시 실행해도 되는가”를 정확히 질문하는 데 쓰였다.

남은 가설을 실제 채택 판단으로 바꾸려면 다음 입력과 관측을 갖춘 후보별 검증이 필요하다.
이는 후속 검증 설계이며 이번 조사에서 실행한 결과가 아니다.

| 입력·중단 조건 | 확인할 결과 | 이 검증이 필요한 근거 |
| --- | --- | --- |
| 정상 PDF, 손상 PDF, 다른 정상 PDF를 한 묶음으로 입력 | 영속 성공 두 개가 손상 입력 때문에 사라지지 않음. 실패 입력과 원인이 남음 | 청크/항목 실패 경계, 불완전 item, 예제 상태 해석 |
| 같은 bytes를 다른 이름으로 재입력하고 두 worker에도 제출 | 공개 결과 유일성 정책과 실패/이미 존재함 상태가 일관됨 | 중복 기본값과 task ID의 한계 |
| 변환 후 공개 직전, 공개 후 ACK 전의 중단 | 재시작 후 누락·중복 공개가 없으며 미완료 상태를 복구함 | 재시도·ACK·외부 상태의 분리 |
| 같은 입력에 변환 설정 또는 도구 버전을 변경 | 의도한 결과 재계산과 문서 정체성 정책을 구별 | 입력 해시만으로 부족한 캐시 식별 |

실행할 제품·버전·설정은 아직 선정하지 않았다.
따라서 이 문서는 가상의 공통 실행 명령이나 성공 결과를 만들지 않는다.
다음 첫 행동은 실제 채택하려는 후보의 릴리스와 중복 정책을 고정하고, 위의 입력별 공개 상태를 관측할 수 있는 방식으로 명령을 구체화하는 것이다.
연구 범위의 검색·원문 대조는 완료했으며, 이 D3/D4 미실시를 제품 채택 완료로 바꾸지 않는다.
