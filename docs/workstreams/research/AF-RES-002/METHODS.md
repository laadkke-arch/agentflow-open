# AF-RES-002 — 같은 목적·부분·다른 분야 원리를 찾는 방법의 비교

상태: 원문 검토 완료, 검색기 구현·성능 실험 미실시. 2026-11-20 KST.
질의·원문별 확인 시각·위치·한계는 [evidence/methods.json](evidence/methods.json)에 있다.
이 파일의 방법 구분은 이번 연구의 비교용이며 미래 제품의 DB·API·순위 계약이 아니다.

## 1. 판단

**목적·제품군, 필요한 부분의 동작·실패 조건, 다른 분야의 관계를 오가며 원문으로 적합 범위를 좁히는 조합을 남긴다.** 전체 사용 경험이 필요할 때 목적·제품군에서 시작하는 것은 기본 출발 제안이다. 이미 특정 부품이나 실패 조건이 정해진 요청은 해당 부분에서 시작할 수 있다. 이번 세 경로의 병렬 수작업 탐색은 특정 시작 순서의 효과나 비용 우위를 검증하지 않았다. 세 경로를 항상 같은 비중으로 실행하거나 하나의 순위로 합칠 근거도 확보하지 못했다. 특히 다른 분야로 멀어지는 것 자체는 성과가 아니다. 옮길 관계와 그대로 유지해야 하는 제약을 설명할 수 있어야 한다.

이 판단은 두 합성 문제의 수작업 검색 관측과 아래 1차 연구를 대조한 **설계 제안**이다. 어떤 검색 엔진이 더 정확하다는 통계적 결론도, 유용성이 입증된 제품 설계도 아니다. 검색 API의 내부 알고리즘은 관측하지 않았다.

## 2. 서로 다른 방법을 무엇과 결합할까

| 비교할 방법 | 작동 원리·얻는 것 | 추가 부담·실패 조건 | 설명 가능성·결합 조건 | 이번 확인 수준 |
| --- | --- | --- | --- | --- |
| 목적/제품군의 키워드·대안 목록 | 익숙한 제품 범주로 후보 이름을 빨리 얻음 | 범주 이름이 같아도 세부 보장은 빠짐. 제품 전체 목적이 달라 유용한 작은 기능은 안 보일 수 있음 | 어떤 단어·목록에서 나왔는지 명확. 원문 조건 확인의 시작점 | P1/P2 실제 웹 질의; 기존 목록 직접 재열람 |
| 동작·실패 조건의 키워드와 코드/문서 추적 | retry, conflict, checkpoint 같은 동작을 좁혀 필요한 부품과 계약을 찾음 | 용어를 알아야 하며 경로에만 있는 단어도 매치. code search 미색인·기본 브랜치 범위 등 한계 | 함수·설정·문서 절로 주장 범위를 설명. 발견 후 버전·호출자·경계 확인과 조합 | P1/P2 실제 질의·고정 소스 관찰; 웹 Code Search 전체 실행은 아님 |
| 전체 문장 의미검색 | 다른 어휘의 문장도 의미 표현으로 가까이 놓음 | 모델·자료 영역·문서 길이에 영향. 한 문장 안의 필수 조건을 유사도만으로 보장하지 못함 | 가까운 문서 발견 이유와 요구 충족 근거는 따로 필요 | BEIR 문헌 검토만; 자체 embedding/BM25 대조 미실시 |
| 목적/메커니즘/결과를 나눈 의미검색 | 전체 주제 대신 원하는 측면을 맞춤 | 나누는 비용·잘못 분해할 위험. 전체 목적을 나누어도 선택 부분이 누락될 수 있음 | 원문 구절과 분리한 의미의 대응을 보존할 때 검토 가능 | SOLVENT 원문 검토만; 자동 분해·벡터 구현 미실시 |
| 선택 부분의 관계·중요 속성을 유지한 추상 질의 | 분야 명사를 바꿔도 유지되는 관계를 탐색 | '자료 관리', '동기화'처럼 너무 넓으면 핵심 불변식이 사라짐. 기술 어휘 사전도 충분하지 않을 수 있음 | 원래 요구→남긴 속성→후보 원리→깨지는 조건을 함께 설명 | P1/P2 수동 질의 및 Focus-Abstraction 연구 검토 |
| 이미 찾은 결과의 결합 | 서로 다른 경로가 놓친 후보를 함께 볼 수 있음 | 상관된 결과의 반복·유명 후보 쏠림. 완성품/부품/원리는 적합성 의미가 다름 | 발견 경로를 유지한 합집합과 역할별 비교부터 가능. RRF는 별도 검토 선택지 | RRF 원문 검토만; 최종 랭킹 설계/구현 없음 |

GitHub 문서는 일반 단어의 경로/내용 매치와 `content:`, `path:`, `symbol:` 같은 한정법을 구별한다. 인덱싱 제외와 전수검색 미지원도 명시한다. 따라서 검색 부재를 코드 또는 기능 부재로 바꾸면 안 된다. 이는 웹 Code Search 문서의 설명이며 이 연결 도구와 같은 내부 구현이라는 주장은 아니다. [M-S06](https://docs.github.com/en/search-github/github-code-search/understanding-github-code-search-syntax), [M-S13](https://docs.github.com/en/search-github/github-code-search/about-github-code-search)

BEIR의 당시 모델 비교에서는 영역이 달라질 때 순위가 바뀌며 BM25도 강한 기준선이었다. 이 때문에 의미검색을 제외하지도, 최신이라는 이유만으로 필수로 정하지도 않는다. 원문은 2021 연구의 특정 모델·자료 결과다. 본 연구는 검색 엔진 내부를 지정하거나 재현하지 않았으므로 P1/P2 결과를 BM25 대 벡터 승패로 해석할 수 없다. [M-S02](https://arxiv.org/html/2104.08663v4)

반대 방향의 제한도 있다. 같은 논문 §6은 정답 후보 수집이 어휘 검색에 치우칠 수 있음을 보이고, TREC-COVID의 미판정 후보를 추가 판정한 뒤 ANCE와 BM25의 상대 성능이 뒤집혔다고 보고한다. 따라서 어휘 검색으로 얻은 후보만 정답으로 삼아 원리/의미 경로를 평가하면 새 후보를 부당하게 오답으로 셀 수 있다. 이 반례 역시 특정 평가 표본의 결과이며 의미검색의 일반 우위는 아니다.

RRF는 순위를 결합하는 간단한 원리지만 요구조건 검사가 아니다. 원문에도 모든 표에서 모든 비교 대상을 이기는 결과는 아니다. 서로 다른 종류의 도움을 먼저 구별하고, 동질적인 후보 집합의 순위 결합이 필요한 경우에만 이후 검토할 선택지로 보존한다. [M-S03](https://cormack.uwaterloo.ca/cormack/cormacksigir09-rrf.pdf)

## 3. 처음 유망했던 가설을 반박한 내용

### 가설 A: 목적과 메커니즘만 분리하면 다른 분야의 좋은 후보를 찾을 수 있다

SOLVENT는 배경·목적·메커니즘·결과를 구별하지만 작은 데이터셋, 누락된 정답 쌍, 문서 장르에 따른 표현 차이를 한계로 둔다. '어떻게 만들었는가'보다 '무엇을 알아냈는가'가 중요한 논문도 있다. 목적/메커니즘 분리 자체를 모든 문서에 강제할 근거는 아니다. [M-S01](https://josephcc.com/static/papers/53236685/paper.pdf)

특정 부분의 재설계를 다룬 별도 연구는 전체 목적보다 선택한 초점과 필요한 속성을 유지하는 추상화를 제안한다. 동시에 전체 문장 의미표현도 관련성에서 예상보다 좋은 결과를 보였으며, 지나친 추상화와 기술 용어 부족을 인정한다. 따라서 '원리 검색이 항상 제품 검색보다 낫다'는 결론은 보류한다. [M-S05](https://joelchan.me/assets/pdf/2018-chi-focused-abstraction.pdf)

**이번에 남긴 수정안:** 목적은 자유문 그대로 둔 채, 특정 실패를 막는 데 필요한 관계를 추가 질의로 만든다. 원문 요구의 대체본으로 삼지 않는다. P1의 '다시 실행 가능'과 '같은 결과의 중복 공개 방지', P2의 '상태 수렴'과 '상충한 사람의 수정 확인'을 따로 묻는 방식이다.

### 가설 B: 멀리 떨어진 분야일수록 새로운 좋은 아이디어다

JPL/BYU는 종이접기에서 태양광 배열 전개로 원리를 옮긴 시제품을 공개했다. 그러나 종이와 패널의 두께 차이 때문에 구조를 다시 설계해야 했다. 공식 보고는 실제 전이 사례를 뒷받침하지만, 내 실험이나 모든 유추의 적용 성공은 아니다. 이 사례는 **소재/실행 조건을 버린 추상화가 실패할 수 있다**는 경계로 쓴다. 문서 처리나 공동 기록의 추천 후보로 끼워 넣지 않는다. [M-S15](https://www.jpl.nasa.gov/news/solar-power-origami-style/)

**이번에 남긴 수정안:** 다른 분야의 후보마다 원래 문제·작동 관계·목표 문제의 대응·유지해야 할 전제·반례를 기록한다. 목표 적용 증거가 없으면 '전이 가설'로 둔다. 내부 소프트웨어 분야 간 전이와 공예→우주 구조 같은 원거리 전이는 구별한다.

### 가설 C: 인기 있는 완성품이면 핵심 실패 조건도 갖춰져 있을 것이다

`document management stars:>10000`을 실제 GitHub 연결 검색에 넣었을 때 반환 후보는 Paperless-ngx 하나였다(M-Q10). 이는 인기도 조건으로 들어온 후보라는 관측이지, 별 수가 검색의 오탐을 유발했다는 인과 실험이 아니다. [CASE_P1](CASE_P1.md)의 버전별 문서·코드 대조를 거치기 전에는 이 후보가 중복 공개 방지 조건을 기본으로 충족한다고 채택할 수 없다.

**관측과 추론의 구별:** 인기도 필터의 결과와 조건 위반 위험은 실제 기록이다. 필터 없는 통제군·전체 순위가 없어 인기 편향의 크기나 인과는 미측정이다. 후보 자체를 '나쁜 제품'으로 분류하는 대신 '이 요구를 만족한다는 추론'을 기각한다.

## 4. 기존 네 후보를 무엇에 재사용했나

기존 표본을 동일한 추천 목록으로 다시 제출하지 않았다. 각 발견 채널이 이번 질문에서 어떤 증거까지 줄 수 있는지 재확인했다. 아래는 수집 스택 선택이 아니다.

| 기존 후보 | 직접 재열람한 범위 | 이 연구에서 남길 역할·한계 |
| --- | --- | --- |
| OpenAlternative | 고정 README의 전환 공지·문서관리·노트 분류 | 후보 이름과 공식 원문으로 가는 출발점. 분류·소개·별 수는 P1/P2 세부 보장의 근거가 아님 |
| OSSInsight | About, live Explorer 안내, 고정 ask route | 활동·인기 지표 참고. 소개 기능과 실제 상태를 별도 확인해야 함. 전체 검색의 필수 경로로 채택하지 않음 |
| Libraries.io | 고정 검색 컨트롤러 | 메타데이터/정렬 원리 참고. 키 접근·실제 응답은 미확인. 패키지 지표로 적용성을 판정하지 않음 |
| AlternativeTo | FAQ·현재 표시 약관 | 같은 주된 목적의 대안 관계를 이해하는 참고. 부분 원리 발견과 주목적 대체는 다름. 경쟁 DB의 수집원으로 채택하지 않음 |

원문: [M-S07](https://github.com/piotrkulpinski/open-source-alternatives/blob/156045dde3d74a6bfdad675c13521718ca0e50b5/README.md), [M-S08](https://ossinsight.io/docs/about), [M-S09](https://github.com/pingcap/ossinsight/blob/77538008b8fe8b0dd3dc6caa3fc4ba987e10360a/apps/web/app/api/explorer/ask/route.ts), [M-S10](https://github.com/librariesio/libraries.io/blob/16ef5c54bc2d2b984963aa1b342a47e595c8a85b/app/controllers/api/search_controller.rb), [M-S11](https://alternativeto.net/faq/), [M-S12](https://alternativeto.net/about/terms/), [M-S14](https://ossinsight.io/explore).

현재 Explorer 페이지는 maintenance 안내이며 고정 코드도 앞에서 503을 반환하는 분기를 가진다. 공개 HTML과 소스를 읽었고 POST는 실행하지 않았다. AlternativeTo 약관은 사이트 콘텐츠로 경쟁 DB를 만드는 사용을 금지한다고 명시한다. 일반 열람으로 다른 데이터 이용 허가를 얻은 것으로 취급하지 않는다. 세부 관측 범위는 원장에 있다.

## 5. 검색 자료 범위와 비용을 넓히는 조건

| 현재 막힌 질문 | 그때 추가할 자료 | 추가 비용/한계 | 멈출 조건 |
| --- | --- | --- | --- |
| 이름을 모름 | 목적 키워드, 제품 목록, 공개 웹 검색 | 소개문이 상세 실패 조건을 생략할 수 있음 | 후보 이름·공식 원문 경로를 얻으면 원문 확인으로 전환 |
| 필요한 기능을 앱 전체와 혼동 | 공식 API/구조 문서, 패키지 설명 | 책임 분할을 읽는 비용 | 재사용할 부분과 앱의 나머지 책임을 설명 가능 |
| 문서의 보장/기본값이 불명 | 같은 버전의 설정·실행 분기·테스트 소스 | 코드 읽기와 버전 핀 비용 | 보장 범위가 밝혀지거나 실행 없이는 판단 불가로 남음 |
| 고유 분야 명사로만 검색됨 | 관련 논문·표준·다른 분야의 원리 문서 | 추상화와 원뜻 대조 비용 | 대응할 관계·전제·반례가 없으면 유사어 후보로 제외 |
| 장애·삭제·동시성 경계가 불명 | 공식 한계 문서, 이슈/실패 보고 | 보고의 환경·재현 여부 확인 필요 | 단일 보고를 전체 실패로 확대하지 않고 필요한 실험을 지정 |
| 후보가 부족해 결과를 반복함 | 다른 표현·어휘·분야로 추가 질의 | 검색 비용 증가, 새 근거 없는 반복 위험 | 두 경로가 같은 설명만 반복하면 미해결과 다음 확인을 기록 |

지금 비교한 비용은 구현·검토 작업의 종류다. 엔진 실행 시간, 인건비, 토큰 비용, 정확도 향상을 실측한 것이 아니다. 질의/원문 개수는 관측 작업량으로만 센다. 어떤 경로가 더 싼지 또는 항상 추가할 가치가 있는지는 이후 사용 맥락에 따라 달라진다.

## 6. 미해결과 가장 작은 다음 확인

1. 각 문제의 한 후보에서 필수 조건 하나를 깨는 최소 입력을 고정하고, 공식 문서·고정 소스·직접 실행의 판정 차이를 비교한다. P1/P2에 구체 입력을 남긴다.
2. 부분 추상화가 다른 좋은 후보를 실제로 추가했는지 확인하려면 같은 문제·같은 시간 또는 검토 예산에서 후보의 발견 경로를 가린 사람이 판단해야 한다. 이번 작업은 그 공통 판정팩을 만들지 않는다.
3. 검색 결과 통합은 역할별 묶음의 중복만 정리하는 안, 사용자가 원하는 도움 종류를 먼저 고르는 안, 같은 종류 안에서만 결합하는 안을 보존한다. 단일 최종 순위와 데이터 모델 선택은 후속 설계에 남긴다.

직접 열지 못한 PMC 문서 M-S04와 지원되지 않는 전역 검색 URL M-Q09는 실패 기록으로 남기고 근거·성공 수에 넣지 않았다. 동일 논문의 다른 호스팅·재열람도 자료 수를 늘리는 용도로 사용하지 않았다.
