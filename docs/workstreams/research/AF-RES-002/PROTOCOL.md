# AF-RES-002 — 탐색 전에 고정한 문제와 관측 규칙

## 1. 질문과 경계

같은 목적의 완성품, 재사용할 부분, 다른 분야의 원리를 찾는 공개 검색 경로를 두 개발 문제에서 비교한다. 아래 문제는 연구자가 만든 합성 개발 문제다. 외부 구현의 실제 요구사항이나 사용자 확정 제품 명세로 취급하지 않는다. 제품 이름은 넣지 않고 검색 전에 고정했다.

AF-RES-002의 `depends_on`은 비어 있다. AF-RES-001·003·004 산출물은 읽거나 사용하지 않는다. 계획의 고정 자료인 기존 4후보 표본과 AF-DOT-001·002 인계는 배경 근거일 뿐 검색 성능 또는 추천 적합성의 검증이 아니다.

## 2. 문제 P1 — 문서 묶음 처리

> 사용자가 폴더의 PDF·이미지 문서를 한꺼번에 넣으면 각 문서를 변환하고 검색 가능한 결과를 저장하는 도구를 만들고 싶다. 손상된 파일 하나 때문에 다른 성공 결과가 사라지면 안 된다. 작업이 중단되어 다시 시작해도 같은 입력의 결과가 중복으로 공개되지 않아야 하며, 실패 항목을 알아보고 다시 처리할 수 있어야 한다. 자체 운영할 수 있어야 한다. 전체 제품을 쓰거나 필요한 처리 부분만 참고하는 두 선택을 열어 둔다.

- 고정 필수 조건: 항목별 실패 격리, 성공 결과 보존, 중단 후 재시도, 같은 입력의 중복 공개 방지, 실패 확인, 자체 운영 가능성.
- 아직 정하지 않음: 프로그래밍 언어, DB, 큐, OCR 정확도 목표, 문서량, 클라우드, 외부 알림, 완전한 exactly-once 실행.
- 금지된 축약: `retry 지원`을 `중복 부작용 없음`으로, `OCR 가능`을 전체 내구성 요구 충족으로 바꾸지 않는다.

## 3. 문제 P2 — 오프라인 공동 기록

> 현장 팀이 연결이 끊겨도 공유 기록을 읽고 각자 수정하는 도구를 만들고 싶다. 연결이 돌아왔을 때 수정이 소리 없이 사라지면 안 되고, 같은 기록의 상충하는 수정은 확인하고 해결할 수 있어야 한다. 사용자가 내용을 자기 파일로 내보낼 수 있어야 한다. 자체 운영을 선호하지만 필수로 고정하지 않는다. 완성된 앱을 쓰거나 동기화 부분만 재사용할 수 있다.

- 고정 필수 조건: 오프라인 읽기·쓰기, 복구 후 병합/충돌 보존, 상충 수정 확인·해결, 사용자 데이터 내보내기.
- 아직 정하지 않음: 단일/다중 기기 수, 중앙 서버 유무, 실시간 동시 타이핑, 암호화 방식, 업무 권한·서명·재고 같은 불변식.
- 금지된 축약: `오프라인`을 `동시 수정 안전`으로, `수렴`을 `사용자 의도 보존`으로 바꾸지 않는다.

## 4. 각 문제에서 비교할 세 경로

| 경로 | 시작 질의의 원칙 | 확인할 것 |
| --- | --- | --- |
| 완성품 | 문제의 사용 목적·운영 조건으로 검색 | 전체 경험 중 실제로 충족한 조건과 미확인 |
| 부품 | 필요한 동작·실패 형태·인터페이스로 검색 | 재사용 단위와 나머지 앱이 책임질 조건 |
| 다른 분야 원리 | 입력→상태 변화→실패/불변식을 분야 명사에서 분리 | 원 분야의 입증 범위, 목표 문제로 옮기는 대응, 깨지는 반례 |

최초 검색은 제품명을 넣지 않는다. 후속 이름 질의·공식 도메인 제한·문서/코드 추적은 허용하되 발견 검색과 원문 검증 검색을 구별해 기록한다. 같은 후보가 여러 경로에 나타나도 발견 순서와 역할을 보존한다.

## 5. 검색과 출처 기록

- 질의별로 검색 시각(UTC), 검색 도구/엔진, 정확한 문자열·필터, 목적, 도구가 실제 반환한 결과에서 관측한 후보와 URL, 선택/제외 이유, 후속 질의·원문 출처 ID를 남긴다. 순위·전체 결과 수를 제공받지 못하면 만들지 않는다.
- 공개 원문을 최소 20개 직접 연다. 검색 결과 snippet만 본 것은 D0이며 이 수에 넣지 않는다. 저장소 내부 지침과 동일 문서의 재열람도 별도 외부 자료로 세지 않는다.
- 원문별 URL, 실제 열람 시각, 문서 제목·고정 버전/commit 또는 절·관측 행, 확인 내용, 한계, 증거 단계(D1 문서/D2 코드/D3 직접 실행/D4 목표 통합)를 남긴다. 움직이는 문서는 불변 출처처럼 말하지 않는다.
- 문서 원문 전체를 복제하지 않고 필요한 짧은 인용과 자체 요약을 저장한다. 검색 결과 전체·대량 카탈로그 수집은 하지 않는다.
- 새 유료 API, 후보 설치·배포, 제품 검색기·DB·최종 순위 알고리즘, 공통 벤치마크는 만들지 않는다. 실제 검색·열람 외 후보 실행과 목표 문제 적용 성공은 미실시다.

## 6. 반례·누락과 비교 규칙

최초 유망 결론마다 실패 조건 하나 이상을 찾는다. 이름·인기도·유사 기능 때문에 생기는 오탐, 문서와 코드의 보장 차이, 모델/시스템의 수렴과 사용자 의도 차이를 따로 기록한다.

관측 가능한 누락은 '이번 질의의 도구 반환 묶음에는 없었으나 후속 경로에서 확인한 후보'에 한정한다. 검색 엔진의 전체 색인 누락·재현율·성능 우위로 확대하지 않는다. 서로 다른 길이·필터의 수작업 질의를 통제 실험이라고 부르지 않는다. 비교에는 추가 질의·원문 확인 부담, 설명 가능한 연결, 결합 조건과 중단 기준을 사용한다.

## 7. 병렬 분담과 산출물

P1과 P2는 서로 독립 탐색하며 상대 후보·결론을 미리 받지 않는다. 주 작성자는 기존 발견 채널과 검색 방법의 원문을 조사하고 마지막에 두 결과를 대조한다. 별도 검토자는 핵심 주장과 원문, 반례, 범위·과장 여부를 확인한다. 내부 하위 에이전트 검토를 새 웹 Pro 세션 교체 시험으로 표시하지 않는다.

작은 묶음: `CASE_P1.md`, `CASE_P2.md`, `METHODS.md`, `RESEARCH.md`. 재현용으로 각 묶음의 출처·질의 JSON, 독립 검토와 검사 기록을 필요한 만큼 둔다. 마지막 파일은 `HANDOFF.md`다. 최종 DB/API 스키마를 확정하지 않는다.
