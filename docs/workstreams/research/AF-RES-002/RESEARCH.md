# AF-RES-002 — 완성품, 재사용할 부분, 다른 분야 원리를 함께 찾기

상태: 연구·문헌 및 정적 코드 관찰 완료, 독립 검토와 인계 대상. 2026-11-20 KST / 2026-11-19 UTC.
입력 기준: `chore/workspace-foundation`의 `46c874671c6d066292750401d75af50136ef95d6`.
이 문서는 검색 방식의 비교와 다음 판단에 필요한 근거를 남긴다. 검색기·제품 DB·공통 벤치마크·최종 순위 알고리즘은 만들지 않았다.

## 1. 결론

**같은 목적의 완성품과 다른 분야의 유용한 부분을 함께 찾으려면, 발견한 경로와 후보가 책임지는 요구 부분을 보존한 채 비교해야 한다.** 목적이 비슷하다는 이유만으로 완성품의 세부 보장을 인정하지 않고, 부품이 유용하다는 이유만으로 완성된 사용 경험을 인정하지 않는다. 다른 분야의 원리를 가져올 때에는 원래 분야에서 유지하던 관계와 목표 문제에서 깨질 조건까지 연결한다.

두 문제 모두 목적 검색에서 시작한 후보가 남았다. 동시에 동작·실패 조건을 확인하자 최초 판단을 제한하는 반례가 나왔다. 따라서 완성품을 우선 폐기하거나 모든 일을 직접 조합하자는 결론은 아니다. **요구에 이미 맞는 완성품을 사용할 가능성과, 필요한 부분만 재사용할 가능성을 함께 유지하는 조사 방식**을 제안한다.

이것은 이번 소표본과 문헌을 종합한 설계 제안이다. 특정 시작 순서, 세 경로의 고정 비중, 단일 결합 점수의 우위는 검증하지 않았다. 전체 사용 경험이 필요한 요청은 목적·제품군부터 살펴볼 수 있고, 필요한 부품이나 실패 조건이 이미 정해졌다면 그 부분부터 시작할 수 있다.

| 고정 문제 | 완성품 경로에서 남은 것 | 부분·원리 경로가 추가한 질문 | 첫 결론을 바꾼 경계 |
| --- | --- | --- | --- |
| P1: 문서 묶음 변환·검색, 실패 격리, 중단 복구, 중복 공개 방지 | Paperless-ngx·Docspell을 조건부 후보로 유지 | 변환, 재전달, 재시도, 계산 재사용, 결과 공개는 어느 부분이 책임지는가? | 기능명 `duplicate`·`retry`와 기본 중복 정책·공개 유일성은 다름 |
| P2: 오프라인 공동 기록, 수정 보존, 상충 확인·해결, 내보내기 | Joplin을 조건부 후보로 유지 | 값 보존, 장치 간 수렴, 사용자의 상충 인지·의미 판단은 어디서 이루어지는가? | 충돌 값이 남아 있어도 기본 화면에는 하나만 보일 수 있음 |

판정의 상세 근거와 조건은 [P1 사례](CASE_P1.md#4-완성품-경로-사용-경험은-가까우나-운영-조건은-별도다), [P2 사례](CASE_P2.md#3-요구-부분과-후보-근거)에 있다. 채택·운영 성공을 판정한 표가 아니다.

## 2. 조사 설계와 실제 읽은 범위

검색 전에 제품명이 없는 서로 다른 자유문 문제를 [PROTOCOL.md](PROTOCOL.md)에 고정했다. P1은 파일별 실패와 중단 후 결과 공개, P2는 여러 장치의 오프라인 수정과 상충 검토를 다룬다. P1에 특정 언어·큐·DB나 정확히 한 번 실행을 추가하지 않았고, P2에 실시간 타이핑·중앙 서버 부재·특정 업무 불변식을 필수로 추가하지 않았다.

각 문제에서 완성품, 재사용할 부분, 다른 분야 메커니즘의 세 경로를 실제 공개 검색으로 탐색했다. 두 사례 담당자는 같은 프로토콜을 읽고 독립적으로 조사했다. 주 작성자는 검색 방법의 1차 연구와 기존 발견 채널을 검토하고, 사례의 핵심 원문을 다시 읽었다. 별도 검토자는 원문과 결론을 교차 확인했다. 동일 모델 계열의 내부 병렬 검토이며 서로 다른 외부 연구자나 별도 웹 Pro 작업자의 재현 실험으로 표현하지 않는다.

| 자료 묶음 | 직접 연 서로 다른 자료 | 읽은 범위 | 별도로 제외한 것 |
| --- | ---: | --- | --- |
| 방법·발견 채널 | 14 | 논문·공식 설명 12, 고정 코드 2 | 본문 접근이 막힌 논문 1 |
| P1 | 16 | 공식 문서·원논문 14, 고정 코드 2 | 차단 페이지, 중복 사본, 검색 snippet |
| P2 | 14 | 문서 관련 절 12, 고정 코드 1, 저자 초록 1 | 읽을 내용이 없는 페이지·실패한 PDF |
| 합계 | **44** | **본문·문서·코드의 관련 부분 43 + 초록 1** | 내부 작업 지침·재열람은 추가 자료로 세지 않음 |

전체 sources 기록은 차단된 M-S04를 포함해 45개다. 읽은 44개는 D1 39개와 D2 5개이며, D1 중 P2-S14는 초록·서지만 읽었다. D3 제품 실행·D4 목표 통합은 0이다. 논문에 저자가 보고한 구현·평가가 있어도 우리 실행 증거로 승격하지 않았다.

질의별 문자열·시각·필터·관측 후보·처리 이유·후속 연결은 [방법 기록](evidence/methods.json), [P1 기록](evidence/p1.json), [P2 기록](evidence/p2.json)에 있다. 각 출처에 URL, 읽은 절/행, 버전 또는 commit, 확인 내용, 한계를 저장했다. 움직이는 문서에는 열람 시점을 붙였고 고정 commit 문서와 구분했다.

P1은 고유 문자열 9개를 반복 포함 10회 제출한 6회 호출이다. P2는 고유 문자열 7개를 반복 포함 10회 제출했다. 초기 복수 질의의 반환 결과가 섞였을 때 P1은 공유 관측 집합으로 남겼고 P2는 질의를 각각 다시 제출했다. 방법 기록의 10개 항목 중 하나는 지원되지 않는 GitHub API URL 호출 실패이므로 검색 결과 0개로 해석하지 않는다. 이 서로 다른 단위를 합쳐 검색 효율이나 성공률의 분모로 쓰지 않는다.

## 4. 최초 유망 결론과 반례

### P1: 재시도와 중복 탐지가 있으면 충분한가

조사한 Paperless 기본 브랜치의 고정 문서는 중복을 기본 허용하고 설정으로 거부를 선택한다고 설명한다. 해당 분기 코드를 확인했지만 안정 릴리스 전체나 실제 배포의 동작으로 일반화하지 않았다. Docspell의 업로드 중복 생략 기본값도 별도로 확인했다. 제품명을 발견한 다음에도 기본값과 버전을 읽어야 하는 이유다. [P1-S01](https://github.com/paperless-ngx/paperless-ngx/blob/4973be8499bc61dc4f791a609d0d31e9ac9ccd41/docs/usage.md), [P1-S06](https://docspell.org/docs/api/upload/)

Celery의 재시도·ACK와 작업 작성자의 멱등성 책임은 서로 다르다. 같은 ID의 서로 다른 두 작업에 관한 제한을 `Task.retry` 자체의 결함으로 확대하지 않았다. 빌드 캐시를 붙여 계산을 줄여도 문서가 사용자에게 한 번만 공개되는지의 판단은 남는다. 수정한 결론은 **실행 시도, 재사용할 계산 결과, 영속 공개 상태를 따로 확인하자**는 것이다. [P1-S09](https://docs.celeryq.dev/en/stable/faq.html), [P1-S12](https://bazel.build/remote/caching)

이 결론도 과도하게 적용하면 새 인프라를 불필요하게 만들 수 있다. 기존 제품의 정확한 버전과 설정이 요구를 충족한다면 전체 제품을 쓰는 선택을 유지한다. P1에서 조립 비용이 더 낮거나 장애 복구가 더 좋다는 실행 비교는 하지 않았다.

### P2: 자동 병합으로 수정 손실 문제가 끝나는가

Automerge와 CouchDB 문서는 여러 값·revision의 보존과 기본 조회에서 보이는 winner를 구분한다. 사용자가 상충을 인지해야 한다는 요구는 앱이 다른 값도 보여 주는지 확인해야 한다. 기본 값만 렌더링되는 화면에서 값이 수렴한다는 관측만으로 P2를 완료 판정할 수 없다. [P2-S09](https://automerge.org/docs/reference/documents/conflicts/), [P2-S11](https://docs.couchdb.org/en/stable/replication/conflicts.html)

그 반대 주장도 충분하지 않다. 모든 변경을 명시적 분기로 남겨 매번 검토시키면 작은 메모의 수정 부담이 커질 수 있다. 같은 속성의 경쟁과 서로 다른 속성의 의미 모순을 구별하고, 실제 기록에서 어느 충돌을 사람이 알아야 하는지 정해야 한다. P2의 상태·결론 모순은 합성 가설이며 특정 CRDT의 구현 결함이나 모든 업무에 조정이 필요하다는 증명으로 사용하지 않았다. [P2 사례의 반례](CASE_P2.md#4-첫-유망-결론을-깨는-반례)

### 검색 방법: 목적·메커니즘 분해와 의미검색이면 모두 찾는가

SOLVENT와 focused-abstraction 연구는 유용한 관점 분리를 제공하지만, 주석 비용·장르·선택한 부분·너무 넓은 추상의 한계를 함께 보고한다. 다른 분야 명사를 제거하다가 필요한 속성까지 지우면 전이 근거가 약해진다. 목적과 메커니즘을 나눈 표현도 요청한 작은 부분을 정확히 잡았는지는 다시 확인해야 한다. [방법 비교와 반례](METHODS.md)

BEIR의 당시 비교에서 강한 어휘 기준선이 나왔다고 하여 의미검색을 제외하지 않았다. 같은 논문의 추가 판정 사례는 어휘 검색에 치우친 정답 후보 집합이 다른 경로의 새 발견을 불리하게 평가할 수 있음을 보여 준다. 처음 찾은 후보 목록을 정답 전체로 삼는 방식 자체를 경계한다. 최신 모델의 보편적 성능이나 이번 웹 검색의 내부 알고리즘에 관한 결론은 아니다. [M-S02 §6](https://arxiv.org/html/2104.08663v4)

## 5. 다른 분야 전이: 무엇이 확인됐고 무엇이 가설인가

| 원 분야 근거 | 직접 확인한 범위 | 목표 문제로의 대응 | 전이가 깨지는 조건 |
| --- | --- | --- | --- |
| 빌드 시스템 → Reflow의 생물정보학·분석 작업 | 제작자의 고정 README가 사용 분야와 증분 계산을 설명함. 외부 운영 재현은 없음 | P1의 입력·변환 정의·산출물을 구분하고 변경 영향을 재계산한다는 가설 | 계산 결과의 재사용을 공개 유일성으로 대신하거나 도구·환경 변경을 식별에서 빠뜨림 |
| DB의 중단 복구 | SQLite 공식 원문의 commit 판별과 파일 시스템 가정 | P1에서 어느 성공이 영속화됐고 무엇을 복구해야 하는지 묻는 가설 | DB 밖 파일·큐·외부 호출까지 한 트랜잭션으로 묶인다고 가정함 |
| DVCS·사진 관리 → 구조화 자료 | TreeDB 논문이 분야 간 대응과 사진 편집 의도 반례를 명시함. 제안 수준 | P2에서 변경 전달과 공동 상태의 병합을 분리하고 의미 있는 충돌 단위를 찾는 가설 | 분기 이력의 사용자 이해 비용을 무시하거나 미합의 상태를 즉시 실행 상태로 사용함 |
| 종이 접기 → 태양광 어레이 시제품 | NASA/JPL이 재료 두께를 고려한 전이 과정을 설명함 | 유추 일반론의 반례: 관계가 맞아도 물리적·운영 조건은 재설계해야 함 | 종이처럼 두께가 거의 없는 재료의 가정을 실제 장치에 그대로 적용함. P1/P2 후보 추천에 사용하지 않음 |

출처: [Reflow 고정 README](https://github.com/grailbio/reflow/blob/90deddd72f8f1b489cab0812e2827c299f77dd19/README.md), [SQLite atomic commit](https://www.sqlite.org/atomiccommit.html), [TreeDB 원논문](https://groups.csail.mit.edu/sdg/pubs/2022/Merge_What_You_Can_PaPoC_2022.pdf), [NASA/JPL](https://www.jpl.nasa.gov/news/solar-power-origami-style/).

따라서 문헌에 다른 분야 연결이 있다는 것과 우리 목표 문제에서 유용하다는 것은 별도다. 이번 조사는 후자의 적용 전제와 반례를 남겼으며 현장 적용 성공은 확보하지 못했다.

## 6. 오탐·누락·인기도를 어디까지 말할 수 있는가

실제 관측한 오탐은 서로 다른 종류였다. P1의 OCR 부품을 완성 앱으로 읽는 역할 혼동, GRAIL Reflow 질의에 나타난 다른 `reflow` 코드의 동명이름, P2의 개인용 예제를 팀용 완성품으로 승격하는 해석이다. 열지 않은 후보는 부적합으로 확정하지 않고 D0로 남겼다.

누락은 반환된 창을 기준으로만 기록했다. P1 단독 부품 질의에 관측되지 않은 Celery·BullMQ 공식 문서를 이름·도메인 후속 질의로 찾았고, P2는 부품 질의에 없던 CouchDB 모델을 DB 관점을 추가한 뒤 확인했다. 이것은 전체 색인 부재나 검색 재현율의 측정이 아니다. 이름을 알고 있던 연구자의 지식과 서로 다른 필터도 결과에 개입했다.

인기도의 인과 효과는 측정하지 못했다. 실제 `document management stars:>10000` 저장소 질의로 Paperless 후보를 얻었지만, 별 기준이 그 후보의 중복 정책 적합성을 보장하지는 않았다. 인기가 높아서 오답이 됐다는 주장이나 덜 유명한 제품이 더 낫다는 순위는 만들지 않았다. 다음에 인기도의 영향을 확인한다면 같은 목적 질의의 별 필터 유무를 대조해 반환 후보와 검증할 요구 조건을 함께 기록해야 한다. 이 대조는 미실시다. [M-Q10 및 M-S07–M-S14](evidence/methods.json)

## 7. 방법을 결합하는 조건과 비용

| 방법 | 추가하는 정보 | 비용·설명 책임 | 사용할 조건 |
| --- | --- | --- | --- |
| 목적·제품군 및 대안 목록 | 전체 사용 경험의 후보와 익숙한 범주 | 같은 범주의 실제 차이, 버전·설정·접근 조건을 원문에서 확인 | 완성된 경험을 찾거나 후보 이름이 필요한 경우 |
| 부분의 동작·실패 조건 | 정확한 책임과 경계, API·함수·정책 | 기술 용어 학습과 호출자·설정·영속 경계의 추적 | 목적 후보의 특정 요구가 미확인되거나 부품 재사용이 목표일 때 |
| 목적/메커니즘 분해 및 관계 추상화 | 분야를 넘어 비교할 부분 | 분해·주석 비용, 속성 유실, 전이 전제와 반례의 설명 | 같은 분야 결과가 같은 한계를 반복하거나 요구의 관계를 다른 분야와 대응할 수 있을 때 |
| 전체 의미 표현·결과 결합 | 다른 표현의 후보와 여러 경로의 보완 | 모델·영역·평가 기준·중복 후보·역할 혼합의 문제 | 별도 검증을 설계할 때의 선택지. 이번에는 문헌만 확인 |

시간·금전·정확도 비용을 수치로 추정하지 않았다. 실제 부담으로 관측한 것은 재질의, 차단 원문의 공식 저장소 추적, 여러 기능 페이지의 연결, 버전 차이 확인, 원 분야 전제의 대조다. RRF 같은 순위 결합을 구현하거나 이 표를 최종 알고리즘으로 확정하지 않았다.

확장 여부는 남은 질문이 결정한다. 후보를 더 늘려도 이미 확보한 동작 설명만 반복된다면 중단할 수 있다. 반대로 기본값·실패 조건·전이 전제의 미확인이 선택을 바꾸면 해당 원문이나 가장 작은 실행을 추가해야 한다. 세 경로를 의무적으로 같은 양만큼 실행하는 규칙은 이 자료로 정당화되지 않는다.

기존 연결 시험의 후보 네 개는 역할을 재확인하는 데만 재사용했다. OpenAlternative는 목적별 후보 입구, OSSInsight는 활동 자료, Libraries.io는 패키지 발견, AlternativeTo는 목적 대안과 일부 대안 관계의 입구다. 이들의 문서·코드는 P1/P2의 구체 보장을 대신하지 않았다. 기존 목록을 다시 요약하는 데서 끝내지 않고 두 문제의 실제 질의·원문·반례를 추가했다. [기존 입력의 고정 출처와 재열람](evidence/methods.json), [방법별 제한](METHODS.md)

## 8. 남은 불확실성과 답을 바꿀 최소 확인

이번 연구의 완료 조건은 탐색 경로와 근거·한계를 비교하는 것이다. 제품별 운영 검증은 수행하지 않았으며 아래는 채택 판단을 위한 후속 입력이다. 검증하지 않은 결과를 성공으로 남기지 않는다.

| 선택을 바꿀 미확인 | 최소 입력·관측 | 첫 구체 행동 |
| --- | --- | --- |
| P1 완성품이 실패·중복 공개 조건을 충족하는가 | 정상 A, 손상 B, 정상 C; A의 이름만 바꾼 재입력; 공개 전/후 중단에서 영속 결과와 실패 연결 확인 | 실제 채택 후보의 릴리스·중복 설정을 고정하고 해당 버전의 입력·결과 조회 명령을 정함 |
| P1 캐시를 가져올 필요가 있는가 | 같은 입력에서 변환 설정·도구 버전만 변경해 기대한 재계산과 공개 정책 비교 | 계산 절감이 실제 목적에 필요한지와 문서 정체성 정책부터 구분 |
| P2 후보의 충돌이 사용자에게 드러나는가 | 두 장치가 단절 상태에서 같은 기록 속성을 각각 수정, 재연결 후 양쪽 수정과 해결 경로·내보내기 확인 | 기록 한 종류와 상충 인지 기준을 고정하고 후보의 두 장치 흐름 검토 |
| P2에 의미 단위 검토가 필요한가 | 서로 다른 속성은 각각 유효하지만 함께 해석하면 모순인 한 기록 | 실제 업무 규칙 한 개를 명시; 이 규칙을 특정 엔진의 일반 보장으로 가정하지 않음 |
| 다른 검색 순서·방법이 더 유리한가 | 새로운 문제에서 순서·사전지식·판정 후보 집합을 구분 | 이 조사와 독립된 후속 비교 필요. 현재 기록으로 우위 수치를 만들지 않음 |

배포 버전·사용 환경을 정하지 않은 상태에서 가상의 공통 제품 실행 명령을 만들지 않았다. 실행을 기다려야 끝나는 필수 연구 검사는 없다. 문서·JSON·허용 경로·세션 계약의 실제 검사와 재검사 명령은 최종 HANDOFF에 기록한다.
