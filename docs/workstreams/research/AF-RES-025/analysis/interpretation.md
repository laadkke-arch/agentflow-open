## Q2. 일반 검색과 관계 검색을 어떻게 비교했는가

질문마다 G/R에 동일 최초 전문을 주고, 양쪽 질의 세 개와 후보 선택 규칙을 모두 먼저 봉인했다. 영어 입력·영어 검색, 같은 모델 표기 GPT-6 Astra Pro, 같은 `system1_search_query`, 같은 공개 웹 범위, 같은 조회일 2026-11-22 UTC를 사용했다. 별도 ChatGPT Pro UI의 모델 선택 화면이나 일반 사용자의 대화형 Pro 검색 세션은 관측하지 않았다. 그러므로 여기서 재현한 것은 **같은 웹 도구에서의 두 질의 구성 경로**이지, 상용 검색 제품 전체의 효과 비교가 아니다.

G는 목적에 유용한 해법과 근거를 자유롭게 찾도록 했고 구조적 추론을 금지하지 않았다. R은 최초 문서의 입력·출력·상태·반복과 필수/선호 조건을 추출해 검색어를 만들었다. R에 새 후보 이름이나 정답 분야를 추가하지 않았다. 예컨대 Q11의 G 첫 질의는 `notebook execute cell metadata passing kernel extension protocol alternatives`, R 첫 질의는 `execute code request per item structured metadata separate payload extension namespace`다. G는 실제 ipykernel 실행 경계에 닿았고, R은 요청 sidecar·REST extension·trace metadata 같은 다른 경계를 더 가져왔다. 이 차이는 후보 이름 수보다 **수신자가 실행 전에 그 값을 실제 입력으로 읽는가**라는 조건에서 판별됐다.

Q08의 R 첫 질의 `versioned set transformation monotonic add only matching rules no recursive reapplication`은 다중 버전 모델 변환 연구를 가져왔다. G의 `backward compatible package features adding optional functionality without breaking existing users`는 호환 API·업데이트 안내를 가져왔다. R은 처리 상태와 trace 관계에 더 가까운 원문을 남겼지만, RFC의 버전 우선순위와 새 출력의 재규칙 입력 금지까지 충족하는 실행 근거는 없었다. 조건을 키워드로 넣었다는 사실 자체가 그 조건의 적중 증거가 되지는 않는다. [CG-C029] [CG-C030] [CG-I05]

예산은 경로당 세 질의, 질의당 도구가 제공한 앞 열 결과, 최초 고유 원문 시도 다섯 개였다. 실패도 다섯 개에 포함하고 같은 원문 재시도만 한 번 허용했다. 후보 선택은 질의 순서와 제공 순위를 따라, 목적/인터페이스에 구체 관계가 있는 첫 적격 원문을 택했다. 양쪽 결과를 보고 다음 경로 질의를 고치지 않았고 질문별 선행 경로를 교대했다. 이 고정 규칙은 선택의 사후 편집을 막지만, 여러 차례 질의를 조정하는 실제 일반 사용자의 성능을 대표하지는 않는다.

원 반환의 링크 단위 오류는 별도 한계다. Q01-G, Q02-R, Q04-G/R, Q06-R, Q07-G, Q10-R, Q12-R에서 세 후보의 근거 묶음이 세 고유 URL을 초과했다. `returns-raw.jsonl`은 원 결과를 보존한다. `returns.jsonl`은 원래 순위·인용 순서에서 세 URL만 남겼다. 새 근거·새 순위는 넣지 않았다. 72개 슬롯은 그대로지만 비빈 슬롯은 69개에서 62개로 줄었다. 주 지표 0:0은 유지됐으나, 이는 예산 오류가 중요하지 않다는 증거가 아니라 이 데이터에서 분자가 이미 0이었다는 사실이다.

## Q4. 어떤 사용 제안이 근거를 갖췄는가

가린 합집합은 93개 후보 키다. 원 반환 72슬롯은 비빈 69슬롯/고유 후보 66개이며, 읽었지만 반환하지 않은 후보 27개도 판독에 포함했다. 서로 다른 경로가 같은 후보에 다른 절을 붙이거나 사후 세 URL판에서 절이 잘렸으므로 104개 인용 묶음을 따로 판독했다. 각 묶음의 필수 술어를 모두 대조한 결과가 337조건행이다. 후보 이름은 근거 주체를 판단하는 데 필요해 남겼고, 경로·순위·검색 순서·원 작성자의 bool을 가렸다. 이 작성자의 자기 판독과 다른 같은 모델 에이전트의 판독을 분리했다.

가림은 완전하지 않았다. 세 키의 한계 문장에 G/R이라는 단어가 남아 별도 판독자가 보고했다. 수정 커밋 후에는 제거했지만 과거 노출은 취소하지 않았다. ‘보류’, ‘반례’ 같은 해석 표현도 packet에 남아 있었다. 별도 판독은 검산과 반론이지 독립 인간 표본이나 이중맹검 실험이 아니다. 원 자기 판독은 2충족·11충돌·56보류·3빈, 교차 판독은 2충족·14충돌·53보류·3빈으로 달랐다. 공통된 충족 두 건만 강조하고 나머지를 자동 정답으로 만들지 않았다.

각 필수 술어에는 주체·시점·판·제안 사용 경계를 붙였다. 공급자 문서가 보장하는 동작, 질문자가 실제로 택했다고 기록한 것, 연구자가 조합하면 가능하다고 제안한 것은 서로 다른 열이다. 후속 채택이 공급자 조건을 대신 증명하지 않으며, 공급자 문서의 가능성이 질문자의 실제 도입을 증명하지도 않는다. `opened_complete`는 필요한 근거를 모두 직접 열었는가, `cited_complete`는 최초 반환 인용만으로 그 근거 전체를 독자가 확인할 수 있는가다. 나중 감사에서 연 코드가 원 반환의 누락을 소급해서 메우지는 않는다.

이 차이를 먼저 고정 의존 021에서 재검산했다. 공식 `replay.py`의 판정은 필수 묶음을 모두 연 뒤 인용과의 교집합이 비지 않았는지 확인했다. Q11c에 필요한 두 구간 중 하나만 답에 인용해도 통과할 수 있었다. 전체 필수 인용을 요구하면 2절의 주소/위치/조건 대응은 6/23·9/23·14/23에서 **6/23·9/23·13/23**으로 바뀌고, 4절은 6/23·14/23·15/23에서 **6/23·13/23·14/23**으로 바뀐다. 실제 바뀐 행은 Q11c이며 대체 허용 묶음도 검산했다. 명령과 고정 SHA는 `baseline-audit.md`와 `tools/audit_baseline.py`에 있다.

이번 실행에서도 표면상 유용하지만 조건 하나가 다른 후보를 보존했다.

- Q01의 Hardwood는 Parquet 읽기라는 목적은 맞지만 Arrow 상호운용을 roadmap에 두었다. qio의 64비트 정수 값은 64비트 offset이 아니고 중첩 형 생략도 있다. 같은 ‘64-bit’가 다른 데이터 경계다. [AR-C004] [AR-C008]
- Q02의 `AsArray`는 downcast를 편하게 할 뿐 호출자 타입 분기 없이 공통 값을 돌려주는 API가 아니다. Bevy reflection은 객체/구조/리스트 관계를 설명하지만 Arrow 배열 어댑터까지 제공한다고 읽지 않았다. [AR-C012] [AR-C013] [AR-C017]
- Q03의 `BatchOf`/`GenerateBatch`는 표 생성에 도움을 주지만 ORC 변환 결과를 독립적으로 재귀 검증하는 기대값 oracle 전체를 증명하지 않는다. 완성된 생성기 한 부품이 전체 검증 설계의 대안은 아니다. [AR-C020]
- Q04의 narrow는 동적 형을 비목표로 선언했다. minarrow의 typed 배열·FFI 설명은 일부 조건을 지원하지만 전체 중첩·공개 안전성 계약은 미확인이다. 사후 세 URL판에서 minarrow README가 잘리면 Q04-M3가 ‘열었음/인용 못함’으로 바뀐다. 이는 **제한판이 새로 만든 공백**이며 원 반환의 Q11c형 인용 누락으로 잘못 보고하지 않는다. [AR-C034] [AR-C035] [AR-C036]
- Q06의 `BUILD_PATH_PREFIX_MAP`은 생산자·소비자·우선순위를 명시하지만 오른쪽 추가/오른쪽 우선 규칙이 자동 remap과 사용자 remap의 의도된 우선순위를 뒤집을 수 있다. draft라는 지위만으로 탈락시킨 것이 아니라 충돌하는 호출 규칙을 읽었다. [CG-C017]
- Q09의 WebSub 202 응답은 비동기 검증의 수락일 수 있다. OGC는 매칭 시작과 응답의 순서를 규정하지만 신뢰성 있는 전달을 범위 밖으로 둔다. 게시자가 구독을 안다는 것, 수신 경로가 준비됐다는 것, 그 뒤 실행한다는 것의 주체가 다르다. [JP-C006] [JP-C007]
- Q10의 Node `listen(0)`와 IPC는 프로세스가 실제 포트를 확보한 뒤 부모에게 보내는 부품으로 적합한 단서를 준다. 다중 채널 식별과 늦게 합류한 클라이언트의 연결 기록은 별도 증거가 필요해 전체 대안으로는 보류했다. [JP-C010] [JP-C011]
- Q12의 NVIDIA Kernel Creator는 조합별 `kernel.json`을 만드는 경로라 ‘조합마다 명세를 늘리지 않음’과 충돌한다. CTX의 schema·치환·실행 문서는 더 가깝지만 사용자에게 입력을 요청하고 허용값을 검증하는 전체 경계가 원 인용에서 완결되지 않았다. [JP-C035] [JP-C032]

구조적 대응이 옳아도 도입 비용은 남는다. Q02에 Bevy reflection을 붙이려면 Arrow 형과 reflection 값 사이의 어댑터가 필요하고, Q09에 broker·durable topic을 도입하면 기존 커널의 소켓 경계보다 훨씬 큰 변경이 될 수 있다. 이는 이번 연구자의 통합 부담 추론이다. 공급자의 성능 주장이나 실제 소요 인시 관측으로 쓰지 않는다.

## Q5. 출처 분야를 가려도 남는 관계와 깨지는 관계

후보 목록과 판정을 먼저 고정한 뒤 원거리 후보 다섯 건에서 출처 이름·분야·경로를 제거한 관계 설명을 별도 판독했다. 최소 두 관계를 연결하되, 관계가 원래 목적의 모든 조건을 보장하는지도 따로 물었다. `relation-check/` 입력과 두 판독 JSON에 원문 위치를 되돌리는 매핑이 있다. 출처를 숨겼다는 것은 원 분야에 관한 일반 사전지식까지 제거했다는 뜻이 아니다.

REL01의 다중 버전 TGG는 처리되지 않은 입력 상태를 다루고 변환 뒤 처리 상태를 바꾼다. REL02는 source–target trace와 단조적 목표 생성을 연결한다. 이 두 관계는 이름이 없어도 유지됐다. 그러나 버전별 규칙의 우선순위, 새 출력이 다른 규칙의 입력이 되지 않는 경계, resolver의 의존 closure는 다른 조건이다. 특히 생성된 target을 문맥으로 다시 쓰는 변환은 Q08의 출력 재입력 금지와 충돌할 수 있다. REL03의 합집합 idempotence도 `a→b`, `b→c`라는 규칙 연쇄를 막지 않는다. 관계 유사성은 반복을 멈추는 운용 의미를 대신하지 못했다. [CG-C029] [CG-C030] [CG-C031]

REL04의 Bevy는 공통 reflection interface와 범주별 탐색을 연결하지만, 이 대응만으로 Arrow의 인덱스별 이질 값을 같은 반환 타입으로 제공하지는 않는다. REL05의 qio는 64비트라는 숫자와 읽기라는 단어가 맞아도 값 폭과 offset 폭이 달라 반증이 됐다. 이들은 각각 구조의 부분 대응과 단어만 맞는 경우를 분리하는 데 사용했다. 원거리 후보가 없었던 질문도 결과이며, 질문·경로별 분류 수는 `evidence/report-facts.json`의 `raw_distant_by_question_route`에 있다. 원거리 신규 완결 적중은 0건이다. 원 반환의 distant_principle 분류에서는 Q02-G에1후보, Q08-R에2후보가 있고 나머지10질문에는0후보다. 이 분류는 제품의 분야 이름보다 제안한 동작의 관계 경계를 기준으로 하며, 별도 익명 반증에 넣은 이미 알려진 원리나 미반환 후보를 적중 수에 더하지 않는다.

### 봉인 뒤에만 읽은 도서관 운영 원문

LC MARC21 Authority의 Tracings 절에서 4XX는 비채택 이름에서 채택 표목으로, 5XX는 관련 채택 표목 사이로 연결되는 관계를 읽었다. 링크의 방향과 관계 종류가 이름 일치보다 중요하다. NACO 2020 매뉴얼 p98–99는 참고형 변경·구별과 새 670 출처를 추가하면서 이전 출처를 보존하는 운영을 설명한다. 같은 문서의 정체성을 합치는 관계와 서로 다른 대상을 관련시키는 관계를 분리하고, 새 근거를 추가하되 옛 관측을 남기는 방법으로 후보/출처 원장에 대응시킬 수 있다. [SP-L01] [SP-L02]

이 대응은 도서관의 전거 판단이 소프트웨어의 기능 동등성을 보장한다는 뜻이 아니다. MARC 4XX/5XX가 다른 관계이듯 같은 저장소 이름을 공유하는 `Array` 재수출과 `ScalarValue` 기능을 하나로 합쳐서는 안 된다. 두 문서는 같은 LC 운영 계보이므로 두 독립 효과 실험으로 세지 않았다. IFLA GARR2001 원문은 공개 이전 URL과 공식 목록을 추적했으나 원 PDF를 읽지 못했다. 공식 resource 전환 페이지도 rewritten summary여서 산입에서 제외했다. NACO는 실제 참조 유지 운영을 대체하지만 GARR 전체의 기원 서술을 대체하지 않는다. 이 실패와 대체 한계는 SP-X01–03에 남겼다.

### 봉인 뒤에만 읽은 제조 운영·연구 원문

Sugimori 등의 1977년 Toyota 원문 pp555–556, §3.2 pp560–562에서 하류 인출, 용기/카드, 보충 생산과 카드 수 제한의 관계를 읽었다. Spearman·Woodruff·Hopp의 1990년 CONWIP §4.1–4.2 pp883–884는 작업 투입에 카드가 필요하고 완료 때 카드가 돌아오며 backlog가 다음 작업을 정하는 관계를 설명한다. 입장 허가 수와 어떤 일을 고르는 순서를 분리할 수 있다는 대응은 출처 분야 이름을 빼도 남는다. [SP-M01] [SP-M02]

그 원문은 번역이 깨지는 조건도 제공한다. CONWIP 설명은 용기별 병목 작업량이 대략 비슷하다는 전제를 두고, 다중 라인 조정이 필요함과 simulation 일반화의 한계를 적었다. 연구 원문 열람은 길이·난도·재시도·여러 질문의 공유 정도가 크게 다르므로 ‘동시 원문 다섯 개’가 같은 비용이라는 보장은 없다. 또한 투입 중인 작업 수를 제한해도 두 작업이 같은 미예약 포트를 고르는 경쟁은 남는다. WIP 원리를 Q10의 포트 소유권 해결로 옮기면 주체와 불변식이 틀린다. 이는 타 분야 원리가 항상 유용하다는 첫 결론에 대한 구체 반례다.

이 네 원문은 주 판정 원격 봉인 `d1f506b1...` 재독 후에만 열었다. G/R 목록에는 새 후보를 하나도 추가하지 않았다. 보조 연구의 제조·도서관 이름을 원 검색이 찾아낸 분야로 소급하지 않는다. `supplements/receipts/`와 `supplements/README.md`가 순서·정확한 절·실패를 보존한다.

## Q6. 후속 결정과 당시 이용 가능성을 대조한 결과

후속 자료는 주 반환과 가린 판정이 원격에서 읽히는 것을 확인한 뒤 열었다. 12질문의 후속 기록과 원 반환 합집합 후보 66개의 역사 행을 만들었다. 당시판 분류의 전체 집계는 **{{HISTORY_COUNTS}}**다. `supported`를 사용하려면 원래 제안 사용의 전체 필수 조건이 그 날짜에 성립해야 한다. 프로젝트가 오래됐다는 사실, 제품 버전 이름, 최근 개정 문서의 오래된 copyright만으로 당시 기능을 확정하지 않는다. 부분 기능은 `feature_evidence`에 따로 남긴다.

유일한 역사 `supported`는 CG-K011의 **자동 defaults 다음 사용자 maps를 주는 조건의 GCC10.3 compiler filename mapping 부품**이다. Rust/Cargo의 무수정 대안이나 사용자 우선순위를 자동으로 보장하는 전체 시스템이 아니다. 뒤늦은 공식 코드·테스트 감사는 이 역사 경계를 지원하지만 원 반환의 M4 인용 부족을 고치지 않으므로 당시 신규 완결 분자는 여전히 0이다. OGC의 역사 `supported` 초안은 Subscriber와 Receiver를 구별한 반례 뒤 unknown으로 정정했고, matching 규칙의 당시 존재만 partial_supported로 남겼다. `followups/jupyter/amendments/JP-AMEND-001.json`은 처음 판단이 틀린 경우를 찾아 바꾼 기록이다.

Q01에서는 2021년 질문자가 2.0.0과 master의 schema override 실패를 재현했고 유지관리자는 일반 read-type override 부재와 Dataset schema 제약을 설명했다. 현재 반환에 쓴 Python `binary_type`/`list_type`은 20.0.0에는 없고 21.0.0에 있으며, 공식 21.0.0 발표일은 2025-07-17이다. Java 큰 버퍼의 일부 경계는 2020년부터 존재했지만 이것이 2025년 Python 옵션을 2021년 기능으로 만들지는 않는다. `ArrowBuf`의 long 크기와 `nioBuffer()`의 int 제약도 분리했다. 이 후보의 현재 조건부 구성은 문서로 제안 가능하지만 큰 파일의 실제 Python→Java 통합 실행은 미실시다. [AR-H003] [AR-H004] [AR-H022] [AR-H023] [AR-H050]

Q02의 후속 메일은 당대 부품과 실제 질문자 선택의 드문 직접 대응이다. 유지관리자가 2021-01-02 고정 코드의 DataFusion `ScalarValue`를 2021-01-28 제시했고 질문자는 필요한 enum이라고 답했다. 이 코드의 `try_from_array`는 Boolean/Utf8/List 등을 처리하고 지원하지 않는 형에는 오류를 낸다. 그러므로 모든 Arrow 형의 만능 해법이라고 확장하지 않는다. 이번 검색은 그 동작을 반환하지 못했으며 후속 발견으로 분자를 올리지 않았다. 질문자가 실제 적용·배포한 diff도 찾지 못했다. 같은 이름의 quiver는 더 조심해야 한다. 2018년 crate의 간단한 placeholder와 2026년 TypedArray 구현이 같은 기능 계보라는 증거는 없다. `followups/arrow/FINDINGS.md`와 Q02의 역사 행이 이 구분을 기록한다.

## Q7. 같은 상한에서 남는 가치와 반대 결과

질문 단위 주 지표는 원 반환·사후 세 URL판, 전체 설계 여섯 건·부분 여섯 건, 상위 세 후보·상위 한 후보 모두 신규 완결 0:0이다. 원제안/가능 후속 노출 제외 후 여섯 질문과 메타데이터까지 제외한 네 질문도 같다. 이 결과는 제한된 목적 표본의 관측이며, 빈약한 근거를 엄격하게 보류한 영향과 검색 자체의 실패를 분리해 보아야 한다. 원 반환의 53개 보류는 대부분 적어도 한 필수 조건이 덜 증명된 경우라, 53개 모두 틀린 제품이라는 의미가 아니다.

양쪽 공통 후보와 경로 독점은 유효성 판정 전에 별도로 계산했다. 원 반환의 공통은 Q02의 AsArray, Q03의 BatchOf/GenerateBatch, Q09의 Azure pub/sub 패턴 세 후보다. 공통이라고 더 적합한 것도 아니고, R에만 나왔다고 새롭게 유용한 것도 아니다. 조건 전체가 완결된 **신규** 공통/독점은 모두 0이다. 현재 완결 새 부품은 G에만 두 건이며 원 인용 묶음과 당시판을 함께 보여 준다.

개선이 없거나 G가 나은 경우를 찾는 경로도 실제 원장을 사용했다. 첫째, Q01에서 R의 ‘64bit/large’ 연결을 값 폭·배열 offset·Java import의 주체로 나누어 검사하자 qio와 Iceberg 읽기의 부족이 드러났고, G의 현재 PyArrow 구성만 조건부 완결이었다. 둘째, Q11에서 R의 extension/metadata 일치를 수신 실행 주체의 입력으로 좁혀 검사하자 trace 기록·REST params는 같은 동작이 아니었고 G만 정확한 현재 어댑터 코드로 이어졌다. 이 둘은 **새 부품 보조 지표에서의 G 우세**이며, 새 대상 주 지표의 G 승으로 바꾸지 않는다. 셋째, Q09와 Q12에서 R의 관계 대응이 더 풍부해 보이는 첫 인상을 readiness 주체·전체 실행 수명주기 조건으로 반박했고, 완결 신규 성공이 없음을 유지했다.

조회·열람의 계측 가능한 비용은 표 3과 `evidence/discovery-summary.json`에 있다. 검색 도구 요청 시간 합은 74.069초, 원문 최초/재시도/절 추가 합은 63.841초다. 병렬 요청이 겹치므로 이는 프로젝트 경과시간이나 사람이 절약한 노동시간이 아니다. 가린 판독의 재열람, 후속 결정·태그 확인, 도서관/제조 보조 원문은 추가 비용으로 분리했다. 도구가 제공하지 않은 토큰, 청구 금액, 모델 사고 연산, 실제 사람 시간은 숫자로 추정하지 않았다. `evidence/cost-summary.json`은 단계별 단위를 그대로 보존한다.

제품에 대한 조건부 제안은 다음과 같다. 설계 전문에서 목적·부분 관계를 추출하는 기능은 **후보를 더 많이 나열한다는 약속보다 후보의 호출 경계와 빠진 근거를 드러내는 데** 먼저 적용할 만하다. 다만 이것은 제품 방향 제안이며 효과가 입증된 결정은 아니다. 주 지표의 0:0을 이유로 관계 검색을 버릴 근거도 없고, 원거리 자료가 나왔다는 이유로 기본 검색보다 낫다고 판매할 근거도 없다. 사용자는 새 제품명, 같은 호스트의 놓친 부품, 이미 아는 부품의 새 제약을 서로 다른 반환 가치로 보아야 한다. 실제 사용자에게 어느 가치가 새롭고 채택 비용을 줄이는지는 다음 관측이다.

## 재현·근거 규모·남은 실행

`sources.json`에는 **{{SOURCE_OBSERVATIONS}}개 관측 행, 보수적인 최소수 산입 기준으로 직접 읽은 고유 외부 원문 {{COUNTED_ORIGINALS}}건**이 있다. 최초 설계 12건과 공급자/후속 원문, 도서관 두 건·제조 두 건을 포함한다. 같은 원문 여러 절·미러·후속 판은 하나로 묶고, 검색 요약·차단·내부 보고는 최소수 밖에 남겼다. 같은 계보의 별도 문서까지 보수적으로 제외한 경우도 있어 전수 고유 문서의 정확한 개수보다는 하한 집계다. 예컨대 JP-F014 후속 댓글은 JP-I03 최초 초안의 복제가 아니며 같은 설계 사건이라 추가 산입을 보류한 별도 문서다. `original_document_id`와 `minimum_count_group_id`, 관계 설명을 분리했다. 이 문서 수를 독립 실험 사건 수로 바꾸지 않는다. 실험의 독립 질문 사건은 여전히 12건이며, 같은 질문의 여러 후보·근거는 상관돼 있다. 단계별 원문 수와 합치는 규칙은 `evidence/source-counts.json`, `tools/assemble_sources.py`, `evidence/source-eligibility-overrides.json`을 참조한다.

재집계는 `SELF_CHECK.md`에 나열한 순서대로 실행한다. 원 입력·원 반환·가린 판정은 봉인 해시로 검사하고, 후속 열과 산술 표시만 재생성한다. 현재 웹을 다시 검색하면 결과가 달라질 수 있으므로 그것은 새 실행으로 기록해야 한다.
