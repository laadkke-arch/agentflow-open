## 판정
**PARTIAL.** 네 설치 자리와 목적에 따른 분기는 정적 control·코드·계약으로 비교했다. 직접 읽은 산입 원자료 33 (A6/B12/C8/D3/E4), 그 중 C8은 편의 대조로만 사용하므로 엄격 모집 조건을 충족한 C는 0 확인. 보수적 엄격 분모 25 (A6/B12/D3/E4; C0), C의 요구 4건 부족, 프로젝트별 예정 자리 8개 미확정. 원장 총 46행, 비산입 13 (접근 실패/불완전 5, 보조 대조 8), 직접 읽은 행 41; 동일 Debian Policy의 절과 binary index/구판 매뉴얼은 보조 대조로 두었다. 소프트웨어/기관 계보 8 (policy, bsd-mailx, cron, exim4, nullmailer, USF-ILL, UDel-ILL, USPS). 동일 사건 댓글/merged 번호 중복 계산 없음. 실제 사건 8건, 정확판 동일 입력 실행/사용자의 최종 원격 수신 관측 없음. 185의 자연 AND 부족을 이번 질문에서 억지로 메우지 않는다.

### Q1 — 누구의 택일인가
[A01 Debian Policy §7](https://www.debian.org/doc/debian-policy/ch-relationships.html)는 comma와 pipe를 구분하고 Depends의 절대성, Recommends의 강한 권고를 구분한다. A02–A05 source control 원문과 P01–P04 binary index를 대조했다. Exim light는 virtual mail-transport-agent를 명시하며 default-mta 공급자로 package index에 표시된다. nullmailer는 후자만으로 OR를 충족할 수 있다. 실제 apt 기본 선택은 기존 설치·preferences 등에 의존하며 실행하지 않았다. bsd-mailx는 Provides mail-reader, mailx; cron은 Provides cron-daemon, Conflicts/Replaces systemd-cron,bcron,cronie; 두 소비자 자체의 Conflicts와 MTA 충돌을 섞지 않는다. cron MTA는 권고이며 Pre-Depends cron-daemon-common 등 필수는 별도. A06 bsd changelog 상단 1.1/2022 entry는 MTA 관계 변경 근거 아님. 배포 page u5 vs index u4 cache 시차, Exim manual 4.98.2-1 cache를 구판 대조로 남김.

### Q2 — 호출 계약과 생략 조건
mailx send branch는 B02에서 recipient 헤더와 stdin을 구성하고 sendmail path를 설정값 또는 B03 기본값으로 선택한다. 일반 argv -i -t, 조건에 따른 -f/-m/-v; DEBIAN 경로는 child 종료를 확인하고 오류는 deadletter 저장으로 이어진다. mailx의 -f (읽을 파일)와 sendmail -f (envelope sender) 별개. -E empty-body 생략(B01), 읽기 경로 자체는 SMTP 송신이 아니다. 로컬 파일·pipe recipient branch는 별도. cron은 B05의 0 bytes/empty MAILTO/unsafe/no MTA early return, 출력 임시 파일 후 실행 완료를 기다려 mail command 작성, To/From/Subject 구성, cron_pclose status 로그. 작업 실패와 메일 실패는 각각 기록. B06 _PATH_SENDMAIL은 system definition 여부에 따라 /usr/lib/sendmail fallback; A07 표준 /usr/sbin/sendmail. [P05 Exim filelist](https://packages.debian.org/trixie/amd64/exim4-daemon-light/filelist)과 [P06 nullmailer filelist](https://packages.debian.org/trixie/amd64/nullmailer/filelist)에 두 경로 모두 있음. 이로써 source fallback 차이가 곧 파일 없음이라는 가설은 기각. compiled binary 실제 경로는 미확인. nullmailer B11/D01에서 옵션이 parse된다고 동일 의미는 아님: -i/-B/-o/-v 무시, -F 이름, -f envelope, -t header recipients. [B13 Exim 구판 man](https://manpages.debian.org/trixie/exim4-daemon-light/sendmail.8.en.html)은 -i의 dot 처리 의미와 -B ignored를 명시; 정확 u5 실행으로 확대 금지.

### Q3 — 어느 목적을 맡는가
Exim B07/B08: internet/relay/local 중 mode에 따라 다름. smarthost 모드가 local delivery도 할 수 있으나 satellite는 로컬 없음; local-only는 remote 거절. local mailbox format 기본 mail_spool이고 maildir_home 대안은 mailx mbox 목적과 같지 않다. nullmailer A05/B09–12/D01–03: sendmail emulator → inject → outgoing queue → send worker → configured remote. queue exit 0은 큐 기록 성공이며 수신 보증 아님. 정적 D02는 tmp/queue hardlink·sync, B12는 same filesystem 요구; D03은 temp failure retention, expiry/permanent bounce, success unlink. adminaddr는 local-address recipients를 지정 주소로 remap, 현판 allmailfrom은 envelope sender override. Header From 수정과 구분하며 C08에서 구판 요청을 최신 기능 부재로 해석하지 않는다. Exim도 큐/설정/경로가 실제 결과를 결정(C05,C06); 동일 인터페이스가 동일 endpoint나 동일 옵션 의미를 보증하지 않는다.

### Q4 — 누가 실제로 무엇을 봤나
C01·C02 사용자 자신의 local read/display 관측 및 경쟁 설명; C06 routing/delivery 보고에서 next-stage final receipt/read 결측. C03/C08은 요청; C07 구성 결과; C04/C05 failure reports. 유지자의 제안/bug fixed는 관측 단계가 아니다. 특히 C06에서는 hostname-qualified와 localhost가 다르게 처리되어 같은 공급자의 동일 이름만으로 결과 예측 불가. 모든 C는 2025-12-31 전 접수, 구판 그대로 보존. 다만 archive=both complete list 접근 실패로 number-ascending first-two의 확인을 못 했으므로 선택 편향 통제 미달. 각 프로젝트 최대 두 편의 대조, 원문 결과가 없는 C03/C07/C08도 남김. 사건 결과를 표집 근거로 쓰지 않았다는 엄격 검증은 후속 프레임이 있어야 가능하다.

### Q5 — 단독과 공동 설치
[A07 §11.6](https://www.debian.org/doc/debian-policy/ch-customized-programs.html#mail-transport-delivery-and-user-agents)에서 MTA는 동일 Provides/Conflicts/Replaces mail-transport-agent 요구. A04/A05 실제 stanza가 그와 일치하며 A01 §7.5와 결합하면 통상의 dpkg/apt 관리 하 두 MTA 동시 정상 설치 불가. 둘 다 같은 sendmail 경로를 제공(P05/P06); 한 package의 다른 파일 경로 또는 wrapper override는 설치 충돌 해결이 아님. 외부 relay를 별도 호스트/서비스로 쓰는 설계는 가능하지만 별개 실행 파일·프로토콜·권한·호스트 구성 필요, 같은 로컬 dpkg 두 후보 합치기와 구별. cron + no MTA는 강한 반례: job 실행 가능하나 출력 있는 경우 폐기 가능. 이미 bsd-mailx를 설치한다면 별도 Depends가 남는다. 읽기-only 기존 mbox는 MTA 배달 기능 없이도 파일 읽기 목적을 충족할 수 있는 대조; 패키지 설치 관계는 여전히 필수.

### Q6 — 다른 분야 원리의 실질적 대조
- [E01 USF ILL FAQ](https://lib.usf.edu/ill/faq/) status L200–208: request received(접수)→potential lender 요청(외부 전달)→received/held/notified(기관 보유/알림)→checked out(이용자 보유). 같은 창구 ILLiad로 접수해도 loan 인도와 다름.
- [E02 Delaware ILL help](https://library.udel.edu/interlibraryloan/askill/help/) L590–603: unfilled 상태와 notified/checked out를 분리; Finished는 fulfilled 또는 cancelled로 의미가 겹친다. 이름이 종료라고 목적 성립으로 처리하면 오판.
- [E03 USPS Where is my package](https://faq.usps.com/articles/FAQ/Where-is-my-package) L24–34,41–42: shipping partner pick-up은 USPS possession이 아님. delivered scan이 있어도 사람이 물건을 찾지 못할 수 있고 이후 service request 경로가 있다.
- [E04 USPS Tracking](https://faq.usps.com/articles/FAQ/USPS-Tracking-The-Basics) L33–38: electronic label과 possession 분리, 예상 시간창은 보증 아님.
- 공통 단계 ID 제안: I=설치/서비스 이용자격, S=접수, Q=보유/대기, H=다음 기관 인계, D=목적지 배달, R=최종 주체가 읽음/수령, X=무효/실패/취소. 각 기관 정의를 원문에 연결하고 동일 stage label이라도 actor와 evidence를 유지. 도서관/USPS는 실제 기관 운영 조건 자료이며 개별 사건 기록은 아님; 메일 대조의 근거 강도를 올려주지 않는다.

### Q7 — 한 질문과 경쟁 설명
표 3의 동일 질문 하나로 목적지를 먼저 가른다. 요구가 단지 compatible sendmail endpoint에서 접수라면 두 MTA가 문서상 조건부 공통 충분성을 가진다; 실제 acceptance나 최종 수신은 주장하지 않는다. local notification은 새 배달과 기존 파일 읽기를 구분. remote relay라면 두 후보를 모두 링크하되 OR 선택이 성립하는 모드/relay 전제 및 한 쪽만 설치하라는 충돌 조건을 붙인다. no-mail cron이면 불필요한 링크를 줄이고 MAILTO/출력 처리 원문만 남긴다. 사용자 발화가 endpoint를 말하지 않으면 보류 질문이 잘못된 강한 추천보다 비용이 낮다.

## 재사용 조건과 비용
추천의 단위는 패키지 이름이 아니라 (소비자 판·operation/argv, 설치 관계의 주체와 강도, provider 판·config, 목적 endpoint/format, stage evidence·actor)로 구분하는 비교 원리다. 저장소 설계나 검색 순위 강제 아님. 링크 하나에 모든 단계가 담겨 있지 않으면 후보 링크와 mode/호출/receipt 근거를 따로 제공; 필요 조건의 AND는 링크 수가 아니라 동시에 만족할 제약이다. 반대로 두 공급자가 OR라도 실제 runtime 의미가 달라 질의 목적에 따라 한쪽을 배제할 수 있다. 비용: 사용자 질문 1회와 mode/format 문서 읽기 추가, 대신 잘못된 설치·출력 유실·설정 재작업 위험 감소. No mail은 다른 관측/log 요구 확인 비용; 큐 접수까지만 목표일 경우 최종 receipt 확인 비용은 사용자 요구 밖으로 명시. 단계 결측은 실패로 치환하지 않는다. 새 빌드·메일 실행·발송은 범위 밖.
