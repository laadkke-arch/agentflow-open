## Q1 — 요구자 조건과 실제 문구

R01–R15 참조. ZIP 제작자는 feature 단위/API의 유연성을, 소비자 Chromium 도입자는 dependency footprint를, WASM 배포자는 target 헤더/컴파일 가능성을 우선하는 서로 다른 문제다. C01 pure Rust 요청은 명시적이지만 PNG 없음. C02는 C toolchain 부재가 아니라 target의 stdlib.h 실패(호스트 clang 존재). C04 OR(두 compressor 중 하나로 충분)와 D04 실제 두 라이브러리 root AND는 별개의 층. C09 safe code 요구는 유지자의 보고이지 공동 요구자의 직접 조건이 아니다. C03 native 허용은 정상 대조. gzip 대안은 탐색한 원 이슈에서 직접 요구 문구를 확보하지 못하여 R11 설계 입력으로만 둔다. gzip/zlib/raw DEFLATE는 컨테이너 호환을 보장하지 않음. 요청 형식 AND/OR, native implementation, native build, unsafe, preference 각각 별도 축.

## Q2 — 네 판의 선언과 배포 원본

B01–B04 및 X01–X08/X17. 마지막 안정판은 출판 날짜 기준으로 고정했다(선택은 완전 blind 아님). png 0.17.10/0.18.0에는 모두 normal required flate2; 직접 fdeflate/miniz_oxide도 사용한다. zip 0.6.6/7.0.0에는 optional normal flate2: 기본값 false지만 zip 자체 default 켜면 deflate 경로를 활성화한다. 2023 deflate는 rust_backend, 2025 deflate는 zlib-rs와 zopfli(별도 압축 구현). zip 7 neutral deflate-flate2가 flate2를 활성화하되 backend는 고르지 않음. zip 0.6.6 stored-only, zip 7 stored-only 또는 zopfli-only에서 flate2 간선 부재가 가능(선언은 존재하며 actual activation은 별개). PNG의 어떤 모드가 flate2를 호출하는지는 encoder/decoder 모드 단위로 분리. PNG old/new tag를 각각 직접 읽었거나 publish SHA로 대체; ZIP 이관 README X07. target-specific dev/host/fuzzing 등은 flate2 normal 간선과 다르게 기록. 발행 orig 2/4, 두 old orig 접근 실패; tag 단독으로 배포 패키지 byte 동치 가정 안 함.

## Q3 — 정확한 합집합 범위

A01/A02: feature는 package identity와 활성 compile unit 안에서 합쳐진다. 동일 name만으로 합산 금지: version/source 다르면 분리, resolver2의 normal vs build/proc macro 및 inactive target/dev 예외, edition/워크스페이스 root의 resolver를 따름. Lockfile은 전체 해석 결과가 될 수 있어 target 활성과 다르다. D03/D04 동일 root는 Chromium edition2021의 Cargo default resolver2를 추론하되 GN 실제 toolchain 단위는 보류. root normal png/zip와 동일 registry flate2=1.1.1 lock은 **실제**; 다른 D01 1.1.5는 한 개발선의 후속 스냅샷이지 같은 build가 아니다. Chromium iOS import commit에서 GN ZIP deps/feature patch까지 확인. PNG GN 및 flate2 GN, 실제 action의 target 확인 실패. Cargo tree만으로 GN 실행을 대체하지 않는다.

## Q4 — 선택 vs 존재 vs 실제 호출

A03/A04, A05/A06, A08/A09, A10: 1.0.28 및 1.1.1 및 1.1.5의 cfg는 any_zlib면 c wrapper, 아니고 miniz_oxide면 rust wrapper. 1.1.5 c_backend alias는 zlib-ng > zlib-rs > cloudflare_zlib > libz_sys. **c라는 모듈명만 보고 C 압축 구현이라고 하면 틀림**. libz-rs-sys v0.5.1 manifest와 Rust source A11/A12가 zlib_rs를 호출하고 rust allocator 전달을 확인한다. flate2 1.1.5 기본 rust_backend와 zlib-rs가 모두 켜져 있어도 실제 wrapper는 하나를 고른다; 두 구현이 모두 호출된다고 해석 금지. 별도 fdeflate/miniz direct, ZIP zopfli path는 같은 flate2 wrapper 밖. PNG 0.18 encoder의 Level은 flate2, FdeflateUltraFast와 non-stream stored-only는 fdeflate; stream branch 별도. ZIP 7 reader의 cfg deflate-flate2 확인. 다른 C 경로가 비선택이어도 Cargo optional dependency가 활성되어 build/link 준비를 할 수 있음. A12 동시 rust-allocator/c-allocator는 compile_error라는 고정 소스 반례; 실제 두 소비자만으로 c-allocator가 요청되었다는 뜻은 아님. 고정판과 실제 invocation은 분리.

## Q5 — evidence ladder 및 중간 판정

선언 → lock identity → resolved target graph → compiler feature flags/build scripts → 링크 artifact → 양쪽 runtime I/O + 사용자 요구 확인 순서. D02–D04는 처음 두 단계+GN ZIP 정적 config; commit-queue 서명은 특정 target build의 통과 로그가 아니다. C04 정확판 ZIP 2.6.1의 E0433 및 수정 git source의 build 보고는 원 이슈 안의 독립 작성자 확인과 수정 비교이나 공동 성공 아님. C05 zopfli-only 실패, C06 2.1.6 좁은 feature 실패, C02 WASM failure/회피책 역시 단독. G12/G15는 두 명시 경로를 고정하면 native backend가 선택된다는 조건부 source 반증이지 관측된 공동 실패는 아니다. Cargo check/빌드 성공/런타임 검증/압축 경로 native 부재/전체 그래프 native 부재를 서로 독립 상태로 유지. 후속 검사 고정 입력과 명령은 HANDOFF; 여기서는 실행하지 않았다. 

## Q6 — 다른 분야의 실재 규칙, 실재 사례, 차이

- NARA E01: 영구 digitized paper/photographic print 기록의 TIFF6와 PNG1.2는 각각 허용 형식이지만 PNG는 Deflate, TIFF는 지정 codec 조건; PDF/A도 허용되나 특정 attachment 사용 금지. TIFF 여러 장을 JPEG2000 PDF/A로 합치는 경우 결과물 품질검사 조건(§1236.46(d))이 추가된다. E02: 같은 transfer request number 및 각 file의 7 metadata 필드, 논리 기록을 여러 파일이 구성할 때 Relation, machine-readable pipe-delimited CSV index. E03: transfer request field discrepancy면 재제출이 필요한 반려 가능. E08: 분리 우선, 완전한 case file 보존에는 혼합 예외, 같은 transfer 전체 제한 등급은 구성원 중 최고 수준. 따라서 각각 허용된 두 포맷은 OR 선택지일 수 있고 함께 납품해야 할 index/relation은 AND; 규칙에 의한 조합 반려 가능성과 실재 반려는 다른 층.
- E09 NARA archivist 실제 AAD 처리/이용: punch card image 해석 raw 파일 1374→12→merged 9,200,232 records(160,390 unreadable 표시 포함), 코드북을 이용하고 원시 파일 유지; 코드값/의미를 함께 제공하는 CSV와 검색(첫해 700,000회 이상 검색 보고). 변환된 자료와 해석 metadata를 별도로 보존해야 실제 사용 가능. 이 사례는 현재 TIFF+PNG 동시 납품 acceptance/rejection이 아님.
- E04 National Rail: A–B, B–C 각각의 ticket이 판매 가능해도 실제 서비스가 B에서 정차하며 시간/열차/구간 조건이 모두 맞아야 한 여정 가능. 정차하면 반드시 내릴 필요는 없다. E05 Rail Ombudsman 2024-07-09 p.4 실재 split-ticket wrong-train 분쟁과 중재; E07 ORR §3.35/3.41 현장 직원이 split 지점에서 내려 다른 열차를 타 유효하지 않게 된 사례 유형과 진정한 실수에도 revenue protection 조치를 보고. 각각의 ticket 개별 유효 조건을 직접 판정할 원자료 없음. E06 실제 2017 fare complaint(through £210 ×2, £179 goodwill)에서 split 대안은 가정이었음. **실제 각각 개별 승인된 두 대상의 공동 제출/이용만 거부된 정확 사례는 미확인**. 문서 규칙은 결합 실패의 가능성/원리를 보여주지만 실제 원 사건을 만들어내지 않는다.
- 공통 추상화: 동일 scope(transfer ID, journey/train, root target)와 구성 조건(메타데이터/정차·시간/cfg)을 먼저 결합해 판정. 차이: 철도 시간/공간 연결, 기록 포맷/보존 정책, Cargo compile-unit resolution은 서로 다른 메커니즘이다. NARA 최고제한 규칙은 monotone restriction의 비교 예이지 Cargo priority와 동일 아님. 개별 OR의 좋은 링크는 AND 공동 보증이 아니다.

## Q7 — 답변 경계·경쟁 설명

N01–N12: 한 링크가 충분한 OR는 단독 후보, AND는 각각 필요한 작업을 연결하되 동일 graph/target 확인 후 공동 검증 링크 또는 한 질문을 추가. 엄격 금지는 추론과 실행을 구분하여 조건부 거절/보류. preference는 native 대안도 보여 주되 우열은 별도 측정. 사용자가 순수 Rust라고만 했을 때 확인해야 할 한 문장: “압축 구현만 Rust면 되는지, host/target 전체 C 빌드 의존 및 unsafe까지 금지인지?” same scope가 이미 주어졌으면 반복 질문하지 말고 가장 작은 미확인 키만 요청.

경쟁 설명 1: flate2 두 경로라면 무조건 같은 backend. G16 resolver2 분리/버전/source 반례. 2: default-features=false면 Rust 유지. A01/A10 다른 경로가 활성화하는 기본값 및 우선순위 반례. 3: c module은 C 구현. A11/A12 Rust wrapper 반례. 4: pure Rust면 safe/무툴체인. C02 다른 codec/target 헤더와 A12 unsafe/allocator 충돌 반례. 5: lock이 두 라이브러리면 공동 동작. D01/D03 lock에는 active target/runtime 없음. 6: 플러그인 두 링크는 항상 유용. R04 OR 요청 및 N01 단독 충분의 대조. 7: 관측된 단독 compile failure는 공동 실패. C04 source 차이 및 G18 공동 root만 확인이 반증.

비용 및 선택지: (i) 링크 두 개와 manifest 정적 규칙만 제공(낮은 조회 비용, 거짓 보장 위험 → 후보라고 제한), (ii) 동일 root lock/패치 근거까지 묶기(재조회 비용, target 활성 불확실), (iii) target/action/입출력 로그·native 검사까지 요구(고비용, 강한 보증; 공개 로그가 없으면 조건 질문으로 축소). 검색기 설계 후보의 비교 가능한 최소 레코드: requirement logic/scope/forbidden predicate, component capability/mode/version/source, edge kind/default/feature/target, unit identity, effective cfg predicate and backend implementation, build/run observation keys, limitation and observation date. DB, 수집기, 최종 검색 표현/추천 점수 미결정. 링크는 원 문서 버전과 최신 상태를 구분하고 동일 lineage 중복 제거; 새 release는 전체 결론 자동 승격 금지.
