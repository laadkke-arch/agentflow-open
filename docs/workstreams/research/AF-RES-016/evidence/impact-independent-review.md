# Q7 영향 분석 — 후속 내부 별도 검토

검토일: 2026-11-20 UTC. 검토자: `/root/vocabulary`, 세션 표시 모델 GPT-6 Astra Pro. 이것은 동결된 이중 코딩 이후의 **내부 별도 검토**다. 새 블라인드 코딩·사람 평가·독립 모델 검증이 아니다. 앞선 Q8와 설계 감사를 수행했던 검토자이며, 이번에는 disagreements에 수록된 두 코더 값과 이유를 읽었다. 원 A/B 파일·원응답·코딩·표본은 수정하지 않았고 커밋·push도 하지 않았다.

## 1. 검토 범위와 우선 결론

실제 입력 파일은 `sample/units.json`이다. `evidence/impact-selection.json`의 30개 ID 전부, 이에 해당하는 `evidence/disagreements.json`의 행, 그리고 지정 고정 004 SHA의 PROTOCOL.md와 EXPECTED.json을 읽었다. 선택 표본은 004 1개·011 24개·012 5개이며, S2가 같은 사례는 12/30, 다른 사례는 18/30이다. 이 수치는 역할 코딩의 차이이지 H/T 판정 변화 수가 아니다.

처음에는 입력별 오판 위험을 검토했고, 이어 root의 요청으로 `evidence/impact.json`과 `evidence/build_impact.py`의 초안 30행을 읽었다. 초안 대조 결과는 §6에 구별해 기록한다. 최종 IMPACT/RESULT 전체를 승인한 검토는 아니며, 후속 원문 I01–I03과 toy 실행을 이 검토자가 별도로 실행·검증한 것도 아니다.

결론을 바꿀 수 있는 위험은 다음과 같다.

1. **역할명 교체와 사용 단위 변경을 섞으면 안 된다.** 004 판정 단위는 문제 × 후보 × 제안 사용 × 설정 × 근거다. 같은 다섯 요소를 유지하면서 app/service, reference/comparison 같은 이름만 바꾼 결과와, 직접 실행 부품을 새 설계 참고로 바꾼 결과는 다른 비교다.
2. **prefer·unclear를 must로 승격하면 안 된다.** T011 안정성, T036 보안·총비용, T041 목록의 최신성·풍부함, T047 복잡성은 선호다. T047의 신뢰성 강도는 unclear다. T048에는 단일 디스크 증설이 필수라고 적혀 있지 않다.
3. **전체 조건을 reference라는 이유로 지우면 안 된다.** not_in_scope는 처음부터 좁은 참고로 제안한 단위에 한한다. 전체 대안이 실패하거나 정보가 부족한 뒤 이를 참고로 다시 명명해 원래 실패·미확인을 없애는 것은 004 규칙과 맞지 않는다.
4. **정보 부족과 알려진 실패를 나눠야 한다.** 012 aiolimiter와 exporter는 proposal/configuration이 비어 있다. 이것만으로 전체 조건을 충족한다는 사용은 추가 가정이다. exporter의 방향도 패킷만으로 확정하지 않는다.
5. **reference는 T=mapped의 동의어가 아니다.** 같은 분야의 일반 선택 조언은 T=not_needed일 수 있다. 전이 대응·연결 작업·실패 조건이 없으면 mapped로 승인할 수 없다. 사용 자체가 미정이면 unknown과 analogy_only도 구별해야 한다.

## 3. SQLite/Postgres의 조건부 T 대비

대상은 `011-T039-009`와 `011-T047-018`이다. root가 제안한 다음 대비는 **원 패킷의 확정 판정이 아니라 연구자 가정 H를 붙인 서로 다른 사용 단위**로 표시하면 004의 T축과 양립한다.

| 조건부 사용 단위 | 추가한 가정 | 가능한 T 기록과 이유 | 보존할 한계 |
|---|---|---|---|
| A: 이미 제공된 실행 가능한 큐 부품을 기존 인터페이스로 사용 | 해당 구현체가 실제 제공되며 현재 문제에 직접 사용한다는 사실 | `not_needed`: 다른 분야·작동 관계를 새 구현으로 옮기는 논증 없이 이미 있는 구현을 사용하는 경우 | 이 가정은 원 packet에 확인되지 않는다. T가 불필요해도 OSS 여부·ZooKeeper 금지·제공 기능·구성이 자동 pass가 되지는 않는다. |
| B: 테이블을 큐처럼 쓰자는 유사성만으로 새 큐를 설계 | 원본의 테이블 관계를 큐에 옮기려 하나 대응·연결이 충분히 제시되지 않음 | `analogy_only`: 테이블↔큐라는 닮음만 있으며 필요한 전달·상태 전이·실패 경계가 설명되지 않은 경우 | 원 packet의 사용 의도 자체가 불명확하다면 `unknown`도 가능한 상태다. reference라는 코드만으로 analogy_only를 확정하지 않는다. |
| C: 새 설계에 구체적인 대응·연결·실패 조건을 추가 | 연구자가 메시지와 행, 제출·전달 상태와 저장 상태 등을 명시적으로 설계 | `mapped`의 후보가 될 수 있음: 관계 보존과 필요한 연결이 실제로 기술된 경우 | 새 설계이지 원응답에서 관측한 판정이 아니다. 구현 성공은 미확인이다. 실제 제안한 전달 계약에 없는 ack·재처리·복제 요구를 필수조건으로 덧붙이지 않는다. |

여기서 claim/ack, 중단 후 소유권, 재처리, 다중 소비자 경계 등은 **그 설계가 그런 계약을 제공한다고 제안할 경우에 확인할 연결의 예**다. T039/T047의 사용자 요구에 004 P02의 내구 큐 계약을 그대로 수입하는 목록이 아니다. 단순 알림 pub/sub와 작업 큐가 무엇을 약속하는지부터 구별해야 한다.

A와 B의 차이는 코드명만의 효과가 아니다. 실행물 존재, 직접 사용 여부, 새 설계 작업의 범위가 바뀐다. 따라서 주 30행의 고정 사용 변화율에 넣지 않고 별도 조건부 예시로 기록한다는 root의 계획이 적절하다. B에서 A보다 H가 개선되는 것처럼 쓰려면 새로운 설계·근거가 무엇인지 명시해야 하며, 단순히 reference로 바꾸어 H 조건을 지운 것이라면 개선으로 세면 안 된다.

004의 실물 대조는 R11/R12와 R17이다. R11/R12는 reference이면서 숫자 상한과 producer 대기·완료 신호의 설계 연결을 유지하고, 구현 H는 unknown으로 남긴다. R17의 보관·암호화·복원 not_in_scope는 처음부터 manifest 포함 검증만 제안한 입력 범위 덕분이다. 이 예외를 전체 큐·백업 대안의 사후 면제에 사용하면 안 된다.

## 4. 변화율·근접 오답에 대한 해석 규칙

- 고정 사용에서 역할명만 바꾼 0/30 변화가 나오면, 같은 증거·요구·설정에 같은 004 규칙을 적용했을 때의 **판정 기록 일관성**이다. 역할 표시를 사람에게 다르게 제시했을 때 행동·판정이 달라지는지를 관측한 실험은 아니다.
- 양쪽이 unknown/INSUFFICIENT인 사례는 두 기록이 같다는 뜻이다. 실제로 기능 충족 여부가 변하지 않는다는 사실을 확인했다는 뜻은 아니다. 판정 기록 불변과 실세계 충족 불변을 구별한다.
- S2 part는 H 부분 합격 점수가 아니고, S2 none는 확정된 H fail이 아니다. S3 unknown도 후보 기능의 부재가 아니다.
- 전체 대안의 알려진 실패가 있으면 이를 보존한다. 원문 부족은 알려진 실패와 다르다. 조건부라는 말을 붙였다는 이유만으로 INSUFFICIENT를 CONDITIONAL_TRANSFER로 올리지 않는다.
- 필수조건을 추출할 수 없는 prefer 중심 사례에서 H 벡터가 비었다는 이유로 DIRECT_DOCUMENTED를 자동 부여하지 않는다. 목표·제안의 충분성과 근거 수준은 여전히 별도 검토 대상이다. 선호를 not_in_scope라는 필수조건 상태에 억지로 넣을 필요도 없다.
- 근접 오답 여부는 역할 불일치와 별도로 근거를 적는다. 이름·관련 주제는 가까워도 알려진 결정적 위반이 있는지, 아직 설정이 없는지, 아예 원거리 무작위 쌍인지 구별한다. 004에는 독립 near_miss enum이 없으므로 해당 상태를 사용할 때 적용한 작업의 정의도 명시한다.
- 단일 연구자가 작성한 반사실 H/T 판단은 작성자 판단으로 표시한다. 이번 후속 검토가 동의한 경계 규칙을 사람 합의나 원래 이중 코딩의 추가 독립 표본으로 세지 않는다.

## 6. root 영향 분석 초안의 후속 대조
