# libass 후속 검토 — AF-RES-053

## 판정

L01(#588)과 L02(#685)의 N·I·D 예측은 봉인대로 모두 **판별불가**다. 후속자료를 읽은 뒤에도 I와 D 중 새로 맞춘 쪽을 정할 수 없다. 정상/경계 × A/B의 예정 8셀 가운데 원판·입력·수치 조작을 모두 맞춘 새로운 후속 출력은 확보하지 못했다. L02의 원그림은 A 경계 실패를 직접 보여 주지만 그 실패는 봉인 전 본문에서 이미 노출됐다. L03은 미충원이며 예측 CSV의 `choice=판별불가`와 `status=미실시·미충원`을 구분한다.

이 문서는 `outcomes.json`의 8셀, `outcome-sources.jsonl`의 LA-O01~24, 열람 영수증을 설명한다. 원문 댓글·그림·소스 코드는 출력의 종류와 알려진 시점을 구분해 사용했다. 사전 카드를 후속 지식으로 다시 채우지 않았다.

## 1. 봉인·열람 순서와 조사 범위

- 원격 예측 봉인: `9b13473a76a381fe27d775524aa65416ec28f591`.
- 첫 후속 요청 준비: `2026-11-23T01:56:50.120240+00:00`. 응답 완료 시각은 별도로 기록하지 않았으므로 요청 준비 시각을 최초 독해 완료 시각으로 바꾸지 않았다. `followup-open-receipt.json`은 frozen predictions/cards/operations/refinements의 SHA256을 보관한다.
- #588 댓글 3개와 timeline 6개, #685 댓글 1개와 timeline 3개를 모두 읽었다. 별도 경계 사례 #598의 댓글 9개, #600의 댓글 1개도 모두 읽었다.
- #588이 지목한 mpv #3008 본문·댓글 5개·그림, #588 후속 답이 지목한 libass PR #384 본문·댓글 8개·그림 2개, #384의 대체 PR #385 본문·댓글 1개·병합 상태·공개 diff 3파일을 읽었다.
- 연구 기준판 0.17.1의 `ass_parse.c`와 `ass_render.c`는 후속 단계에서 처음 읽었다. 이 구현은 당시 카드에 보인 공식 API 한 절에 포함되지 않는다.
- 원첨부 6개와 선행 첨부 3개를 내려받았다. 정적 그림 8개는 직접 봤고 GIF는 도구가 표시한 첫 프레임만 봤다. 동영상 재생, GIF 전체 프레임 분석, 정량 픽셀 측정은 미실시다.

원문 전체·그림 파일은 ignored `_scratch_not_for_commit/`에만 있다. 공개 파일에는 주소·확인 내용·한계·해시를 남긴다. 원문 저장본은 본문을 읽을 당시의 current API 판이며 최초 작성판 복원으로 부르지 않는다.

## 2. L01 — 중앙이라는 목표와 구현된 중앙 조작은 다르다

[#588의 첫 후속 답](https://github.com/libass/libass/issues/588#issuecomment-1028326022)은 큰 띠에서 event 전체가 들어갈 anchor를 계산하고 가능하면 가운데 놓는 방안을 설명한다. 동시에 두 번째 자막, 아주 큰 띠, 화면 확대, event MarginV의 의미가 정책을 갈라 놓는다고 지적한다. 이는 구현 가능성과 실패 경계의 설명이다. 완성 코드, 수치 MarginV, 같은 입력의 실제 중앙 출력은 붙어 있지 않다. LA-O01.

[작성자의 다음 답](https://github.com/libass/libass/issues/588#issuecomment-1028466424)은 아주 큰 띠에서는 영상 바로 아래 위치도 좋을 수 있으며 top/center/bottom 선택을 원한다고 넓어진 목표를 보여 준다. 최초 요구의 큰 띠 중앙 목표를 영상 근처 배치 목표로 바꿔 성공이라 부르면 표적이 달라진다. reader가 영상과 자막 사이에서 눈을 움직이는 거리를 줄이는 목표와 designer가 띠 안 중심을 맞추는 목표는 같은 척도가 아니다.

[원첨부](https://user-images.githubusercontent.com/4148154/152122669-c753d86c-7520-4cfc-b9d9-7b157fc2f99b.png)는 상단에 하단 기준, 하단에 원하는 중심 기준을 그린 비교 구성이다. [mpv #3008 원그림](https://cloud.githubusercontent.com/assets/11010067/14164246/290b4b78-f6d4-11e5-9c7b-21debc1aec8f.jpg)을 뒤에 열어 같은 구성을 확인했다. 다른 해시·파일 형식은 별도 구현 시험을 뜻하지 않는다. LA-O02/15.

[mpv 선행 논의](https://github.com/mpv-player/mpv/issues/3008#issuecomment-203739140)는 두 줄을 넘는 자막이 아래로 벗어나는 위험을 지적한다. 다른 댓글은 화면에 들어가도록 위로 밀어 넣는 방안을 제안한다. 어느 쪽도 L01의 고정되지 않은 B 값을 실행해 검증한 결과가 아니다. mpv 본문은 무띠에서도 중심 기준을 원하므로 무띠에서는 기존 default를 선호한 #588과 목적 범위도 다르다. LA-O13~15.

| 예정 셀 | 확인한 것 | 실제 출력 채점의 결손 |
| --- | --- | --- |
| 정상 A | 작은 띠·무띠에서 default가 좋다는 원작성자 선호 | 완성 ASS·frame 크기·원판·설정 없음 |
| 정상 B | 정의상 정상 분기에서는 A를 유지 | 구현과 출력 없음; 정의상 같음을 관측 동률로 세지 않음 |
| 경계 A | 큰 띠 한 줄을 하단 기준에 둔 원그림 | 원판·입력·MarginV 추적 없음; 최초 상태 묘사 |
| 경계 B | 중앙 배치 요구 도식과 유지보수자 설명 | 실제 margin 값·block 측정·분기 구현·출력 없음 |

**링크의 용도:** #588 후속 답은 기능을 설계할 때 정책 질문과 실패 경계를 확인하는 데 쓸 수 있다. **적용 중단:** 그 설명만으로 중앙 margin 수치, 모든 동시 자막 수용, 화면 이탈 방지를 보장하려 할 때 중단한다.

## 3. L02 — t 예외는 구현에서 확인됐지만 B의 성공은 아니다

[#685의 후속 답](https://github.com/libass/libass/issues/685#issuecomment-1454495083)은 해당 동작이 ASS 참조 구현과 맞추는 표준 동작이라고 설명하고 명시적 위치 지정을 권한다. 이는 오류 수정 약속이나 특정 B 실행 결과가 아니다. 같은 시각의 close event에는 commit_id가 없다. 종료를 해결로 세지 않았다. LA-O03/24.

[0.17.1 파서](https://github.com/libass/libass/blob/e8ad72accd3a84268275a9385beb701c9284e5b3/libass/ass_parse.c#L668-L726)의 t 분기는 collision detection 상태를 끈다. [렌더러](https://github.com/libass/libass/blob/e8ad72accd3a84268275a9385beb701c9284e5b3/libass/ass_render.c#L3248-L3307)는 그런 event를 자동 충돌 배치 루프에서 건너뛴다. 따라서 전체 자막이 자동으로 서로를 피할 것이라는 일반 기대에 실행상 예외가 있다. 다만 이 코드를 봉인 뒤 읽었으므로 N 카드의 사전 판별력을 올리는 데 쓰지 않는다. LA-O05/06.

같은 [렌더러 L2881–2887](https://github.com/libass/libass/blob/e8ad72accd3a84268275a9385beb701c9284e5b3/libass/ass_render.c#L2881-L2887)은 event MarginV가 0일 때 style 값을 선택한다. A의 style 10/event 0과 B의 흰 event 비영 margin 증가를 구분하는 근거는 확보됐다. 그러나 B의 숫자는 봉인 때 정해지지 않았다. 필드를 바꿀 수 있다는 사실은 충분히 분리되는 값을 이미 알았다는 뜻이 아니다.

[원첨부](https://user-images.githubusercontent.com/46261767/222871559-67c7f8f8-c88a-4c30-9e47-30a6ad721404.png)에서는 흰색과 노란색 글자가 하단 중앙에서 겹친다. 원문에는 VLC 3.0.18만 있고 libass 패치판은 없다. 한 프레임은 0~5초 전체에서 내용과 alpha/timing을 보존하는지도 보이지 않는다. 이것은 봉인 전 알려진 A 경계 실패의 시각 재확인이다. LA-O04.

| 예정 셀 | 확인한 것 | 실제 출력 채점의 결손 |
| --- | --- | --- |
| 정상 A | 저자가 지목한 t를 제거하는 보충 대조는 연구자 정의 | 저자가 제출한 정상 fixture·출력 없음; alpha 시간변환도 달라짐 |
| 정상 B | 같은 보충 대조에서 흰 event margin 증가 후보 | 숫자 margin·출력 없음 |
| 경계 A | 원입력 실패 그림과 호환 규칙 설명 | libass 원판·실행 해시·프레임 시각 없음; 실패는 사전 노출 |
| 경계 B | 비영 event margin이 style 값을 덮는 구현 | 필요한 margin 값·동시 분리·전체 시간 보존 출력 없음 |

**링크의 용도:** #685 답과 고정판 파서는 자동 collision을 사용할 수 있는 event 조건을 확인하는 데 쓴다. **적용 중단:** t를 없애거나 발화 자체를 숨겨 원래 animation·표시 시간을 바꿔 놓고 해결이라고 부를 때, 또는 명시적 pos 제안을 frozen MarginV 조작과 같다고 취급할 때 중단한다.

## 4. 독립 반례 두 건과 관점 차이

### 4.1 #598 — 화면 위의 같은 위치도 단위와 상태가 다르면 같은 계산이 아니다

[#598 후속 논의](https://github.com/libass/libass/issues/598#issuecomment-1065991906)는 GUI 화면 좌표, ASS PlayRes의 style margin, 비디오·전체 화면 높이를 혼합했을 가능성을 묻는다. 중간 제안의 실패 보고를 거쳐 [작성자는 overscan.top을 반영한 식이 동작한다고 보고](https://github.com/libass/libass/issues/598#issuecomment-1187410504)했다. 최종 성공은 작성자 보고이고 같은 판·같은 화면의 수치 출력은 없다. LA-O07.

원그림의 자막과 calibration bar를 직접 봤다. GIF는 첫 프레임만 봤으므로 화면 위쪽으로 이동할수록 오차가 커진다는 주장은 저자 보고 범위를 넘겨 독립 실측으로 쓰지 않았다. 이 사례는 frame margin이 screen px라는 N과 style MarginV가 script 좌표라는 I의 구분이 왜 중요한지 보여 준다. print의 물리적 프레임 중심을 곧바로 수신 API 숫자로 옮기는 데도 같은 단위 확인이 필요하다는 것은 이 사례에 근거한 연구자의 추론이다. LA-O08/09.

이 요구는 본문에 식·workaround·상대 결과가 이미 있어 주표본에서 제외했다. 나중에 찾은 성공식을 L01의 B 값으로 끼워 넣지 않는다.

### 4.2 #600 — 회전된 글자와 세로 조판은 보존하는 속성이 다르다

[#600 유지보수자 답](https://github.com/libass/libass/issues/600#issuecomment-1055846785)은 당시 libass가 실제 세로 조판 대신 일부 glyph 회전을 수행한다고 설명한다. 저자의 [외부 엔진 비교 그림](https://user-images.githubusercontent.com/100724690/156239287-8eec647a-d02c-43f6-8e5b-80b7e1387515.png)과 [libass 그림](https://user-images.githubusercontent.com/100724690/156239541-21fda112-8be0-4e3e-ab0e-3b2eb8bee6e9.png)을 직접 대조하면 괄호·구두점의 방향과 간격, 열의 길이가 달라진다. LA-O10~12.

독자는 문자 관계와 읽기 순서를 보존해야 한다. 화면 요소를 돌릴 수 있다는 API 능력만으로 그 목표를 보장할 수 없다. 원문은 Kana를 정상 대조로 지정하지 않았고 두 그림은 다른 엔진이므로 정상/경계 주표본이나 libass 구판/신판 비교로 편입하지 않았다.

### 4.3 지도·인쇄 규칙을 자막에 옮기는 적용 중단 조건

L02-D의 봉인된 연결은 지도 곡선 라벨의 일부 숨김과 가독성의 절충이었다. 두 자막 event의 내용을 보존해야 하는 L02에서 event나 단어를 숨기면 정적 겹침은 줄어도 목표를 잃는다. t를 제거하면 변환 시간도 달라진다. 이는 실제로 D가 숨김 조작을 실행했다는 관측이 아니라 **목표 보존 조건으로부터의 추론**이다. frozen D는 이미 판별불가였으므로 새 오답으로 세지 않는다.

L01-D의 CSS 자동 너비 절은 고정된 페이지 상자의 수평 중심을 다룬다. ASS의 수직 위치, 동시 event, 화면 pan/zoom, 발화 시간은 그 절이 보장하지 않는다. L01은 중앙이라는 유사한 목적을 얻었을 뿐 수신 조작의 수치나 실행 규칙을 얻지 못했다. donor 자체의 해석은 root 원전 원장과 함께 읽어야 하며 이 문서는 수신 측 반례만 추가한다.

## 5. 구판/신판 반례 탐색의 한계

[#384](https://github.com/libass/libass/pull/384)는 병합되지 않았고 [#385](https://github.com/libass/libass/pull/385)가 2020-07-05에 대체 병합됐다. 공개 diff 3개는 margin 사용에 따른 fit 크기·좌표변환·clipping을 바꾼다. 이는 실제 패치의 존재다. #588보다 앞선 패치이므로 #588 요구를 뒤에 해결한 근거가 아니다. LA-O16/20~22.

[#384의 외부 엔진 관측](https://github.com/libass/libass/pull/384#issuecomment-605161837)과 그림 2개는 pan 조건에 따라 자막이 영상 바로 아래 또는 화면 하단으로 가고 오른쪽 내용이 잘리는 것을 보여 준다. 같은 libass 조작의 두 판 출력이 아니다. #385의 files 응답에는 시험·기대 이미지 파일이 없었다. 전역적으로 시험이 없다고 단정하지 않으며, 이번에 찾은 범위에서는 **동일 입력·동일 조작의 libass 구판/신판 실제 차이는 미확인**이다.

| 새 I/D 성과 판정 가능 사례 | 0/2 선정 사례 | 두 사례 모두 미확인; 우월성 비율은 해당 없음 |

실제 사례 두 건을 읽었다는 분모와 새 성과를 채점할 수 있는 분모는 다르다. I/D가 같은 판별불가를 냈다는 문서상 일치는 있지만, 이를 성공률의 동률로 세지 않는다. 렌더러 빌드·실행·픽셀 정량 검사는 미실시다. 기존 B가 미고정인 상황에서 사후에 값을 골라 만든 출력으로 봉인 예측을 정답 처리하지 않는다.

## 7. 최소 재개 자료와 확인 명령

첫 행동은 L01의 완성 ASS·video/frame/black-bar 크기·실제 libass 판과 B margin 계산 규칙, L02의 VLC에 포함된 정확한 libass 판·font 파일·frame/PlayRes·B event margin 값을 확보하는 것이다. 모두 동결한 뒤 새 실행 프로토콜에서 정상/경계 × A/B를 비교해야 한다. 이 새 실행은 이번 역사판 사전 예측과 별도 분석이다. 현재의 미정 값을 임의 숫자로 대신한 실행 명령은 제공하지 않는다.

이번에 판정에 쓴 고정 소스를 다시 확인하는 명령은 다음과 같다. 이는 렌더 출력을 만든 명령이 아니다.

```sh
git -C docs/workstreams/research/AF-RES-053/streams/libass/_scratch_not_for_commit/libass-source show 0.17.1:libass/ass_parse.c
git -C docs/workstreams/research/AF-RES-053/streams/libass/_scratch_not_for_commit/libass-source show 0.17.1:libass/ass_render.c
```

직접 출력의 결손을 바꿀 최소 공개 자료는 같은 원판·입력·실제 B 값이 함께 붙은 L01과 L02의 작성자 후속 출력 또는 고정 기대 그림이다. 단일 B 정상 그림만 오면 경계 A의 오답까지 채점하지 않는다.
