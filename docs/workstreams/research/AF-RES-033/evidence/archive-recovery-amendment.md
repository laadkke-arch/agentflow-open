# 초기판 복원의 추가 경로 — 질의 봉인 전

## 발견과 적용 시점

제공 집합은 `aba0565e5d992dc358c9c7913b2ad7868248db8d`에서 이미 고정됐다. 수신 표집은 진행 중이며, 수신 입력/질의의 원격 봉인·실제 검색·후속 결말 열람은 아직 하지 않았다. Rust의 잠정 적격 네 본문과 Kubernetes의 일부 적격/탈락 본문을 읽은 이후의 보완이다. 수신 작성자는 제공 분야·제목·본문을 여전히 보지 않았다.

현재 GitHub PR 커밋 목록에서 생성 전 유일한 head를 찾지 못하는 행이 많이 발생했다. 별도 문맥의 검토자가 [GH Archive](https://www.gharchive.org/)의 공개 시간별 `PullRequestEvent` 중 `action=opened`를 검사한 결과, 잠정 Rust 네 건의 생성 당시 head가 기존 복원값과 모두 일치했다. 같은 경로로 앞선 복원 실패를 다시 확인할 수 있게 됐다. 현재 생존 이력이 없다는 이유를 당시 본문 자체의 부재로 굳히지 않기 위한 보완이다.

## 바뀌는 복원 수단과 그대로 적용할 표집 기준

1. 생성 시각·PR 번호 순서, 새 기술 제안 적격성, 전체/부분 범위 기준, 프로젝트별 네 건과 범위 구성 규칙을 그대로 적용한다. 제공 집합·검색 설정·질의 예산·채점 기준도 바꾸지 않는다.
2. 현재 이력으로 생성 전 head를 복원하지 못한 앞선 행을 **잠정 복원 실패**로 보존한다. 공개 생성 이벤트에서 당시 `head.sha`와 `base.sha`를 확인할 수 있으면 해당 고정판의 첫 diff와 blob을 다시 복원한다. 결과가 좋은 설계를 선택하기 위한 교체가 아니다.
3. 이벤트는 프로그램 안에서 저장소·PR 번호·`action=opened`로 거른다. 출력·저장 필드는 이벤트 ID/시각, PR 생성 시각, head/base SHA와 검증용 아카이브 위치뿐이다. 제목·본문·닫힘/병합·후속 댓글·상태 필드는 읽거나 표시하지 않는다. 아카이브 전체는 공개 산출물에 저장하지 않는다.
4. 고정 `base...head` 비교의 추가/이름 변경된 제안 Markdown 경로를 첫 diff 경로 순으로 검사한다. 커밋·경로·blob 결합을 검증하고, 그 본문만 수신 작성자와 별도 범위 판독자에게 전달한다. 사건의 생성 head에 포함되지 않은 나중 본문은 사용하지 않는다.
5. 앞서 넘긴 복원 실패 중 더 이른 적격 제안이 복원되면 원래 생성순 규칙에 따라 표본에 들어간다. 잠정 선택에서 밀린 행도 본문 열람/이유를 원장에 남긴다. 이전 행과 시도를 삭제하지 않는다. 재복원에 실패하면 URL·오류·다음 복원 자료를 남기고 그 다음 행으로 간다.
6. 새 경로에서 복원한 앞선 본문을 열기 전에 이 보완을 원격 커밋한다. 최종 여덟 본문·부분 목표·질의를 함께 봉인한 후에만 검색과 후속 결과 열람을 한다.

## 민감도와 한계

현재 생존 이력 경로만 사용했을 때의 잠정 표본과 생성 이벤트 보강 후 실제 표본의 차이를 기록한다. 본문을 읽은 뒤 복원 수단을 확장했다는 점은 사전 등록 수준의 완전 고정과 구별한다. 다만 제공 원문을 본 통합 작성자가 질의를 작성하지 않고, 복원 여부는 head/경로/본문의 존재와 기술 제안 적격성으로 판정하며, 어떤 검색 성공률·제공 대응·후속 결말도 표본 결정에 쓰지 않았다.

공개 아카이브는 생성 당시 이벤트의 보존 사본이며 GitHub의 현재 화면보다 직접적인 시점 근거를 제공한다. 아카이브 누락, 잘못된 PR 연결, 동일 head에서의 경로 오류는 별도로 검사한다. 한 건의 이벤트 일치가 이후 모든 이력이나 실제 구현/채택을 증명하지 않는다. 첫 네 Rust 검사는 [opening-archive-checks.jsonl](opening-archive-checks.jsonl), 추가 복원 시도는 별도 `archive-recovery-*` 파일에 남긴다.
