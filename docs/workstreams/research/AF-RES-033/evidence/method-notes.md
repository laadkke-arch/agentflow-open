> **F02 정정 — 재개 감사에서 철회:** 아래 과거 GTFS/예정 운행 해석은 동일 SHA256 PDF·재다운로드·로컬 렌더의 “MTA Real Time data” 확인으로 철회됐다. 현재 관측과 한계는 [정정 영수증](../field/resume-field-correction.json) 및 [재개 현장 감사](../field/resume-field-audit.md)를 따른다. 개별 실제 운행의 원로그·집계 코드를 재실행한 것은 아니다. 과거 문장은 해석 변경 이력으로만 보존한다.

# 방법·노출 기록

## 사전 규칙을 유지한 보완

- Git HTTPS 읽기는 성공했고 첫 push는 사용자 이름을 읽을 수 없어 종료코드128이었다. 인증·계정·권한 설정을 바꾸지 않고 이미 연결된 GitHub 도구의 tree/commit/ref로 원격 저장했다. ref에는 읽은 이전 SHA를 조건으로 넣었다. 로컬 사본은 원격 커밋을 fetch한 뒤 `reset --mixed`로 맞췄으며 작업 중 파일은 보존했다.
- 기존 `.gitattributes`는 모든 텍스트의 LF를 요구한다. 최초 수신 frame의 CRLF→LF 변환은 행·값·순서 변화가 아니다. 이후 CSV 작성기는 LF를 명시한다. 외부 원문 raw hash와 canonical text hash는 다른 값일 수 있다.
- `retrieval.py`의 첫 원격판 이후 출력 CSV의 LF를 명시하도록 한 줄 수정했다. 검색 점수/토큰화/순위/창 규칙은 동일하며 첫 실행 전에 다음 봉인에 포함한다.

## 노출 단위

제공 수집자와 수신 질의 작성자는 `fork_turns=none`인 별도 문맥이다. 질의 작성자는 제공 분야·발행처·제목·본문·근거 평가를 받지 않았다. 제공 수집자는 수신 질문·질의·후속 결말을 받지 않았다. 이 상태는 입력 봉인까지 유지한다.

제공 디렉터리의 최초 검색은 예상보다 많은 원문 요약을 반환했다. 이 사전 노출은 제공 수집자에게만 있었고 SCOPE에 기록했다. 수신 질문을 맞춰 후보를 고를 수 있는 노출과 구별한다. 원장에 URL/제목 집합을 고정한 다음 적격성 검토를 수행했다.

통합 작성자는 요구된 010 HANDOFF와 029 HANDOFF·Q01/Q11을 읽었다. 최초 029 읽기 출력이 커서 잘렸으며 후속으로 핵심 본문·Q01/Q11 행을 분리해 읽었다. 통합 작성자는 이 정보를 질의 작성자에게 전달하지 않았다. 029의 기존 사건이나 사후 보강을 이번 표본에 넣지 않는다.

통합 작성자가 별도 현장 사례4개를 수신 입력 봉인 전 수집했다. 이는 원래 후보18에 들어가지 않으며, 질의 작성자에게 전달되지 않았다. Q6의 현장 검증에만 사용하고 원 검색 분자를 보강하지 않는다.

## 원문 해석에서 발견한 실제 경계

NYC 교통 PDF의 텍스트 추출은 다음 페이지의 MTA real-time 출처를 앞 그래프와 혼동하기 쉬웠다. 실제 p13 화면을 확인하니 시간대별 운행 비교의 출처는 GTFS였다. F02는 예정된 정차 패턴의 비교로 기록하며 실제 운행 실적 또는 모든 차량 출발 관측으로 표현하지 않는다.

ONS MYE3 전후판은 공식 페이지에서 연결된 v1·v2를 직접 받았다. 357개 식별 코드로 맞춰 비교한 결과39행/78셀만 달랐고 변경 열은H/I였다. 순이동J열과 인구 합계O열은 이 표에서 그대로다. 전체 워크북이나 ONS 추정 알고리즘을 재실행한 결과로 확대하지 않는다.
