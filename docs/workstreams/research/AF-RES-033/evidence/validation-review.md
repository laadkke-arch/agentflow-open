# 최종 결과의 읽기 전용 검산 검토

## 작업 경계

교통 48개 전수 판독은 원격 관측 커밋 `889c5e792a3db3856bf5be8c90d9486490ce8677`에 봉인된 뒤 별도 validator 작업으로 전환했다. 이 작업에서는 원 순위·질의·집계 데이터를 읽어 조인을 검사한다. 이전 교통 판독이 질의/순위에 노출되기 전에 완료되었다는 시점과 구분하며, 봉인한 판정·원장·입력·corpus를 수정하지 않는다.

작성 파일은 `validate_results.py`와 이 검토 문서뿐이다. 스크립트는 네트워크를 사용하지 않고 읽기만 수행하며 stdout에 JSON 영수증을 출력한다. bytecode 쓰기를 비활성화한다. git은 현재 SHA를 읽기만 하며 커밋·push는 실행하지 않는다. 원 판단의 타당성을 자동으로 재판정하거나 독립 인간 실험으로 주장하지 않는다.

## 실행 방법

RESULT 작성 전 초기 검사에 사용한 명령:

```sh
python -B docs/workstreams/research/AF-RES-033/validate_results.py --require-cache
```

완성된 RESULT와 원문 캐시를 함께 검사한 최종 명령:

```sh
python -B docs/workstreams/research/AF-RES-033/validate_results.py --require-cache --require-report
```

원문 캐시가 없는 새 clone의 한계를 명시적으로 검사할 때:

```sh
python -B docs/workstreams/research/AF-RES-033/validate_results.py --metadata-only --require-report
```

`--metadata-only`는 실제 새 clone 생성의 대체 실험이라고 주장하지 않는다. 같은 데이터에서 캐시를 사용하지 않는 경로를 실행한 것이다. 기본 실행도 원문 캐시가 없으면 누락과 제한을 영수증에 남기고 가능한 빈도벡터·메타데이터 조인을 검사한다. `--require-cache`는 해당 원자료가 없으면 실패한다. `--require-report`는 RESULT가 없으면 실패한다. 영수증 저장은 호출자가 stdout을 기록하는 별도 행위이며 스크립트 자체는 파일에 쓰지 않는다.

## 발견한 검사 가정과 처리

초기 도구는 최소수 자료 모두에 비어 있지 않은 `fixed_url`을 요구해 20개 실패를 출력했다. 원장을 확인하니 F03과 후보 18개의 `fixed_url`은 명시적인 null이고, 원 주소·판 정보·캐시 SHA·한계가 별도로 남아 있었다. 이는 원장 행을 빠뜨린 것이 아니라 불변 웹주소가 확립되지 않은 자료를 정직하게 표현한 상태다. validator를 다음처럼 고쳤으며 원장을 수정하지 않았다.

- `fixed_url` 필드는 반드시 존재하지만 null은 허용한다.
- 출처 중복 비교에는 고정 URL이 있으면 그것을, 없으면 원 URL을 사용한다. 고유 원문 판단은 별도 duplicate_group도 검사한다.
- null 19건을 영수증의 `no_immutable_web_url` 경고에 모두 열거한다.
- 고정 URL의 부재를 현시점 live URL이 불변이라는 주장으로 바꾸지 않는다. 캡처 바이트의 SHA 일치는 원 자료의 의미나 발행자 진위를 독립적으로 증명하지도 않는다.

## 새 clone에서 재현되는 것과 남는 한계

commit에 남은 질의·문서 빈도벡터·창 빈도벡터와 ranker는 본문 캐시 없이도 원 점수 288행과 순서·동률 처리·반환 메타데이터를 재생한다. 그러나 저장된 문자열의 실제 내용, 창 해시가 어떤 원문 조각을 가리키는지, 다단 PDF 해석, 한 문장의 잘린 부분까지 포함됐는지는 원문 바이트 없이 다시 확인할 수 없다. source의 단순 링크, 고정 metadata 또는 작업자가 작성한 표만으로 직접 열람이 독립 재현되었다고 하지 않는다.

`metadata-only`가 통과해도 캐시 내용 재검을 통과했다는 뜻은 아니다. 원문이 없는 상태에서 positive 근거가 반환 창 안에 완결되었다는 주장을 새로 만들지 않는다. 현재 데이터에서는 반환된 문서 자체의 strict support가 없으므로 원문 캐시 없이도 인용 완료 0이라는 논리적 상한은 검증할 수 있지만, 48개 창의 정확한 글자·근거 위치 확인은 캐시가 있어야 가능하다.

## RESULT 검산 상태

RESULT가 작성 중이었던 초기 실행은 `report_checked: false`였다. 그 영수증은 최종 결과 검사 통과를 뜻하지 않는다. 아래 최종 실행은 완성된 RESULT를 읽어 `report_checked: true`로 통과했다.

완성 직후의 첫 실행에서는 표2의 합계 행, `= 18`로 명시한 분모와 `S0/1·R0/1` 표기를 검사기가 잘못 해석하여 17개 실패를 출력했다. 실제 집계 오류가 아니었고 원 표를 고치지 않았다. 검사기가 개별 수신 8행과 합계 1행을 구분하고, 각 질문 단위 분모와 후보 18개 분모를 각각 비교하도록 수정했다. 이와 별도로 실제 문서 결함 한 건인 미반환 R05–L06의 `returns.jsonl` 링크를 발견해 보고했다. 작성 담당자가 원 순위가 있는 `rankings.csv` 링크로 수정했으며, 최종 실행은 미반환 후보를 반환 파일에 있는 것처럼 연결한 링크가 없음을 확인했다.

최종 RESULT는 제목 직후의 세 필수 표, 정확한 열 이름과 순서, 첫 표의 반환 합집합 37개와 전수 판독 전용 R05–L06 1개, 둘째 표의 수신 8행과 합계 1행, 반례 표의 양측 원문 URL, 마지막 정확히 세 행의 약점 표를 충족했다. 마지막 표 뒤에는 추가 본문이 없다. 첫 표의 원 S·R 순위·반환 여부·창 ID와 줄 위치, 둘째 표의 수신별 지지·충돌·부분·미확인 수와 인용 완료 분자·분모, 분야별 집계표와 엄격/넓은 해석의 상위 1·3 비교표를 원장으로 다시 계산했다. 서술의 인과관계와 근거의 의미까지 자동 검증했다고 주장하지 않는다.
