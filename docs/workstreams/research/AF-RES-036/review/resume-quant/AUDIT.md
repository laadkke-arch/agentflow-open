같은 N에서 H를 더한 뒤 행동이 달라진 사건은 **0/12**다. 같은 H에서 N을 더한 BH→BNH에는 보류→기준 일치 12개가 있으나, 이 가운데 확정 유지↔교체의 역전은 없다. B/BH를 보류로 두는 사전 규칙의 영향이 있으므로 이 숫자를 독립적인 이력 무용성의 인과 추정치로 읽을 수 없다. R01은 BNH에서 대체 후보 tarball URI를 언급하지만 `replacement_verified_in_packet=false`이므로 검증된 대체 URI 획득의 성공으로 추가 가산할 수 없다.

BN→BNH에서 수집자 사전노출 제외 분모는 10, 같은 프로젝트·대상 중복 제외는 4, 두 조건 함께 제외는 3, N 카드에 이력이 있는 사례 제외는 7이다. 수집자 노출·프로젝트/대상·카드 이력·제공자 배경·과잉 한정 등을 함께 제외한 기록된 결합 집합은 G05/R03 두 사례다. 판독자가 신고한 어떤 선행 관련 사례도 없는 집합은 G05/R06 두 사례이고, 거기에 N 카드 이력도 제외하면 G05 하나다. **수집자의 목적 재서술을 모두 제외한 집합과 외부 독립 gold만 남기는 집합은 각각 0**이며 `해당 없음`이다. 앞의 2사례 집합을 이러한 최엄격 조건까지 충족한 실험이라고 부르면 안 된다.

## 발견한 원장 누락과 정정

기존 집계기는 `collectors/gnu`, `bioc`, `cross`, `root`만 모으므로 이후 `adjudicators/gnu`와 `adjudicators/bioc`의 자료가 공통 원장에 빠져 있었다. 기준판정 12행의 `primary_source_ids`가 공통 sources에 모두 연결되지 않았지만 별도 기준판정 원장에는 실제 자료가 존재했다. 빠진 것은 **source64개 ID·attempt64행**, 그중 실제 GET59개였다.

부모에게 누락을 보고하고 허용받은 뒤 `reconcile_ledgers.py`를 dry-run으로 검토하고 적용했다. [integration-dry-run.json](integration-dry-run.json), [integration-applied.json](integration-applied.json)에 명시적 source→canonical 대응, 정정 전후 해시, 보존 검사가 있다. `before/`에는 원격 시작판의 기존 집계 파일을 보존했다. 원래 raw ledger·기준판정·보기·답안은 수정하지 않았다.

같은 소비자 원문·POSIX2018의 장·같은 함수·같은 vignette는 기존 행의 variant로 연결했다. 별도 판·릴리스 공지·추가 구현 멤버·검색/실패 기록 등은 보조행으로 남기되 `count_minimum=false`다. BC-consumer-R04는 devel.html과 intro.html을 한 archive에 담은 복합 기록이므로 BIO-B04를 carrier로, `also_covers_source_ids=[BIO-B06]`를 함께 남겼다. canonical 대응이 전체 HTTP 응답 바이트의 동일성을 뜻하지 않도록 명시했다.

정정 후 **공통 source행81 / raw variant126 / alias126 / 적격 최소수50**이고, attempt266행이다. 전의 적격50·범주별 분모는 그대로다. source행81에는 검색·실패·복합 배포 메타데이터 보조행이 있으므로 이를 고유 적격 원문81이라고 쓰면 안 된다. 12개 기준판정의 모든 출처 ID가 이제 공통 원장과 조인된다.

저장 bytes도 해당 요청의 임시 full-body 저장값 기준으로 각각 같다. 이는 Git 원격의 보관량이나 wire bytes가 아니다. 동시 실행의 경과 합을 벽시계/노동으로 쓰지 않는다. 실패에는 HTTP 오류 응답을 포함하며 네트워크 연결 오류만을 의미하지 않는다. 이후 재개 감사의 새 요청은 위 시간창 밖이다. 기존 collection-only 수치는 summary 안의 별도 scope로 보존했다. 공통 비용 원장에는 실제 GET216행, archive 재사용4행, 모의 재조회48행이 구별되어 있다.

## C1/C2 비용 비교의 확인 범위

재조회는 실제 실행되지 않았다. 48개 모의 행의 URL/attempt 연결·바이트·명시 retrieval 수·redirect 포함 exchange 수·예산 여부는 원 관측에서 정확히 재계산된다. 주소를 이미 알고 같은 응답 바이트가 다시 온다고 가정했으며 경로 재발견·사람 판독·실서비스 비용은 미측정이다.

| 같은 비교 과업 | C1의 공유 취득 하한 | C2의 공유 취득 하한 | 해석 |
| --- | --- | --- | --- |
| 봉인 N 본문 재구성 | 17회 / 3,056,003 bytes | 17회 / 3,056,003 bytes | 현재 근거 확인의 네트워크 차이 없음 |
| 봉인 N/H 본문 재구성 | 29회 / 16,067,466 bytes | 17회 / 3,056,003 bytes + H local read12 | 이력 재구성이라는 요구가 있을 때의 조건부 모의 절약; 이번 행동 정확도 이익과 같지 않음 |

전체 12참조의 실제 직렬화 예시는 문맥+링크 7,754 bytes, B 보존 12,153 bytes, B/H+provenance 38,145 bytes다. C1 모의 실험은 약한 문맥+링크만이 아니라 이미 판·배포물·member를 담은 B를 사용한다. 따라서 문맥+링크만으로 이 정확도를 얻었다는 주장은 성립하지 않는다. 원래 query 시각을 포함한 전체 packet hash까지 재생했다는 주장도 하지 않는다.

## 재실행

### 재개 감사 원장 연결

첫 정량감사 이후 세 문맥이 재열람한 기록도 별도 phase로 연결했다. `review/resume-sources`의 원문9행·실측 GET10행·미계측 도구/실패5행, `review/resume-cross-costs`의 원문9행·웹 open/find16행, root의 `evidence/resume-web-reads.json`4개 open을 공통 원장에 조인했다. 추가 원문18개 ID는 기존 canonical 행의 variant/alias이며 적격 최소수 추가0이다. canonical행81·적격50을 유지하고 raw variant/alias144, attempt301, costs303행이 됐다.

모든 새 시도와 비용행은 `phase=resume_audit`다. 측정 GET10회는 최소12 exchanges, 실패1, 수신5,951,115 bytes, full-body 저장0, 경과합57.063329초다. 별도 미계측25행은 웹 동작24개와 로컬 import 실패1개다. 이 웹 동작의 transport/cache 요청수·bytes·경과는 알 수 없어 GET나0-byte 요청으로 바꾸지 않았다. 이후 같은 원문을 이미 열었더라도 서로 다른 도구의 실패는 성공으로 소급하지 않았다.

완료된 실험의 `evidence/cost-summary.json`은 **216 GET 범위와 파일 hash를 그대로 유지**한다. 별도 [resume-cost-summary.json](../../evidence/resume-cost-summary.json)에 재개phase와 결합 실측값을 둔다. 결합 실측은226 GET·248 최소 exchanges·14실패·263,036,195 수신bytes·257,085,080 임시full-body 저장bytes·2004.155345초다. 재개 phase의0 저장bytes는 full raw response를 남기지 않았다는 뜻이며 발췌/원장 저장까지0이라는 뜻이 아니다. 이 재열람은 C1/C2의 두 번째 과업 실험이 아니므로 기존 모의 비교가 실제 재생으로 바뀌지 않는다.

CX-G02의 현재 canonical `read_location`은 **§1 Overview of main changes, web87–90**으로 정정했다. 틀렸던 Main points/About this release 표현과 기존 원문 variant는 보존하고 `read_location_correction`에 전후값·이유·근거를 넣었다. 수정은 위치 이름에 한정되며 2023경계를 쓴다는 결론·원문 최소수는 같다. [resume-integration-applied.json](resume-integration-applied.json)에 모든 조인·보존 확인을 기록했다.

RESULT의 첫 세 표는 정확한 요구 header를 가지며, 현재 표 행 수는12/14/18, 마지막 약점표는 정확히3행이다. 표3의 사례12행 모두에서 GET·실패·bytes·경과합·C1/C2 직렬화bytes를 직접 재계산해 일치시켰다. 포함된 ID가 제외 ID로 오해되지 않도록 표2의 마지막 열 표기를 명료하게 하고, 표3의 마지막 열에는 한계의 반복 대신 실제 다음 자료를 쓰도록 부모에게 전달했다. 이 감사는 RESULT 본문을 수정하지 않았다.

```sh
python -B docs/workstreams/research/AF-RES-036/review/resume-quant/verify_ledgers.py --receipt audit-final.json
```

이 명령은 입력을 읽고 자기 경로의 감사 영수증만 쓴다. `reconcile_ledgers.py --apply`는 `before/` 입력에서 생성하므로 이후 더해진 새로운 원장을 덮어쓸 수 있다. 이번 정정의 재현용으로만 보존하며 향후 추가 기록 이후에는 그대로 다시 실행하지 않는다. 기존 `scripts/assemble_ledgers.py` 역시 기준판정 원장을 읽지 않으므로 다시 실행하면 이번 추가분을 떨어뜨린다.
