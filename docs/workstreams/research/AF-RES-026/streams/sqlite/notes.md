# SQLite 계열 T0 봉인 메모

## 모집 원장과 직접 읽은 범위

최초 규칙 `cecbfb981b9a7ccfd59f7bc40a23445a19d020fa` 뒤에 조사했다. SQLite 공식 `timeline`의 과거 날짜 쿼리는 browser verification 또는 접근 실패였고 RSS의 b 매개변수는 과거 창을 반환하지 않았다. 접근제한을 해제하지 않고, 같은 공식 서비스의 공개 `thisdayinhistory?today=2026-01-DD`를 대체 원장으로 사용했다. 2022-01-01부터 09일까지의 **metadata**를 날짜순으로 읽어 Post와 Edit/Reply를 구별했다. `ledger-metadata.json`은 본문 없이 그 metadata와 읽은 UTC/렌더링 SHA를 보존한다. 2022 section의 Post를 모았고, 제목만으로 success 상태를 선별하지 않았다.

처음 21개 root의 원판 전문을 열어 13개를 제외하고 8개를 선택했다. 마지막 선정은 2022-01-06 06:14:34.072Z의 S08이다. 1월6일 이후 21개 root는 목록만 이미 봤으므로 상한 뒤 미심사로 frame에 남겼다. 제목에 bug가 있다는 이유만으로 제외하지 않았다. S03은 타입과 view를 바꾸는 구체 migration 목표가 있어 포함했다. 순수 fuzzing PoC/패치 제안/문서편집 요청/발표/프로젝트 수용 정책은 사용자 지원의 부분 설계 질문이 없어 제외했다. 이 운영적 경계 자체에 편집자 판단이 있으므로 모집단의 발생률은 추정하지 않는다.

각 root는 `/raw/<artifact>`의 W byte 영역 전체를 읽었다. 원본 전체는 저장하지 않았다. raw SHA3-256이 Fossil의 artifact ID와 일치하고 본문 SHA-256, D UTC 시각, U 계정, root의 parent 부재를 기록했다. 정확한 phrase 위치는 `body-locations.json`에 있다. 첫 reply의 본문은 수집 프로그램 안에서 버리고 D/G/I/U header만 판독자에게 출력했다. 이는 후속 **본문을 읽은 것과 다르다**. 각 selected root가 첫 reply 이전임을 확인했다. 실제 수신 시각을 클라이언트 wall clock으로 치환하지 않았다.

## 노출 예외와 선후 통제

초기 검색에서 S01 ATTACH 스레드의 답 한 문장이 검색 결과 ref 줄에 섞여 출력되었다. 내용은 open_v2 오류검사와 ATTACH 오류검사를 구별하라는 것이었다. 해당 검색 URL은 `https://sqlite.org/forum/forumpost/76963f0026b6b12a`. 해결 전체·작성자 후속은 아직 읽지 않았지만 이 노출을 무시할 수 없어 **S01은 엄격한 사전/사후 비교에서 제외**했다. 원판 자체의 확정 여부는 별개로 confirmed이다. 대체 성공 사례로 교체하지 않았다.

`forumpost/d5ac4dc797?t=s&unf`는 초기원판 대신 00:53:57 수정본을 보여줬다. 수정도 첫 답 02:54:03 이전이었다. 이후 직접 읽은 raw의 00:49:41 원판을 T0로 삼고 두 판을 혼동하지 않았다. 다른 7건은 후속 본문을 보지 않았다. timeline에 답의 존재/시각/제목은 보이지만 답의 내용·수락·성공은 표집 기준이 아니다.

I/C/Q 24메시지는 모두 한국어 300자 이하이며 실제로 작성자에게 전송하지 않은 연구자 문구다. 문서 링크의 tag URL은 메시지 길이를 위한 표현이고, sources의 동일 파일은 관측한 full commit에 고정되어 있다. 후보 최대2와 같은 source 집합을 I/C/Q에 적용했다. S07은 질문자가 이미 autovacuum을 말했는데 regular VACUUM과 VACUUM FULL을 다시 묻는 불필요 질문 반례로 보존했다. 처음에는 SQLite FULL/INCREMENTAL 변수 초안을 썼지만 C의 분기와 일치하지 않아 **후속 열람/첫 봉인 전**에 PG 작업 종류로 정렬했다. T1 결과를 보고 바꾼 것이 아니다.

## T0의 주요 경계

- S01·S02·S07·S08은 입력에 있는 사실을 다시 묻는 질문의 반례 후보다.
- S03의 OFF는 예제 설정이며 변경 금지가 아니다. view는 이미 교체 예정이어서 안전한 일차 제안은 변수 답과 무관할 수 있다.
- S04의 rowid 출력은 COMMIT 영수증이 아니다. S05는 같은 연결 접근이 이미 명시되었고 실제 threading mode가 비어 있다. 성능 희망을 안전성 필수조건으로 바꾸지 않았다.
- S06은 소스 형태를 알아도 정확한 버전이 더 필요할 수 있다. 한 질문으로 모든 불확실성이 해결된다고 쓰지 않았다. 작성자의 “여러 빌드 시스템을 쓰는 이유는 묻지 말라”는 제한도 보존했다.
- S08의 parameter 바인딩 수정은 NOT NULL 열의 값 제공까지 자동 해결하지 않는다.

## 직접 열었지만 최소수에 더하지 않은 자료

`sources.json`은 selected8, 당시 제공자 문서/테스트8, 구현·같은 문서판4, 제외 원문13, 일별 원장9, 수집 도움말1을 구별한다. 실제 최소수는16이다. S-D07/S-D08은 코드파일에 들어 있는 공급자의 설계/설정 설명으로 분류했으므로 더 엄격히 “독립 매뉴얼/테스트만”을 세는 민감도에서는2개를 빼고14를 보고할 수 있다. 공급자 구현 S-D02/S-D05/S-D09와 중복 API판 S-D06은 보수적으로 최소수 밖에 두었다.

탐색 중 현재 PostgreSQL14 웹 문서를 읽었지만, 해당 주장에는 REL_14_1 `maintenance.sgml`의 정확한 당시 문구를 다시 읽어 사용했다. `test/alter.test`(3.34.0)는 view에 ALTER 자체를 적용하는 다른 테스트라 S03의 근거로 쓰지 않았다. `test/alterlegacy.test`는 legacy 설정/실패 사례를 훑었으나 최종 근거는 altertab.test와 alter.c로 제한했다. `src/pragma.c`의 auto/incremental/synchronous 분기는 읽었으나 최종 S07 후보는 PG regular/FULL 비교로 정렬해 더하지 않았다. `test/attach.test`에서 실제 생성-flag 경계 테스트를 찾지 못해 근거로 쓰지 않았다. `test/inserting.test.js`는404였고 대신 node-sqlite3 v5.0.2 README Usage를 읽었다. 전체파일을 다운로드했어도 본문을 판독자에게 출력하지 않은 파일은 직접 원문 수로 세지 않았다.

## 다음 행동

원격 봉인 전 root의 정합성 검토에 따라 S06 C 문구를 Q와 같은 amalgamation/split-source 변수로 정렬했다. 같은 후보·판·원문을 유지했고 다른 7사례의 메시지는 바꾸지 않았다. `pre-freeze-revisions.json`에 전후 문구·UTC·범위가 있다. 정확한 설치판이 여전히 없어 경로 제안만 가능하며 컴파일 성공으로 올리지 않는다.

root가 계열 묶음을 커밋한 뒤 원격 고정판을 확인한다. **24건 전체 봉인을 root가 통지하기 전까지 후속 본문은 열지 않는다.** 그 뒤 30일 창의 실제 reply/작성자 발화와 90일 구현을 읽고, 후보/변수/원판을 바꾸지 않은 채 T1을 별도 파일로 기록한다. 이 작성자는 자기 계열의 T0/T1을 모두 맡으며 독립 중복 코더가 아니다.
