# C 계열 T1 판독 및 반증 기록

## 봉인과 접근 순서

T0 C 묶음은 `682b77f015e63ce05d6b6c2fcdc6348052c6d472`, 전체 24건 봉인은 `68fc97fadceb46f9945a71fcc53730e29f6c62bf`다. 통합자가 exact-SHA 원격 확인을 알린 뒤 2026-11-22 05:08:38 UTC에 T1 열람을 시작했다(`t1-receipt.json`). 최초판·문구·후보는 수정하지 않았다. C01 재판독은 `t0-corrections.json`으로 남겼으며 정보 이득으로 세지 않는다. T0/T1은 같은 연구자가 판독했고 통합자의 이견 검토가 있었을 뿐, 가림 독립 판독이 아니다.

원본 메일 전문은 T0에, 후속은 봉인 후에 직접 읽었다. 공개 HTML의 Message-ID, Date, isoreceived, 본문 SHA256, 응답 링크를 `root-metadata.json` 및 `t1-message-metadata.json`에 기록한다. 본문 원문 전체는 저장하지 않고 위치·짧은 요약만 둔다. 원본 raw MIME의 서명/배달 헤더 전체와 메일 자체의 Git 보존은 확인하지 못했다. 공식 Hypermail 보존판이라는 범위에서 최초판을 확정한다.

C05에서 [작성자의 0037](https://curl.se/mail/archive-2022-01/0037.html)은 빈 임시 디렉터리를 쓰며 적절한 파일명이면 move/rename한다고 밝힌다. **필요시 rename한다는 기존 사실은 직접 읽었지만 basename 보존 필수성의 완전한 yes/no는 명시되지 않았다.** 엄격 Q 값 회수는 0/8, 이 문장을 보존 불필요로 넓게 해석하는 민감도는 1/8이다. 이 부분값이 경로제거 또는 고정 `-o`의 기술적 적합성을 바꾸지는 않았다. 이 해석 차이를 숨기지 않고 `q_value_partial`에 남겼다.

C01의 `C01-R2=unknown`은 판독 오류다. 원문에 브라우저를 적어 놓고도 연구자가 curl 재현이라는 갈림을 만들었다. 후속 답에서 깨달았다고 새 사실 획득으로 세면 질문의 가치를 부풀린다. 통합자의 봉인 전 이견과 본 실행의 자기 보정을 모두 기록하되 봉인 문구는 그대로 둔다.

## 실제 조건부 답과 진전의 범위

C05 [첫 실제 답 0033](https://curl.se/mail/archive-2022-01/0033.html)은 경로 제거와 저장 위치를 설명하고, Content-Disposition이 없으면 `-O`의 URL 기반 이름이 쓰인다는 조건을 알려 준다. 추가 질문은 0회다. 작성자는 [0037](https://curl.se/mail/archive-2022-01/0037.html)에서 설명이 충분하다고 수용하고 기존 workflow를 밝힌다. **조건부 설명 뒤 결정 수용이 관측된 사례이며, 새 구현이 해결됐다는 사례는 아니다.** 첫 답에 기술 문서 링크는 없었다. 공급자는 그 뒤 [0038](https://curl.se/mail/archive-2022-01/0038.html)에서 문서 수정과 링크를 알렸다. [문서 수정 커밋 a6f2272](https://github.com/curl/curl/commit/a6f227252cfc80c7c44be395f5a6952221313b74)는 root를 직접 참조하고 경로/저장 위치 설명을 추가한다. 기존 기능이 바뀐 diff는 아니다.

C03은 [7.55.1 progress.c](https://github.com/curl/curl/blob/8839c05fba1f8415eec17eff8ac60cc3a50eb51e/lib/progress.c)의 `Curl_pgrsUpdate` 평균 분모와 [progress-bar.d](https://github.com/curl/curl/blob/8839c05fba1f8415eec17eff8ac60cc3a50eb51e/docs/cmdline-opts/progress-bar.d)의 진행량 설명을 연결하면 원 글의 동작 질문에 답할 수 있다. [실제 첫 답](https://curl.se/mail/archive-2022-01/0026.html)도 타이머 분리가 없다고 확인한다. 작성자 후속은 없어 재현·수정·성공은 미확인이다.

C02 [0062](https://curl.se/mail/archive-2022-01/0062.html)·[0063](https://curl.se/mail/archive-2022-01/0063.html)의 감사는 두 번의 실행 성공으로 세지 않았다. C01의 빈 cookiejar 보고도 frozen 후보 `-v`의 실패가 아니라 다른 시도 `-c`의 실패이며 발생 시점도 확정하지 못한다.

## JSON의 후속 개발과 소급 오류

C06은 질문자와 공급자가 동일한 공개 계정/인물 역할이다. [1월21일 0060](https://curl.se/mail/archive-2022-01/0060.html)에서 직접 PR8314를 만들었다고 알렸고, [2월1일 32160cae](https://github.com/curl/curl/commit/32160cae847b4e42d52edb033615f88b12ce5c05)의 diff와 test383–386을 직접 읽었다. `--json`은 준비된 데이터의 전송과 헤더를 묶는 옵션이며 `--jp` 생성 구현은 그 diff에 없다. 이 커밋의 파일 입력은 binary 경로이며 최초 문서/블로그의 `--data` 표기는 구현과 세부가 다르므로 원 코드/테스트가 기술 해석 우선이다. 테스트 **본문을 읽었으며 이 실행에서 테스트를 돌리지는 않았다.**

[2월5일 0012](https://curl.se/mail/archive-2022-02/0012.html)에서 작성자는 `--json`에 parsing 복잡성을 넣지 않았고 가능한 미래 `--jp`로 남긴다고 설명한다. 이는 구현 후의 범위 선택이다. 첫 글과 당시 wiki는 두 안을 모두 검토했으므로, 생성이 처음부터 필수/불필요였다는 답으로 소급하지 않는다. 이 개발행동은 별도 90일 열에 두고, 후속 부재를 포함한 8건의 T0/T1 후보 판정과 섞지 않는다.

반대 방향도 직접 찾았다. [1월20일 0048](https://curl.se/mail/archive-2022-01/0048.html)은 제3자가 응답 parsing까지 추가하자고 했고, [0059](https://curl.se/mail/archive-2022-01/0059.html)는 HTTP metadata로 응답을 감싸자고 제안했다. 원 wiki가 특별 응답 처리를 제안하지 않았다는 사실을 금지로 읽지 않았고, 이 제3자 요구를 T0 필수로 승격하지도 않았다. 소급하면 당시 A/B 둘 다 부당하게 탈락한다. [2월5일 0011](https://curl.se/mail/archive-2022-02/0011.html)의 자동 배열화 제안과 [2월6일 0014](https://curl.se/mail/archive-2022-02/0014.html)의 기존 API 소비자 관점 반론은 같은 기능이라도 공급자 문법 편의와 사용자의 서버 제약이 다를 수 있음을 보여 준다. 채택 효과의 크기로 환산하지 않는다.

## 비용, 검열, 인접 사례

추가 목적 질문→작성자 답으로 세면 C07의 [0058](https://curl.se/mail/archive-2022-01/0058.html)→[0061](https://curl.se/mail/archive-2022-01/0061.html) 한 쌍이 있고 기다림은 서버 시각 기준 10.973시간이다. localhost 기능의 대상 관련성을 물은 뒤 개발자 사용자 대상이라는 답이 왔다. 이것은 frozen Q와 다른 변수이며, 엄격히 기술 입력을 추가로 요청한 쌍만 세면 0건이다. C04의 실제 추가 문자 질문은 답이 없어 root+30일에서 우측 검열한다. C06 구현 후 결합 이유의 질문→답은 90일 개발 열에 따로 둔다.

가상 I/C의 발송상 추가 왕복은 0, 가상 Q는 답한다는 조건 아래 최소 1이다. 실제로 이 문구를 보낸 적이 없으므로 공개 스레드의 응답 지연을 가상 Q의 비용으로 대입할 수 없다. 링크 수와 연구자가 연 고유 메일 페이지 수는 대리 비용이며 사용자 클릭 수가 아니다. 같은 페이지를 여러 번 여는 재시도 총횟수는 정확히 저장되지 않아 미확인으로 남긴다.

후속 탐색은 원 root의 Reply/In-Reply-To 계보 및 [2월](https://curl.se/mail/archive-2022-02/)·[3월](https://curl.se/mail/archive-2022-03/)·[4월](https://curl.se/mail/archive-2022-04/) 원장의 제목·발신자·기능 범위다. 다른 제목으로 생긴 모든 대화·GitHub 전역·삭제 자료의 완전한 회수는 보장하지 않는다. 주 스레드 30개 후속 메일, 관련/인접 15개 메일을 직접 읽었으며, 인접 번호를 열다가 JSON과 무관한 SSH 질문/답 2개도 읽었다. 이 둘은 `C-X0215/16`으로 범위 밖 탐색에 남겼다. 0015의 UTF-8 가정 파싱 실패는 web reader로 본문 접근을 회복했다. 원자료 삭제로 코딩하지 않는다.

C05와 같은 표시 작성자의 [2월15일 별도 root](https://curl.se/mail/archive-2022-02/0024.html)는 `time-cond`와 `dump-header`에 확정 파일명을 쓰려는 요구다. January root와 In-Reply-To 연결이 없어 새 요구가 생긴 동일 구현이라고 확정하지 않는다. 이 별도 스레드에서는 [--head 제안](https://curl.se/mail/archive-2022-02/0027.html)을 [작성자의 옵션 충돌 보고](https://curl.se/mail/archive-2022-02/0028.html)가 반박한다. 실제 추천 충돌이라는 보조 반례는 있지만 이를 고정 8건의 오승인 분자로 몰래 편입하지 않는다. C08과 같은 bruce의 [2월25일 DOM 질문](https://curl.se/mail/archive-2022-02/0048.html)도 30일 밖이며 원 Fetch404와 명시 연결이 없다.

## 재현과 통합에 필요한 주의

`python docs/workstreams/research/AF-RES-026/streams/curl/build_t1.py`는 보존된 metadata와 판독 코딩에서 T1 산출물만 다시 만든다. 네트워크 원문을 재조회하려면 `harvest_t1.py`에 `followups.csv`의 개별 URL을 전달한다. 이 도구는 metadata/본문 해시만 저장하고 전문은 출력한다. UTF-8 이외 메일은 현재 parser 한계가 있어 web reader 또는 명시 charset 디코딩이 필요하다. 역사 코드 테스트 실행은 이 연구가 주장한 검증에 포함되지 않는다.

`judgments.csv`의 supported는 해당 후보의 **명시한 제한적 사용/설명**과 조건의 관계다. `hold` 문구가 정확하다는 것과 근거 있는 사용 승인은 다르다. frozen I에서 사용을 무조건 승인한 것은 없으며, C의 조건부 사용 설명도 실제 사용 조건 충족과 같은 수로 세지 않는다. 100행은 8건의 두 시점×후보×조건이며 100개의 독립 관측이 아니다. C08의 후보 NONE 행은 후보가 없어도 원 질문이 남도록 한 것이다.

집계는 `t1-summary.json`, 사례 상세는 `case-analysis.jsonl`에 있다. Q 직접 답 분모가 0이면 해당 없음이며 0% 성공률이 아니다. C05 결정 수용과 C06 공급자 개발을 합친 진전 보고는 2/8, 새 개발행동만은 1/8, 외부 사용자가 제안된 기존 기능을 새로 실행해 성공했다고 확인한 것은 0/8이다. 세 값의 의미가 다르다. 최초판에 이미 있는 Q 변수는 C01/C03/C07의 3/8이며, 새 적격 작성자 사실로 같은 후보의 기술판정이 바뀐 것은 0/8이다.

8개 root는 8명의 독립 사용자나 8개 독립 구현이 아니다. C01/C04/C08은 같은 공개 발신자 bruce이고 C01/C08은 browser-extension 맥락도 겹치지만 같은 구현이라는 명시는 없다. 이 둘 또는 bruce 3건을 묶는 민감도는 가능하다. C06/C07은 같은 공급자 겸 질문자로서 별도 제외 분모가 필요하다. 원 root는 교체하지 않는다.
