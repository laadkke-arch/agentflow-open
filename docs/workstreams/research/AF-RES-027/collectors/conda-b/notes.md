# conda-forge 보조 B · 공식 원장 3회 역추적

## 상태·범위

3/3 사전 지정 원장 조사를 완료했다. A 봉인 `1714a55a529c7da42596ac0779d398f3aacf97c3`의 원격 재열람이 2026-11-22 05:05:37 UTC에 확인된 뒤 시작했다. 이 파일은 같은 표시 모델의 별도 수집·판독 결과이며 외부 독립 검토가 아니다. A 분모에 더하는 참조·성공·지연은 **0개**다.

각 원장의 2019–2023년 첫 관련 주 브랜치 변화를 선택했다. 제안 브랜치 이력과 first-parent 병합 이력을 함께 대조했고, 실제 업로드는 Anaconda 배포 API 및 작은 패키지 아카이브로 확인했다. 현재 API의 업로드 필드는 과거 배포 호스트의 기록이지만, 현재 label이 과거에도 같았는지나 당시 solver가 그 빌드를 고른 사실까지 증명하지 않는다.

`sources.json` 30행 가운데 보수적으로 최소수에 넣은 원문 묶음은 20개다: 상류 9, 과거 소비자 판 3, 후속 소비자 원문 8. 같은 편집의 PR·diff·불변 파일과 같은 소비자 커밋의 호출 파일은 `related_original_urls`로 묶고 한 번만 센다. 39개 고정 blob의 해시·크기·행 수는 `git-object-receipts.json`에 있다. 직접 읽은 위치는 sources의 `directly_read_location`에 별도로 적었으므로 해시 계산이 전체 내용을 의미적으로 읽었다는 뜻은 아니다. 사례·부수 사건 수와 원문 수는 구별한다.

## B-C01 · 이름이 달라진 대상과 소비자 패키지는 다르다

BC-S01의 전후 recipe는 최상위 `package.name`을 `matplotlib-split`에서 `matplotlib-base`로 바꾸지만, 산출물 `matplotlib`, `matplotlib-base`, `mpl_sample_data`는 유지한다. 2018년 분리는 조사 범위 경계를 확인하는 자료로만 남겼다. 선택한 2019년 Linux 배포 영수증은 실제 `matplotlib` 메타패키지가 본체를 정확한 빌드로 요구함을 보여 준다. 이 명명 관계를 `NAME_ONLY_FOR_CONSUMER_REFERENCE`로 분류했으며, NumPy 요구 조건 등 다른 빌드 변화가 전혀 없었다는 뜻은 아니다. [상류 병합](https://github.com/conda-forge/matplotlib-feedstock/commit/08bc9282bb815e646617b28a94c85b6bc9ac31d3), [배포 원장](https://api.anaconda.org/release/conda-forge/matplotlib/3.0.2).

Xarray의 선택 참조는 문서 환경이다. RTD가 파일을 가리키고 같은 판의 Sphinx 설정이 Matplotlib를 호출한다(BC-S03). 첫 후속 주 브랜치 판도 그 참조를 갖는다(BC-S04). 그러나 2019년 10월 환경 정리에서 직접 명시가 없어졌다(BC-S05). 365일 끝의 새 환경 파일에도 직접 명시가 없다(BC-S06). 간접 의존성으로 설치됐을 가능성은 이번 실행으로 검증하지 않았다. 따라서 “미수정 상태로 계속 사용했다”도 “상류 이름 변경을 바로잡았다”도 판정하지 않는다.

반증을 위해 같은 프로젝트의 나중 변경도 봤다. 2020년 `matplotlib-base` 전환은 시험 환경 최적화다(BC-S07). 문서 환경의 같은 참조가 그때 고쳐졌다는 증거로 가져오면 단위가 바뀐다. 현재 Pixi 문서 환경은 `viz`의 **버전 상한·하한 없는** `matplotlib-base`를 포함한다. 같은 파일의 3.10.*는 별도 최소 버전 시험 feature이며 문서 환경에 적용되지 않는다(BC-S08). 주소와 프로젝트명만 보관하면 이 차이를 복원하기 어렵다.

대안 후보 NCAR/wrf-python도 과거·현재 원문을 열었다(BC-S09). 현재 개발 환경에는 명시적 채널과 Matplotlib가 있지만, 조사한 과거 설치 문서의 선택 의존성을 그 환경 파일의 과거판으로 연결할 수 없어 날짜 사슬에서 제외했다.

## B-C02 · 분리가 있어도 CLI 참조는 그대로 맞을 수 있다

BC-S10의 출력 분리는 라이브러리를 새 이름으로 분리하면서 mamba CLI 이름을 보존한다. BC-S11에서 41,864바이트 실제 배포 아카이브의 파일 목록과 의존성을 직접 읽었다. 선택 Linux CPython 빌드의 업로드는 2021-11-18 16:30:03.576 UTC다. 최초 PyPy 빌드는 이보다 약 9초 이르므로 보편적인 첫 시행 시각으로 합치지 않았다.

Snakemake의 옛 문서는 conda-forge에서 mamba를 설치한 뒤 CLI로 환경을 만든다(BC-S12). 첫 후속 주 브랜치와 창 말 v7.18.2의 공개 소스에도 명령이 남는다(BC-S13–14). 공급자 산출물 계약과 소비자 요구가 맞는다는 근거이며, 당시 모든 플랫폼에서 설치가 성공했다는 직접 실행 결과는 아니다. 의도적인 역사 보존이라고 말할 근거도 없다.

반대 역할의 소비자인 conda-libmamba-solver에서는 초기 수입 코드가 `libmambapy`를 사용하고 mamba 자체를 import하지 말라고 명시한다(BC-S16). 그러나 저장소 이력이 2022년부터이고 코드는 `conda/conda`에서 왔다. 최초 관측 전에 이미 바뀌었으므로 정정 지연을 알 수 없다. CLI와 API를 주소 하나로 통합해 후계명을 추천하면 두 목적에 같은 답을 줄 수 없다.

## B-C03 · 우회 수정 뒤 옛 이름으로 복귀

공식 2022-04-23 공지는 구성요소의 공개와 `qt` 메타패키지 전환 계획을 말한다(BC-S18). 실제 선택 Linux `qt` 5.15.2 업로드는 6월 2일이다(BC-S19). 따라서 4월 공지를 `qt` wrapper의 배포 시각으로 대신하지 않았다.

QtPy의 원래 고정판은 이전 Qt 버전도 시험한다(BC-S20). 12월의 Python 3.11 추가는 요구가 달라진 새 CI 행이다. 그 행에서 개발자는 solver 충돌을 직접 보고하고 구성요소별 설치가 해결된다고 적었다(BC-S21–22). 같은 보고를 상류 이슈에 옮긴 BC-S23은 독립 실패 한 건을 늘리지 않는다. 보고된 개발 CI 실패는 확인되지만, 실제 사용자 오추천 피해는 미확인이다.

상류가 Qt 5.15.6 wrapper의 WebEngine 판 제약을 완화한 뒤(BC-S24–25), 소비자는 이유를 명시하고 `qt`로 돌아온다(BC-S26). 이는 후계 구성요소를 알고도 기존 이름을 선택하는 사례다. 별도 보조 목적 `B-C03-R2`에서는 동일 Python 3.11 용도의 **상류 수정 업로드 → 소비자 소스 수정**을 좁게 계산할 수 있다.

| 보조 시간 쌍 | 결과 | 해석 범위 |
| --- | --- | --- |
| Linux 수정 패키지 업로드 2023-01-12 15:27:37.161 → 복귀 소스 커밋 20:55:58 | 19,700.839초, 약 5.47시간 | 소스 수정까지의 간격. 실제 CI 적용이나 전체 전파율이 아니다. |
| 같은 업로드 → 주 브랜치 병합 2023-01-13 15:33:04 | 86,726.839초, 약 24.09시간 | 제안 커밋과 병합을 구별한 소스 통합 간격. |
| 복귀 소스 커밋 → 최초 확인한 공개 소스 릴리스 v2.3.1 | 6,487,807초, 약 75.09일 | 태그의 CI 파일에 최종 `qt` 참조가 실린 기간. CI 실행 배포 지연으로 쓰지 않는다. |

v2.3.1 릴리스는 2023-03-28 23:06:05 UTC이며 두 변경을 함께 안내한다(BC-S27). 실제 태그 파일에는 이미 되돌린 `qt`가 있다. 따라서 커밋 ancestry에 우회 수정이 있다는 이유만으로 우회가 소비자 릴리스에 실렸다고 말할 수 없다. 복귀와 창 말 파일은 여전히 그 이름을 쓴다(BC-S28).

당시 CI 실행 URL은 404이고, 두 병합 SHA의 현재 Actions 조회도 0행이다(BC-S30). 이는 보존·조회 실패이며 과거 실행이 0건이라는 뜻이 아니다. QtPy와 feedstock에는 공통 유지관리자가 있어, 별도 소비자 프로젝트라는 사실을 인적 계보의 독립성으로 바꾸지 않았다. CQ-editor 대안 후보는 PyQt 참조여서 직접 Qt 패키지 사슬에서 제외했다(BC-S29).

## 기록 단계 비교·재현

주소만 있으면 recipe 최상위 이름과 소비자 산출물 이름, mamba CLI와 Python API, Qt 5.12와 Python 3.11/Qt 5.15 시험을 가를 수 없다. 패키지·버전·호출 목적을 더하면 변경 필요성의 일부를 판정할 수 있다. 당시 파일과 이력·업로드·소스 릴리스까지 더해야 참조 폐기, 목적 변화, 우회와 복귀, 실제 배포 미확인을 구분한다. 원래 사건의 범위를 넘어 숫자를 채울 수는 없다.

분석은 코드 설치·실행 없이 공개 문서, Git 객체, 배포 아카이브의 metadata/files만 읽었다. 사람이 걸린 시간이나 운영 기록 비용을 측정하지 않았다. 수집 링크 수와 파일 크기는 영수증에서 셀 수 있지만 효율 실험이나 독립 맹검 측정이 아니다.

원장 재현은 해당 공개 저장소를 새 임시 위치에 clone한 다음 다음 읽기 명령으로 한다. 현재 작업용 bare clone은 인계 전에 제거했다.

```text
git log HEAD --first-parent --reverse --format='%H %cI %s' -- recipe/meta.yaml
git show <case의 before_commit>:recipe/meta.yaml
git diff <before_commit> <after_commit> -- recipe/meta.yaml
git log --follow --format='%H %cI %s' -- <consumer path>
git show <source 또는 window_snapshot SHA>:<consumer path>
```

Qt CI 재개에는 [실행 3718737526](https://github.com/spyder-ide/qtpy/actions/runs/3718737526), job 6307127310의 보존 로그, 사용된 conda 판·플랫폼, 당시 채널 repodata가 먼저 필요하다. 보고자가 적은 재현 명령은 `conda create -n test-env python=3.11 pyqt=5.15 qt=5.15`이며, 비교 입력은 `python=3.11 pyqt=5.15.7 qt-main=5.15.6 qt-webengine=5.15.4`다. **현행 채널로 실행하면 2022년 실패를 재현하는 검사가 아니다.** 복구한 원래 환경 정보와 동시대 불변 repodata를 고정한 뒤 동일 conda 판으로 실행해야 한다. 현재 원문으로 부족한 부분을 검증 완료로 표시하지 않는다.
