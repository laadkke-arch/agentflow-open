## Q4: 남은 기록과 남은 화면의 구분

지도18단어가 말하는 것은 흔적의 존속이고, 정정 이후 모든 후속 편집의 존속은 아니다. RESULT는 더 강한 Clean/dirty 설명을 창 밖 원문 지식으로 표시하고, Casablanca의 v12 access 제거와 v13 name:fr 추가를 다른 작성자/사건으로 구분한다. name:fr 제거를 '다른 사람의 독립 문장 삭제'로 바꾸지 않았고, v15=v10의 외형으로 v12의 선택적 보존을 입증하지 않은 점이 정확하다.

Payap는 같은 객체ID의 v1/v3 상태 복원과295객체 ID 집합 일치만 확인한 범위를 유지한다. 한 객체의 상태 일치를295객체 모두의 지리적 타당성 또는 뒤 변경 보존의 성공으로 일반화하지 않는다.

회계22단어의 원거래+역분개 존속은 현재 잔액 효과의 상쇄와 다르다. RESULT는 원거래의 완전 불변성도 주장하지 않고, GnuCash의 수정·삭제와 reverse의 메타데이터 변경을 반례로 든다. 감사 기록의 존속을 화면 텍스트의 존속으로 옮기면 사용자 목표가 바뀐다고 명시한 점이 적절하다. 2017 대사 보고는 수치 원장 없는 작성자 진술임을 유지하므로 엔진 결함 판정으로 과장하지 않는다.

## Q5/Q7: 무엇을 실제로 더 예측했는가

D18/D22는 origin·group·GC·private stack·undoInputRule·closeHistory의 구현 규칙을 제공하지 않는다. RESULT는 정확 조작 선택의 근거를 API/고정 구현에 두고 donor는 보존 변인을 다시 묻는 참고로 제한한다. root의 D 초안이 교정 E보다 먼저였다는 시간 사실과, 한 모델이 전체 자료를 알고 있었다는 한계가 함께 적혔다. PT1 선노출이나 YN2 본문 기대값을 새 적중으로 계산하지 않는다.

원래 구현 선택 질문에는 제품 API/수정 링크를, 목표 명세 질문에는 지도/회계 참고 링크를 반환하는 구분은 현재 원장에 합당한 **설계 해석**이다. 다만 질문이 실제 사용자에게 얼마나 유용했는지나 사람이 더 정확히 예측했는지는 측정하지 않았으므로, 문장 수준에서도 실증된 효과처럼 표현하지 않는 것이 좋다.

## 전달한 수정 사항

1. **기존 오기:** 마지막 약점의 '자연6자리'는 총6자리/자연4자리로 고쳐야 한다. root가 이미 인지한 항목이다.
2. **효과 표현:** Q7의 '이번 자료가 입증한 것은 그런 질문의 유용한 구분'은 '이번 자료에서 확인한 것은 서로 다른 보존 변인의 구분'처럼 쓰면 인간 질문 효용을 측정했다는 오해를 줄인다. 이 수정은 결론을 바꾸지 않는다.
3. **비교 단위 표현:** Q5 첫 문장의 '18행은 같은 초기 상태...'를 '각 자리의 세 보기는 같은 초기 상태...'로 고치면 서로 다른 여섯 사례가 같은 초기 문서를 쓴다는 오해를 막는다.
4. **자료군별 한계 문맥:** final-counts의 limits 문구 일부가 일반 템플릿처럼 반복된다. 예컨대 request와 fix 항목의 D14 설명, 원논문 항목의 API 판 설명은 각각 맞는 자료군으로 옮기거나 해당 항목의 제한으로 대체하면 된다. 숫자와 배당은 맞다.
5. **선택적 인용 보강:** Q4의 GnuCash 수정·삭제 문장은 [6.6 Editing](https://www.gnucash.org/docs/v5/C/gnucash-manual/trans-edit.html)·[6.7 Deleting](https://www.gnucash.org/docs/v5/C/gnucash-manual/trans-delete.html)을 바로 연결하면 D09의 반대 근거를 더 직접 추적할 수 있다. 해당 근거는 donor 원장에 이미 있다.

이 다섯 항목 외에 추가 연구를 요구하지 않는다. 검토 이후 root가 고친 내용은 그 실제 파일/커밋으로 기록하면 된다. 본 검토는 main 파일·봉인 카드·예측을 수정하지 않았으며 최종 계약 검사·원격 SHA readback을 대신하지 않는다.
