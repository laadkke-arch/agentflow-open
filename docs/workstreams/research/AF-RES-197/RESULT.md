## Q1~Q7 답과 결손
**Q1. 동사와 초기 예제.** 고정 세 사건의 UI 동사는 모두 확인했다. M1 2면 select all, M2 동일 filter 순회, M3 page header만; 실제 일괄 동사는 M04의 edit/download/status/invoice로 뒤늦게 드러났다. M04의 파일 3/1은 실제 산출물이 아니다. TanStack T01은 데이터 회수 목적, T03은 상위 callback의 선택 객체 전달이라는 경계 사례다. 적격 순서로 세 자연 사건을 확정하지 못했으므로 3/3이라고 말하지 않는다. M1~M3 original opening revision까지 복원하지 못했으며 현재 열리는 body로 최초 판정을 저장했다. M1/M2/M3 sandbox 본문 접근 실패 X05-X07. [requests.csv](requests.csv), [frame.csv](frame.csv).

**Q2. 분모.** P(현재 면에서 조작할 후보), V(방문한 면 중 직접 선택한 ID들), F(현재 필터 일치 서버 전체), U(원본 전체), ?(미지정)를 분리한다. M01/M03 P 조작 대 M02 V 보존은 동일 개념이 아니라 조작 범위와 누적 대상이다. M2는 F 전체 선택이 아니라 직접 체크한 페이지. T08 보강은 명시적 global intent지만 filter universe 미확정. T07과 T13 같은 작성자/동일 예제는 한 사건으로 묶었다. 전체 모집은 불완전. 저자 의도와 maintainer 구현 설명이 다른 경우 모두 남긴다. [M05](https://github.com/mui/mui-x/issues/14074#issuecomment-2268112115), [M07](https://github.com/mui/mui-x/issues/2672#issuecomment-929871306).

**Q3. I=ID 상태, O=적재 객체.** MUI v7.11.0 모델은 ID array [C04](https://github.com/mui/mui-x/blob/v7.11.0/packages/x-data-grid/src/models/gridRowSelectionModel.ts#L1-L5); v8.0.0 모델은 include/exclude Set [C05](https://github.com/mui/mui-x/blob/v8.0.0/packages/x-data-grid/src/models/gridRowSelectionModel.ts#L8), 현재 문서에는 제외 최적화 opt-out도 있다(C15). 이전 API를 새 API로 소급하지 않는다. TanStack v8.5.15 [C16 L199-201](https://github.com/TanStack/table/blob/v8.5.15/packages/table-core/src/core/table.ts#L199-L201)에서 명시 getRowId 없으면 parent/index; v8.5.15 [C06 L191-208](https://github.com/TanStack/table/blob/v8.5.15/packages/table-core/src/features/RowSelection.ts#L191-L208) selected model은 state와 core rows를 결합. v8.8.4 [C07 L90-130](https://github.com/TanStack/table/blob/v8.8.4/packages/table-core/src/features/RowSelection.ts#L90-L130) toggleAllRowsSelected는 preGroupedFlatRows 범위; manual pagination [C08 L235-253](https://github.com/TanStack/table/blob/v8.8.4/packages/table-core/src/features/Pagination.ts#L235-L253)은 pre-pagination model 반환, pageCount는 서버 ID 목록이 아니다. [C12 guide](https://tanstack.com/table/v8/docs/guide/row-selection) manualPagination 명시: 선택 state에는 미적재 ID가 있어도 row model에는 전달된 data만 존재. 전 행 로컬 적재 [D05](https://github.com/TanStack/table/blob/v8.8.4/examples/react/row-selection/src/main.tsx) 100000개 fixture는 반례: 추가 조회가 항상 필요한 것은 아니다. T05/T06과 X11 #3619은 index 문제가 실제 보고되었다는 근거. T01/T02 같은 작성자 ID 예시의 4 true keys 중 하나가 다음 회신에서도 반복되나 처음 body에는 literal ID 없음. 요구한 body→동일 literal ID 조건 미충족. 정확 patch 미상의 MUI, T01, T07 판본 대조는 실제 설치판 검증이 아닌 당시 코드/태그 기반 설명.

**Q4. 필터·데이터 변화.** D01/C01: 이미 서버에서 페이지가 잘린 data에 재-slice하면 현재 면 선택 오류가 나므로 PR이 client일 때만 paginated selector 적용. D03/C02: 숨은 선택이 남는 결함 때문에 filter.items 존재 시 reset 추가; D02/C09/C10: 같은 필터 누적을 깨는 부작용 수정, filter update 이벤트에서 nonmatching ID cleanup, keepNonExistentRowsSelected true는 bypass. 실제 PR과 source 시험 기대 원값은 표2. 두 정책은 하나가 항상 옳지 않다. C17 v8.0.0의 exclude 최적화 guard(visible-only/선택가능성/필터/autoSelection)는 현재 문서의 표현과 같이 읽되 당시 exact source와 current docs 차이를 남긴다. 현재 문서는 exclude에서 제거된 row의 ID 제거 규칙을 all-client에 한정하고 keep flag를 제공(C15 L187-191). 서버 dataSource의 universe에 자동 적용된다고 결론내리지 않는다. 같은 filter 시험 [0]→[0,3,4]는 D02/C10 정적 expected이며 실제 실행은 미확인; 실제 사용자 동일 ID를 대신하지 않는다.

**Q5. 제출과 수신.** I/O와 S(선언/호출), R(서버 수신/처리)를 분리. T03은 선택 객체 callback을 부르는 코드와 data fetch를 부르는 코드가 있을 뿐 selection payload를 API에 전송하는 내용이 없다. T13 실제 posted GraphQL query는 page take/skip/storeId/sort, selection state 별도. T12 backend에서 ID 조회한다는 유지자 진술은 원작성자 API 수신 근거 아님. T10 allIds 응답 방향은 서버→클라이언트, 수천 건이라는 진술로 처리 ID receipt를 만들지 않음. D06 page header 소비자 예와 D07 object cache 소비자 예는 UI/data 전달 대안이지 서버 batch completion 아님. **실제 수신/처리 확인 0건**. 따라서 구현 검증으로 권할 수 있는 것은 UI/API state 경계까지. 아래 server contract는 검증 대상인 조건부 설계 대안, 실행 성공 주장이 아니다.

**Q6. QGIS 비교.** [G01](https://docs.qgis.org/3.44/en/docs/user_manual/working_with_vector/attribute_table.html) table filter 표시와 provider/layer query subset 분리. [G02](https://docs.qgis.org/3.44/en/docs/user_manual/managing_data_source/create_layers.html) Save Features As vs Save Selected Features As와 extent 추가 옵션; [G04](https://docs.qgis.org/3.44/en/docs/user_manual/processing_algs/qgis/vectorgeneral.html) native:saveselectedfeatures는 선택이 없으면 empty output. [G03](https://docs.qgis.org/3.44/en/docs/user_manual/processing_algs/qgis/vectorselection.html) select by expression METHOD 0/1/2/3 = new/add/remove/within; extract by expression은 새 output. [G06 공식 예 L626-647](https://docs.qgis.org/3.44/en/docs/user_manual/introduction/general_tools.html) regions.shp의 TYPE_2=Borough 선택→copy/paste to new layer. [G05 공식 예 L92-124](https://docs.qgis.org/3.44/en/docs/training_manual/vector_analysis/basic_analysis.html) roads highway null 제외 layer subset→Save Features As→roads_34S. 표 표시 밖 feature가 layer universe에 남아 있고 선택된 상태라면 selected-only 저장 후보; layer subset 자체 밖이면 현재 layer 범위가 다름; export extent가 더 좁힐 수도 있다. 출력 layer ID 재할당/실제 파일 검사 미실시. 교훈은 표시/선택/출력 universe 분리이지 GIS 도구가 HTTP 서버 pagination을 구현한다는 주장 아님.

**Q7. 답 결정.** 명시 P 조작은 즉답(M03/M01). 범위 명시 V는 stable ID와 적재 object 경계를 동반, same-filter 보존과 cross-filter 정책 구별(M02/M04/M05). global F/U를 실행하려면 다른 두 링크, 실제 수신까지 확인 전 보류. 잘린 요청은 한 문장(표3). 원본 전체는 filter를 무시하는 별도 선택지이며 F인지 U인지 모호할 때 확인. 선택 표시 문제만이면 UI 먼저, 실제 서버 export/edit 포함 시 서버 계약의 원리·비용을 조건부 제시. 답변 평가를 실제 원작성자에게 하지 않았으므로 정확도나 질문 절약률 측정 없음. ## 경쟁 설명과 관점
- 요청 작성자는 동사(편집·다운로드)와 대상 분모를 의도. UI 작성자는 header candidate IDs, partial click semantics, selection disabled rows와 count를 다룸. 백엔드 처리자는 허용된 ID·필터 snapshot·예외, 수신/처리 결과가 중요. GIS 편집자는 표시와 layer 범위/선택/extent/새 layer를 다룸. 하나의 check count나 'all' label은 네 관점 모두의 근거가 아님.
- 설명 A: 버그의 본질은 단순 checkbox 계산. M1의 재-slice 및 M3의 header 대상에 맞지만 T01의 unloaded object, T08 global intent 설명 못 함.
- 설명 B: 모두 stable ID 문제. T05/T06에 강하지만 M2에서 stable ID가 있더라도 reset하면 잃고 T08에서 모르는 ID를 생성 못 함.
- 설명 C: 전부 서버 조회 문제. T01의 객체 회수와 T08 global all에는 유용하나 M03 명시 current page만 원하는 UI에 불필요하며 D05 로컬 전체 적재에서도 과잉.
- 설명 D: filter가 바뀌면 언제나 선택 reset. D03 hidden rows 해제 문제 해결에 맞으나 같은 filter의 header까지 reset했던 D02 반례. 반대로 항상 유지도 M05·G03 new selection/within 동작과 불일치.
- #4639/#4655에서 7+3=10 체크 수를 current model 10과 비교하는 오류는 global count와 page count의 차이. 실제 request/response trace가 없으므로 서버 결과 추론 금지. #6039 14 total, 10+4 페이지, 3/4 선택 시 상태 다른 보고(T11)는 마지막 부분 페이지에서 count 기반 설명을 추가 반증한다.

## 조합 조건과 비용 — 최종 구조 미정
1. **P local selection**: 현재 적재·선택가능한 IDs에만 toggle, 기존 타 면 ID는 정책에 따라 보존; 비용 현재 페이지 크기. 명시 P UI only면 D04/D06 또는 MUI prop 하나로 충분. 조회·일괄 변경을 실행한다면 서버 검증은 별개.
2. **V explicit ID set**: 안정·유일·불변 ID로 hoist, 선택 여부 true만 집계, 현재 page 객체와 별개; 메모리/전송 O(k) (k=선택 ID 수), 서버 ID 조회로 최신 데이터/권한 확인. 객체 cache(D07)는 표 side display에 유용, stale/삭제/중복/undefined/false-key 문제 검증 필요. 전체 적재 client라면 API 그대로 이용(D05).
3. **F/U enumeration**: 서버가 해당 분모 전체의 허용 ID를 일괄 제공, explicit IDs를 보내는 후보. T10은 전자의 소비자 보고만 뒷받침. O(N) ID 전송 및 memory, 조회/작업 사이 삭제·수정·권한 변화. snapshot token/버전, 선택가능성 포함, 수신 후 재검증과 partial 실패 목록; 작은 N에는 간단.
4. **F/U predicate+exceptions**: server-authorized scopeToken(tenant/filter/snapshot 또는 live 정책/권한)과 excluded IDs를 보낸다. 예시 request(가상): {mode:"allMatching",scopeToken:"q@t0",excludeIds:["b"],operation:"export",idempotencyKey:"req-1"}. explicit request 예(가상): {mode:"ids",ids:["a","c"],operation:"export",idempotencyKey:"req-2"}. UI의 MUI exclude를 그냥 서버 처리 ID로 역직렬화하지 않는다. O(e) 예외 수(e) + query 평가; 큰 N에서 compact, predicate/authorization, TOCTOU, scope expiry, snapshot semantics, server-side count/preview 비용. 서버가 받은 집합/실제 처리/실패를 별도 receipt로 확인하고 권한 재검증(고객 filter 문자열 직접 실행 금지). U는 명시 원본 범위/권한, F는 filter predicate, unknown scope 거절 또는 질문. 새 행 추가 시 live와 snapshot 결과 다름.
5. **혼합**: current page header "이 페이지 선택"과 global banner "현재 검색 결과 N개 선택"을 분리, actual IDs count vs current page count 분리, scope 변경 시 보존/초기화 명시. UI-only vs 작업 contract 각각 링크. N은 서버 측 대상 범위·eligible 기준의 확인된 count여야 하며 현 page size 곱으로 임의 생성하지 않음. destructive action은 확인·권한·idempotency, 내보내기 역시 보안 범위 확인. 이 제안의 성과/실행은 미검증.
