## 대안 비교와 적용 비용

- **A: alias 유지 + 짧은 판 표시.** 현재판 탐색이나 불변 대조(total/BICUBIC)에 저비용. API 경계에서 실패하는 이유는 별칭의 의미 변화; C01/C03이 반례. 원문에 목표판이 없으면 버전 확인을 선행.
- **B: target-specific 숫자 doc + 원문 보조.** 읽기 쉬운 API 문서, 두 urllib3 고정판에서 본문 확인. Pillow 숫자판 실패 시 단독으로는 사용자 이동을 막음. 필요할 때만 SHA/source fallback(C). 실제 status·fragment 확인을 작업별로 해야 함.
- **C: SHA source/RST + 날짜 있는 release note.** 실행 가능성 판정의 근거로 강함; 초보 사용자에게는 line range와 짧은 이유가 필요. SHA는 코드만 고정하며 당시 rendered page나 dependency 환경을 복원하지 못함. 빌드 성공이 CDN 동일성을 보장하지 않음. 원문 href 교체와 역사 수정은 별도.
- **D: 시점별 alias 관측 + archive 보조.** 역사 독자·호스팅 관리자에게 유리, 재방문·보관 비용과 역사 데이터 공백이 큼. 과거 미관측은 unknown, 미래 관측만으로 이전 상태를 소급하지 않음. 현재 HTML id/redirect 검증은 저렴한 1회 probe, 당시 snapshot은 별도 비용. 제품의 저장 구조나 전체 설계는 확정하지 않음.

## 추가 분석
사용 목적 × 대상 버전 × 근거 역할(call support / history / navigation)의 조합이 최소 분기다. 기록은 원문 href, 입력/확인 판, observed UTC, provenance type, anchor 확인 여부와 근거 위치를 분리한다. link alive 단일 점수, 현재 deprecated 문자열 검색만으로 판단하지 않는다. 논쟁: old name이 보이면 언제나 교체? X06 history에서는 old name이 바로 이유이므로 유지가 맞음. 동일한 숫자판 doc가 다시 접근된다면 P의 primary를 B로 바꾸되 코드 판정은 유지. 옛 HTML anchor가 살아 있으면 fragment 교체 필요성은 소멸. 기존 공개 소비자 오류만 인용했으며 신규 실행/벤치마크·독립 검토 없음. 2개 API 변경 사건과 W3C 1개 개정 비교, 직접 고유 원자료 38/22(같은 lineage 내 여러 파일은 사건을 늘리지 않음), 59 ledger 행(21 미산입), 18 목적 자리.
