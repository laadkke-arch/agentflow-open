## 모집·실행·비교 분모와 결원

- 모집은 지정 원순번6건 전부다. jq #3/#4/#6, Pandoc #3/#5/#6이며 교체·탈락0. 6질문×2경로=12회, 주 대응쌍은6개다. 동일 조사의 A→B/B→A 교차이지 독립 맹검이 아니다.
- 사전 봉인: A만 완결0, B만 완결0, 양쪽3(J1/J3/P2), 어느 쪽도 완결 아님3(J2/P1/P3). P2는 주 분모에 남기되 엄격 동등비교에서 비교불가1로 분리한다. 따라서 유효5쌍의 분류는 A만0/B만0/양쪽2/어느 쪽도 아님3이다. P2 원 Quarto 연결을 보수적으로 해석하면 전체6쌍의 양쪽 완결은2, 어느 쪽도 완결 아님4다.
- B의 추가 완결은 유효5쌍 중0건이다. 다만 jq3건은 정당한 인접 도구가 없어 애초 B=A다. 실제 허용 집합이 다른 신규3쌍 중 정상 비교가 남는 것은 P1/P3 두 쌍이고 여기에서도 추가 완결0/2다. A만/B만 완결인 불일치쌍 자체가0이므로 **불일치쌍 중 B 승률은 산출 불가(분모0)**다. 동률을 B의 성공으로 세지 않는다.
- 검색24회, 결과 노출23회(그중 booktabs 코퍼스가 없는 부분검색1), 전면 실패1. 본문 열람33/48회, 실패 접근1을 포함한 별도 자료 접근34회. A는15본문, B는18본문+실패1. 경로명 탐색9회는 검색결과 노출과 분리 기록했다. B의 인접 저장소 검색 노출은0행이고 인접 원문6개는 경로명 탐색으로 직접 골랐다.

- C2는 J2/P2 두 건에서 공석이다. 모든 원 질문자의 실제 사용판은 미확인이다. P2 이미지와 J1 jqplay는 직접 검증에 실패했다. booktabs 본문/바이트, 원 Quarto 연결, P1 실제 Unicode·폰트 파일, P3 전체 명령/bib/CSL도 공석이다. 교정 JN2/PN1/PE1 세 건과 타 분야 대조는 신규6쌍/승률에 기여0이다.

## 판단: 도구 이름보다 입력과 다음 소비를 연결하되, 범위를 넓힌 효과는 입증하지 못했다

이 기록에서 B가 A보다 완결된 답을 더 찾았다는 증거는 없다. 그러나 “인접 단계를 허용해도 쓸모없다”는 결론도 성립하지 않는다. 고정 정렬에서 주 도구가 먼저40행을 차지해 B의 추가 저장소가 검색결과에 나오지 않았고, P2는 검색 파서 실패까지 있었다. 관측값은 **현재 질의·고정 코퍼스·행 순위·같은 조사자의 기억을 포함한 절차에서 추가 완결0**이다. 소스 범위만의 인과 효과는 분리할 수 없다. [검색 원장](searches.jsonl), [코드 감사](evidence/review/preseal-audit.md), [쌍 집계](pairs.csv)가 이 제한을 드러낸다.

가장 강한 사후 반례는 P3다. 표면에는 CSL·Better BibTeX가 등장했으나 채택 답은 Pandoc reader의 `example_lists`를 끄는 방법이었다. [고정 reader](https://github.com/jgm/pandoc/blob/c3038dcd54152c4e18e49db31676b79ee7cc29b2/src/Text/Pandoc/Readers/Markdown.hs)는 Example 목록에 확장 guard를 걸고, [목록 파서](https://github.com/jgm/pandoc/blob/c3038dcd54152c4e18e49db31676b79ee7cc29b2/src/Text/Pandoc/Parsing/Lists.hs)는 @label과 마침표를 목록 표식으로 읽을 수 있다. [회귀 기대출력](https://github.com/jgm/pandoc/blob/c3038dcd54152c4e18e49db31676b79ee7cc29b2/test/command/6836.md)는 example label이 숫자 참조가 되고 별도 citation은 Cite로 남는 차이를 보여준다. 이 사후 근거는 두 경로가 허용했던 주 도구 내부에 있었지만 어느 경로도 반환하지 않았다. 질문자의 해결 보고는 이 해법과 맞지만 정확 입력의 새 실행 검증은 아니다.

J1/J3는 기존 도구의 전체 매뉴얼에서 구체 경로를 얻은 자리다. J1은 방문과 갱신을 같은 jq 안에서 하고, J3은 인수 문자열을 실제 객체 인덱스로 사용한다. J2에서는 잘린 JSON을 다른 파서나 Jsonnet으로 보완하는 추정을 하지 않았다. 주어진 JSON 문서 자체가 없고 새 값도 없으면 읽기/갱신 연산 설명은 부분 답이다. [jq EOF 파서](https://github.com/jqlang/jq/blob/71c2ab509a8628dbbad4bc7b3f98a64aa90d3297/src/jv_parse.c)와 [인수 자료형 시험](https://github.com/jqlang/jq/blob/71c2ab509a8628dbbad4bc7b3f98a64aa90d3297/tests/shtest)은 각각 입력 완전성, 문자열/JSON 값 구분의 이유를 뒷받침한다.

## 방법·노출·비용을 해석할 때의 조건

첫 통합판은 `c2709abf8d25163eed75a7553ebcbde966105b55`이고 계획판 `62a80b9f…`와 다르다. 새 작업 브랜치를 실제 통합판에서 만들고 manifest로 owned path와 AF088 의존 SHA를 고정했다. 원 R0는 GUID API의 가장 이른 보존 본문이며 개설 순간의 바이트라고 주장하지 않는다. 웹 revision 접근 실패 뒤 공식 StackExchange API를 사용했고 실패도 원장에 남겼다. 답/채택/현재본문 최초 노출은 사전 판정의 원격 커밋 뒤다. [노출 영수증](evidence/outcome-exposure.jsonl).

질의는 R0 대상/행동/입출력과 조사자가 이미 아는 매뉴얼 표제어로 만들었다. `walk`, `booktabs` 같은 단어의 사전 지식이 들어 있으므로 처음 보는 일반 사용자 검색과 같지 않다. `search_plan.json`의 두 regex를 고정하고 공식 저장소만 검색했다. 주 도구→인접 저장소, 주 매뉴얼→문서→구현/시험, 경로/행 순으로 상위40개 match 행을 노출했다. 질문·해답 사이트를 검색 소스로 쓰지 않았다. 파일명 탐색은 별도로 남겼다. 이 순위가 인접 자료를 밀어낸 사실 자체가 이번 실험의 약점이다.

동일 원문을 B에서 기억해도 B의 실제 open이 있어야 근거로 인정했다. 모든 실제 반환 source는 그 경로의 열람에 대응한다. P2-B는 실패한 booktabs PDF 뒤 네 파일을 읽어 성공본문 기준4이나 요청 시도 기준5다. 처음부터 시도4를 적용하면 마지막 default.latex의 로드 순서 근거를 못 읽는다. 이를 숨기지 않고 비교불가와 민감도에 남겼다. 검색2 파서의 splitlines 문제를 고쳤으나 같은 질의를 다시 실행하지 않아 원 로그를 유리하게 교체하지 않았다.

사후 코드는 문서 적합(D1), 공개 채택/질문자 행동(D2), 정확 입력·판·출력 실행(D3)을 분리했다. 상류 fixture는 구현자가 기록한 기대출력이며 이 연구자의 실행 성공이 아니다. 현재 채택 표지는 과거 채택시각이나 질문자 성공을 뜻하지 않는다. J3 최초 답의 숫자 불일치와 J1 생략부호 실패는 “좋은 해법 링크”와 “완결되어 실행 가능한 답”이 갈라지는 실제 자료다. [최초판 영수증·후속 표](evidence/outcomes/report.md).

## Q7 · 다른 분야의 두 계열 대조

### 오디오: 코덱 이름과 출력 목적이 다르다

[RFC7845](https://www.rfc-editor.org/rfc/rfc7845.html)는 입력 sample rate 메타데이터와48kHz granule clock을 구별한다. 즉시 재생과 원 sample rate의 PCM 파일 복원은 같은 “Opus 지원”으로 요약할 수 없다. [FFmpeg 고정 매뉴얼](https://github.com/FFmpeg/FFmpeg/blob/b08d7969c550a804a59511c7b83f2dd8cc0499b8/doc/ffmpeg.texi)의 stream copy는 한 프로그램이 demux/mux를 함께 하므로 압축 비트를 다시 인코딩할 필요가 없는 경우를 보여준다. [opusfile API](https://opus-codec.org/docs/opusfile_api-0.12/group__stream__decoding.html)도 decoder와stereo downmix를 함께 담당한다. 앞단 인코더 변경이 불필요한 반례다.

반대로 PCM 포인터를 WAV 소비자에 바로 잇는 조합은 미완결이다. [공식 opusfile 예제](https://github.com/xiph/opusfile/blob/a55c164e9891a9326188b7d4d216ec9a88373739/examples/opusfile_example.c)는 RIFF/WAVE header·byte order·채널수까지 써야 하며 긴 파일에는 경고 한계가 있다. [Safari 지원 발표](https://webkit.org/blog/16574/webkit-features-in-safari-18-4/)와 [실제 Ogg/Opus 시간축 실패](https://bugs.webkit.org/show_bug.cgi?id=293310)도 다르다. Safari18.5 보고자는07:32:36.61이7:58:26으로 표시됐지만 같은 Opus를 WebM으로 remux하면 정상이라고 했다. 이 공개 대조는 인접 컨테이너 변경이 도움이 된 반례이나 원 파일/FFmpeg 정확판과 이 연구자의 실행은 없다.

### 전자책: 같은 EPUB도 다른 레이아웃·사용자 스타일 계약이다

[W3C 읽기 시스템 규격](https://www.w3.org/TR/2023/REC-epub-rs-33-20230525/#sec-css)은 저자 스타일과 사용자 상호작용에 따른 재정의를 구별한다. [EPUB3.3](https://www.w3.org/TR/2023/REC-epub-33-20230525/#layout)의 reflowable/pre-paginated는 같은 확장자 안의 다른 목표다. [ReadiumCSS 범위](https://github.com/readium/css/blob/49d1f549185efc4aa3ac6bedb5e11b5011b3851a/README.md#scope-of-this-project)는 fixed layout을 제외하고 [설정 메커니즘](https://github.com/readium/css/blob/49d1f549185efc4aa3ac6bedb5e11b5011b3851a/docs/CSS12-user_prefs.md)은 로드된 CSS/변수 주입 위치를 요구한다. 이름이 같은 EPUB 두 링크를 잇는 것만으로 실제 호환이 생기지 않는다.

[KOReader13295](https://github.com/koreader/koreader/issues/13295)는 독자 스타일 재정의 뒤 코드 고정폭·제목 표시가 달라진 실제 보고이고, [고정 수정 코드](https://github.com/koreader/koreader/blob/fd54ddbd8f1aabcef1cc0adf3d8477fe84149cdb/frontend/ui/data/css_tweaks.lua#L430-L455)는 소비자 선택자를 조정한다. 저자 본문을 다시 생성하지 않는 해결 경계가 있지만 병합/기능 설명만으로 질문자의 수정판 성공을 확인할 수 없다. 이 사례의 두 이미지는 직접 열어 비교했으며 같은 사건의 보조자료로만 셌다. [오디오 상세](evidence/audio/report.md), [전자책 상세](evidence/ebook/report.md).

## 가장 중요한 불일치 또는 약점3건

1. **틀릴 수 있는 주장:** 현재 추가완결0이 인접 범위의 효과를 반영한다는 해석. **다음 조사 대상·입력:** 같은6R0·고정판·질의를 유지한 새 실험에서 실패 접근도 과금하고, 파일 단위 중복 제거 또는 소스별 노출 배정을 사전에 정한다. 기존 기록은 재채점하지 않는다. **판정을 바꿀 관측:** 인접 자료가 실제 노출·선택된 B에서 동일4시도 안에 A가 놓친 모든 제약을 완결하면 범위확대의 이점이 관측된다. 아직 그런 관측은 없다.
