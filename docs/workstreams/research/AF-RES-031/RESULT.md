## 해석과 보존 범위

**제공자·소비자.** API 설명과 upstream 소스는 대상판과 호출 조건을 좁힌다. P21-SE에서 같은 값이 32비트로 돌아왔고, Java가 받은 큰/작은 스트림이 나뉘었다. JAV-BIN은 명명된 시험 1개에 성공했어도 원 holder의 논리행이 0이어서 실제 값 근거가 약하다. JavaHolderControl은 같은 설정에서 count 2만 추가해 hello world와 null, 긴 오프셋 11을 읽었다. Python→Java C Data의 값 근거는 CD-LARGE와 CD-STORED에서 별도로 확인했다. [A06 원 시험](https://github.com/apache/arrow-java/blob/7a581880a85358315d05da08296cf570b3643924/c/src/test/java/org/apache/arrow/c/RoundtripTest.java#L149-L171) · [A15 setter](https://github.com/apache/arrow-java/blob/7a581880a85358315d05da08296cf570b3643924/vector/src/main/java/org/apache/arrow/vector/LargeVarBinaryVector.java#L232-L246) · [실측](receipts/java-holder-control/holder-first.stdout)

**접합부.** IPC는 표준 스트림의 schema와 batch를 연결한다. 동일 프로세스의 C Data 교량은 JPype JVM에서 PID를 맞추고 Python 객체 해제 뒤에 실제 Java 벡터의 foreign pointer와 값을 검사했다. ABI source release 슬롯이 비고 allocator close 후 PyArrow pool이 기준으로 돌아왔다. 큰 사례는 단일 LargeBinary 버퍼의 고주소 접근이다. 목록·대형 파일·다른 JVM의 전체 전송은 별도다. [A09 소유권 명세](https://github.com/apache/arrow/blob/apache-arrow-21.0.0/docs/source/format/CDataInterface.rst#L606-L685) · [A11 JVM Invocation API](https://docs.oracle.com/en/java/javase/21/docs/specs/jni/invocation.html#creating-the-vm)

**Rust 호출자.** 정적 배열에서 ArrayRef를 가져오는 일과 결과 enum을 해석하는 일은 호출자가 맡는다. 고정 공급자가 내부 datatype 분기와 downcast를 하며 List child를 같은 accessor로 재귀 변환한다. 유효 null의 형도 보존했다. Binary의 오류가 보여주듯 임의 타입 접근 범위는 제한된다. 형 정보가 없는 UI나 무효 인덱스를 위한 추가 입력은 별도 계약이다. 공급자 오류와 Cargo resolver 실패 단계는 각각 실행했다. [D04 구현과 원 시험](https://github.com/apache/arrow/blob/4b7cdcb9220b6d94b251aef32c21ef9b4097ecfa/rust/datafusion/src/scalar.rs#L245-L289)

**Jupyter 송수신.** 2021 최초 초안은 content 안의 위치를 제안했고 후기 공개 PR의 원문은 root 위치를 강조한다. 공개 PR70은 열려 있고, 2023 ipykernel PR1169는 별도 릴리스다. 그 구현과 초안의 유사성은 채택 판단에 사용하지 않았다. 6.26의 cell_id 값은 원 v1의 예상을 뒤집었고, 6.27부터 같은 signature의 cell_meta에 사전 전체가 전달됐다. 파일의 메타데이터는 송신자의 복사 여부가 좌우했다. [J01 초기 Reference](https://github.com/jflam/enhancement-proposals/blob/6966750bbd4d921a2b39e223713eba30fb81f7b1/cell-metadata/transmit-cell-metadata.md#L149-L212) · [J08 PR 상태](https://github.com/jupyter/enhancement-proposals/pull/70) · [J10 구현 설명](https://github.com/ipython/ipykernel/pull/1169)

**환경 관리자.** 새 Cargo.lock 해결은 yanked ahash로 중지됐다. 배포 당시 원 lock은 미확인이고, 뒤의 공식 3.0.0 lock을 seed로 삼아 동일 고정 소스의 resolver를 복구했다. 6.27.0 배포 삭제 표시는 %edit 결함 때문이며 메시지 micro-check의 관측과 별개다. 6.27.1의 여섯 값도 첫 실행과 빈 폴더에서 일치했다. [배포물](artifacts.csv) · [도구/컴파일/실행 벽시간](receipts/costs.csv) · [잠금](evidence/locks/)

**반례와 전이.** [다른 분야](CROSS_DOMAIN.md)에서 CRS 라벨에 따른 축·단위, 대칭 좌표의 무감도, BagIt의 바이트 검증과 TIB의 실제 Adobe/PDFBox 렌더링 경계를 비교했다. 범위를 통제한 형식 검사는 바이트 이동이나 인수의 생김새 확인에는 충분할 수 있다. 소비자의 해석 또는 결과값까지 필요한 경우 해당 경계의 출력 증거를 요구한다.
