## Q4 기술적 충분성과 부족: 원문 반례와 별도 설계 반례
1. 3142 단순 lazy prefix termination에 takewhile 충분. 그러나 filter와 prefix가 다르다. 설계 반례 xs=[1,0,2]에서 bool 필터는 [1,2], takewhile은 [1]. 원문 prime 두 절의 순서 해석(조건이 실패하면 어디까지 읽는가) 및 후대 infinite count의 종료 위험 I11. 원문 약 10%는 if-generator vs lambda takewhile의 비교, 새 문법 성능이 아니다.
2. 559 local helper로 임의 args, None 충분. shared identity/discovery를 요구하면 부분. Mock은 호출 기록과 기본 반환값이 달라 대체 불가. 실제 breakpoint는 hook override 시 환경변수 무시. Barry의 2017-09-11 empty disable 설명은 당시 작업 코드, 출시 v3.7은 empty default. 이 차이를 숨기면 잘못된 실행 카드.
3. 616 빈 suffix에서 s[:-0]는 빈 문자열; guard 없던 2019의 실제 제안 코드에 MRAB 지적. 문자열의 반복 affix 한 번만 제거, strip 문자집합 vs substring. 설계 반례 "foofooBar", prefix "foo": exact 한 번은 "fooBar", lstrip은 "Bar". tuple ("", "Foo")와 겹치는 "Foo", "FooBar "는 순서 결정이 필요(P03/D06); 반복 제거 while startswith에서 prefix=""이면 진행 없음은 설계 추론. 기존 cookiejar quotes처럼 단일 문자 우회는 충분. M12 Stinner는 casefold 검사, 조건부 side effect, 확정 길이 unconditional slice 등은 새 API에 곧바로 대체 못한다고 지적; Cannon의 넓은 grep은 일부 불일치. 일반적 표준화와 적용 불가 위치를 둘 다 보존. 저자의 단일 ns 비교는 특정 Windows win32 pyperf 보고이며 동일 조건 재현 안 함.
4. 618 zip_longest sentinel의 값 동일성 검사 대신 identity를 사용해야 실제 None과 충돌하지 않는다. 3+ iterator 및 side effects가 있으면 padded row를 만들며 여러 iterator의 값을 더 소비할 수 있어 strict의 최대 추가 1개 비교 계약과 다름(정적 추론, 실행 필요). Sized mismatch를 eager 검사하는 zip_equal과 lazy built-in은 failure timing 차이. 짧은 입력을 의도한 zip과 infinite를 섞은 zip에는 strict가 오히려 잘못된 조건. 소비를 먼저 중단하면 strict도 뒤 mismatch를 검증하지 못함. 이 반례들은 근접 링크≠동일 계약을 보여준다.
