# AF-RES-090 — SELF_CHECK

검산 상태: **PARTIAL**. 대상은 묶음 3의 원격 결과판 `833071b378ab379188c7b62c4a013621a4958bdf`에서 통합한 원장·관측이며, 작성 시각은 2026-11-23T16:53:30.720475+00:00이다. 이 파일 작성 중 새 외부 요청은 하지 않았다. 고정 후보, 주 판독 영수증, 보조 원문·패키지 대조, UI 관측과 독립 동료 검토를 서로 대조했다.

필수 원자료의 수는 충족했다. 그러나 주 판독의 GitHub B 세 행에서 지정 본문을 받지 못했고, R1 외부 참조의 생성 당시 판 관계와 R2의 실제 SVG/재생 payload는 확인하지 못했다. IIIF의 과거 필수 이미지 실패도 현재 관측으로 재현하지 못했다. 따라서 자료 수 충족을 전체 목적의 검증 완료로 바꾸지 않는다.

Python/R의 모든 주 판독 행에 대해 열람 수·응답 바이트 합·상태·최종 URL·SHA-256을 영수증과 대조했다. 같은 URL의 독립 시점 응답은 같은 결과라고 가정하지 않았다. 예를 들어 R2-body-B는 503, R2-next-B는 별도 요청에서 200이다. 해당 200 응답의 GitHub `rawLines` 286줄에 마지막 LF를 복원하면 고정 HTML과 같은 15,974바이트 및 SHA-256 `c812426f5a97f8361e64a7a3beb8a35d5dde4bd2270b70dc1f1567080471ca0c`가 된다. 이것은 **소스 바이트 대조**이며 재생 성공 검사가 아니다. 검산 내역은 [동료 검토](streams/cross/peer-review.json)에 있다.

확정한 부정과 미확인은 다음처럼 구별한다.

- P1 latest의 8.2.0과 R1 현재 서비스의 1.1.14는 목표판과 다르므로 **판 반박**이다. 예제 일부가 같아도 반박을 취소하지 않는다.
- P3-next가 두 번 안에 도착한 것은 `1.x/options/`다. 봉인한 root 지원 표에 도달하지 못했다는 것은 확인했지만, 그 표의 존재나 접근 가능성이 부정된 것은 아니다.
- R2 고정 `Using SVG files` 절 안의 SVG/재생 명시 경로·payload 부재는 **범위가 한정된 부정**이다. 프로젝트 어디에도 SVG가 없거나 예제를 실행하면 SVG를 만들 수 없다는 뜻은 아니다.
- 404/503 응답을 받았다는 사실은 확인했지만, 응답 뒤 목표 파일의 부재·영구 장애·원인·역사적 제공 여부는 **미확인**이다.
- 분모가 있는 0/8과, 비교 가능한 관측이 없는 **0/0 산출 불가**를 구별한다. JS/R/Python 예제 실행 성공률과 IA 과거 오류의 현재 동일 조건 재현율은 산출 불가다.

## Q2. 두 번째 열람의 목표를 사전에 무엇으로 봉인했는가?

[Python 봉인](streams/python/freeze.json), [R 봉인](streams/r/freeze.json), [UI 후보 봉인](streams/ui/freeze.json)을 함께 대조했다. 선택한 후보에 도착한 후 더 유리한 후보로 바꾸지 않았다. P3는 처음의 정적 HTML만 보면 드러나지 않던 version menu를 **후속 이동 전** 열어 동적 링크를 봉인했다. 이를 정적 HTML의 링크와 혼동하지 않는다.

## Q4. 다음 링크·Raw·상대 URI를 실제 독자 경로와 일치시켰는가?

HTML의 상대 경로는 `base` 또는 문서 URL의 맥락에 의존하고, 생성기는 원 소스 경로를 출력 경로로 바꿀 수 있다. 이 일반 규칙은 개별 파일의 접근성 관측을 대신하지 않는다.

## Q7. IIIF와 EPUB를 다른 분야의 실제 반례로 어떻게 사용했는가?

외부 사례는 네 프로젝트의 **16판독·8대응쌍 밖**이다. IIIF/EPUB 규격의 일반 규칙과 실제 파일의 현재 관측을 구별했다. 자료·실패 영수증·탐색 경로는 [타 분야 findings](streams/cross/findings.md), [원장](streams/cross/sources.jsonl), [검색·조회 기록](streams/cross/evidence/search-log.json)에 있다.

| 주장·적용 조건 | 규격 및 실제 자료 ID·원 URL | 반례 탐색·직접 확인 | 남은 빈칸·다음 최소 관측 |
|---|---|---|---|
| IIIF Manifest의 Canvas 식별자와 필수 외부 이미지 URI는 같은 역할이 아니다. 내장 Canvas는 별도 dereference 없이 읽을 수 있다. | 규격 [XF-IIIF-SPEC](https://iiif.io/api/presentation/3.0/); 실제 [XF-IIIF-MANIFEST](https://iiif.io/api/cookbook/recipe/0001-mvm-image/manifest.json); [XF-IIIF-IMAGE](https://iiif.io/api/presentation/2.1/example/fixtures/resources/page1-full.png); [XF-IIIF-CANVAS](https://iiif.io/api/cookbook/recipe/0001-mvm-image/canvas/p1). | Canvas URI는 301 뒤 HTTP 200의 404 안내 페이지에 도착했다. 그러나 완전한 Canvas는 Manifest 안에 있고, 실제 PNG는 200 `image/png`, 128,352바이트, 1200×1800으로 Manifest와 맞았다. “목록 URI가 안 열리면 작품은 읽히지 않는다”는 단순 결론을 반박한다. | 이는 **필수 이미지 실패** 사례가 아니다. IIIF와 EPUB에서 소프트웨어 도움말로 옮길 수 있는 조건은 명확하다. **목적에 필요한 자원이 무엇인지**, 그것이 **본문 안에 있는지·패키지 안 파일인지·외부 URI인지**, 목록의 식별자와 독자가 실제 열 주소가 같은 역할인지, 그리고 실제 payload와 판 지문을 확인했는지를 나눠야 한다. 이 조건은 단일 HTML 또는 고정 파일의 유용성을 평가하는 데 적용된다. 한편 IIIF viewer와 EPUB reading system의 전용 해석 규칙은 GitHub 소스 보기에 그대로 적용할 수 없고, 패키지에 정적 파일이 존재한다는 사실은 JS 실행·전체 예제 성공·외부 자원의 영구성을 보장하지 않는다.

## 검산 후 남기는 판정 경계와 다음 첫 행동

원자료 수와 16행·8쌍 기록은 충족했으며, “언제 한 문서로 충분한가”의 긍정 사례와 “언제 다른 파일·판 관계가 필요한가”의 반례를 모두 확보했다. 실제로 수행하지 않은 실행, 지정판 외부 참조, 현재 재현할 수 없었던 IIIF 필수 자원 실패는 **미확인**으로 남겼다. 자료가 많은 점으로 이 빈칸을 지우지 않는다.

재조사를 시작한다면 먼저 주 회차에서 503을 받은 정확한 GitHub B URI 하나를 새 UTC로 열어 소스 완전성·MIME·판·실제 후속 조작을 기록한다. 이 결과는 새 회차 증거이며 기존 503 행의 대체값이 아니다. 그 뒤 필요한 주장에 따라 R1의 생성 당시 R 판과 고정 manual, R2의 실제 SVG/재생 payload, IA의 옛 Manifest와 실제 참조 tile을 각각 최소 단위로 관측한다. 미확인과 확정 부정은 위 Q별 판정 조건에 따라 독립적으로 갱신한다.
