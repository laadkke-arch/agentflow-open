## Q1 — 원래 공식 이름과 정정의 관계
네 점 모두 6.0/6.1/16.0 UnicodeData의 Name이 그대로이고, 정정은 NameAliases에 별도 등재된다. FE18의 BRAKCET은 자료 오기가 아니라 보존된 Name 원문이다. U+2118 SCRIPT CAPITAL P도 Name이며 WEIERSTRASS ELLIPTIC FUNCTION은 정정 별칭이다. U+01A2 OI/GHA와 U+A015 WU/ITERATION MARK의 차이는 같은 code point의 이름 역할이지 동일 이름을 가진 두 코드가 아니다. U01–U06 원행 및 S01/S02 정책, S03 코드표 주석 참조. 검색용 이름과 인용/표시용 Name을 섞으면 역사 인용이 변경된다. 두 대조 점에서 000A의 <control>은 공식 Name이 아니라 placeholder이고 FEFF에는 독립 Name이 있다.

## Q2 — 추가 경계와 검색 가능성

## Q3 — CPython
고정 v3.13.0의 15.1.0 데이터는 P01, P03, P05에서 일치. U10/U11 여섯 코드의 relevant names와 aliases는 16.0.0과 같지만 다른 판을 실제 포함하므로 판은 각각 기록. P03 가상 alias slot은 모든 alias type을 읽고 P02 lookup은 slot을 실제 코드로 바꾸며 name은 alias를 쓰지 않는다. 따라서 5개 Name 입력 성공 예상, 13 alias 문자열 모두 성공 예상, 역방향 5개 Name과 000A ValueError 또는 default 예상. Python 3.13의 최신 웹 문서와 3.13.0 고정 RST는 구분했다. 실 실행 0.

## Q4 — ICU
I01 76.1 헤더 버전 16.0, I05 전처리 데이터 ucd;16.0.0으로 서로 지지한다. I04/I05에는 모든 alias type이 존재하지만 I06 296–337은 correction만 names[3]에 저장하며 I07이 setProps/build/writeBinaryData를 연결한다. 따라서 UNICODE choice old→code 5개(000A는 Name 없음으로 N/A), ALIAS choice correction→code 4개 성공 예상, control/alternate/abbreviation 9개 실패 예상. EXTENDED는 Name이 없는 경우 합성 이름을 제공하며, U+000A는 <control-000A> 예상. correction 문자열은 ordinary/extended가 아닌 ALIAS choice에서 조회한다; 각 choice의 역방향은 표2와 consumers.csv에 기록. I03 01A2의 세 choice 시험 기대만 직접 해당 표본, 나머지는 원행+고정 구현 추론. I01 헤더는 없는 이름 U_INVALID_CHAR_FOUND라 하지만 I02 1557/1608/1629 구현은 U_ILLEGAL_CHAR_FOUND. ## Q5 — 제어/대체/약칭/주석 반례
000A의 Name 없음에도 Python lookup의 formal control/abbreviation 경로는 정상 예상; 역방향 name은 ValueError/default. ICU ALIAS에서는 이 control/abbr가 모두 제외될 것으로 예상된다. FEFF는 Name ZERO WIDTH NO-BREAK SPACE, alternate BYTE ORDER MARK, abbreviation BOM/ZWNBSP. Python lookup은 셋 예상 성공이나 name은 고정 Name; ICU correction 전용은 셋 예상 실패. U02의 Unicode_1_Name 필드, S03/S04의 %, =, *, x 표기, U01의 typed alias 행을 분리해야 한다. 특히 NamesList에서 FEFF가 참조한 200B/2060/FFFE를 alias_of로 바꾸면 서로 다른 대상이 같은 이름으로 취급되는 거짓 성공을 만든다. LINE FEED (LF) 전체 legacy 표시 문자열도 하나의 formal alias로 승격하지 말 것. 관련 주석 검색은 explanation/related candidate로 분리.

## Q6 — 전거 레코드 (부분 확인)
LOC MARC 010(L02)은 전거 control number와 취소/무효 번호, 400(L01)은 이형 접근점, X00(L03)은 personal name 구조를 규정한다. 역사 전거 레코드의 직접 교육 문서 전사(L05, n79090096, 005 20040623033151.0): 100 Williams, Tennessee, 1911-1983, 400 Williams, Thomas Lanier, 1911-1983, 670 근거가 동일 레코드에 있다. 이는 한 객체의 두 접근점이라는 문자 사례와 유사하다. 반면 L04 Twain 예시의 500 관련 접근점은 400 동의어와 다른 관계다. L05 Kate Davis 교육 연습에서 1951- 및 1959-라는 두 접근점/각각 다른 670 문헌 증거를 보여주므로 bare name의 동일성은 불충분하다. 그러나 예시는 실제 두 레코드의 현재 원본/LCCN을 확인한 결과가 아니며, 403/429 등으로 현행 전거 쌍을 읽지 못했다(F06–F09/F18–F20). **Q6 실레코드 대조 미충족**. Unicode stable scalar key와 달리 전거는 기관의 레코드 ID·날짜·이력·관련 레코드·인물 동일성 근거를 별도로 보존해야 한다. 동명인/이명/복수 정체성을 구분하며 레코드 ID가 영원히 고정된 인물 ID라는 추론은 금지.

## Q7 — 세 목적의 최소 반환
검색용은 정정 alias 원행+code로 들어가고, 인용용은 인용 판/실제 문자열/원문 위치로 들어가며, 표시용은 해당 소비자의 고정판 API 계약+Name으로 들어간다. 세 링크가 같은 code로 묶여도 역할과 시점은 독립이다. cards.md에 예시와 필드를 두었다. 추천은 A/B/C 중 **B를 기본, 역사 재현·정정 근거가 중요하면 C를 선택**하는 조건부 설계이지 제품 최종 결정이 아니다.

## 관점·비용·조립 대안
| 저장안 | 얻는 것 | 잃는 것/비용 | 적합 조건 |
|---|---|---|---|
| A code만 | 동일 Unicode 객체로 안정적으로 연결 | 입력 literal, 역할, 인용 판, 당시 검색 근거 재현 불가 | 최신 코드 표시만 필요한 임시 검색 |
| B code+판+이름 역할+원문 문자열/근거 ref | old/alias 구분, 소비자별 반환과 시점 기록, 변경과 신원을 분리 | 별칭/소비자 관계 테이블, 버전별 검증 비용 | 일반 저장 추천 |
| C B+정정 원행/출처/추가·직전 부재 증거 | FE18 오타·공백·이전 인용 재현, 감사 가능 | 원문 저장·해시·링크 유지 비용, 최초 관측/승인 구별 필요 | 역사 인용, 정정/감사, 법적·표준적 근거 |
문자 도구 작성자는 API choice/데이터/오류 상태를 우선한다. 사전 편집자는 정정 의미와 원래 문자열 병기, 과거 판을 우선한다. 검색 이용자는 정정 용어로의 접근과 결과에서의 공식 Name/alias 역할 표시를 원한다. 전거목록 편집자는 100/400/500·670·identifier 및 중복/병합 판단을 요구한다. 어느 관점도 단순 label 교체나 label=identity를 보장하지 않는다.

권장 구조: Object(namespace, stable_key) ← NameClaim(literal, role, source_version, source_id, row, first_observed, absence_kind) ← LookupClaim(consumer, consumer_version, included_ucd, choice, input, direction, expected_result, evidence_kind). Citation(original_literal, original_URI/version, observed_at)은 재기록하지 않고 Object와 연결. Formal aliases는 role에 따라 검색 색인하고 annotation은 separate relation. 정정 이름이 생겨도 기존 object key나 과거 citation 문자열을 덮지 않는다. 211의 과거 기능 근거와 현재 alias 생존 분리, 213의 공통 부모와 child identity 분리와 결합 가능; 두 선행의 PARTIAL을 확정 증거로 확대하지 않는다.
