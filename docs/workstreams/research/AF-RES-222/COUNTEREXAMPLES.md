# 반례와 정정
- **C1 이름은 수정되지 않는다.** U+FE18의 공식 문자열 BRAKCET을 BRACKET으로 조용히 고치면 역방향의 정확한 공식 출력과 옛 인용이 손실된다(U02/U06/U04). 5.0 alias 원행 끝의 공백은 역사적 원문 보관에서 유지하고 검색 정규화는 별도 기록한다(U07). 01A2의 OI와 GHA, A015의 WU와 ITERATION MARK, 2118의 SCRIPT CAPITAL P와 WEIERSTRASS는 동일 코드지만 의미·역할을 바꾸지 않는다.
- **C2 살아 있는 이름이 과거 검색 기능을 보장하지 않는다.** U+2118의 correction은 6.0 전체 NameAliases 0행, 6.1 존재. Python 3.3 이후 alias 지원과 현재 3.13.0 데이터의 버전은 별개. 5.0 최초 관측 3개에 대해 4.1 직접 파일 404는 과거 부재로 계산하지 않는다. S01/S04만 formal 제도 경계를 지지한다.
- **C3 같은 UCD 별칭이어도 소비자가 다르다.** I05 전처리 데이터에 LINE FEED/LF/BYTE ORDER MARK/BOM/ZWNBSP가 있어도 I06 296–337에서 correction만 names[3]으로 뽑는다. P03은 alias 종류별 제외를 하지 않는 방식. 검색기 자체 인덱스의 성공을 ICU ALIAS 성공으로 보고하면 거짓 성공이다. 000A에는 Name이 없고 UnicodeData의 Unicode_1_Name은 legacy 필드; ICU EXTENDED <control-000A>는 합성 이름이지 Name이나 correction이 아니다.
- **C4 annotation은 이름이 아니다.** NamesList U+FEFF의 x 참조 200B/2060/FFFE를 동의어로 승격하면 다른 문자 코드로 잘못 반환할 수 있다. U+000A의 'LINE FEED (LF)' 전체는 legacy/표시 문자열이지 formal alias 두 개를 합친 단일 이름이 아니다. U+2118의 소문자 calligraphic p 설명과 U+0041 LATIN CAPITAL LETTER A 등을 단순 토큰 색인하면 다른 코드가 섞인다. 주석 검색 결과는 후보로만 반환하고 유형을 표시한다.
- **C5 문서/구현 불일치.** uchar.h 3806ff U_INVALID_CHAR_FOUND와 unames.cpp 1557/1608/1629 U_ILLEGAL_CHAR_FOUND가 다르다. 정적 구현의 오류 sentinel은 0xFFFF(1519ff)로 유효 코드 포인트 값과 겹치므로 UErrorCode 우선. 0 길이의 이름은 오류와 동일하지 않다. 버퍼 오버플로, 선행 오류 상태, 잘못된 인자를 별도 처리한다.
- **C6 사람 이름은 문자 코드가 아니다.** L05의 역사 전거 n79090096에서 100 선택형/400 이형 접근점이 한 레코드에 있다. L04 Twain 예시에는 500 관련 접근점도 있으므로 동일 인물이라도 이름을 하나의 레코드로 자동 합치는 것은 틀릴 수 있다. L05 Kate Davis 동명이인 교육 사례는 서로 다른 날짜/670 증거를 구별해야 함을 보여주지만 두 실제 LCCN은 확인하지 못했다. F06–F09/F18–F20은 접근 실패. 전거 레코드의 병합·폐기·이전 번호는 L02의 canceled/invalid로 별도 추적하고 문자열 자체를 식별자로 쓰지 않는다.
- 반증 탐색 후 변경: 처음에는 ICU 실제 생성 데이터가 불명확했으나 고정 generator 위치를 찾아 correction 전용을 확인(I06,I07). 이는 런타임 관측이 아니다. 전거 일반화는 실레코드 한 쌍 미확보로 조건부 유지.
