# AF-RES-067 결과 — 부분 인계

**판정 가능한 답:** 공개 원본의 주소와 짧은 이유만으로는 “이 산출물을 만든 특정 실행이 특정 입력 바이트를 읽었다”를 단정하지 않는다. Debian의 `.buildinfo`는 설치되어 결과에 영향을 줄 *수 있는* 패키지들을 기록한다. STScI의 `CRDS_CTX`는 참조 선택 규칙의 pmap, `R_FLAT`은 선택된 flat 파일 이름을 기술한다. 어느 쪽도 단독으로 실제 실행의 입력 바이트 지문을 제공하는 것은 아니다. 단, 위 주 8개 사례의 원 헤더·buildd 로그가 없어 **이 표본에서의 실제 빈도·성과는 아직 판정할 수 없다**. [deb-buildinfo](https://manpages.debian.org/testing/dpkg-dev/deb-buildinfo.5.en.html) · [CRDS_CTX](https://archive.stsci.edu/jwst/keyword/build9.3/meta_ref_file_crds_context_used.html) · [R_FLAT](https://archive.stsci.edu/jwst/keyword/build8.0/meta_ref_file_flat_name.html).

## Q1~Q7 — 근거와 한계

**Q1 — 객체 ≠ 실행.** Debian tracker의 2024-02-29 jq 1.7.1-3와 2024-01-03 pandoc 3.1.3+ds-1 원문은 각각 `Architecture: source`인 서명된 source 업로드이며 amd64.buildinfo SHA256을 열거한다. 이는 대상으로 정한 **amd64 binary .deb build**와 별개다. [jq 원문](https://tracker.debian.org/news/1508449/accepted-jq-171-3-source-into-unstable/) lines13–40 · [pandoc 원문](https://tracker.debian.org/news/1491612/accepted-pandoc-313ds-1-source-into-unstable/) lines13–46. MAST의 `_cal.fits` 제품 이름은 노출 식별 부분과 처리 타입을 담지만 고유 처리 run을 보장하지 않는다. [파일명 원전](https://archive.stsci.edu/jwst/keyword/latest/meta_basic_filename.html) lines5–22.

**Q2 — 작성 약속과 실제 값 분리.** dpkg는 `Installed-Build-Depends`를 영향 가능 설치 항목으로 정의하고 .changes의 `Checksums-Sha256`을 업로드 파일 지문 목록으로 정의한다. JWST 파이프라인 문서는 CRDS 규칙 파일 .pmap→.imap→.rmap→reference, NIRCam flat 선택 조건을 설명한다. 하지만 이번 대상의 `.buildinfo` 바이트·FITS 헤더 필드 값은 확보하지 못했다. [buildinfo](https://manpages.debian.org/testing/dpkg-dev/deb-buildinfo.5.en.html) · [changes](https://manpages.debian.org/trixie/dpkg-dev/deb-changes.5.en.html) · [CRDS](https://jwst-pipeline.readthedocs.io/en/2.0.0/jwst/references_general/explain_rmaps.html) · [flat](https://jwst-pipeline.readthedocs.io/en/1.18.x/jwst/flatfield/reference_files.html).

**Q3 — 같은 사건 연결.** source upload `*.buildinfo` digest는 정확히 그 업로드의 목록 파일에만 연결된다. 동일 빌드의 `.deb`, buildd attempt/log, signed binary `.changes`를 조인한 영수증은 **관측 0/4 확보**. MAST API의 동일 observation products 연결은 처리 실행 키와 다른 층이다. [MAST products](https://mast.stsci.edu/viz/docs/products.html) lines20–40.

**Q4 — 이름과 바이트.** 지금 해시를 계산한 원산출물 **0/8**, 동일 소비 실행이 기록한 실제 읽기 바이트 지문 **0/8 확보**. 이는 과거 프로세스가 읽지 않았음을 뜻하지 않는다. `CRDS_CTX`와 `R_FLAT`의 공식 의미는 확인했지만 주 4 cal 제품 자체를 열지 못했다. FITS CHECKSUM/서명/업로드 SHA는 적용 객체를 분리해야 한다.

**Q5 — 대안 배제 반례.** jq 및 pandoc의 서로 다른 signed source upload 원문이 존재한다. 같은 패키지판에서 다른 재빌드의 원 실행 키와 출력이 동일/상이하다는 반례는 **미확인**. CRDS 선택은 입력 metadata에 의존하므로 한 전체 pmap만으로 개별 flat을 유일 판정할 수 없고 다른 pmap이 같은 참조를 선택하는 구체 실측도 **미확인**. [CRDS matching](https://jwst-pipeline.readthedocs.io/en/2.0.0/jwst/references_general/explain_rmaps.html).

**Q6 — V0/V1/V2.** 위 24셀은 모두 예약됐으나 실제 원산출물을 특정하지 못해 귀속 평가 **미확인**. 업로드 보조원문의 출력 digest를 선택된 원 .deb 해시로 이동하지 않는다. 새 URL 요청 실패 기록은 [search-log.jsonl](search-log.jsonl), 셀별 확인 비용은 [views.csv](views.csv). 웹 도구의 텍스트 길이를 수신 HTTP 바이트로 간주하지 않았다.

**Q7 — 반환 문장.** 패키지 유지보수자에게 “source upload의 서명된 목록에 .buildinfo 해시가 있다”, 감사자에게 “그 해시는 해당 목록 객체의 기록이다”, 보정 과학자에게 “pmap과 참조명이 다른 층이다”, 과거 인용자에게 “원산출물 고정 hash와 실행 키가 없는 상태”라고 안내할 수 있다. [문장 카드](cards.md). 원처리 이후 같은 URI의 실제 바이트가 달라졌다는 실측 사례는 **미확인**.
