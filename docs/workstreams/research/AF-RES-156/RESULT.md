SCOPE.md 원판, timeline.csv 27행, SCOPE_CORRECTION.md, release_refs.csv를 같이 사용한다. 정식 .0 기능판은 패치판과 구별했다. 동일 날짜의 3.1.8/3.2.10 배포 순서를 임의 지정하지 않았다. 해당 전 날짜의 마지막 판 3.1.7/3.2.9의 실제 timezone.py를 읽었다. pandas v1.4.4 및 이전 v1.1.5,1.2.0,1.3.0,1.4.0의 timezones.pyx에는 explicit ZoneInfo 판별이 없고 v1.5.0은 #46425와 릴리스에서 해당 지원을 확인했다. generic tzinfo 경로 모든 API는 조사하지 않아 최초 가능한 단일 호출까지 확정하지 않는다. v2.3.3에는 ZoneInfo detection과 pytz string default 공존, v3.0.0은 ZoneInfo string default. v3.1.0은 관측했고 v3.1.1은 패치, 두 번째 기능판은 미관측. D6–D8 commit 날짜와 5.0 release 날짜 구별. 태그 object SHA와 merge SHA는 서로 다른 객체; ancestry/실행 별도 확인 필요.

### Q2 자체 구현 vs 어댑터 vs 기본 교체
D0의 원문은 Python PEP495/615가 나와 기존 pytz를 shim으로 대체할 수 있는지 보는 PoC. 작성자는 호환 동작을 최대한 유지할 목적, 문서는 미작성이라고 했고 리뷰어가 추가 의존에 반대했다. 자체 tzdb 구현 계획이 아니다. D1은 existing pytz + non-pytz, D2 default+dual support, D3/D4 direct stdlib UTC, D5 경고, D6–D8 제거. P1은 기존 tzinfo route 확장, P2 기존 라이브러리 간 default 교체, P4는 소비자 자신의 vectorized speed-path를 오히려 새로 구현. P8은 새 route 때문에 필요한 adapter. D4와 P2의 의존 선언만 삭제하는 부분을 implementation saving에서 제외했다. merge_parents.csv에는 PR base/최초 visible commit/실제 merge parent/merge date를 구별. first visible은 최초 작업 시작이 아니며 first diff·모든 branch ancestry는 미검증.

### Q3 보존 계약 및 입력
- UTC 순간: D1 Paris 2011-09-01 12:20 offset +02 테스트 소스, D3 migration writer alias→stdlib 동일 객체, X1 UTC 직접 import. P7 Tokyo 1800 UTC instant가 JSON에서 59초 이동했다고 저자가 제시; field path/Series 차이도 구분. 시간 이름/약어 보존은 D1 str(tz) 변화 및 P2 객체 type change로 시험 필요. 이름/약어만으로 offset을 결정하지 않는다.
- wall time/fold/gap: D1 Paris 2015-10-25 02:30, offset +02와 +01의 다른 instant. PEP495 fold는 순서, pytz is_dst는 DST/표준 선택. Dublin negative DST, Warsaw 1915 shift 반례(S30,S31). D2 작성자는 ambiguous/nonexistent API 미해결 가능성을 PR에 적음. P2 ambiguous/nonexistent exception class ValueError; P6의 Tokyo 1677 표현범위 부족은 gap이 아니다. 사용자 정책은 명시.
- serialization/comparison: PEP615 raw file ZoneInfo는 key가 있어도 pickle 불가; by-key pickle은 transition bytes를 담지 않는다. P8은 이를 이용해 raw data fallback. PEP495 equality에서 다른 tzinfo 인스턴스의 fold-dependent offset 조건이 존재(S28). 비교 결과가 같은 순간만으로 객체 동일/exception/serialize 동치라고 할 수 없다.
- 데이터 출처와 성능: P4 cache를 key로 만드는 것은 고정 파일 데이터에 불충분. P8 저자의 from_file Tokyo bytes + US/Eastern key는 13시간 차이 보고. AF-RES-147 Beirut edition/보존값 문제와 같은 종류의 실패 조건이지만 147 데이터 재실행 안 함.
- 증거: diff와 시험 소스는 실제 변경 근거, PR author runtime/fuzz는 당사자 보고, release note는 배포 선언. CI 실행 log/artifact 및 이 작성자의 실행은 0건, 테스트 존재와 통과를 합치지 않음.

### Q5 사람 시간 및 반복 부담
실측 사람시간·대안 기간과 단계가 맞는 사람시간·지원 티켓 처리시간을 찾지 못했다. D0의 정성적 소규모 판단, D1의 촉박한 마감, P2의 'couple dozen tests'는 각각 계획/정성 보고·예상이지 관측된 노동량이 아니다. D6–D8 삭제·P2 의존 항목 삭제·D4 rename을 노동 절감으로 환산하지 않는다. PR commit 수/라인/리뷰 경과일을 시간으로 곱하지 않는다. E01–E12를 1회성, 후속(두 기능판 예정), 별도 경계로 분리했다. runtime benchmark의 단위는 ms, author fuzz의 단위는 cases. 비교 대안은 explicit pytz 실행/slow path 등 기술적 비교만 관측. 
순절감의 올바른 대상은 같은 기능/서비스/기간에서 L(비교 대안 설계+구현+검사+운영) − L(도입 조사 제외한 이관+호환+검사+문서+운영+퇴역)이다. 사람별 겹치지 않는 기록만 합산, 상류와 하류의 동일 티켓 시간 중복 제거. 현재 관측 사람시간 분모 0, 값 결측. 금액·시간·%의 순절감 산출 불가. 데이터 없음이 노동 없음은 아니다.

### Q6 반증과 대안
관측: Django 4.x에 USE_DEPRECATED_PYTZ 지원, 5.0 제거. 실제 그 설정을 사용하며 전환을 지연한 서비스의 자료는 아직 미확인. X1의 alias 경고 보고와 #636은 5.0 공식 제거를 직접 참조하므로 동일 사건의 노동 이동 증거; 같은 UTC 객체임에도 별도 패치. X2 자동 치환은 오히려 잘못된 import를 생성, X3 오류와 보정. pandas P3은 2.2.3/3.0.1의 explicit pytz 비교로 구부품 경로를 실제 시험, 성능 대안 확인; 실제 운영 장기 유지 미확인. 
작성자 예상: D0 PoC는 shim 의존에 반대, #14848은 DST API 필요 가능성, P5는 미래 날짜에 대한 여러 대안, P8은 동등성 probe를 검토했다가 residual hole 및 복잡성 때문에 제거. 
연구자 대안(미실측): Django 기존 4.x 설정 보존 후 개별 폼/API 감사, 또는 바로 ZoneInfo 전환; pandas explicit pytz 유지(선택 타입·설치) vs string ZoneInfo(예외/API 업데이트) vs from_file fallback(원 규칙 보존). 구부품 지연의 사람 노동/보안/지원 장기 합계는 알 수 없다. 어떤 한 건도 전체 조직 비용으로 일반화하지 않는다.

### Q8 설계자에게 줄 두 사례
**Django D2/D6/X1.** 예: UTC를 만드는 코드가 django.utils.timezone.utc를 호출하던 서비스에서 datetime.timezone.utc를 사용하면 같은 표준 UTC 객체에 의존할 수 있고 별칭·일부 serializer 보정을 없앨 수 있다. 그러나 4.1 경고를 처리하고 5.0에서 import/migration이 실행되는지 테스트해야 한다. 기존 API 유지(4.x opt-out)는 지원판·종료판, fold/gap 정책, localize/normalize 사용처 감사가 전제; 직접 ZoneInfo는 불명확한 입력의 명시적 선택 필요. 자동 adapter X2는 실제 X3 ModuleNotFoundError를 생성, 시험의 기대 문자열도 틀릴 수 있음. [Django 4.0](https://docs.djangoproject.com/en/4.0/releases/4.0/), [django-upgrade #172](https://github.com/adamchainz/django-upgrade/issues/172). 반증은 서비스별 실제 전후 테스트·시간기록 및 설치판.
**pandas P2/P8.** 예: pd.Timestamp(2024,1,1).tz_localize("US/Pacific") 호출로 표준 timezone type을 쓰고 별도 mandatory pytz 설치를 피할 수 있다. 그러나 .tz type, 예외, DST 중복/부재, pinned tzdata, bulk 성능, JSON offset seconds를 검증해야 한다. explicit pytz 유지도 3.0에서는 설치 명시·예외 변경, 표준부품 직접 사용은 from_file key 데이터 identity 및 후속 fallback 확인. #66828에서 file rules를 key로 다시 읽는 최적화가 틀림. [3.0](https://pandas.pydata.org/docs/whatsnew/v3.0.0.html), [#66828](https://github.com/pandas-dev/pandas/pull/66828). 반증은 실제 3.0.3 vs 3.1.0 동일 TZif bytes/key/UTC inputs의 출력 및 latency, 소비자 이관 시간/대안 시간. 예시는 원문 계약의 반환 형식이며 이 작성자 실행 결과가 아님.
