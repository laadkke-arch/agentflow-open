# AF-RES-001 — 질문·원문·해석 경계의 일차 근거

분담 B / 기준 저장소 SHA `11137686f238b7a7f66e7fdeb72f5f6c49565486`.
확인: 2026-11-19 UTC, 2026-11-20 KST. 실제 열람 마감 시각 2026-11-19T15:12:54Z 이후 작성.

이 파일은 **서로 다른 원문 9개를 직접 열어 해당 절을 읽은 조사 기록**이다. 같은 NASA PDF의 여러 절, W3C의 최신 주소와 날짜 고정 주소는 각각 한 자료로 센다. 공식 설명·표준의 규정·논문 관측과 이 과제에 대한 연구자의 추론을 나눴다. 제품 실행, 사용자 시험, 새 모델/API 호출은 수행하지 않았다. 원문의 다른 모든 절을 읽었다는 뜻은 아니다. 이 분담은 근거 조사이며 완성된 제품안의 독립 검토는 아니다.

## 1. 자료별 확인 기록

### B01 — GOV.UK Design System, Question pages

- 원문: <https://design-system.service.gov.uk/patterns/question-pages/>
- 위치/버전: 확인일 현재 HTML의 `When to use this pattern`, `Back link`, `Asking multiple questions on a page`; 별도 고정 릴리스는 제공되지 않은 관측이다.
- 근거 수준: **문서 설명**. 실제 서비스의 응답률·완료시간 실측이 아니다.
- 확인: 모든 질문에 필요한 이유가 있어야 하며, 타당한 응답인 경우 모름·확신 없음도 허용한다. 이미 받은 정보를 다시 요구하지 않고, 답변을 돌아가 수정할 수 있게 한다. 한 페이지 한 질문을 출발점으로 제시하지만, 반복 업무를 빨리 전환하는 내부 사용자에게는 관련 질문 묶음이 적합할 수 있다고 명시한다.
- 입력에 대한 추론: 빈 필드 채우기 자체를 추가 질문의 이유로 삼지 않는다. 원문에 있는 환경·제약은 재입력시키기보다 출처를 보여 주며 수정 가능하게 재사용한다.
- 한계/반례: 일반 행정서비스 양식 패턴이다. 전문가의 설계 탐색에 한 질문씩 강제하는 최적 UX나 질문 수를 증명하지 않는다. 관련된 제약을 한꺼번에 수정하려는 사용자에게 지나친 직렬 질문은 손해가 될 수 있다.

### B02 — GOV.UK Service Standard, Understand users and their needs

- 원문: <https://www.gov.uk/service-manual/service-standard/point-1-understand-user-needs>
- 위치/버전: 확인일 현재 HTML `Why it’s important`, `What it means`.
- 근거 수준: **공식 서비스 설계 지침**.
- 확인: 정부와 상호작용하는 한 부분에만 시야를 가두지 말고 사용자가 이루려는 목적과 전체 문맥을 이해하라고 한다. 특정 해법보다 사용자의 문제에 초점을 맞추고 초기 가정을 조사·프로토타입 등으로 시험하도록 권한다.
- 입력에 대한 추론: 사용자가 선택한 부품 이름과 별도로 그 부품을 통해 바꾸려는 결과를 유지해야 한다. 다만 전체 문맥을 살피라는 지침이 전체 아키텍처 제출의 필수화를 뜻하지는 않는다.
- 한계/반례: 지침은 사용자가 명시한 해결 수단을 마음대로 지우라는 권한이 아니다. 조직 표준이나 기존 자산 때문에 특정 수단을 반드시 써야 하는 경우에는 그 제약도 원뜻이다. 이 과제에서 실제 사용자 조사나 프로토타입 시험은 하지 않았다.

### B03 — NASA Systems Engineering Handbook, SP-2016-6105 Rev2

- 원문: <https://www.nasa.gov/wp-content/uploads/2018/09/nasa_systems_engineering_handbook_0.pdf>
- 위치/버전: **SP-2016-6105 Rev2**. 인쇄 p11 §2.4, p49 §4.1, p60 `RATIONALE`, p197–199 Appendix C; PDF 페이지 인덱스는 각각 20, 58, 69, 206–208이다.
- 근거 수준: **공식 공학 지침**; 이 제품에서의 효과 실험은 아니다.
- 확인: 요구 충족 verification과 의도된 환경에서 목적을 달성하는 validation을 구분한다. 초기 목표는 꼭 수치형일 필요가 없다. 요구의 이유·가정·운영과의 관계를 보존하며, 구현 방법을 제한하는 요구라면 그 제한 이유도 적는다. Appendix C는 가정 확인과 추적성을 요구한다.
- 입력에 대한 추론: 목적·검증 가능한 조건·이미 정한 구현 제약을 서로 바꿔 쓰지 않는다. ‘빠르게’를 모델이 임의의 지연시간으로 확정하거나, 필수 기술 선택을 ‘목적과 무관’하다며 삭제하지 않는다.
- 한계/반례: 우주 시스템의 요구 기준선 절차를 탐색 입력에 통째로 이식할 근거는 없다. Appendix C의 긍정형 요구와 추정치/TBR 권고도 원문의 금지 조건 삭제나 AI 수치 추정의 근거가 아니다.

### B04 — W3C Web Annotation Data Model

- 날짜 고정 원문: <https://www.w3.org/TR/2017/REC-annotation-model-20170223/>
- 별칭으로 읽은 주소: <https://www.w3.org/TR/annotation-model/>. **한 자료로 집계**.
- 위치/버전: W3C Recommendation 2017-02-23, §4.2.4 Text Quote Selector, §4.2.5 Text Position Selector, §4.3.1 Time State.
- 근거 수준: **표준의 표현 규정**.
- 확인: 인용 선택자는 선택문과 전후 문맥으로 위치를 구별한다. 위치 선택자는 원문 수정에 취약하므로 자원 상태를 함께 쓰도록 권고한다. Time State는 적절한 시점의 표현 또는 영구 사본을 가리킬 수 있다. 인용 선택자를 만들 때의 텍스트 정규화는 원문 자체의 변경이 아니다.
- 입력에 대한 추론: 파생된 목적·제약 해석이 어느 버전의 어느 문장에서 나왔는지 재확인할 수 있어야 한다. 정규화한 선택자와 원문 보존은 별개다.
- 한계/반례: 정확한 구절을 찾았어도 해석이 맞다는 보증은 없다. 여러 구절이 같은 문장을 가지면 매칭이 여전히 모호할 수 있다. 모든 본문을 인용 객체로 복제하는 것은 필요하지 않으며 권리·접근 제약도 고려해야 한다.

### B05 — W3C PROV-DM

- 날짜 고정 원문: <https://www.w3.org/TR/2013/REC-prov-dm-20130430/>
- 별칭으로 읽은 주소: <https://www.w3.org/TR/prov-dm/>. **한 자료로 집계**.
- 위치/버전: W3C Recommendation 2013-04-30, §2.1.1–2.1.3, §4 예시, §5.2.1 Derivation, §5.2.2 Revision.
- 근거 수준: **표준의 개념 규정**.
- 확인: 원본·결과인 entity, 사용·생성을 수행한 activity, 책임 있는 agent를 구분한다. derivation은 다른 개체를 바탕으로 생성·변형된 관계다. 한 작업이 어떤 자료를 사용하고 다른 결과를 만들었다고 해서 결과가 모든 사용 자료에서 파생됐다고 자동 결론 낼 수 없다는 예시도 있다.
- 입력에 대한 추론: ‘원문에 근거한 AI 해석’은 작성자·변환·대상 문장을 남기는 별도 판단으로 유지한다. 단순히 입력 문서 목록 전체를 모든 해석의 근거로 붙이지 않는다.
- 한계/반례: 표준은 참인 주장만 표현하는 인증체계가 아니다. 현실·가상 개체도 다루며, 파생 관계의 성립 판단 자체는 명세 밖이다. 따라서 출처 링크의 존재를 사용자가 확정한 요구 또는 검증된 사실로 승격하면 안 된다.

### B06 — JSON Schema, Annotations

- 원문: <https://json-schema.org/understanding-json-schema/reference/annotations>
- 위치/버전: 확인일 현재 `Annotations` 문서의 `title`/`description`, `default`, `examples`; Draft 6·7 등의 도입 표기가 있는 설명서이며 특정 검증기 버전은 시험하지 않았다.
- 근거 수준: **공식 명세 해설**.
- 확인: 설명·제목·예제 등 annotation은 검증 조건 자체와 다르다. `default`는 검증 과정에서 빠진 값을 채우지 않으며, 별도 문서·양식 생성 도구가 활용할 수 있다. 문서는 default가 생략된 값의 의미를 표현하는 용도로 흔히 쓰인다고도 설명한다.
- 입력에 대한 추론: 모델이 원문에 없는 실행환경이나 제한을 ‘기본값’으로 자동 보충한 뒤 사용자 요구로 취급해서는 안 된다. 기술적으로 유효한 JSON도 원문에 충실한지 별도 검토가 필요하다.
- 한계/반례: 이 설명은 모든 양식 도구가 default를 적용하지 않는다는 보장이 아니다. 제품에서 기본 의미를 명시적으로 합의했다면 적용 가능하다. 따라서 문제는 기본값 자체가 아니라 근거·사용자 의미 없이 확정하는 것이다.

### B07 — JSON Schema, object / Required Properties

- 원문: <https://json-schema.org/understanding-json-schema/reference/object>
- 위치/버전: 확인일 현재 `Properties`, `Required Properties`; 미존재 속성과 `null` 예시.
- 근거 수준: **공식 명세 해설**.
- 확인: `properties`에 정의됐다고 필수 입력이 되는 것은 아니며 `required`가 별도로 필요하다. `null` 값의 속성과 아예 없는 속성은 같지 않다. 문서의 문자열 email 예시는 null이 문자열이 아니어서 유효하지 않다.
- 입력에 대한 추론: 미입력·모름·해당 없음·명시적 무제약을 구분할 수 있는 의미 규칙이 필요하다. 이는 JSON의 문법 차이만으로 자동 결정되지 않으며, 자유문에 붙이는 상태표시로도 표현할 수 있다.
- 한계/반례: `null`이 곧 ‘모름’이라는 의미는 이 문서가 정하지 않는다. 의미 구분을 위해 반드시 특정 필드명·enum·DB를 채택해야 한다고도 결론 낼 수 없다. 허용된 빈값을 모두 오류로 막는 것은 초기에 일부만 아는 사용자에게 부적절하다.

### B08 — Aliannejadi et al., Asking Clarifying Questions in Open-Domain Information-Seeking Conversations

- 원문: <https://ciir-publications.cs.umass.edu/getpdf.php?id=1339>
- 고정 식별: SIGIR 2019, pp475–484, DOI <https://doi.org/10.1145/3331184.3331265>.
- 실제 읽은 위치: 초록·§6 결과·Table 3/4·실패 분석. Table 3은 PDF p7의 화면도 직접 확인했다.
- 근거 수준: **원논문의 오프라인 실험 보고**. 이 과제의 실행 결과가 아니다.
- 확인: 논문은 NeuQS와 OriginalQuery를 비교한 facet별 MRR에서 45% 개선·19% 악화를 보고한다. 이 비교의 facet별 값은 1~3턴의 성능을 평균낸 것이다. Table 4의 추가 정보 후 악화는 관측이며, 어휘 불일치가 원인일 수 있다는 설명은 저자의 해석이다. 최고 질문을 사후 선택한 oracle 수치는 실제 자동 질문기의 보장값이 아니다.
- 입력에 대한 추론: ‘더 질문했다’나 ‘더 길게 설명했다’를 성공 기준으로 쓰지 않는다. 원래 목적을 유지하고, 질문이 실제 어떤 분기를 구별했는지와 잘못 좁혔는지 확인해야 한다.
- 한계/반례: TREC 주제·크라우드소싱 답·특정 검색모델의 결과다. 현재 LLM, 한국어 설계 기록, 타 분야 원리 탐색의 개선율로 일반화할 수 없다. 사용자 부담·이탈 비용도 이 수치로 결정할 수 없다.

### B09 — Horvitz, Principles of Mixed-Initiative User Interfaces

- 원문: <https://www.microsoft.com/en-us/research/wp-content/uploads/2016/11/chi99horvitz.pdf>
- 서지 확인: <https://www.microsoft.com/en-us/research/publication/principles-mixed-initiative-user-interfaces/>
- 고정 식별/위치: CHI 1999, DOI <https://doi.org/10.1145/302979.303030>; `Principles for Mixed-Initiative UI` 항목 2–9와 LookOut의 편집 가능한 제안. PDF 업로드 경로의 2016은 논문 발표연도가 아니다.
- 근거 수준: **원논문의 설계 원리와 프로토타입 설명**.
- 확인: 의도 추측의 불확실성과 개입 시점·비용을 함께 고려하며, 불필요한 질문으로 방해하는 비용을 논한다. 불확실할 때 서비스의 정밀도를 낮추는 방식과 사용자가 자동 분석을 중단·수정하는 통로를 제안한다. LookOut은 추정한 일정 정보를 보여 주고 사용자가 고칠 수 있게 했다.
- 입력에 대한 추론: 불확실하다는 이유만으로 탐색을 전부 막지 말고, 확실한 부분만 다루거나 복수 해석을 보존하는 대안도 비교한다. AI 분해는 되돌리고 고칠 수 있는 제안이어야 한다.
- 한계/반례: 옛 일정 도우미의 원리로 이 제품의 적정 질문 수·수정 비용을 확정할 수 없다. 단순한 사용자의 짧은 요청을 고치는 작업이 더 비싸다면 AI 분해가 이득이라는 전제부터 시험해야 한다.

## 2. 초기 결론을 반박해 수정한 지점

| 처음 떠오른 가설 | 원문에서 확인한 반례/한계 | 이 과제에서 유지할 판단 |
| --- | --- | --- |
| 불확실하면 더 물으면 된다 | B08은 질문 후 악화도 보고한다. B09는 방해 비용과 정밀도를 낮추는 선택을 다룬다 | 질문은 빈칸 수가 아니라 오해가 바꾸는 선택에 연결한다. 답이 없으면 확실한 범위 또는 나란한 가정 아래 탐색할 수 있다 |
| 목적만 남기고 기술명은 제거하면 자유로운 탐색이 된다 | B03은 구현 수단을 제한하는 요구에도 이유를 보존하게 한다 | 기술명은 예시·현재 상태·후보안·필수 제약 가운데 어느 것인지 원문으로 판별하고, 불명확하면 병기한다 |
| 원문 링크를 붙였으면 충실한 해석이다 | B04는 대상 선택 표현, B05는 파생 경로다. 어느 쪽도 참 판단기를 제공하지 않는다 | 원문의 해당 문장과 해석이 연결돼야 하지만, 그 연결만으로 확인됨을 주장하지 않는다 |
| 구조화 필드를 모두 채우면 누락을 막는다 | B01은 모름을 허용한다. B06/07의 문법·기본값은 의도 확인과 다르다 | 필요한 필드가 막는 실제 오류를 먼저 제시한다. 지식 없는 완성값 대신 미상 범위를 남긴다 |
| 원문을 그대로 두면 추가 표현은 필요 없다 | 긴 원문에는 현재/예전/조건/철회가 섞일 수 있고, 원문은 스스로 선택 부분을 명시하지 않을 수 있다 | 원문은 기준점이다. 선택한 부분·현 시점 목적·중요 조건의 가벼운 표시는 도움이 될 수 있으나 새 의미를 만들지 않는다 |

마지막 행은 이 연구자의 논리적 반례이며 문헌의 직접 실험 결과가 아니다. 후속 사례 대조에서 실제로 누락되는 문장을 찾지 못하면 필드를 추가할 근거로 쓰지 않는다.

## 3. 합성 입력으로 보는 잘못된 질문과 질문 없이 가능한 범위

| 합성 원문 | 위험한 재작성/질문 | 보존할 구분 | 답 없이 가능한 범위 / 좁히기 전에 필요한 정보 |
| --- | --- | --- | --- |
| “Redis 같은 대기열이면 될까? 서버를 다시 켜도 처리할 파일을 잃지 않게 하고 싶다.” | `must_use=Redis`로 저장하고 Redis 기능만 탐색 | 재시작 후 파일 손실 방지가 목적. Redis는 질문 속 후보 | 지속성·접수 확인·재처리 원리를 비교 가능. 적용 후보를 좁힐 때 운영 제약과 손실 범위를 확인 |

## 4. 후속 설계자가 비교할 추가 질문 규칙 후보

다음은 **문헌을 바탕으로 한 연구 제안**이며 최종 UI·API 계약이 아니다.

1. 원문에 이미 답이 있으면 다시 묻지 않는다. 모호한 지시어나 충돌하는 두 문장이 있는 경우에는 해당 위치를 보여 주며 무엇이 갈리는지 적는다.
2. 질문마다 `그 답 때문에 달라지는 판단`을 적는다. 어느 답이 와도 탐색 범위가 같다면 필수 질문으로 만들 근거가 약하다.
3. 초기에 꼭 분명해야 하는 것은 사용자가 도움받으려는 대상/문제와 명시적 금지 조건이다. 전체 주변 구조와 수치 성능은 그 정보가 적합성 판단을 바꾸는 지점에서 추가한다. 이 순서가 효과적인지는 아직 미검증이다.
4. 모름은 무제약으로 바꾸지 않는다. 탐색은 계속할 수 있어도 `제약을 만족한다`는 판단은 보류한다. 질문에 답할 수 없는 사용자에게 같은 질문을 반복하지 않는다.
5. 답이 없을 때는 확정 범위·가정별 분기·보류된 판단을 보여 준다. 이를 한 조건문으로 조용히 합치지 않는다.
6. 부정·조건·시점·대상 범위를 해석 과정에서 잃으면 추측을 멈춘다. 원문의 금지를 제거하거나 예시를 필수 기술로 만드는 경우에는 해당 파생 항목을 채택하지 않는다.

답을 바꿀 최소 확인: 동일한 합성/공개 사례에서 자유문 보존, 사람이 확인하는 가벼운 구조화, 수정 가능한 AI 분해 제안을 비교하고, 원문의 금지·조건·시점이 각각 어디에 남는지 독립 판정한다. 실제 추가 질문 비용이나 검색 품질은 이 대조만으로 확인되지 않으므로 별도의 사용자/검색 시험 결과로만 보고해야 한다.

## 5. 재검토용 핵심 주장

- **질문은 항상 이득이 아니다:** B08 §6/Table 4를 원문과 대조한다. 45%·19%는 NeuQS와 OriginalQuery의 facet별 MRR 비교(각 facet에서 1~3턴 평균)이며 사용자의 과제 성공률이 아니다. 어휘 불일치는 가능한 원인 해석으로만 읽는다.
- **해결 수단을 목표로 오해하는 것과 명시적 수단 제약을 삭제하는 것이 모두 오류다:** B03 p60과 합성 Redis 두 문장을 대조한다.
- **근거 위치와 파생 경로는 충실성 판정의 재료다:** B04/B05가 해석을 자동 인증한다고 읽지 않았는지 확인한다.
- **모름을 보존하는 것은 특정 JSON 값의 의무가 아니다:** B06/B07에서 기술적인 누락/null 구별을 사용자 의도의 의미 규칙으로 오인하지 않았는지 확인한다.
