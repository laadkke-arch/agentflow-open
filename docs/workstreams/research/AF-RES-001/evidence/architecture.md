조사 분담 A. 기준 저장소 커밋: `11137686f238b7a7f66e7fdeb72f5f6c49565486`.

- 열람일: 2026-11-20 KST / 2026-11-19 UTC. 기록 시각: 2026-11-19T15:12:11Z.
- 실제 수행: 아래 서로 다른 공식 원문 9개를 웹으로 열고 관련 본문을 읽었다. 큰 명세는 표시한 절만 읽었다.
- 증거 종류: 모두 **공식 문서 설명**이다. 제품 실행, 소스 코드 관찰, 사용자 시험, AI 분해 실험은 하지 않았다.
- 고정성: OpenAPI 3.1.1·AsyncAPI 3.0.0은 버전 URL이다. arc42·C4·Structurizr는 변경 가능한 문서이므로 열람일과 절을 함께 기록한다. 페이지에 보이는 최신 바이너리 버전을 문서의 검증 버전으로 간주하지 않았다.

## 1. 핵심 판단과 재검토할 주장

1. **대상 부분의 이름만으로 입력 관점을 정할 수 없다.** AsyncAPI는 기술한 애플리케이션을 기준으로 send/receive를 읽으며, 송신자 명세를 뒤집어 수신자 명세로 만드는 것을 권장하지 않는다. 선택 부분·행위 주체·자료 방향을 함께 보존할 이유가 된다. [A07]
2. **입력 도식의 선이 실행 사실이라는 보장은 없다.** OpenAPI의 Link는 설계 시점 관계이고, Structurizr는 명시하지 않은 부모 관계를 기본으로 파생한다. 원문에 적힌 관계, 도구가 파생한 관계, 관측한 실행을 구분해야 한다. [A06, A08]
3. **주변 문맥의 최소량은 질문의 수준에 달려 있다.** arc42는 업무 입출력과 기술 채널을 구분하고, C4는 시스템 문맥에서 기술 세부를 생략한다. 따라서 프로토콜이 답을 바꾸지 않는 초기 목적 탐색에 프로토콜 필드를 의무화할 근거가 없다. 반대로 실제 연동 가능성을 말하려면 기술 경계를 확인해야 한다. [A03, A04]
4. **자유문에 목표·제약·원문 연결을 덧붙이는 방식은 비교 후보가 된다.** arc42는 짧은 요구 요약과 기존 요구 문서 참조를 병행하며 제약을 별도로 설명한다. 다만 이것이 입력 정확도나 검색 품질을 높인다는 실험 증거는 이번 자료에 없다. [A01, A02]

root 재검토 우선순위는 1→2→3→4다. 1·2는 구체 명세 반례이며, 3·4는 문서 원리를 탐색 입력에 전이한 제안이다.

### A07 — AsyncAPI Specification 3.0.0

- 원문: <https://www.asyncapi.com/docs/reference/specification/v3.0.0>

### A08 — Structurizr DSL, Implied relationships

- 원문: <https://docs.structurizr.com/dsl/implied-relationships>
- 위치·범위: Implied relationships, Configuring implied relationships; 웹 본문 198–236행.
- 확인한 내용: DSL은 기본으로 파생 관계를 만든다. 예시의 사용자→컨테이너 관계에서 사용자→상위 시스템 관계가 유도된다. `!impliedRelationships false`로 끌 수 있고, true일 때 상위 요소 조합과 기존 관계 존재 여부가 결과에 영향을 준다.

### A09 — Structurizr DSL, Identifiers

- 원문: <https://docs.structurizr.com/dsl/identifiers>
- 위치·범위: Identifiers, Identifier scope; 웹 본문 198–257행.
- 확인한 내용: 요소·관계를 참조하려면 식별자를 쓸 수 있으며, 참조할 필요가 있을 때만 필요하다고 설명한다. 기본 식별자는 전역 범위여서 두 시스템 내부의 같은 api 식별자가 충돌한다. hierarchical 설정은 요소 식별자를 범위화하지만 관계 식별자와 group에는 동일하게 적용되지 않는다.
- 입력에 대한 추론: ‘API’ 같은 표시 이름만으로 선택 부분을 붙이면 다른 위치의 동명 대상을 잘못 잡을 수 있다. 기존 식별자가 있으면 재사용하고, 없으면 최소한 원문 위치·주변 범위를 함께 남기는 비교안이 타당하다.
- 한계·반례: 이는 DSL 내부 참조 규칙이다. 장기 카탈로그 식별 체계나 서로 다른 제품의 동일성 판단 원리로 확대하지 않는다. 짧은 단일 목적 문장에 영구 ID를 새로 강제할 근거가 아니다.

| receive를 send로 뒤집으면 반대편 구조가 된다 | 소비자가 읽는 채널과 생산자가 쓰는 채널 사이에 라우팅이 있을 수 있다 | 관점이 확인된 부분만 표현; 반대편은 미상 | A07 |
| 그림에 나타난 선은 사용자가 명시한 선이다 | 사용자가 컨테이너에 접근하는 선으로 상위 시스템 접근 선이 자동 생성된다 | 명시/도구 파생 표시; 파생 근거 보존 | A08 |
| 문맥을 빠짐없이 받으면 원뜻 보존이 좋아진다 | ‘오프라인 편집 후 합치기 원리’ 질문에 배포도·모든 서비스·모든 프로토콜 입력을 강제한다 | 현재 답을 바꾸는 경계만 질문; 그 밖은 선택 자료로 둔다 | A03–A05에서 전이한 추론 |
| 구조화는 대상을 명확히 하므로 항상 이득이다 | 사용자가 ‘선택한 API’라고 했고 두 시스템에 동명 API가 있는데 AI가 하나를 선택한다 | 선택 위치를 식별할 수 없으면 나눠 기술하거나 위치만 확인 | A09 |
| 모호함을 없애려면 모든 미상을 질문해야 한다 | 메시지 재시도 원리를 탐색하는데 보안 프로토콜을 아직 정하지 않았다 | 원리 비교는 진행 가능; 실제 연동 적합성만 보류 | A03, A07에서 전이한 추론 |

## 4. 구조화가 유익하거나 과해지는 조건

**유익한 조건:** 기존 정형 명세·도식이 있고 특정 operation/부분을 고를 수 있으며, 실제 자료 방향·연결 근거·경계가 답을 바꾸는 경우다. 원문에 있던 식별자와 필드를 재사용하면 같은 이름, 반대 관점, 여러 콜백의 혼동을 드러낼 수 있다. 이는 구조화의 작동 원리 설명이며 성능 우위 측정이 아니다.

**과해지는 조건:** 원리·상호작용 아이디어를 찾는 짧은 목적, 아직 주변 기술을 정하지 않은 초기 설계, 전체 구조를 받기 어려운 작은 부분 질문이다. 강제 트리·유형·프로토콜을 채우게 하면 미상에 값을 만들어 넣거나 우연히 현재 쓰는 기술을 고정 요구로 바꾸기 쉽다. 이는 합성 반례의 위험 가설이며 실제 사용자 발생률은 미측정이다.

**함께 쓸 수 있는 안:** 자유문 원문을 유지하면서 선택 위치와 알려진 제약만 붙이고, 구조화/AI 분해 결과는 원문을 가리키는 제안으로 둔다. 기술 명세는 관련 부분만 연결한다. 상위 파생 관계와 추가 해석은 확인된 입력과 분리한다. 특정 필드가 필요한 이유는 위 반례에 연결하되, 이 문서에서 최종 API·JSON 스키마는 정하지 않는다.

## 5. 답 없이 진행할 범위와 멈출 조건

| 빠진 정보 | 진행할 수 있는 탐색 | 멈춰야 하는 판정 | 최소 추가 확인 |
| --- | --- | --- | --- |
| 구체 프로토콜 | 사용자의 목적을 만족할 원리·형태 비교 | 실제 연동·교체 가능하다는 단정 | 연동이 필요한 순간 현재 인터페이스/환경 |
| 구조의 현재/계획 구분 | 두 해석을 나눠 가능한 원리 정리 | 이미 운영 중이라는 서술 | 문서가 기술하는 시점·상태 |
| sender/receiver 관점 | 원문의 기술된 관점 그대로 읽기 | 반대편 topology·방향 자동 생성 | 어떤 애플리케이션의 명세인지 |
| 동명 대상의 위치 | 두 후보 위치를 병기한 일반 원리 비교 | 특정 부분 변경/연결을 전제한 추천 | 선택한 대상의 원문 위치 또는 부모 범위 |
| 제약의 강제성 | 필수라고 명시된 문장만 고정하고 나머지 대안 보존 | 선호를 금지로 승격해 후보 배제 | 해당 제약을 바꿀 수 있는지 |

이 표는 질문을 전부 막으라는 규칙이 아니다. 현재 단계의 주장 범위를 줄여 진행할 수 있다. 답을 받아야만 결정할 수 있는 사항을 대신 추정해서 ‘적합’ 판정으로 넘어가는 행동을 멈추라는 제안이다.

## 6. 최소 후속 검증

같은 원문 1개를 고정하고, 자유문 유지/가벼운 구조화/AI 분해 제안 3가지에서 (a) 목표를 구현 선택으로 바꾼 문장, (b) 누락된 금지·조건, (c) 뒤집힌 방향, (d) 파생을 사실로 올린 관계를 원문 대비 표시한다. 작성자와 별도의 검토자가 표와 원문을 대조한다. 이번 조사에는 실제 AI 호출·사용자 시험이 없으므로 이 비교 결과를 검색 품질 향상 또는 사용자 시간 절약으로 보고하지 않는다.
