# P3·P1 — 소스, 생성, 게시와 실제 응답의 연결

## 현재 판정

P3의 **주 관측창(2025-11-11~13 UTC) 동시 제공은 미확인**이다. 11월 14일의 두 보관 응답을 새로 확보했지만 원래 창 밖이고, stable/options는02:26:28, 1.x는11:28:00의 서로 다른 시각이다. 어느 쪽의 연속 게시 유효구간도 확보하지 못했다. 이를 같은 날의 동시 제공이나 11월12일 게시 증거로 바꾸지 않는다.

P1은 선택 SHA의 latest 생성 성공이 확인된다. 따라서 지금 named7.0.1이404라는 사실로 과거에도 해당 소스의 문서가 생성되지 않았다고 말하면 틀린다. 한편 그 성공만으로 당시 latest가 독자에게7.0.1을 반환했다는 주장도 아직 지지되지 않는다.

## Q1 — 원 약속과 연구 가정

고정 P3 README의 L5는 stable 배지, L44·140은`stable/options/#enable`, L53은 지원 종료 Python(예:Python2) 독자를`1.x/`로 보낸다. 이때의1.x는 구계열 문서이지 특정1.x patch의 영구 불변판이 아니다. 유지 기간은 적혀 있지 않다. v3.3.0 릴리스 원문은2025-11-12T19:28:16Z이며 Docker29 호환 수정·test-runtime 추가 등을 설명한다. 문서 보존기한이나 특정 HTML 바이트 보존 약속은 없다.

P1 README L4·18·99는 latest/루트 문서를 안내한다. release7.0.1은2025-12-16T17:53:11Z에 발행됐고 musllinux 필터 기능을 설명한다. named7.0.1을 영구 게시하겠다는 두 번째 요구는 찾지 못했다. 고정판을 현재 읽으려는 목적은 이 조사에서 추가한 목적이며 원 소유자의 약속과 분리했다.

P3의2025-10-12~12-13 공개 이슈/PR 검색에서 documentation에 걸린6개 본문도 검사했다. 의존성 갱신·빌드 기능·배포 wheel 문제였고 구판 문서 유지 기간의 발화는 발견하지 못했다. 검색 결과는 최소 원자료 수에 넣지 않는다. 이 검색이 모든 토론을 소진했다는 주장도 하지 않는다.

P3의 소스별 전체 조회는count4,next=null이며 latest30298913도 반환한다. 이 추가 run은 소스 이력의 문맥으로 남기고 사전 지정 tag두 run을 교체하지 않았다. 생성 도구는 P3 MkDocs, P1 Sphinx8.2.3이며 원 로그에 실제 명령·출력 디렉터리와exit0이 있다.

APIv2의run16 `task_executed_at=19:33:07.043447Z`는 원 명령 시각과 맞는다. APIv3의finished와 실제 명령 시각은 다르므로 한 게시 시각으로 합치지 않는다. APIv2의`is_uploaded=false`도 게시 실패로 읽지 않았다. 현재 공식 모델 코드에서 이 필드는 **upload API를 이용한 산출물 업로드 유형**을 뜻한다. 현재 코드의 의미 확인을2025년 당시 모든 내부 동작의 증명으로 확대하지 않는다.

현재 tag의index에는`Build Date UTC:2025-11-12 19:33:19.984472+00:00`이 있다. 두 tag후보 중run16 생성 구간과 맞으므로 후보를 좁히는 근거다. 반대로 tag/options의 서버mtime은`1762975695.896559606`(19:28:15.896559606)이며run14 구간과 맞는다. 보관된stable/options의mtime은`1762976000.100373631`(19:33:20.100373631)이다. 이 메타데이터는 발행 서버가 제공한 값이며 연구자가 생성 순간을 관측한 값이 아니다. 동일 파일 바이트가 재생성·복사돼도 오래된mtime이 남을 수 있어 파일별run을 확정하지 않는다.

공개 APIv3·v2 본문, UI가 연결한 원 로그, version downloads, 현재 공식 API 문서·v2 URL/serializer, sitemap을 살폈다. 대상 두 run의 **파일별digest와 산출물ID를 묶은 공개 manifest를 확보하지 못했다.** v3.3.0의downloads는빈객체, root/tag sitemap은빈urlset, 1.x sitemap의loc는9개 모두None이다. 이것을 서비스 내부 manifest가 없다는 증명으로 쓰지 않는다. 비공개 admin경로는 요청하지 않았다.

CDX에 `statuscode:200`만 적용한 최초 조회는1.x의`warc/revisit`를 놓쳤다. all-status prefix 보강으로 이를 찾고 원 보관 payload를 읽었다. 주 관측창의stable/1.x all-status prefix에는 결과가 없다. **CDX 공석은 실제 사이트가 당시 없었다는 반증이 아니다.** 보조 prefix의collapse=urlkey도 전체 연속성을 재구성하는 조회가 아니다.

보관 stable/options와 현재 v3.3.0/options는 원바이트가 다르지만, RTD가 주입한`readthedocs-version-slug` 한 필드의stable→v3.3.0 치환 후 완전히 동일하다. 치환은정확히1회이고 정규화 지문은`4576ddf765b26c8bcc16853c229239cb6306278559fd2c1005590be67ed96a4d`다. 이 비교는 **options 한 파일**에 한정한다. root는slug뿐 아니라BuildDate도 달라 동일 규칙을 적용하지 않았다.

보관1.x/root는 현재1.x/root와 원바이트가 그대로 같다(SHA256`5fae3b9eaad47ef3d274e1824196809e817473331dbac71e2d5263946bb77eff`). 현재readthedocs-data.js의source는2021run과 같다. 이 결과는 개별 두 관측의 내용 보존을 지지하며2025-11-11~13 또는그사이연속성은증명하지 않는다.

현재stable changelog는4.3.5(2026-10-27)다. 현재stable와현재tag에서anchor가둘다있어도허용 옵션 목록이달라,anchor존재만으로같은판을판정할수없다. 실제 fragment는서버요청에전달되지않으므로HTML의id=enable와절내용을직접확인했다. 브라우저스크롤·JS동작은실행하지않았다.

## Q5 — 사전 권고와 역사 근거 후의 선택

사전 권고는원격`586b33488f6338ee8309a671d270656d837df636`의prerecommendations.json이다. P3은현재v3.3.0/options와1.x를반환하고과거동시성은유보했고,P1은7.0.1독자목적에유보했다. 이조사자는082의공백을알고있어맹검이아니다. 일부러틀린사전주장을만들어사후뒤집기점수를높이지않았다.

역사 근거를 더해도 두 **기본 링크 선택**은 유지된다. P3에는정확한보조capture링크와시각을덧붙일수있고,P1에는선택소스가latest에서실제로생성된근거를덧붙일수있다. 사전부터유보한역사공개는여전히유보한다. 기각된싼추론은`현재named404⇒그소스의문서생성없음`, `현재별칭/고정판이열림⇒당시두판공존`, `동일소스⇒특정run의파일`이다. 이기각은사전권고가실제로그오류를범했다는주장이아니다.

## 보존·계측 경계

sources.jsonl은58조회·원문행과논리GET영수증을연결한다. 같은프로젝트의README·run·응답·보관본은하나의소비자계보로묶는다. RTD공식문서·현재모델코드는한계약계보로묶는다. 검색·빈index·접근실패·중복JSON은최소원자료수에서제외한다. 원문전체는재생가능한작업영역에두고커밋에는짧은추출·응답지문·UTC·URL·관측내용을남긴다.

전송gzip바이트의SHA1은CDXdigest와대조하고,해제된HTML은별도SHA256·길이로기록했다. 발행자ETag·mtime·source SHA와연구자가계산한파일hash를서로같은필드로덮어쓰지않는다. 비용은본문수신량·논리GET이며TLS/헤더/redirect내부hop이나사람시간·서비스요금은미측정이다.
