## Q1~Q7 답과 근거
- Q1: 선택 대상은 admission, reservation, start, completion 중 하나. [K407](https://github.com/kubernetes-sigs/kueue/issues/407)에서 aggregate quota 3 CPU가 허용한 C=1.5 CPU는 1/2 CPU 노드의 조각에 맞지 않아 pending, D=.5가 뒤에 막힘; C와 D를 동시에 admission 대기로 보면 오분류. [SGPU](https://lists.schedmd.com/mailman3/hyperkitty/list/slurm-users@lists.schedmd.com/thread/MFYI3SQLYCCD5TIGDBUHWB4FMZ7QCO3O/)의 A100 501490/H100 500060 우선권은 실제 ID와 자원 종류를 보여주지만 도착 시각, start trace, 설정 없음. 당시 상태는 snapshot.

## 대안과 조합 조건
1. **입력 최소화**: A/B 자원/우선권/도착, 선택 상태와 실제 현 상태만 묻고 가까운 코드 링크를 붙인다. 지원 범위 넓으나 time slot이나 권한 없으면 결정을 보류.
2. **보류권과 자원권 분리**: 명시적 defer 가능, rank retention, TTL/expiry, voluntary vs eviction 기록. 도서관 비유가 유용한 경우. 사용자가 의사표현할 수 없거나 취소 불가 약속이면 M1 적용 금지; M3처럼 장애의 책임을 먼저 분리.
3. **조건 필터+보호 시간창**: physical fit, shared dependency, walltime, setup/preemption cost, protected start/expiry, eligibility; 실제 제약이 다를 때만 외부 링크를 제공. R1이 이미 동형이면 새 선택 대신 적용 조건 설명. M2의 만료와 결합 가능하나 high-priority carryover는 무조건 권리가 아님.
4. **원자성/공정성 별도**: Kueue cohort/nominal reclaim, Slurm tenant usage and priority weights가 외부 유추보다 먼저 해결하는 경우가 있음. 같은 사람의 예약 순번과 계정 단위 사용 공정성은 다름.
