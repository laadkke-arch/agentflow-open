# AF-RES-019 사전 분석 계획

## 1. 연구 대상과 날짜

대상은 외부에서 확인할 수 있는 추천 이유의 조건 변경이다. 프로젝트 하나와 구체적 이유 하나를 단위로 삼고, 여러 판에 걸친 동일 발표는 한 사건으로 묶는다. 시행일 T는 그 이유가 현재 지원되는 경로에서 처음 성립하지 않게 된 날짜다. 발표일에는 정책을 먼저 알 수 있으므로 발표→시행과 시행 대비 지연을 각각 계산한다. 기존 판·포크·자체 호스팅의 권리가 유지될 수 있는 범위를 별도로 기록한다. 시행일이 일 단위로 확인되지 않으면 일 단위 계산에서 뺀다. UTC 달력으로 12·6·3·1개월을 뺀다. 말일이 없는 달은 마지막 날로 맞춘다. 사건 당일 자료는 사전 신호에서 제외한다. 관측 창은 T−12개월부터 T 전날까지다. 시행 전 공지가 이미 공개된 기간을 제외한 민감도 결과도 낸다.

## 2. 대조군

사건과 같은 생태계와 주요 범주(패키지 키워드, 분류자, 공식 설명의 같은 기능) 후보를 최소 1개 검토한다. 데이터 수집 전 사건 범주의 후보를 열거한다. 최초 도달 가능 기본 이력의 커밋 연도 차가 2년 이하고, T 직전 365일의 비병합 작성자 수가 같은 구간(0, 1–3, 4–15, 16–63, 64+)이어야 엄격 매치다. 여러 후보가 통과하면 범주를 더 구체적으로 공유하는 쪽, 연도 차가 작은 쪽, 사전 열거 순으로 하나 선택한다. 기본 브랜치 절단, 사용자 이메일 없는 기록 또는 첫 커밋 이전 시점은 관찰 불가로 처리한다. 동일 대조 프로젝트를 엄격 매치에서 재사용하지 않는다.

대조 이유가 창에서 유지되는지 시작·끝의 릴리스, 지원 공지, 레지스트리·Git 파일판 등을 대조한다. 현재 게시 여부는 역사적 무사건의 단독 근거가 될 수 없다. 서비스는 동시기 범주와 최초 공개 연도 근거로 후보를 고르고, 양쪽의 Git 작성자 구간을 알 수 없으면 서비스 비교 행으로 보존한다. 범주, 연도, 작성자 또는 무사건 확인이 부족한 후보는 엄격 매치 분모 밖에 둔다. 후보를 남겨 탐색적 비교의 민감도를 따로 계산한다. 1년 이상 유지 반례의 후속 창은 T+365일까지 별도로 확인한다.

## 3. 정의와 임계값

기본 브랜치 HEAD와 조회한 태그를 고정한다. 기본 브랜치에 도달하는 비병합 커밋을 커미터 UTC 시각으로 자른다. 작성자 수는 로컬에서 정규화한 author email을 사용하며 이름·메일·개인 프로필을 출력하지 않는다. 90일·365일 창은 열린 왼쪽 경계와 닫힌 오른쪽 경계를 사용한다. T−12 전에 존재하되 활동이 없으면 0, 프로젝트 자체가 없으면 미확인이다. 위험 순위는 아래 경보 방향에 맞추고 이진 신호는 동률이면 0.5로 센다. 태그는 조회 시 보이는 판 태그의 생성 날짜를 쓴다. 가벼운 태그는 대상 커밋 시각을 대용하며 후일 추가·삭제 여부는 복원되지 않는다.

| ID | 원천과 계산 | 경보 임계값 |
| --- | --- | --- |
| git_commits_90d | Git 최근 90일 비병합 커밋 | 3 이하 |
| git_commit_age | Git 최근 비병합 커밋 이후 일수 | 90일 이상 |
| git_authors_365d | Git 최근 365일 서로 다른 작성자 | 2 이하 |
| git_top_author_share | Git 최근 365일 최다 작성자 몫. 커밋 0건은 정의 불가 | 0.8 이상 |
| git_tag_age | Git 마지막 판 태그 이후 일수. 판 태그가 없으면 미확인 | 180일 이상 |
| git_tag_gap | Git 직전 두 판 태그 사이 일수. 두 개 미만은 미확인 | 180일 이상 |
| git_license_change | Git 루트 LICENSE/LICENCE/COPYING 또는 명시한 제품 하위 라이선스에서 최근 90일 변경. 내용이 동일한 경로 이동과 초판 도입 분리 가능 시 제외 | 1건 이상 |
| git_readme_notice | Git 루트 README 또는 유지 공지에 대상 프로젝트/패키지의 deprecated, unmaintained, archived, maintenance mode, looking for maintainers, moved to 표현. 번들·설치 로그·제삼자 공지 제외. 문맥 선별 전에는 문자열 신호로 따로 표시 | 있음 |
| git_cla_added | Git 루트 및 .github의 CLA·기여 약관 파일 도입이 최근 365일 | 1건 이상 |
| git_package_changed | Git 저장소 URL이나 패키지 이름을 최근 365일 간 비교할 수 있는 매니페스트에서 실질 변경. 동일 URL의 ssh/https/.git 표기 정규화 | 변경 있음 |
| registry_release_gap | 레지스트리 마지막 두 게시 판 사이 일수. 같은 판의 여러 파일은 첫 업로드 | 180일 이상 |
| registry_inactive | 레지스트리의 날짜 있는 deprecated·yanked 활성 상태 | 활성 |
| registry_license_changed | 두 게시 판의 레지스트리 라이선스 표기가 달라질 때. 판별 업로드 시점 메타데이터로 입증할 수 없으면 현대 응답 기반 대용치에만 기록 | 최근 90일 중 변경 있음 |

README 원문과 매니페스트 파일은 작은 고정판만 읽는다. 신호 변경 날짜는 확인한 Git 커밋의 커미터 일자, 또는 이미 나타난 스냅샷의 일자를 상계로 기록한다. 정확한 날짜를 되살릴 수 없으면 구간 표기한다. PyPI yanked/npm deprecated 판 표시는 관측일 상태다. 업로드 일자와 npm 전체 time.modified를 그 표시의 시행일로 소급하지 않는다. 레지스트리에서 두 판의 라이선스 이력이 없거나 수정 시각을 확인할 수 없는 경우와 서비스에 저장소가 없는 경우는 별도 결측 코드로 남긴다.

사전 조합 A = git_commit_age OR git_tag_age OR git_readme_notice, 조합 B = git_commits_90d AND git_authors_365d, 조합 C = git_license_change OR git_package_changed. 결측이 있어도 OR에 확인된 참이 있으면 참, AND에 확인된 거짓이 있으면 거짓. 나머지 논리값이 결정되지 않으면 결측이다. 해석할 분모는 짝 양측이 관측된 경우가 기본이고 사전에 정한 임계값을 조정하지 않는다.

## 4. 평가와 비용

네 시점 각각 AUC를 추정한다. 대표 표의 T−1개월 AUC는 양측 순위값이 있는 짝을 재표집하는 2,000회 백분위 부트스트랩(난수 시드 19019, 2.5/97.5 백분위)이다. 주 경보 혼동표는 12개월 동안 이용 가능했던 사전 관측에서 한 번이라도 임계값을 넘은 경우다. 동일한 표본에서 TP, FP, FN, TN과 계산 가능 여부를 함께 기록하며 정밀도 TP/(TP+FP), 재현율 TP/(TP+FN)이다. 두 그룹의 경보 상태가 정해진 짝을 1차 분모로 삼는다. 1차 표본이 작을 때 탐색 매치는 별도 층에 제시한다. 사건 대조 표본 정밀도의 모집단 적용은 실제 기준율을 넣어 민감도로만 다룬다. 앞선 날짜는 활동 신호는 가능한 일별, 스냅샷 신호는 감지한 날짜 상계로 산정한다. 창 시작에 이미 경보 상태면 좌측 검열이다. 이벤트와 대조의 실제로 읽은 사례를 같이 보고한다.

달력 월·분기·연 첫날 UTC와 요청 시 14·90·365일 간격을 비교한다. 15의 요청 간격 가정을 계승하며 각 요청 간격은 T−12개월의 다음 날을 기준으로 위상 전체 또는 결정적으로 균등한 위상으로 민감도를 낸다. 탐지 관측 창은 T−12개월부터 min(T+365일, 데이터 수집일)까지다. 원문 직접 방식은 공지·시행 중 해당 사건의 확인 가능한 최초 문서 이후 첫 확인이다. 신호 경보 방식은 그 주기의 관측에서 최초 양성일을 표시한다. 신호 후 원문 방식은 원문이 나오거나 상태가 확인 가능한 뒤의 양성 확인일에 확인한다. 시행 대비 음수는 먼저 알려진 안내를 뜻한다. 신호만의 양성은 사건 확인이 아니므로 사전 경보 수와 확인 가능한 적중·오경보·미탐을 구별한다. 비적용 서비스와 자료 결측은 예측 평가에서 따로 표시하고 운영 시뮬레이션의 접근 가능 분모도 산출한다.

익명 수집 요청 사이 간격과 동시성, 오류, UTC, 요청 수, 바이트, 벽시간을 기록한다. HTTP는 응답 본문 크기, Git은 protocol trace가 본 GET/POST와 받은 pack 바이트를 써서 헤더·TLS 등을 제외한다. 작업자 원문 도구 시간과 HTTP 벽시간을 별도 기록한다. 전체 clone 비교는 사전 측정 부분 clone의 pack 10 MiB 이하에서 각 유형에 가능한 첫 2개와 짝 대조 2개를 상한으로 삼고 60초에 제한한다. 큰 저장소는 부분 clone만 사용한다. 1천·1만 외삽은 초기 수집, 확인 1회, 반복 시나리오의 분모와 비용 정의를 함께 표시한다. 지속 작업이나 인증 토큰은 만들지 않는다.
