# 문서적 완결과 실행 성공의 경계 검토

검토 대상은 봉인 `d03ca37daf0c43688c68bc39417d84a9b84803e9`의 Pandoc 판정, 사후 공개 후속·보조 실행, 현재 통합 `pairs.csv`, 계약 시작 실패 영수증이다. 추가 외부 원문이나 실행을 수행하지 않았으며 frozen 파일을 수정하지 않았다. 이 문서는 판정 근거와 한계를 별도로 검토한 것이지만 **Pandoc 판정과 사후 실행을 맡았던 같은 연구자의 검토이므로 독립 블라인드 평가자 검증은 아니다.**

## 가장 약한 표현: “5/8 성공”

통합 [pairs.csv](../../pairs.csv)의 8쌍 중 J1·J3·J4·P3·P4가 양쪽 완결이고 J2·P1·P2는 어느 쪽도 완결이 아니다. 따라서 정확한 표현은 **“고정 비교판과 문서적 채점 규칙에서 A와 B가 각각 5/8 요청에 완결 후보를 반환했다”**이다. 두 경로가 같은 질문에 답하므로 이것을 독립 성공 10건으로 세면 안 된다. 사용자 환경의 실행 성공률, 채택률, 독립 평가자의 최초 발견률도 아니다.

P3/P4의 사전 [문서 합성안](../pandoc/documentary-syntheses.md)은 주어진 입력에 필요한 연결을 문서로 닫은 구체 코드·명령이다. 실제 실행은 봉인 뒤 별도로 수행했다. [execution.json](../post-pandoc/execution.json)의 사후 관측은 P3의 Pandoc 변환 단계에는 강한 지지를 주지만 P4의 그림 생성 끝단은 확인하지 못했다. 이 서로 다른 증거 수준을 5/8이라는 한 숫자에 합치면 결과가 과장된다.

### 권장 첫 문장

> 고정된 8개 요청에서 A와 B는 각각 5개에 문서상 완결 후보를 반환했다. A만 또는 B만 완결인 쌍은 0개였다. 이 수치는 원 사용자 환경의 실행 성공률이 아니다. 사후 보조 실행은 P3의 Pandoc 변환 단계를 확인했고, P4는 AST 경계를 확인한 뒤 TeX 환경 의존성에서 실패했다.

“A와 B의 성능이 같다”도 과한 표현이다. 불일치쌍 0은 이 표본·노출·공통 검토에서 차이를 관찰하지 못했다는 뜻이다. 큰 매뉴얼이 상위 두 자리에 남았고, 최종 P3/P4 검토에 양경로 기억이 있었으며, 이진 완결 점수는 짧은 링크·실패 위치 진단·추가 반대조건 설명의 차이를 모두 담지 않는다. [경로 감사](route-audit.md)는 접근 계약을 검사했으며 해석의 참이나 기억 효과가 없음을 검증한 자료가 아니다.

## P3: 원 값 생산을 유지하지만 입력 표지를 바꾼 사전안

| 구분 | 실제 근거와 전제 | 아직 주장할 수 없는 것 |
|---|---|---|
|원 요청|[R0](https://stackoverflow.com/revisions/1B054996-200D-4090-BAC2-A656EDCBC92D/view-source)는 R 청크에서 HTML 문자열을 생산하고 inline R로 YAML에 넣어 template의 signature로 사용한다. 2.11.2에서 쓰던 출력이3.1.11에서 달라졌고 Pandoc 옵션을 묻는다.|원 R/rmarkdown 전체 설치판과 실제 knit된 Markdown 바이트는 본문만으로 확정되지 않는다.|
|봉인된 구성|원 대입 뒤 raw HTML 표지를 추가한다. 같은 R 값 생산→inline R→YAML 경로를 유지하며 그 문자열이 Markdown raw 형식으로 읽히게 한다. [P3-A](../routes/P3-A/judgment.json)/[P3-B](../routes/P3-B/judgment.json)의 최종 반환은 같은 주 도구 매뉴얼 하나다.|CLI 옵션만 바꾸는 답과 같은 작업은 아니다. 사용자가 원 R 문자열 조작 위치에 한 줄을 추가해야 한다.|

|사후 실행|정확한 signature와 template를 추출한 합성 중간 Markdown을 Pandoc3.6에 넣었다. 표 내부 br는38→0, 행4·셀12와 원 table 바이트는 유지됐다. 원치 않는 변환을 피한다는 Pandoc 단계의 예상은 실제로 맞았다.|R이 없어 R 청크·knitr·YAML 직렬화 전체를 실행하지 않았다. 원 사용자2.11.2/3.1.11도 실행하지 않았다.|
|사후 공개 답|[최초 답](https://stackoverflow.com/revisions/DF73AC92-8281-499B-963C-D995EEE0FB91/view-source)은 markdown_in_html_blocks를 끄는 옵션을 제시한다. 현재 채택됐고 답 이미지에는 R4.4.2/rmarkdown2.29/Pandoc3.1.11.1이 보인다.|채택 시각과 질문자 재실행은 미확인이다. 이미지의 판은 답변자에게 귀속하며 질문자의3.1.11과 동일시하지 않는다.|

원 질문의 표현은 “Pandoc 옵션”을 선호한다. 사전 조건표는 “signature에 새 br가 생기지 않게 한다”는 출력 목표를 고정했으므로 raw 표지 방식도 그 규칙에서 완결로 판정했다. **‘원 문자열 수정 없이 옵션만 사용’이 별도 필수조건이었다면 사전 raw 표지안은 같은 방식의 완결로 부를 수 없었을 것**이다. 이 차이는 사후에 조건을 새로 넣어 점수를 바꿀 이유가 아니라 카드에 적용 위치와 비용을 정확히 적어야 하는 이유다.

사후의 더 직접적인 답은 인접 프로젝트의 새 원문에서 나온 것이 아니라 [주 도구 매뉴얼의 다른 절](https://github.com/jgm/pandoc/blob/8a72b8449ddccd84fcdffc1a09ae18c4baaca32a/MANUAL.txt#L5282-L5318)과 연결된다. 같은 파일이 노출되었다는 사실만으로 연구자가 그 파일 안의 가장 적절한 절을 처음부터 찾았다고 말할 수 없다. 두 수정안의 사후 HTML은 동일했지만 원문을 수정하는 위치와 다른 HTML 블록에 미칠 영향은 다르다. 따라서 “B만 완결0”과 “최종 반환 링크가 최선이었다”는 별개의 주장이다.

## P4: 외부 실행 단계가 필요해도 인접 저장소의 문서가 필수인 것은 아니다

이 비교의 A/B 허용 집합은 **노출·열람할 근거 파일의 프로젝트 범위**다. 주 도구 공식 문서에 있는 외부 프로그램 호출 예제를 A가 읽지 못하게 하거나, 반환하는 해결책이 주 프로그램 하나의 프로세스 안에서만 실행되어야 한다고 정한 실험이 아니다. 이는 사용자가 명시한 “노출 자리를 배정하는 규칙”과 맞춘 해석이다.

P4의 핵심 `pdflatex→pdf2svg→Image` 예제는 A에도 노출된 [Pandoc의 lua-filters.md](https://github.com/jgm/pandoc/blob/8a72b8449ddccd84fcdffc1a09ae18c4baaca32a/doc/lua-filters.md#L777-L874) **한 파일 안에 있었다**. 그러나 최종 완결 반환은 그 한 파일만이 아니다. [MANUAL.txt](https://github.com/jgm/pandoc/blob/8a72b8449ddccd84fcdffc1a09ae18c4baaca32a/MANUAL.txt)의 raw_tex와 embed-resources 설명까지 **두 파일**이 전체 연결을 지지한다. [P4-A](../routes/P4-A/judgment.json)/[P4-B](../routes/P4-B/judgment.json)에서 같은 두 파일을 반환했다.

| 연결 | 사전 구성에 필요했던 전제 | 사후 실제 관측 |
|---|---|---|
|LaTeX→RawBlock|raw_tex가 활성화되고 원 TikZ 환경이 RawBlock으로 전달됨|고정3.6의 원 TeX에서 RawBlock2개, TikZ 포함1개를 확인했다.|
|RawBlock→독립 TeX|단일 비중첩 tikzpicture를 추출하며 원 automata/positioning/arrows와 전역 tikzset를 별도 preamble에 보존함|봉인 필터 바이트를 그대로 실행했으며 실제 콜백이 pdflatex 단계에 도달했다. 일반 문서의 모든 preamble 명령을 자동 복사한 것은 아니다.|
|TeX→PDF|동작하는 pdflatex format와 standalone/xcolor/tikz 및 원 라이브러리 설치|pdflatex.fmt 부재로 내부 exit1. Pandoc은 exit83으로 실패했다.|
|PDF→SVG|pdf2svg가 사용 가능함|이 환경에 없었다. 앞 단계 실패 때문에 이 호출은 시험하지 못했다.|
|SVG→HTML|필터 Image 생성과 embed-resources 내장, 원 라벨·화살표의 시각적 보존|SVG와 HTML 성공 출력이 없어 미확인이다.|

따라서 다음 세 문장을 구분해야 한다.

- **지지됨:** 이 입력에 맞춘 외부 그림 렌더링 파이프라인을 주 도구 공식 자료 두 개로 구체적으로 구성할 수 있었다.
- **지지되지 않음:** A는 외부 의존 없이 TikZ를 자체 렌더링했다.
- **지지되지 않음:** 봉인 필터가 원 사용자 환경에서 그림까지 성공적으로 만들었다.

원 질문은 [해당 diagram.lua 호출로 이미지가 나오지 않는 예](https://stackoverflow.com/revisions/5938869D-E61B-410C-97F5-035731293446/view-source)를 주지만 그 필터만 사용해야 한다는 조건을 고정하지 않았다. 최종안은 RawBlock 필터로 대체한다. 원 `diagram.lua`의 사용자 설치 commit도 미상이고, B에서 읽은 것은 고정 비교판의 CodeBlock dispatch다. 그것이 그 비교판에서의 입력 불일치 진단을 지지하지만, 움직이는 main 링크의 원 설치 바이트를 복원했다고 주장하지 않는다.

P4는 “외부가 꼭 필요했는데 A가 실패한 사례”가 아니다. 현재 관측은 **외부 실행 의존을 기술하는 근거가 이미 A의 주 도구 문서 안에 있었던 사례**다. 외부 의존 필요성과 B의 인접 원문 노출 필요성을 동일시하면 이 실험의 질문이 바뀐다.

## P1의 self-answer와 문서 한계

[질문자 self-answer](https://stackoverflow.com/revisions/6F659201-6815-46E2-BB6F-5C2C61CC5090/view-source)는 성공 자술이므로 사용자 행동 근거로 남겨야 한다. 다만 공개 코드는 모든 Strong 요소를 test 스타일 Span으로 바꾸는 것이며 원 `.custom` paragraph→DocBook simpara role→DOCX CustomStyle의 이름·유형 연결을 재현하지 않는다. 완전 명령·판·reference.docx·생성 DOCX도 없다.

권장 표현은 “질문자가 AST 변환으로 다른 대상의 스타일 지정에 성공했다고 보고했다”이다. “질문자가 원 요청을 해결했으므로 사전 반박은 오답” 또는 “채택이 없으므로 이 방법은 실패”는 둘 다 근거를 넘는다. P1의 기존 경로 연결 반박과 다른 입력 대상의 우회 성공은 함께 존재할 수 있다. [사후 outcomes 행](../post-pandoc/outcomes.json)은 이를 분리한다.

## PARTIAL과 실패 manifest의 권장 표현

[SCOPE.md](../../SCOPE.md)와 [manifest.json](../../manifest.json)이 직접 보여 주는 사실은 다음과 같다. 지정한 session start는 종료값2로 거부됐다. 고정 의존 `work/research-af-res-092=e0d7ecda64bab2bd5d5779a9fb2a18d39a83bcdf`와 실제 원격 끝 `e742bc665efde0d3883ec4d0f5479e03e914fcbf`가 달랐기 때문이다. 현재 manifest는 성공 계약이 아니라 그 실패의 영수증이다. 최종 session check의 실제 종료값은 실행 기록을 얻은 뒤 따로 표시해야 하며 이 검토는 그것을 미리 성공 또는 실패로 만들어 쓰지 않는다.

이것을 단순 형식 문제라고 축소해서는 안 된다. 동시에 “핵심 연구가 없어 PARTIAL”이라고 쓰면 존재하는 8질문·16경로의 봉인 비교 자료를 오해하게 한다. **계약 상태, 연구 관측의 충족 여부, 원 사용자 환경의 실행 확인 범위를 각각 적어야 한다.** SCOPE 첫 줄의 RUNNING은 사전 작성 시점의 기록이므로 원 기준을 조용히 덮어쓰지 말고 최종 결과·인계에서 현재 상태와 근거를 명시하는 편이 맞다.

### RESULT/HANDOFF 권장문구

> 연구 상태는 PARTIAL이다. 8질문·16경로의 봉인된 노출·열람·문서 판정은 갖추었고, 이 자료에서 A/B 각각 문서적 완결5/8을 보고한다. 다만 고정 선행 SHA와 현재 의존 브랜치 끝이 달라 session start의 성공 계약을 만들지 못했다(exit2). manifest.json은 실패 영수증이며 성공한 계약 검사를 대신하지 않는다. 또한 문서적 완결을 원 사용자 실행 성공으로 일반화하지 않는다. Pandoc 보조 실행은 P3의 합성 중간 입력 단계만 확인했고 P4의 전체 그림 생성은 외부 실행 환경 결손으로 미확인이다. 실제 session check와 저장소 공통 검사의 대상 SHA·종료값은 별도 검사 원장으로 보고한다.

중앙 진행 담당에게 넘길 첫 행동은 **사용자가 지정한 선행 결과 SHA를 유지한 채, 변한 의존 브랜치 끝과 계약 도구의 기대를 어떻게 정합하게 처리할지 결정하는 것**이다. 연구자가 임의로 의존 SHA를 바꾸거나 실패 영수증을 성공 manifest 스키마로 꾸며 통과시키는 것은 이 결손을 해결하지 않는다. P4의 다음 실행은 해당 행의 TeX 포맷·패키지·pdf2svg를 갖춘 환경에서 동일 입력과 동일 봉인 필터로 수행해야 한다.

## 최종 편집 확인 사항

- 첫 분모 설명에 “문서적 완결”을 적고 “실행 성공5/8”을 쓰지 않는다.
- P3의 사후 실행은 합성 중간 Markdown에 대한 Pandoc 단계, 공개 답 이미지의 판은 답변자의 판이라고 적는다.
- P4에는 외부 의존 조건과 실제 exit83을 함께 남긴다. 핵심 예제 한 파일과 최종 반환 두 파일을 혼동하지 않는다.
- P1 self-answer는 입력·대상이 바뀐 성공 자술, P3 채택 답은 같은 주 도구의 다른 절이라는 차이를 유지한다.
- 계약 실패·원판 실행 미확인·문서 비교 완성을 각각 표시한다. 관측하지 못한 A만/B만 사례를 필수 예시 수를 채우기 위해 성공 또는 실패로 만들어 넣지 않는다.
