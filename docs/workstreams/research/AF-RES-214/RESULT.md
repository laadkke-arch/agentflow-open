## Q1 — 제안 전 알고 있던 기능

C2는 beta3 코드에 showModal/close; C4는 이미 registerDialog 및 Blacklight 의존. 이는 **조직의 코드상 사용**이다. C2 API base가 최초 PR 생성일 2022-10-07보다 늦은 2023-01-31이므로 초기 제안 전의 정확한 SHA를 검증한 4/4라고 표현하지 않는다. C1/C3/C4도 API base만 확보했고 최초 revision parent/개인 최초 지식 별도 미확인. 다음 조사: PR commits API 최초 parent, git log -S registerDialog/showModal 및 도입 PR의 리뷰 날짜.

## Q4 — 발견 효과와 계보
완전한 사건 기준: (1) 제안 전 정확한 대안의 부재/개인의 미인지 진술, (2) 다른 사람이 링크를 알려준 UTC와 당시 이용 가능한 조건, (3) 같은 사람이 선택을 바꿨다고 명시, (4) 뒤의 실제 patch/설정/사용. 네 제거에서 0/4 완전 사슬을 관측. 결과가 0 효과라는 결론이 아니다. 4/4 body는 support rationale, 그중 C3의 정책이 날짜 포함 직접 자료로 뒷받침. ## Q5 — 유지, 철회, 행동 동등성의 반례
R01 Safari14 실험 flag: close 누락, 답변은 form method/dialog 및 backdrop 결손 지적; 기능 검사 통과가 품질 증거가 아니다. R03 Safari15.3 2022-07 제보는 공급자 15.4 출시 후에도 구판 사용자 존재 사례. R02 slot focus failure, R05 Firefox flag와 환경별 상충/재현 불가; 유지자가 제안한 지원 범위 제한은 합리적이지만 사용자 실제 목적을 자동 충족하지 않는다. R04 showModal+close 감지 제안도 행동 동등성 보장 아님. R06 upstream types 있음과 compile/runtime 동등성은 다른 문제; 사용자 rollback 보고. R01/03/02/05/06은 작성자 보고이며 직접 실행/독립 확인 아님. B03 README는 native가 있는 경우 registerDialog가 대체하지 않고 adjacent backdrop, stacking context/Tab 관련 제약 및 focus restoration extension을 명시. B04 현행 standard는 modal top layer/inert, focus restore 조건과 close event를 명시. **옛 브라우저의 동작과 지금의 표준 텍스트를 동일시 금지.** C1 native-first가 충분한 환경에서는 fallback 동적 import 자체가 사용되지 않았을 가능성(조건부 기대값); 삭제 전 모든 사용자가 실제 동일 동작을 얻었다는 측정은 없음. 
관점별: patch 작성자는 불필요한 dependency/lock과 유지보수 제거를 얻을 수 있고, 지원 정책 관리자는 제외 사용자 영향과 notice를 따로 추적해야 함. 키보드 사용자는 focus 및 inert/close 행동 계약이 우선. 유지자는 feature-detect, CSS/stacking 차이 및 제한적 지원 비용. 타입 소비자는 버전별 compile 오류가 중요. 반증: 사용자가 실제 이전 OS를 의무 지원하거나 target browser의 showModal만 존재하고 close/focus를 실패하면, native-only 추천→조건부 polyfill 혹은 tested alternative로 바꾼다. 완전히 지원하는 matrix와 행위 테스트가 확인되면 fallback 유지 추천을 제거 검토로 전환. 링크를 통한 선택 전환이 날짜·동일 actor로 확인되면 discovery 문구를 추가.

## Q7 — 탐색기 설계용 근거 조립 (제안이지 구현 아님)
최소 단위는 (목표/부분, 후보/원문, 공급자 판, consumer 정책 조건/시점, 이전 사용/전환 기록, runtime·docs·types 구분, first confirmed release/production unknown, lineage, evidence_kind, counter, last_checked). 동일 이름이더라도 동작 계약 또는 target 판이 다르면 별도 링크 슬롯. 
- A: 표준 우선 링크(WHATWG + browser supplier release) → 정책 부합 여부 확인; 적은 탐색 비용, 하지만 역사적 사유/구판 실동작을 놓칠 수 있음.
- B: 소비자 사례 + version-pinned code+policy+release. 목표가 기존 설계 제거라면 F13/F14 또는 P01/F01을 우선; 근거 추적 비용, 적용 환경 차이. C2/C4는 동일 lineage를 별도 보여 주되 발견 수를 늘리지 않는다.

표현 규칙: C1/C2/C3/C4에는 '기존 코드가 이미 쓰던 표준' (API base 한정) 가능. C3 '지원판 인상 후 제거' 근거 명확. C1 '지원표 충족으로 제거했다고 작성자 설명'만; C2/C4 '브라우저 지원을 이유로 제거했다고 설명'만. D1 '문서 정리', D2 '별도 타입 선언 제거/공급자 번들 선언'. '외부 링크로 첫 선택 변경' 문구는 어느 주사건에도 허용되지 않는다. 지원판이 아닌 다른 trigger(공급 계보 패치 복사, 타입 오류, 문서 누락) 발견 시 첫 링크를 바꾼다. PR/태그/registry 문서는 행동 기록이 아니며 줄수/번들 크기에서 인시 절약 추정 금지.
